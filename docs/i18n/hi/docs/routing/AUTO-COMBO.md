## शून्य-कॉन्फ़िगरेशन ऑटो-रूटिंग (`auto/` प्रीफ़िक्स)

> **नया:** कॉम्बो बनाने की आवश्यकता नहीं है। किसी भी क्लाइंट में सीधे `auto/` प्रीफ़िक्स का उपयोग करें।

### त्वरित उदाहरण

| मॉडल ID        | वैरिएंट  | व्यवहार                                                           |
| -------------- | -------- | ----------------------------------------------------------------- |
| `auto`         | डिफ़ॉल्ट | सभी कनेक्टेड प्रोवाइडर, LKGP रणनीति, संतुलित वेट                  |
| `auto/coding`  | कोडिंग   | गुणवत्ता-प्रथम वेट, कोड जनरेशन के लिए उपयुक्त                     |
| `auto/fast`    | तेज़     | कम-लेटेंसी वाला भारित चयन                                         |
| `auto/cheap`   | सस्ता    | लागत-अनुकूलित रूटिंग (सबसे कम लागत पहले)                          |
| `auto/offline` | ऑफ़लाइन  | सर्वाधिक कोटा उपलब्धता वाले प्रोवाइडर को प्राथमिकता देता है       |
| `auto/smart`   | स्मार्ट  | बेहतर मॉडल खोज के लिए गुणवत्ता-प्रथम + उच्च अन्वेषण दर (10%)      |
| `auto/lkgp`    | lkgp     | स्पष्ट LKGP (डिफ़ॉल्ट `auto` के समान)                             |
| `auto/chaos`   | chaos    | समानांतर फ़ैन-आउट, प्रति प्रोवाइडर एक मॉडल (फ़ॉल्ट इंजेक्शन नहीं) |

### श्रेणी × टियर संयोजन (`auto/<category>:<tier>`)

OpenRouter-शैली के सफ़िक्स **किस प्रकार का रूट** (श्रेणी) और **उसे कैसे अनुकूलित करना है** (टियर) को अलग करते हैं, ताकि आप उन्हें स्वतंत्र रूप से संयोजित कर सकें (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **श्रेणियाँ** (क्षमता के आधार पर उम्मीदवार पूल फ़िल्टर करें): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` विज़न-सक्षम मॉडल बनाए रखते हैं; `reasoning` रीजनिंग/थिंकिंग मॉडल बनाए रखता है।
- **टियर** (स्कोरिंग वेट / पूल फ़िल्टर चुनें): `fast` (शीघ्र डिलीवरी) · `cheap` (उपनाम `floor`, लागत-बचतकर्ता) · `reliable` (सर्किट-ब्रेकर स्वास्थ्य + लेटेंसी स्थिरता) · `free` / `pro` (`classifyTier` के माध्यम से मॉडल टियर के आधार पर पूल फ़िल्टर करें — फ़्री-टियर बनाम प्रीमियम)।

| उदाहरण                 | इसका परिणाम                                              |
| ---------------------- | -------------------------------------------------------- |
| `auto/coding:fast`     | कोडिंग पूल, कम-लेटेंसी वेट                               |
| `auto/coding:cheap`    | कोडिंग पूल, लागत-अनुकूलित (`auto/coding:floor` का उपनाम) |
| `auto/reasoning:pro`   | केवल रीजनिंग/थिंकिंग मॉडल, प्रीमियम टियर                 |
| `auto/vision`          | विज़न-सक्षम मॉडल (कोई टियर नहीं → संतुलित वेट)           |
| `auto/multimodal:free` | मल्टीमोडल-सक्षम मॉडल, केवल फ़्री टियर                    |

कोई भी मान्य `auto/<category>[:<tier>]` आवश्यकता पड़ने पर रिज़ॉल्व होता है; एक चयनित उपसमूह `/v1/models` और डैशबोर्ड (`open-sse/services/autoCombo/builtinCatalog.ts` में `AUTO_SUFFIX_VARIANTS`) में प्रदर्शित किया जाता है। फ़िल्टरिंग **फ़ेल-ओपन** है — यदि कोई बाध्यता किसी कनेक्टेड मॉडल से मेल नहीं खाती, तो पूरे पूल का उपयोग किया जाता है, ताकि रूटिंग कभी न टूटे। मुख्य स्कोरर (`combo.ts`) अपरिवर्तित है; श्रेणी/टियर फ़िल्टर `buildAutoCandidates` में लागू होता है।

> **लाइव मॉडल इंटेलिजेंस:** `ARENA_ELO_SYNC_ENABLED` फ़्लैग चालू होने पर ऑटो-रूटिंग की उपयुक्तता लाइव **Arena ELO** रैंकिंग + **models.dev** टियर डेटा से निर्धारित होती है (अन्यथा स्थिर फ़िटनेस मैप पर फ़ॉलबैक होता है)।

**उपयोग कैसे करें:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**क्या होता है:**

1. OmniRoute `src/sse/handlers/chat.ts` में `auto/` प्रीफ़िक्स का पता लगाता है
2. डेटाबेस से सभी **सक्रिय प्रोवाइडर कनेक्शन** क्वेरी करता है
3. उन्हें फ़िल्टर करके केवल मान्य क्रेडेंशियल (API कुंजी या OAuth टोकन) वाले कनेक्शन रखता है
4. प्रत्येक कनेक्शन के लिए मॉडल निर्धारित करता है (`connection.defaultModel` या प्रोवाइडर का पहला मॉडल)
5. मेमोरी में एक **वर्चुअल कॉम्बो** बनाता है (DB में संग्रहीत नहीं)
6. चयनित वैरिएंट के वेट प्रोफ़ाइल + LKGP रणनीति का उपयोग करके रूट करता है

**मुख्य गुण:**

- ✅ **हमेशा सक्रिय:** किसी टॉगल, कॉम्बो निर्माण या कॉन्फ़िगरेशन की आवश्यकता नहीं
- ✅ **डायनेमिक:** वर्तमान में कनेक्टेड प्रोवाइडर को स्वचालित रूप से दर्शाता है
- ✅ **सेशन स्टिकिनेस:** LKGP सुनिश्चित करता है कि अंतिम सफल प्रोवाइडर को प्राथमिकता दी जाए
- ✅ **मल्टी-अकाउंट जागरूक:** प्रत्येक प्रोवाइडर कनेक्शन एक अलग उम्मीदवार बनता है
- ✅ **कोई DB राइट नहीं:** वर्चुअल कॉम्बो केवल अनुरोध के लिए मौजूद रहता है, पर्सिस्टेंस ओवरहेड शून्य

### प्रति-कुंजी उम्मीदवार नियंत्रण (#7819, स्तर 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` के बाद का सफ़िक्स, या
आधार चैनल के लिए शाब्दिक `auto`) एक **केवल-पढ़ने योग्य** एंडपॉइंट है, जो मौजूदा
रेज़िलिएंस रीड्स (कभी भी अपरिष्कृत ब्रेकर `state` नहीं) का पुनः उपयोग करते हुए लाइव
रीचेबिलिटी से युक्त किसी `auto/*` चैनल के वर्तमान उम्मीदवार पूल को सूचीबद्ध करता है:

- प्रोवाइडर सर्किट ब्रेकर — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- कनेक्शन कूलडाउन — रिज़ॉल्व की गई `provider_connections` पंक्ति पर `rateLimitedUntil` /
  `testStatus`
- मॉडल लॉकआउट — `isModelLocked(provider, connectionId, model)`

प्रत्येक उम्मीदवार में इस API कुंजी का `excluded` फ़्लैग भी होता है। बहिष्करण
प्रति-API-कुंजी (`auto_candidate_overrides` तालिका, माइग्रेशन `128`) संग्रहीत किए जाते हैं —
OmniRoute एकल-टेनेंट है और इसमें कोई `users` तालिका नहीं है, इसलिए `apiKeyId` वास्तविक
प्रति-कॉलर पहचान का निकटतम विकल्प है — और इन्हें
`open-sse/services/autoCombo/virtualFactory.ts` में उम्मीदवार-पूल चोकपॉइंट पर शुद्ध,
यूनिट-परीक्षित `filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`)
के माध्यम से लागू किया जाता है। फ़िल्टर **फ़ेल-ओपन** है: सेट न किया गया apiKeyId/channel
या DB लुकअप विफलता, दोनों ही स्थितियों में पूल बिना फ़िल्टर किए रहता है, इसलिए बिना किसी
कॉन्फ़िगर किए गए ओवरराइड वाला ऑपरेटर इस सुविधा से पहले जैसी बाइट-दर-बाइट समान रूटिंग देखता है।

**फ़ॉलो-अप इश्यू के लिए स्थगित:** प्रति-कैंडिडेट वेट + स्पष्ट क्रम निर्धारण (लेवल 3
— मौजूदा वेटेड/प्राथमिकता स्ट्रैटेजी पाथ में फ़ीड होता है) और प्रत्येक `auto/*`
चैनल के लिए किसी विशिष्ट `combo.ts` स्ट्रैटेजी को पिन करना (लेवल 4)। इस खुले प्रश्न
के लिए #7819 योजना देखें कि सिंगल-टेनेंट मॉडल को देखते हुए ओवरराइड प्रति-API-कुंजी
रहने चाहिए या ग्लोबल हो जाने चाहिए।

**पर्दे के पीछे:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## वास्तविक मॉडल Id से मेल खाने वाले कॉम्बो नाम

जिस कॉम्बो का `name` किसी मूल मॉडल id के समान होता है (उदाहरण के लिए, `gpt-5.5`
नाम वाला कॉम्बो), वह बग नहीं, बल्कि एक **जानबूझकर बनाया गया, समर्थित पैटर्न** है:
यह प्रत्येक मॉडल id के लिए प्रोवाइडर फ़ॉलबैक का तंत्र है, जिसका दस्तावेज़ीकरण
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) में किया गया है। चूँकि मूल मॉडल id के समाधान से पहले कॉम्बो
समाधान की जाँच की जाती है
(`src/sse/services/model.ts` में `getComboForModel()`), इसलिए मूल
id `gpt-5.5` के लिए अनुरोध को सीधे किसी एक प्रोवाइडर को भेजने के बजाय कॉम्बो के लक्ष्यों (जैसे
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) के माध्यम से रूट किया जाता है
— यह [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) के लिए बनाई गई
कॉम्बो-से-पहले-पुनर्लेखन प्राथमिकता का पुनः उपयोग करता है और इसका रिग्रेशन परीक्षण
`tests/unit/responses-combo-resolution-3227.test.ts` तथा
`tests/unit/combo-name-codex-responses-rewrite.test.ts` द्वारा किया जाता है।

किसी ऐसे नाम के साथ कॉम्बो बनाना या उसका नाम बदलना, जो किसी वास्तविक मॉडल id को
छिपा देता हो, **कभी अस्वीकार नहीं किया जाता** — ऐसा करने से यह दस्तावेज़ीकृत कार्यप्रवाह टूट जाएगा। इसके बजाय
(#8530), जब (नया) नाम किसी वास्तविक मॉडल id से टकराता है, तब `POST /api/combos` और `PUT /api/combos/[id]`
प्रतिक्रिया में एक गैर-अवरोधक `warning` फ़ील्ड जोड़ते हैं:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

बूट के समय, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) एक पंक्ति वाली `[STARTUP]` चेतावनी भी लॉग करता है,
जिसमें मॉडल id को छिपाने वाले प्रत्येक मौजूदा कॉम्बो की सूची होती है, ताकि जिन ऑपरेटरों को यह स्थिति
गलती से मिली है (#6940 के अनुसार जानबूझकर नहीं), उन्हें इसका संकेत मिल सके।
पहचान सहायक `src/lib/combos/modelNameCollision.ts` में मौजूद है।

## क्लाइंट से कस्टम कॉम्बो को कॉल करना

स्थायी कॉम्बो (Settings → Combos) केवल तभी उपयोग किए जाते हैं, जब क्लाइंट `model` फ़ील्ड में कॉम्बो का **सटीक नाम** भेजता है — कॉम्बो नाम का कोई फ़ज़ी या आंशिक मिलान नहीं होता, और इसमें कोई `auto/` उपसर्ग शामिल नहीं होता। समाधान क्रम (`src/sse/services/model.ts` में `getComboForModel()`):

1. कॉम्बो नाम का सटीक मिलान (`model: "my-combo"`),
2. `combo/<name>` उपसर्ग (`model: "combo/my-combo"`),
3. मॉडल→कॉम्बो ग्लोब मैपिंग (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

दो सामान्य समस्याएँ:

- **`auto` आपके कॉम्बो का उपयोग नहीं करता।** `auto`/`auto/*` अपना स्वयं का शून्य-कॉन्फ़िगरेशन उम्मीदवार पूल बनाता है और स्थायी कॉम्बो का उपयोग केवल तभी करता है, जब किसी कॉम्बो का नाम वास्तव में `auto` हो (अनुशंसित नहीं)। किसी कॉम्बो के माध्यम से रूट करने के लिए उसका सटीक नाम भेजें — `auto` नहीं।
- **`openrouter/auto` एक वास्तविक सशुल्क OpenRouter उत्पाद** ("Auto Best Available") **है**, OmniRoute उपनाम नहीं। यह OpenRouter रजिस्ट्री (`open-sse/config/providers/registry/openrouter/index.ts`) की एकल स्थिर मॉडल प्रविष्टि है और इसका बिल अलग से लिया जाता है। इसे `auto` पूल से बाहर रखने के लिए Settings → Routing → Hide paid models का उपयोग करें।

मूल भ्रम, जिसका यह दस्तावेज़ीकरण करता है, उसके लिए [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) और [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) देखें।

## यह कैसे काम करता है (Persisted Auto-Combos)

Auto-Combo Engine एक **16-फैक्टर स्कोरिंग फ़ंक्शन** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` में परिभाषित) का उपयोग करके प्रत्येक अनुरोध के लिए गतिशील रूप से सर्वश्रेष्ठ प्रदाता/मॉडल का चयन करता है। डिफ़ॉल्ट भार (weights) का योग `1.0` होता है; कस्टम भार `normalizeScoringWeights()` द्वारा पुन: सामान्यीकृत (renormalized) किए जाते हैं। सोलह में से दो — `cacheAffinity` और `resetWindowAffinity` — का डिफ़ॉल्ट भार `0` होता है; `DEFAULT_WEIGHTS` में `reliability` का भार `0` होता है लेकिन सामान्य पैक्स में `0.03` और `reliability-first` में `0.04` होता है, और `quality` का पैक्स में `0.02` होता है (`quality-first` में `0.03`): इनकी गणना अभी भी प्रत्येक उम्मीदवार के लिए की जाती है, और `cacheAffinity` स्कोर के बाहर प्रॉम्प्ट-कैश डिडुप्लीकेशन को नियंत्रित करता है, इसलिए शून्य-डिफ़ॉल्ट कारक डिफ़ॉल्ट रूप से वोट नहीं करते हैं जबकि पैक्स करते हैं।

![Auto-Combo 16-factor scoring](../diagrams/exported/auto-combo-scoring.svg)

> **Unreadable quota (#15347).** जब किसी provider के पास quota fetcher होता है लेकिन वह कुछ भी
> readable वापस नहीं करता (failed fetch, missing credentials, message-only usage, या बिना किसी
> parseable `windows` और बिना किसी finite `percentUsed` वाला विकृत snapshot, जिसमें `percentUsed: null` भी शामिल है), तो उम्मीदवार
> `quota` axis पर `0` स्कोर करता है और इसका अंतिम स्कोर
> `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) से गुणा किया जाता है, जो connection-status penalty जैसा ही
> soft-penalty पैटर्न है। एक असफल usage रीड टेलीमेट्री के बारे में प्रमाण है,
> न कि provider के बारे में, इसलिए यह किसी भी वास्तविक रीडिंग से पूरी तरह नीचे रैंक करता है, जिसमें 100%-used की पुष्टि की गई
> रीडिंग भी शामिल है, लेकिन इसे कभी भी hard-blocked या बेदखल (evicted) नहीं किया जाता है। बिना किसी कैप वाला provider `unlimited: true` रिपोर्ट करता है और
> full quota के रूप में स्कोर करता है; बिना किसी रजिस्टर्ड quota fetcher वाले provider के पास कोई टेलीमेट्री सोर्स नहीं होता है
> और वह डिफ़ॉल्ट `100` बनाए रखता है।

**Sum:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` जैसा कि `DEFAULT_WEIGHTS` में घोषित किया गया है; उपयोगकर्ता-कॉन्फ़िगर किए गए weights को स्कोरिंग से पहले `normalizeScoringWeights()` द्वारा एक distribution में पुन: सामान्यीकृत (renormalized) किया जाता है।

### `weighted` सिमेंटिक्स

`weighted` प्रति अनुरोध एक **आनुपातिक रैंडम ड्रा** है (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), इक्वलाइज़र नहीं:

- प्रत्येक अनुरोध `weight / totalWeight` की संभावना के साथ **एक** चरण ड्रा करता है; शेष चरणों को उस अनुरोध के लिए फॉलबैक चेन के रूप में घटते भार (weight) के क्रम में व्यवस्थित किया जाता है।
- एक चरण जिसका भार `0` (या गायब) है, उसे **कभी ड्रा नहीं किया जाता** है जबकि किसी अन्य चरण का भार > 0 है — यह केवल ड्रा किए गए चरण के विफल होने के बाद ही फॉलबैक के रूप में काम कर सकता है। केवल जब **सभी** भार 0 होते हैं, तो चयन समान (uniform) हो जाता है।
- जिन चरणों के लक्ष्य अनुपलब्ध हैं — प्रदाता सर्किट ब्रेकर `OPEN`, कनेक्शन कूलडाउन, मॉडल लॉकआउट — उन्हें ड्रा होने से पहले हटा दिया जाता है (`open-sse/services/combo/targetResolution.ts`), इसलिए एक एकल स्वस्थ चरण अस्थायी रूप से हर अनुरोध जीत सकता है।
- `stickyWeightedLimit` (कॉम्बो कॉन्फ़िगरेशन, डिफ़ॉल्ट `1` = बंद) पुनः ड्रा करने से पहले ड्रा किए गए चरण को उतनी लगातार सफलताओं के लिए पिन करता है।

सख्त रोटेशन के लिए `round-robin` का उपयोग करें; `weighted` पर समान वेट सांख्यिकीय — न कि सख्त — संतुलन देते हैं।

### एजेंटिक पाइपलाइन मोड

कम से कम दो मॉडलों वाला एक `pipeline` कॉम्बो `config.agenticOrchestration.enabled` के साथ प्लानर/एक्जीक्यूटर रूटिंग का विकल्प चुन सकता है। पहला टारगेट प्लानिंग और अंतिम उत्तरों के लिए जिम्मेदार होता है; दूसरा टारगेट क्लाइंट-नेटिव टूल कॉल उत्सर्जित करता है। OmniRoute रिक्वेस्ट प्रोटोकॉल से टूल-रिजल्ट निरंतरता (continuations) का पता लगाता है, प्लानर से पूछता है कि क्या एक और टूल राउंड की आवश्यकता है, और गतिशील रूप से एक्जीक्यूटर या प्लानर में से किसी एक को क्लाइंट-फेसिंग अंतिम चरण बनाता है।

टूल-रिजल्ट निरंतरता पर, OmniRoute निष्पादन को तब भी रोकता है जब दो लगातार पूर्ण राउंड अपरिवर्तित परिणामों के साथ समान टूल कॉल को दोहराते हैं, या जब दो लगातार राउंड में प्रत्येक स्पष्ट रूप से चिह्नित परिणाम विफल हो जाता है। परिवर्तित परिणाम बार-बार कॉल की अनुमति देते हैं (उदाहरण के लिए, पोलिंग)। गार्ड एक नए यूजर रिक्वेस्ट पर रीसेट हो जाता है, समानांतर कॉल को एक राउंड में समूहित करता है, और Anthropic, Chat Completions, Responses और Gemini हिस्ट्री का समर्थन करता है। प्लानर कारण प्राप्त करता है और अंतिम उत्तर के लिए जिम्मेदार होता है, भले ही वह एक और टूल राउंड का अनुरोध करे।

दूसरे टारगेट के बाद के अतिरिक्त मॉडल क्रमित एक्जीक्यूटर बैकअप के रूप में होते हैं। एक विफल HTTP रिस्पॉन्स या ट्रांसपोर्ट एक्सेप्शन अगले एक्जीक्यूटर पर आगे बढ़ता है, जिसमें वही प्लानर निर्णय और नेटिव टूल होते हैं, लेकिन उस एक्जीक्यूटर का अपना स्टेप प्रॉम्प्ट और रिज़ॉल्व्ड कनेक्शन होता है। पहला सफल रिस्पॉन्स अपरिवर्तित लौटाया जाता है, जिसमें SSE स्ट्रीमिंग शामिल है; एक सफल स्ट्रीम शुरू होने के बाद की विफलताओं को यहाँ पुनः प्रयास (retry) नहीं किया जा सकता है। यदि सभी एक्जीक्यूटर विफल हो जाते हैं, तो अंतिम विफलता लौटा दी जाती है। क्लाइंट एबॉर्शन डिस्पैच को रोक देते हैं।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

एक्जीक्यूटर एक रिस्पॉन्स में कई स्वतंत्र कॉल उत्सर्जित कर सकता है। आश्रित कॉल को बाद के क्लाइंट टूल-रिजल्ट टर्न में संभाला जाता है, जिसमें प्लानर हर परिणाम की समीक्षा करता है। `maxToolRounds` डिफ़ॉल्ट रूप से `8` होता है और `1`–`32` स्वीकार करता है; एक बार पहुँच जाने पर, प्लानर को सर्वोत्तम उपलब्ध अंतिम उत्तर देना होगा। आंतरिक प्लानर निर्णय बफ़र किए जाते हैं, जबकि चयनित क्लाइंट-फेसिंग रिस्पॉन्स मूल स्ट्रीमिंग प्राथमिकता को संरक्षित करता है।

### `round-robin` स्टिकी बैच और अकाउंट विस्तार

Round-robin बैच किया जाता है, न कि प्रति-चरण एक-अनुरोध (one-request-per-step):

- `stickyRoundRobinLimit` (कॉम्बो कॉन्फ़िग, फिर `comboStickyRoundRobinLimit`, फिर `settings.stickyRoundRobinLimit`, डिफ़ॉल्ट **3**) रोटेट करने से पहले उतनी लगातार सफलताओं के लिए उसी टारगेट को बनाए रखता है। वन-रिक्वेस्ट रोटेशन के लिए कॉम्बो ओवरराइड को `1` पर सेट करें। कॉम्बो एडिटर प्रभावी मान और यह किस लेयर से आया है, यह दिखाता है।
- `connectionAwareExpansion` (कॉम्बो कॉन्फ़िग, फिर सेटिंग्स, डिफ़ॉल्ट **false**) रोटेशन से पहले प्रत्येक प्रोवाइडर-लेवल स्टेप को प्रति-अकाउंट टारगेट में विस्तारित करता है। ग्रुप-B रणनीतियाँ (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) तब तक प्रोवाइडर-लेवल व्यू रखती हैं जब तक यह चालू न हो। कॉम्बो एडिटर inherit / on / off को एक्सपोज़ करता है; inherit ग्लोबल डिफ़ॉल्ट (off) का उपयोग करता है।
- प्रॉम्प्ट-कैश लोकैलिटी रूटिंग (`promptCacheAffinityEnabled`, डिफ़ॉल्ट **true**) पिन किए गए कनेक्शन को पुनर्व्यवस्थित करती है ताकि मिलान वाले कैश की (keys) एक ही अकाउंट पर रहें। यह पिन किए गए प्रति-अकाउंट स्टेप्स पर round-robin और weighted रोटेशन से अधिक प्राथमिकता लेती है। यदि आपको सख्त रोटेशन की आवश्यकता है तो इसे Settings → Combo defaults के अंतर्गत बंद कर दें। कोई प्रति-कॉम्बो ओवरराइड नहीं है।

एक मॉडल पर मल्टी-अकाउंट रोटेशन के लिए, स्टिकी लिमिट `1` के साथ **एक डायनामिक-अकाउंट स्टेप** (खाली `connectionId`, पूरा पूल) को प्राथमिकता दें, न कि तीन पिन किए गए `connectionId`s को। पिन किए गए स्टेप्स और एफिनिटी एक ही अकाउंट पर कोलैप्स हो जाते हैं, भले ही RR काउंटर आगे बढ़ता रहे।

## फ़्यूज़न रणनीति

`fusion` ऐसी एकमात्र रणनीति है जो किसी एक लक्ष्य को **नहीं** चुनती। यह प्रॉम्प्ट को
**प्रत्येक पैनल मॉडल के पास समानांतर रूप से** भेजती है, फिर एक कॉन्फ़िगर करने योग्य **जज मॉडल**
सभी पैनल प्रतिक्रियाओं से एक अंतिम उत्तर तैयार करता है। इसे अपस्ट्रीम `decolua/9router`
(OpenRouter के Fusion डिज़ाइन) से पोर्ट किया गया है; कार्यान्वयन `open-sse/services/fusion.ts` में है।

यह कैसे काम करता है:

0. **टूल-युक्त बाइपास** — ऐसा अनुरोध जिसमें एक गैर-रिक्त `tools` ऐरे हो और
   `tool_choice` स्पष्ट रूप से `"none"` न हो, वह पैनल को पूरी तरह छोड़ देता है: इसे
   सीधे एक मॉडल (कॉन्फ़िगर किया गया जज, या `panel[0]`) पर रूट किया जाता है, जबकि
   `tools`/`tool_choice` को बिना बदलाव के आगे भेजा जाता है। पैनल सदस्यों के पास टूल
   एक्सेस नहीं होती और जज का संश्लेषण निर्देश टूल-कॉल उत्सर्जन को हतोत्साहित करता है,
   इसलिए एजेंटिक/टूल-कॉलिंग क्लाइंट को संश्लेषित गद्य के बजाय वास्तविक टूल-कॉल निर्णय
   मिलता है (#6771)।
1. **फ़ैन-आउट** (केवल टूल-रहित अनुरोधों के लिए) — प्रॉम्प्ट को सभी पैनल
   मॉडलों के पास एक साथ भेजा जाता है, टूल हटाकर और नॉन-स्ट्रीमिंग को बाध्य करके
   (संश्लेषण के लिए जज को पूरा गद्य चाहिए)।
2. **कोरम-ग्रेस संग्रह** — जैसे ही `minPanel` उत्तर आ जाते हैं, पीछे रह गए मॉडलों
   के लिए एक छोटा ग्रेस टाइमर शुरू हो जाता है, फिर जो कुछ भी एकत्र हुआ है उसके साथ
   फ़्यूज़न आगे बढ़ता है। इससे सबसे धीमे मॉडल के कारण वॉल टाइम पर पड़ने वाला दंड
   सीमित रहता है और एक हार्ड टाइमआउट से बाधित होता है।
3. **जज संश्लेषण** — पैनल उत्तरों को अनाम बनाया जाता है (`Source 1`, `Source 2`, … —
   ताकि जज मॉडल ब्रांड के बजाय विषय-वस्तु को महत्व दे) और जज को सौंपा जाता है, जो
   सहमति / विरोधाभासों / आंशिक कवरेज / विशिष्ट अंतर्दृष्टियों / अनदेखे पहलुओं का
   विश्लेषण करता है, फिर **एक** प्रामाणिक उत्तर लिखता है। जज कॉल क्लाइंट के मूल
   `stream` फ़्लैग + टूल को बनाए रखती है, इसलिए स्ट्रीमिंग और डाउनस्ट्रीम टूल उपयोग
   फिर भी काम करते हैं।
4. **सुचारु अवनयन** — 0 पैनल उत्तर → `503`; ठीक 1 उत्तरदाता → वही उत्तर
   सीधे लौटाया जाता है (फ़्यूज़ करने के लिए कुछ नहीं); एकल-मॉडल पैनल सीधे उत्तर देता है।

पैनल सदस्य एक `combo-ref` चरण (`{kind: "combo-ref", comboName: "..."}`) भी हो सकता है, जो
किसी अन्य कॉम्बो को संदर्भित करता है — यह **एक ब्लैक-बॉक्स पैनल आवाज़** के रूप में रिज़ॉल्व
होता है (संदर्भित कॉम्बो में पूर्ण रिकर्सिव डिस्पैच, न कि उस कॉम्बो के अपने लक्ष्यों का
फ़ैन-आउट), और इसमें वही गहराई/चक्र सुरक्षा होती है जिसका उपयोग पहले से ही प्रत्येक अन्य
combo-ref-उपयोग करने वाली रणनीति करती है (#6764)।

### कॉन्फ़िगरेशन

कॉम्बो के `config` ब्लॉब पर कॉन्फ़िगर किया जाता है (कोई स्कीमा माइग्रेशन नहीं — यह मौजूदा
`combos` तालिका का पुनः उपयोग करता है):

| फ़ील्ड                                   | प्रकार   | डिफ़ॉल्ट       | उद्देश्य                                                                            |
| :--------------------------------------- | :------- | :------------- | :---------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | पहला पैनल मॉडल | अंतिम उत्तर का संश्लेषण करने वाला मॉडल                                              |
| `config.fusionTuning.minPanel`           | `number` | `2`            | ग्रेस टाइमर शुरू होने से पहले आवश्यक सफल उत्तर (`[2, panelSize]` की सीमा में सीमित) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | कोरम पूरा होने के बाद पीछे रह गए मॉडलों के लिए कितनी देर प्रतीक्षा करनी है          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | पूर्ण सीमा, ताकि कोई एक अटका हुआ मॉडल अनुरोध को रोक न सके                           |

डिफ़ॉल्ट मान `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) में मौजूद हैं।

### उदाहरण

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

फिर इसे किसी भी कॉम्बो की तरह कॉल करें: `{"model":"fusion-panel","messages":[...]}`।

## वर्चुअल ऑटो-कॉम्बो फ़ैक्टरी

Auto Combo इंजन को पहले से परिभाषित कॉम्बो की आवश्यकता नहीं होती। इसके बजाय, `open-sse/services/autoCombo/virtualFactory.ts` तत्काल उम्मीदवार बनाता है:

1. `getProviderConnections({ isActive: true })` (सभी सक्षम कनेक्शन) प्राप्त करता है
2. वैध क्रेडेंशियल वाले कनेक्शन फ़िल्टर करता है (API कुंजी या `hasUsableOAuthToken()` के माध्यम से गैर-समाप्त OAuth टोकन)
3. मॉडल उपलब्धता + मूल्य निर्धारण के लिए `getProviderRegistry()` के साथ क्रॉस-रेफ़रेंस करता है
4. प्रत्येक टपल `(provider, model, connection)` के लिए एक `VirtualAutoComboCandidate` बनाता है
5. डिस्पैच लक्ष्य के रूप में `connection.defaultModel` (या रजिस्ट्री का पहला मॉडल) चुनता है
6. 16-फ़ैक्टर वाले `scorePool()` और वेरिएंट के वेट पैक का उपयोग करके प्रत्येक उम्मीदवार को स्कोर करता है
7. `handleComboChat()` के लिए परिणामी इन-मेमोरी `AutoComboConfig` लौटाता है — इसे कभी भी DB में स्थायी रूप से संग्रहीत नहीं किया जाता

इसका अर्थ है कि **`auto/*` सक्षम वाला नया प्रोवाइडर जोड़ने पर उम्मीदवार पूल अपने-आप विस्तृत हो जाता है** — कॉम्बो को मैन्युअल रूप से संपादित करने की आवश्यकता नहीं होती। वर्चुअल कॉम्बो प्रत्येक अनुरोध के लिए दोबारा बनाया जाता है, इसलिए नए जोड़े गए या फिर से स्वस्थ हुए कनेक्शन तुरंत चुन लिए जाते हैं।

## स्व-उपचार

- **अस्थायी बहिष्करण**: स्कोर < 0.2 → 5 मिनट के लिए बहिष्कृत (प्रगतिशील बैकऑफ़, अधिकतम 30 मिनट)
- **सर्किट ब्रेकर जागरूकता**: OPEN → स्वतः बहिष्कृत; HALF_OPEN → प्रोब अनुरोध
- **घटना मोड**: >50% OPEN → अन्वेषण अक्षम करें, स्थिरता अधिकतम करें
- **कूलडाउन रिकवरी**: बहिष्करण के बाद पहला अनुरोध कम टाइमआउट वाला एक "प्रोब" होता है

## बैंडिट अन्वेषण

5% अनुरोध (कॉन्फ़िगर करने योग्य) अन्वेषण के लिए यादृच्छिक प्रोवाइडरों तक रूट किए जाते हैं। घटना मोड में यह अक्षम रहता है।

## API

**`POST /api/combos/auto` का कोई समर्पित एंडपॉइंट नहीं है** — Auto-Combo का उपयोग दो तरीकों से किया जाता है:

1. **Zero-config (अनुशंसित):** `model: "auto"` या `model: "auto/<variant>"` के साथ कोई भी चैट कंप्लीशन अनुरोध भेजें। वर्चुअल फैक्ट्री प्रति अनुरोध कॉम्बो बनाती है — किसी पर्सिस्टेंस या API कॉल की आवश्यकता नहीं है।

2. **`strategy: "auto"` के साथ पर्सिस्टेड कॉम्बो:** `POST /api/combos` के माध्यम से एक नियमित कॉम्बो बनाएं और `strategy: "auto"` के साथ `config.auto.weights` / `config.auto.candidatePool` सेट करें। उसी स्कोरिंग इंजन का उपयोग किया जाता है; कॉम्बो `combos` में संग्रहीत होता है और ID द्वारा पुन: प्रयोज्य (reusable) होता है।

डिस्कवरी के लिए, `GET /api/combos/auto` प्रत्येक वेरिएंट को उसके रिज़ॉल्व्ड कैंडिडेट पूल के साथ, और `context_length` / `max_output_tokens` (कैंडिडेट पूल की विंडो में MAX) को सूचीबद्ध करता है। क्लाइंट्स (उदाहरण के लिए opencode प्लगइन) को `0` के बजाय इन मानों का विज्ञापन (advertise) करना चाहिए: शून्य कॉन्टेक्स्ट opencode के ऑटो-कॉम्पैक्शन को पूरी तरह से अक्षम कर देता है, जिससे सेशन तब तक बढ़ते रहते हैं जब तक कि गेटवे का हिस्ट्री पर्ज कॉन्टेक्स्ट को नष्ट नहीं कर देता। MAX का विज्ञापन करना सुरक्षित है क्योंकि ऑटो-कॉम्बो कॉन्टेक्स्ट प्री-फ़िल्टर बड़े आकार के अनुरोधों को बड़ी विंडो वाले कैंडिडेट्स पर रूट करता है।

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### ऑटो राउटर रणनीतियाँ

पर्सिस्टेड `strategy: "auto"` कॉम्बो `config.routerStrategy` (या लेगेसी `config.auto.routerStrategy`) को इनमें से किसी एक पर सेट कर सकते हैं:

- `rules` — डिफ़ॉल्ट वेटेड स्कोरिंग
- `score` — उच्चतम कॉन्फ़िगर की गई वेटेड स्कोर का चयन करता है। सटीक टाई होने पर कॉन्फ़िगर किए गए कैंडिडेट ऑर्डर को बनाए रखा जाता है; मौजूदा `explorationRate` पूरे रैंक किए गए पूल से सैंपल लेता है।
- `cost` / `eco` — सबसे सस्ता हेल्दी प्रोवाइडर
- `latency` / `fast` — रिलायबिलिटी पेनल्टी के साथ न्यूनतम p95 लेटेंसी
- `sla-aware` / `sla` — उन कैंडिडेट्स को प्राथमिकता दें जो p95 लेटेंसी, एरर-रेट और वैकल्पिक कॉस्ट SLO को पूरा करते हैं
- `lkgp` — लास्ट नोन गुड प्रोवाइडर पहले
- `nadir` — [Nadir](https://getnadir.com) के डिसीजन API से पूछें कि पूल में किस मॉडल की प्रॉम्प्ट को आवश्यकता है; ऑप्ट-इन, `rules` पर फ़ेल-ओपन

### राउटर रणनीतियाँ विस्तार से

ऑटो-कॉम्बो इंजन 7 प्लगेबल **RouterStrategy** इम्प्लीमेंटेशन को एक्सपोज़ करता है जिन्हें आप `config.routerStrategy` (या लेगेसी `config.auto.routerStrategy`) के माध्यम से स्वैप कर सकते हैं। प्रत्येक रणनीति `RoutingContext` (टास्क प्रकार, टूल/विज़न हिंट्स, टोकन अनुमान, वैकल्पिक SLA पॉलिसी, वैकल्पिक लास्ट-नोन-गुड प्रोवाइडर) दिए जाने पर कैंडिडेट पूल से एक प्रोवाइडर चुनती है।

#### 1. `rules` (डिफ़ॉल्ट) — 16-फैक्टर वेटेड स्कोरिंग

मौजूदा स्कोरिंग इंजन को रैप करता है। `OPEN` सर्किट-ब्रेकर कैंडिडेट्स को फ़िल्टर करता है, फिर वर्तमान टास्क प्रकार और `getTaskFitness()` के साथ `scorePool()` चलाता है, और टॉप-स्कोरिंग प्रोवाइडर को चुनता है।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें**: डिफ़ॉल्ट। तब उपयोग करें जब आप सभी सिग्नलों के बीच संतुलित ट्रेड-ऑफ़ चाहते हैं।

**Alias**: `rules` (कोई उपनाम नहीं)

---

#### 2. `cost` / `eco` — सबसे सस्ता हेल्दी प्रोवाइडर

कैंडिडेट पूल को `costPer1MTokens` (आरोही क्रम) के अनुसार सॉर्ट करता है और सबसे सस्ते को चुनता है। पहले `OPEN` कैंडिडेट्स को फ़िल्टर करता है।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें**: लागत-संवेदनशील वर्कलोड, बैच प्रोसेसिंग, या बैकग्राउंड जॉब्स।

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — रिलायबिलिटी पेनल्टी के साथ न्यूनतम p95 लेटेंसी

`p95LatencyMs + (errorRate * 1000)` द्वारा सॉर्ट करता है। एरर-रेट पेनल्टी यह सुनिश्चित करती है कि अविश्वसनीय प्रोवाइडर्स को कम रैंक किया जाए, भले ही उनकी नाममात्र लेटेंसी कम हो।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कब उपयोग करें**: लेटेंसी-संवेदनशील वर्कलोड जैसे रियल-टाइम चैट, ऑटो-कंप्लीट, या इंटरैक्टिव कोडिंग असिस्टेंट।

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — लेटेंसी/एरर/कॉस्ट SLO अनुपालन

प्रत्येक कैंडिडेट को इस आधार पर स्कोर करता है कि वह कॉन्फ़िगर की गई SLO पॉलिसी को कितनी अच्छी तरह पूरा करता है:

| कारक            | भार | सूत्र                                                 |
| --------------- | --- | ----------------------------------------------------- |
| विलंबता स्कोर   | 35% | `threshold / max(value, ε)`                           |
| त्रुटि स्कोर    | 35% | `threshold / max(value, ε)`                           |
| स्वास्थ्य स्कोर | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)     |
| लागत स्कोर      | 10% | `threshold / max(value, ε)` या व्युत्क्रम सामान्यीकृत |
| स्थिरता स्कोर   | 5%  | व्युत्क्रम सामान्यीकृत विलंबता stddev                 |

जब `hardConstraints: true` होता है, तो उम्मीदवारों को मुख्य रूप से **उल्लंघन स्कोर** (वे किसी SLO से कितना अधिक हैं) के आधार पर क्रमबद्ध किया जाता है, और फिर समग्र स्कोर के आधार पर। अन्यथा यह केवल समग्र स्कोर होता है।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA फ़ील्ड** (कॉम्बो कॉन्फ़िगरेशन पर सेट):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**कब उपयोग करें**: सख्त विलंबता, त्रुटि-दर, या लागत बजट वाले प्रोडक्शन वर्कलोड के लिए।

**उपनाम (Aliases)**: `sla-aware`, `sla`

---

#### 5. `lkgp` — अंतिम ज्ञात अच्छा प्रदाता (last known good provider) पहले

पहले **अंतिम ज्ञात अच्छे प्रदाता** (यदि सेट है) को आज़माता है, फिर `rules` रणनीति पर वापस आ जाता है। सत्र स्टिकनेस (session stickiness) के लिए उपयोगी — एक ही प्रदाता बातचीत में फॉलो-अप अनुरोधों को संभालता है।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**कब उपयोग करें**: मल्टी-टर्न बातचीत जहाँ आप चाहते हैं कि एक ही प्रदाता फॉलो-अप अनुरोधों को संभाले (उदाहरण के लिए, कैशिंग, संदर्भ निरंतरता, या मूल्य निर्धारण स्थिरता के लिए)।

**उपनाम**: `lkgp` (कोई उपनाम नहीं)

---

#### 6. `nadir` — Nadir के माध्यम से प्रॉम्प्ट-जागरूक मॉडल चयन

ऊपर दी गई प्रत्येक रणनीति उम्मीदवारों को उनके स्वयं के टेलीमेट्री द्वारा रैंक करती है; उनमें से कोई भी अनुरोध को नहीं पढ़ता है। `nadir` अंतिम उपयोगकर्ता टर्न और पूल के मॉडल आईडी को [Nadir](https://getnadir.com) के निर्णय API (`POST /v1/bucket`) पर भेजता है और उस मॉडल पर रूट करता है जिसे Nadir उस मेनू से चुनता है (`simple` → सबसे सस्ता सक्षम मॉडल, `complex` → फ्रंटियर मॉडल)। उस मॉडल की सेवा करने वाला कनेक्शन अभी भी `rules` द्वारा चुना जाता है, इसलिए कोटा, स्वास्थ्य और लागत यह तय करते रहते हैं कि कौन सा खाता उपयोग करना है।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` और `OMNIROUTE_NADIR_BASE_URL` दो स्ट्रिंग्स के लिए env फ़ॉलबैक हैं। `baseUrl` केवल स्व-होस्ट किए गए Nadir के लिए आवश्यक है (अंत में `/v1` स्वीकार्य है)। बिना की (Keyless) कॉल Nadir के अनाम टियर पर जाती हैं, जो प्रति IP दर-सीमित (rate-limited) है।

बॉक्स से क्या बाहर जाता है: अंतिम उपयोगकर्ता संदेश का टेक्स्ट (पहले 16k वर्ण), उम्मीदवार मॉडल आईडी और एक `source: "omniroute"` चैनल टैग। कोई सिस्टम प्रॉम्प्ट, इतिहास, टूल या हेडर नहीं।

विफलता व्यवहार फेल-ओपन है: टाइमआउट (डिफ़ॉल्ट 2000 ms), एक non-2xx, एक अप्राप्य होस्ट, एक विकृत प्रतिक्रिया या पूल के बाहर का चयन `rules` निर्णय पर हल होता है और कारण का उपसर्ग `NadirStrategy: fallback (…)` होता है। एक विफल कॉल के बाद रणनीति 30 सेकंड के लिए नेटवर्क को छोड़ देती है, इसलिए एक आउटेज प्रति अनुरोध एक के बजाय प्रति 30 सेकंड में एक टाइमआउट खर्च करता है। रूटिंग इवेंट्स केवल तब `strategy: "nadir"` रिपोर्ट करते हैं जब Nadir ने वास्तव में चुनाव किया हो।

**कब उपयोग करें**: ऐसे पूल पर मिश्रित-कठिनाई वाला ट्रैफ़िक जो मॉडल टियर (एक छोटा, एक मध्यम और एक फ्रंटियर मॉडल) तक फैला हो, जहाँ हमेशा-फ्रंटियर वह लागत है जिसे आप कम करना चाहते हैं।

**उपनाम**: `nadir` (कोई उपनाम नहीं)

### कस्टम राउटर रणनीतियाँ

आप सार्वजनिक API के माध्यम से अपना स्वयं का `RouterStrategy` कार्यान्वयन पंजीकृत कर सकते हैं:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

फिर इसका उपयोग करें:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

| --------------- | ----------- | ------------------------------------------------ |


## कार्य उपयुक्तता

6 कार्य प्रकारों (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) में 30+ मॉडलों को स्कोर दिया गया है। वाइल्डकार्ड पैटर्न समर्थित हैं (उदा., `*-coder` → उच्च कोडिंग स्कोर)।

## Auto वेरिएंट का सारांश

साधारण `auto` (डिफ़ॉल्ट) तथा `autoPrefix.ts` में घोषित 6 `AutoVariant` मानों को मिलाकर, कुल **7 उपयोग किए जा सकने वाले मॉडल ID** हैं:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` स्वयं 6 मानों को सूचीबद्ध करता है; 7वाँ विकल्प "कोई वेरिएंट नहीं" है — साधारण `auto` — जिसे `parseAutoPrefix()` द्वारा `variant: undefined` के रूप में संभाला जाता है।)

## टियर Auto-Combo में कैसे समाहित होते हैं

16-फ़ैक्टर वाला स्कोरिंग फ़ंक्शन (`open-sse/services/autoCombo/scoring.ts`) टियर
सदस्यता को दो संकेतों के रूप में मानता है: `tierPriority` (0.0476) और `tierAffinity` (0.0476)। संपूर्ण
`DEFAULT_WEIGHTS` सेट के लिए ऊपर दी गई प्रामाणिक [स्कोरिंग फ़ैक्टर तालिका](#how-it-works-persisted-auto-combos) देखें — प्रत्येक पैक के ओवरराइड (ship-fast/cost-saver/quality-first/
offline-friendly) "प्रति पैक वेट प्रोफ़ाइल" तालिका में सूचीबद्ध हैं।

केवल टियर, टियर 1 को पहले रखने के लिए **बाध्य** नहीं करता — यदि टियर 1 की लेटेंसी खराब है या
लागत-बनाम-गुणवत्ता इष्टतम नहीं है, तो टियर 2 विजेता होता है। टियर क्रम को बाध्य करने के लिए, कॉम्बो
रणनीति `priority` का उपयोग करें और प्रदाताओं को टियर के अनुसार व्यवस्थित करें।

टियर 1 (सब्सक्रिप्शन) को मज़बूत प्राथमिकता देने के लिए, `tierPriority` का वेट बढ़ाएँ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

टियर की परिभाषाओं और प्रदाता वर्गीकरण के लिए [`docs/guides/TIERS.md`](../guides/TIERS.md) देखें।

## परीक्षण और कवरेज

### नियतात्मक रूटिंग-निर्णय मैट्रिक्स (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` मॉक किए गए अपस्ट्रीम के साथ वास्तविक कॉम्बो पाइपलाइन के माध्यम से सभी 19
सार्वजनिक रणनीतियों के रूटिंग **निर्णय** को शुरू से अंत तक प्रमाणित करता है।
कवरेज में शामिल हैं:

- सभी 19 `ROUTING_STRATEGY_VALUES` रणनीतियाँ (क्रमबद्ध, भारित, लागत, संदर्भ, फ़्यूज़न, …)।
- `quota-share` (आंतरिक) शुरू से अंत तक: वास्तविक `selectQuotaShareTarget` सीम (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) के माध्यम से DRR निष्पक्षता + संतृप्ति होने पर प्राथमिकता में कमी।
- प्रत्येक लक्ष्य संख्या में `context-relay` सार्वभौमिक-हैंडऑफ़ कवरेज।

यह सूट CI (`test:integration` जॉब) में `--test-concurrency=1` और
`--test-force-exit` के साथ चलता है, ताकि यह नियतात्मक रहे और इसे लाइव क्रेडेंशियल की आवश्यकता न हो।

### गेटेड लाइव स्मोक परीक्षण (CI में नहीं — वास्तविक प्रदाता)

| कमांड                                  | यह क्या करता है                                                                             |
| :------------------------------------- | :------------------------------------------------------------------------------------------ |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` के साथ इन-प्रोसेस वास्तविक रूटिंग; लाइव OmniRoute DB का स्नैपशॉट लेता है |
| `npm run test:combo:live:vps`          | लाइव OmniRoute सर्वर के विरुद्ध HTTP कॉल (`COMBO_LIVE_BASE_URL` सेट करें)                   |
| `npm run test:combo:live:vps:failover` | वही, जानबूझकर बनाए गए फ़ेलओवर परिदृश्यों के साथ                                             |

ये स्मोक परीक्षण वास्तविक वायर पथ (कॉम्बो → प्रदाता → पूर्णता) का परीक्षण करते हैं। इन्हें
जानबूझकर CI से बाहर रखा गया है, क्योंकि इनके लिए लाइव क्रेडेंशियल और VPS पहुँच आवश्यक है।
