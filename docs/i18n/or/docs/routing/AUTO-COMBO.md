## ଶୂନ୍ୟ-କନଫିଗ୍ ସ୍ୱୟଂଚାଳିତ ରାଉଟିଂ (`auto/` ପ୍ରିଫିକ୍ସ)

> **ନୂଆ:** କମ୍ବୋ ସୃଷ୍ଟି କରିବା ଆବଶ୍ୟକ ନାହିଁ। ଯେକୌଣସି କ୍ଲାଏଣ୍ଟରେ ସିଧାସଳଖ `auto/` ପ୍ରିଫିକ୍ସ ବ୍ୟବହାର କରନ୍ତୁ।

### ବର୍ଗ × ସ୍ତର ସଂଯୋଜନ (`auto/<category>:<tier>`)

OpenRouter-ଶୈଳୀର ସଫିକ୍ସଗୁଡ଼ିକ **କେଉଁ ପ୍ରକାରର ରୁଟ୍** (ବର୍ଗ)କୁ **କିପରି ଅନୁକୂଳିତ କରାଯିବ** (ସ୍ତର)ଠାରୁ ପୃଥକ କରେ, ଯାହାଦ୍ୱାରା ଆପଣ ସେଗୁଡ଼ିକୁ ସ୍ୱାଧୀନ ଭାବରେ ସଂଯୋଜନ କରିପାରିବେ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ବର୍ଗଗୁଡ଼ିକ** (କ୍ଷମତା ଅନୁଯାୟୀ ପ୍ରାର୍ଥୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରେ): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍ଗୁଡ଼ିକୁ ରଖେ; `reasoning` ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍ଗୁଡ଼ିକୁ ରଖେ।
- **ସ୍ତରଗୁଡ଼ିକ** (ସ୍କୋରିଂ ଓଜନ / ପୁଲ୍ ଫିଲ୍ଟର୍ ବାଛେ): `fast` (ଶୀଘ୍ର ପ୍ରେରଣ) · `cheap` (ଉପନାମ `floor`, ଖର୍ଚ୍ଚ-ସଞ୍ଚୟକାରୀ) · `reliable` (ସର୍କିଟ୍-ବ୍ରେକର୍ ସ୍ୱାସ୍ଥ୍ୟ + ବିଳମ୍ବତା ସ୍ଥିରତା) · `free` / `pro` (`classifyTier` ମାଧ୍ୟମରେ ମଡେଲ୍ ସ୍ତର ଅନୁଯାୟୀ ପୁଲ୍ ଫିଲ୍ଟର୍ କରେ — ମାଗଣା ସ୍ତର ବନାମ ପ୍ରିମିୟମ୍)।

| ଉଦାହରଣ                 | ଏଥିରେ ରିଜଲ୍ଭ ହୁଏ                                        |
| ---------------------- | ------------------------------------------------------- |
| `auto/coding:fast`     | କୋଡିଂ ପୁଲ୍, କମ୍-ବିଳମ୍ବତା ଓଜନ                            |
| `auto/coding:cheap`    | କୋଡିଂ ପୁଲ୍, ଖର୍ଚ୍ଚ-ଅନୁକୂଳିତ (ଉପନାମ `auto/coding:floor`) |
| `auto/reasoning:pro`   | କେବଳ ରିଜନିଂ/ଥିଙ୍କିଂ ମଡେଲ୍, ପ୍ରିମିୟମ୍ ସ୍ତର               |
| `auto/vision`          | ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍ (କୌଣସି ସ୍ତର ନାହିଁ → ସନ୍ତୁଳିତ ଓଜନ)     |
| `auto/multimodal:free` | ମଲ୍ଟିମୋଡାଲ୍-ସକ୍ଷମ ମଡେଲ୍, କେବଳ ମାଗଣା ସ୍ତର                |

ଯେକୌଣସି ବୈଧ `auto/<category>[:<tier>]` ଚାହିଦା ଅନୁସାରେ ରିଜଲ୍ଭ ହୁଏ; `/v1/models` ଏବଂ ଡ୍ୟାସ୍ବୋର୍ଡରେ ଏକ କ୍ୟୁରେଟ୍ କରାଯାଇଥିବା ଉପସେଟ୍ର ପ୍ରଚାର କରାଯାଏ (`open-sse/services/autoCombo/builtinCatalog.ts`ରେ `AUTO_SUFFIX_VARIANTS`)। ଫିଲ୍ଟରିଂ **ଫେଲ୍-ଓପନ୍** ଅଟେ — ଯଦି କୌଣସି ସୀମାବନ୍ଧନ ସହ କୌଣସି ସଂଯୁକ୍ତ ମଡେଲ୍ ମେଳ ନ ଖାଏ, ତେବେ ସମ୍ପୂର୍ଣ୍ଣ ପୁଲ୍ ବ୍ୟବହୃତ ହୁଏ, ଯାହାଦ୍ୱାରା ରାଉଟିଂ କେବେ ଭଙ୍ଗ ହୁଏ ନାହିଁ। ମୂଳ ସ୍କୋରର୍ (`combo.ts`) ଅପରିବର୍ତ୍ତିତ ରହେ; ବର୍ଗ/ସ୍ତର ଫିଲ୍ଟର୍ `buildAutoCandidates`ରେ ପ୍ରୟୋଗ କରାଯାଏ।

> **ଲାଇଭ୍ ମଡେଲ୍ ଇଣ୍ଟେଲିଜେନ୍ସ:** `ARENA_ELO_SYNC_ENABLED` ଫ୍ଲାଗ୍ ଚାଲୁ ଥିବାବେଳେ ସ୍ୱୟଂଚାଳିତ ରାଉଟିଂ ଉପଯୁକ୍ତତା ଲାଇଭ୍ **Arena ELO** ର୍ୟାଙ୍କିଂ + **models.dev** ସ୍ତର ଡାଟା ଦ୍ୱାରା ନିର୍ଦ୍ଧାରିତ ହୁଏ (ଅନ୍ୟଥା ସ୍ଥିର ଉପଯୁକ୍ତତା ମ୍ୟାପ୍କୁ ଫେରିଯାଏ)।

### ପ୍ରତି-କୀ ପ୍ରାର୍ଥୀ ନିୟନ୍ତ୍ରଣ (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` ପରେ ଥିବା ସଫିକ୍ସ, କିମ୍ବା
ମୂଳ ଚ୍ୟାନେଲ୍ ପାଇଁ ଆକ୍ଷରିକ `auto`) ହେଉଛି ଏକ **କେବଳ-ପଠନୀୟ** ଏଣ୍ଡପଏଣ୍ଟ, ଯାହା ବର୍ତ୍ତମାନର
ସହନଶୀଳତା ପଠନଗୁଡ଼ିକୁ ପୁନଃବ୍ୟବହାର କରି ଲାଇଭ୍ ପହଞ୍ଚଯୋଗ୍ୟତା ସହ ସଜ୍ଜିତ ଏକ `auto/*` ଚ୍ୟାନେଲ୍ର
ବର୍ତ୍ତମାନର ପ୍ରାର୍ଥୀ ପୁଲ୍ ତାଲିକାଭୁକ୍ତ କରେ (କେବେ ମଧ୍ୟ କଚ୍ଚା ବ୍ରେକର୍ `state` ନୁହେଁ):

- ପ୍ରଦାତା ସର୍କିଟ୍ ବ୍ରେକର୍ — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ସଂଯୋଗ କୁଲ୍ଡାଉନ୍ — ରିଜଲ୍ଭ ହୋଇଥିବା `provider_connections` ଧାଡ଼ିରେ `rateLimitedUntil` / `testStatus`
- ମଡେଲ୍ ଲକ୍ଆଉଟ୍ — `isModelLocked(provider, connectionId, model)`

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀ ଏହି API କୀର `excluded` ଫ୍ଲାଗ୍ ମଧ୍ୟ ବହନ କରେ। ବହିଷ୍କରଣଗୁଡ଼ିକ
ପ୍ରତି-API-କୀ ଆଧାରରେ ସଂରକ୍ଷିତ ହୁଏ (`auto_candidate_overrides` ଟେବୁଲ୍, ମାଇଗ୍ରେସନ୍ `128`) — OmniRoute
କୌଣସି `users` ଟେବୁଲ୍ ନଥିବା ଏକକ-ଟେନାଣ୍ଟ ପ୍ରଣାଳୀ, ତେଣୁ `apiKeyId` ହେଉଛି ସର୍ବନିକଟ ପ୍ରକୃତ ପ୍ରତି-କଲର୍
ପରିଚୟ — ଏବଂ ଶୁଦ୍ଧ, ୟୁନିଟ୍-ପରୀକ୍ଷିତ
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ମାଧ୍ୟମରେ
`open-sse/services/autoCombo/virtualFactory.ts`ର ପ୍ରାର୍ଥୀ-ପୁଲ୍ ଚୋକପଏଣ୍ଟରେ ପ୍ରବର୍ତ୍ତିତ ହୁଏ।
ଫିଲ୍ଟର୍ଟି **ଫେଲ୍-ଓପନ୍** ଅଟେ: ଏକ ଅସେଟ୍ apiKeyId/channel କିମ୍ବା ଏକ DB ଲୁକଅପ୍ ବିଫଳତା, ଉଭୟ
ପୁଲ୍କୁ ଫିଲ୍ଟର୍ ନ କରି ରଖେ; ତେଣୁ କୌଣସି ଓଭରରାଇଡ୍ କନଫିଗର୍ କରିନଥିବା ଅପରେଟର୍ ଏହି ବୈଶିଷ୍ଟ୍ୟ ପୂର୍ବରୁ ଥିବା
ରାଉଟିଂ ସହ ବାଇଟ୍-ସମାନ ରାଉଟିଂ ଦେଖନ୍ତି।

**ପରବର୍ତ୍ତୀ ଇସ୍ୟୁ ପାଇଁ ସ୍ଥଗିତ:** ପ୍ରତି-ପ୍ରାର୍ଥୀ ଓଜନ + ସ୍ପଷ୍ଟ କ୍ରମ ନିର୍ଦ୍ଧାରଣ (ସ୍ତର 3
— ବିଦ୍ୟମାନ ଓଜନଯୁକ୍ତ/ପ୍ରାଥମିକତା କୌଶଳ ପଥଗୁଡ଼ିକୁ ଯୋଗାଣ କରେ) ଏବଂ ପ୍ରତ୍ୟେକ `auto/*`
ଚ୍ୟାନେଲ୍ ପାଇଁ ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ `combo.ts` କୌଶଳକୁ ପିନ୍ କରିବା (ସ୍ତର 4)। ଏକକ-ଟେନାଣ୍ଟ
ମଡେଲ୍କୁ ବିଚାର କରି ଓଭର୍ରାଇଡ୍ଗୁଡ଼ିକ ପ୍ରତି-API-କି ଆଧାରିତ ରହିବା ଉଚିତ କିମ୍ବା ବୈଶ୍ୱିକ ହେବା
ଉଚିତ, ସେହି ଅମୀମାଂସିତ ପ୍ରଶ୍ନ ପାଇଁ #7819 ଯୋଜନା ଦେଖନ୍ତୁ।

## ପ୍ରକୃତ Model Id ସହ ମେଳ ଖାଉଥିବା Combo ନାମଗୁଡ଼ିକ

ଯେଉଁ comboର `name` ଏକ bare model id ସହ ସମାନ (ଉଦାହରଣ ସ୍ୱରୂପ, ନାମ
`gpt-5.5` ଥିବା ଏକ combo), ତାହା ଏକ **ଉଦ୍ଦେଶ୍ୟମୂଳକ, ସମର୍ଥିତ ପ୍ୟାଟର୍ନ**, bug ନୁହେଁ: ଏହା
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)ରେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା
ପ୍ରତ୍ୟେକ model-id ପାଇଁ provider fallback ବ୍ୟବସ୍ଥା। କାରଣ bare-model-id resolution ପୂର୍ବରୁ
combo resolution ଯାଞ୍ଚ କରାଯାଏ
(`src/sse/services/model.ts`ରେ `getComboForModel()`), ତେଣୁ bare
id `gpt-5.5` ପାଇଁ ଏକ requestକୁ ସିଧାସଳଖ ଗୋଟିଏ providerକୁ ପଠାଇବା ପରିବର୍ତ୍ତେ
comboର targets (ଉଦାହରଣ ସ୍ୱରୂପ,
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) ମାଧ୍ୟମରେ route କରାଯାଏ
— ଏହା [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) ପାଇଁ
ନିର୍ମିତ combo-before-rewrite precedenceକୁ ପୁନଃବ୍ୟବହାର କରେ ଏବଂ
`tests/unit/responses-combo-resolution-3227.test.ts` ଓ
`tests/unit/combo-name-codex-responses-rewrite.test.ts` ଦ୍ୱାରା regression-test କରାଯାଇଛି।

ଏକ ପ୍ରକୃତ model idକୁ shadow କରୁଥିବା ନାମରେ combo ସୃଷ୍ଟି କିମ୍ବା rename କରିବା
**କେବେ ମଧ୍ୟ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ ନାହିଁ** — ଏପରି କଲେ ଏହି ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା workflow ଭାଙ୍ଗିଯିବ। ଏହା ପରିବର୍ତ୍ତେ
(#8530), (ନୂଆ) ନାମଟି ଏକ ପ୍ରକୃତ
model id ସହ ମେଳ ଖାଇଲେ `POST /api/combos` ଏବଂ `PUT /api/combos/[id]` responseରେ ଏକ non-blocking
`warning` field ଯୋଡ଼ନ୍ତି:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Boot ସମୟରେ, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) ମଧ୍ୟ model idକୁ shadow କରୁଥିବା ପ୍ରତ୍ୟେକ ବିଦ୍ୟମାନ comboର ତାଲିକା ସହିତ ଏକ ଏକ-ଧାଡ଼ିଆ `[STARTUP]` warning
log କରେ, ଯାହାଦ୍ୱାରା #6940 ଅନୁଯାୟୀ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବରେ କରିବା ପରିବର୍ତ୍ତେ
ଦୁର୍ଘଟଣାବଶତଃ ଏହାର ସମ୍ମୁଖୀନ ହୋଇଥିବା operatorsମାନେ ଏକ ସଙ୍କେତ ପାଆନ୍ତି।
Detection helperଟି `src/lib/combos/modelNameCollision.ts`ରେ ରହିଛି।

## ଏକ Clientରୁ Custom Comboକୁ Call କରିବା

Persisted combos (Settings → Combos) କେବଳ ସେତେବେଳେ ବ୍ୟବହୃତ ହୁଏ, ଯେତେବେଳେ client `model` fieldରେ comboର **ଅବିକଳ ନାମ** ପଠାଏ — combo ନାମର କୌଣସି fuzzy କିମ୍ବା partial matching ନାହିଁ, ଏବଂ କୌଣସି `auto/` prefix ମଧ୍ୟ ସମ୍ପୃକ୍ତ ନୁହେଁ। Resolution କ୍ରମ (`src/sse/services/model.ts`ରେ `getComboForModel()`):

1. ଅବିକଳ combo-name match (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

ଦୁଇଟି ସାଧାରଣ ଭୁଲ:

- **`auto` ଆପଣଙ୍କ combos ବ୍ୟବହାର କରେ ନାହିଁ।** `auto`/`auto/*` ନିଜର zero-config candidate pool ନିର୍ମାଣ କରେ ଏବଂ କେବଳ ଯଦି କୌଣସି comboର ନାମ ଆକ୍ଷରିକ ଭାବରେ `auto` ଥାଏ, ତେବେ persisted combosକୁ ବିଚାର କରେ (ଏହା ସୁପାରିସ କରାଯାଏ ନାହିଁ)। ଏକ combo ମାଧ୍ୟମରେ route କରିବାକୁ, ଏହାର ଅବିକଳ ନାମ ପଠାନ୍ତୁ — `auto` ନୁହେଁ।
- **`openrouter/auto` ହେଉଛି ଏକ ପ୍ରକୃତ paid OpenRouter product** ("Auto Best Available"), OmniRoute alias ନୁହେଁ। ଏହା OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`)ର ଏକମାତ୍ର static model entry ଏବଂ ଏଥିପାଇଁ ପୃଥକ ଭାବରେ bill କରାଯାଏ। ଏହାକୁ `auto` poolsରୁ ବାଦ ଦେବା ପାଇଁ Settings → Routing → Hide paid models ବ୍ୟବହାର କରନ୍ତୁ।

ଏଠାରେ ଡକ୍ୟୁମେଣ୍ଟ କରାଯାଇଥିବା ମୂଳ ଦ୍ୱନ୍ଦ୍ୱ ପାଇଁ [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) ଏବଂ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) ଦେଖନ୍ତୁ।

## ଏହା କିପରି କାମ କରେ (Persisted Auto-Combos)

Auto-Combo Engine ଏକ **16-factor scoring function** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` ରେ ପରିଭାଷିତ) ବ୍ୟବହାର କରି ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ସର୍ବୋତ୍ତମ provider/model କୁ ଡାଇନାମିକାଲି ଚୟନ କରେ। ଡିଫଲ୍ଟ ୱେଟ୍‌ଗୁଡ଼ିକର ସମଷ୍ଟି `1.0` ଅଟେ; କଷ୍ଟମ୍ ୱେଟ୍‌ଗୁଡ଼ିକୁ `normalizeScoringWeights()` ଦ୍ୱାରା ପୁନଃ ନର୍ମାଲାଇଜ୍ କରାଯାଏ। ଷୋହଳଟି ମଧ୍ୟରୁ ଦୁଇଟି — `cacheAffinity` ଏବଂ `resetWindowAffinity` — ର ଡିଫଲ୍ଟ ୱେଟ୍ `0` ରହିଥାଏ; `DEFAULT_WEIGHTS` ରେ `reliability` ର ମୂଲ୍ୟ `0` ରହିଥାଏ କିନ୍ତୁ generic packs ରେ `0.03` ଏବଂ `reliability-first` ରେ `0.04` ରହିଥାଏ, ଏବଂ packs ରେ `quality` ର ମୂଲ୍ୟ `0.02` (`quality-first` ରେ `0.03`) ରହିଥାଏ: ଏଗୁଡ଼ିକ ଏବେ ମଧ୍ୟ ପ୍ରତ୍ୟେକ candidate ପାଇଁ ଗଣନା କରାଯାଏ, ଏବଂ `cacheAffinity` ସ୍କୋର ବାହାରେ prompt-cache deduplication କୁ ଗେଟ୍ କରେ, ତେଣୁ ଜିରୋ-ଡିଫଲ୍ଟ ଫ୍ୟାକ୍ଟରଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବରେ ଭୋଟ୍ କରନ୍ତି ନାହିଁ ଯେତେବେଳେ କି packs କରନ୍ତି।

### `weighted` ସେମାଣ୍ଟିକ୍ସ

`weighted` ହେଉଛି **ପ୍ରତି ଅନୁରୋଧ ପାଇଁ ଏକ ଆନୁପାତିକ ରାଣ୍ଡମ୍ ଡ୍ର** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ଏହା ଏକ ଇକ୍ୱାଲାଇଜର୍ ନୁହେଁ:

- ପ୍ରତ୍ୟେକ ଅନୁରୋଧ `weight / totalWeight` ସମ୍ଭାବନା ସହିତ **ଗୋଟିଏ** ପଦକ୍ଷେପ ଡ୍ର କରେ; ବାକି ପଦକ୍ଷେପଗୁଡ଼ିକ ସେହି ଅନୁରୋଧ ପାଇଁ ଫଲବ୍ୟାକ୍ ଚେନ୍ ଭାବରେ ଓଜନ ଅନୁଯାୟୀ ଅବରୋହୀ କ୍ରମରେ ସଜାଯାଇଥାଏ।
- ଯେଉଁ ପଦକ୍ଷେପର ଓଜନ `0` (କିମ୍ବା ନାହିଁ) ତାହା **କେବେବି ଡ୍ର ହୁଏ ନାହିଁ** ଯେତେବେଳେ ଅନ୍ୟ କୌଣସି ପଦକ୍ଷେପର ଓଜନ > 0 ଥାଏ — ଏହା କେବଳ ଡ୍ର ହୋଇଥିବା ପଦକ୍ଷେପ ବିଫଳ ହେବା ପରେ ଫଲବ୍ୟାକ୍ ଭାବରେ କାର୍ଯ୍ୟ କରିପାରିବ। କେବଳ ଯେତେବେଳେ **ସମସ୍ତ** ଓଜନ 0 ଥାଏ, ସେତେବେଳେ ଚୟନ ସମାନ ହୋଇଯାଏ।
- ଯେଉଁ ପଦକ୍ଷେପଗୁଡ଼ିକର ଲକ୍ଷ୍ୟଗୁଡ଼ିକ ଅନୁପଲବ୍ଧ — ପ୍ରଦାନକାରୀ ସର୍କିଟ୍ ବ୍ରେକର୍ `OPEN`, କନେକ୍ସନ କୁଲଡାଉନ୍, ମଡେଲ୍ ଲକଆଉଟ୍ — ସେଗୁଡ଼ିକୁ ଡ୍ର ହେବା ପୂର୍ବରୁ ହଟାଇ ଦିଆଯାଏ (`open-sse/services/combo/targetResolution.ts`), ତେଣୁ ଏକ ସୁସ୍ଥ ପଦକ୍ଷେପ ଅସ୍ଥାୟୀ ଭାବରେ ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ଜିତିପାରିବ।
- `stickyWeightedLimit` (କମ୍ବୋ କନଫିଗ୍, ଡିଫଲ୍ଟ `1` = ବନ୍ଦ) ପୁନଃ-ଡ୍ର କରିବା ପୂର୍ବରୁ ସେତେଗୁଡ଼ିକ କ୍ରମାଗତ ସଫଳତା ପାଇଁ ଡ୍ର ହୋଇଥିବା ପଦକ୍ଷେପକୁ ପିନ୍ କରେ।

କଠୋର ରୋଟେସନ୍ ପାଇଁ `round-robin` ବ୍ୟବହାର କରନ୍ତୁ; `weighted` ଉପରେ ସମାନ ଓଜନ (weights) ପରିସଂଖ୍ୟାନଗତ — କଠୋର ନୁହେଁ — ସନ୍ତୁଳନ ଦେଇଥାଏ।

### Agentic pipeline mode

ଅତି କମରେ ଦୁଇଟି ମଡେଲ ଥିବା ଏକ `pipeline` କମ୍ବୋ, `config.agenticOrchestration.enabled` ସହିତ ପ୍ଲାନର/ଏକ୍ସିକ୍ୟୁଟର ରାଉଟିଂକୁ ବାଛିପାରିବ। ପ୍ରଥମ ଟାର୍ଗେଟ୍ ପ୍ଲାନିଂ ଏବଂ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ପାଇଁ ଦାୟୀ; ଦ୍ୱିତୀୟ ଟାର୍ଗେଟ୍ କ୍ଲାଏଣ୍ଟ-ନେଟିଭ୍ ଟୁଲ୍ କଲ୍ ନିର୍ଗତ କରେ। OmniRoute ରିକ୍ୱେଷ୍ଟ ପ୍ରୋଟୋକଲରୁ ଟୁଲ୍-ଫଳାଫଳର କଣ୍ଟିନୁଏସନ୍ ଚିହ୍ନଟ କରେ, ପ୍ଲାନରକୁ ପଚାରେ ଯେ ଆଉ ଏକ ଟୁଲ୍ ରାଉଣ୍ଡ ଆବଶ୍ୟକ କି ନାହିଁ, ଏବଂ ଗତିଶୀଳ ଭାବରେ ଏକ୍ସିକ୍ୟୁଟର କିମ୍ବା ପ୍ଲାନରକୁ କ୍ଲାଏଣ୍ଟ-ଫେସିଂ ଚୂଡ଼ାନ୍ତ ପଦକ୍ଷେପ ଭାବରେ ସ୍ଥିର କରେ।

ଇଚ୍ଛାଧୀନ `config.agenticOrchestration.contextCompaction` ପ୍ରତ୍ୟେକ ପ୍ଲାନର କିମ୍ବା ଏକ୍ସିକ୍ୟୁଟର ଡିସପ୍ୟାଚ୍ ପୂର୍ବରୁ ଏକ ପୃଥକ ପେଲୋଡ୍ ବଜେଟ୍ ପ୍ରୟୋଗ କରେ। ଏହାକୁ ସ୍ପଷ୍ଟ ଭାବରେ ସକ୍ଷମ କରନ୍ତୁ:

```json
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

ଏଗୁଡ଼ିକ ହେଉଛି ଅପରେଟରଙ୍କ ଦ୍ୱାରା ଚୟନ କରାଯାଇଥିବା ସିରିଆଲାଇଜଡ୍ JSON କ୍ୟାରେକ୍ଟର ବଜେଟ୍, ଟୋକେନ୍ କଣ୍ଟେକ୍ସଟ୍ ୱିଣ୍ଡୋ କିମ୍ବା ଗ୍ୟାରେଣ୍ଟିଡ୍ ଅପଷ୍ଟ୍ରିମ୍ ସୀମା ନୁହେଁ। ସଠିକ୍ ମଡେଲ ID ଗୁଡ଼ିକ ଡିଫଲ୍ଟକୁ ଓଭରରାଇଡ୍ କରେ। ଥ୍ରେସହୋଲ୍ଡରୁ ଅଧିକ ହେଲେ, କମ୍ପାକ୍ସନ୍ ସମାନ ଟୁଲ୍ ଡେଫିନିସନ୍ ଗୁଡ଼ିକୁ ହଟାଇଦିଏ, ଡାଇଜେଷ୍ଟ ସହିତ ଅତ୍ୟଧିକ ବଡ଼ ଟୁଲ୍ ପ୍ରମାଣକୁ ଛୋଟ କରେ, ଏବଂ ଟାର୍ଗେଟ୍ ଅନୁପାତ ଆଡକୁ ପୁରୁଣା ସମ୍ପୂର୍ଣ୍ଣ ହିଷ୍ଟ୍ରି ଗ୍ରୁପ୍ ଗୁଡ଼ିକୁ ହଟାଇଦିଏ। ଏହା ସିଷ୍ଟମ୍/ଡେଭଲପର୍ ନିର୍ଦ୍ଦେଶାବଳୀ, ସର୍ବଶେଷ ୟୁଜର୍ ରିକ୍ୱେଷ୍ଟ, ପାରାଲେଲ୍ କଲ୍/ଫଳାଫଳ ସହିତ ଶେଷ ଟୁଲ୍ ରାଉଣ୍ଡ, ଏବଂ Gemini ର ଲିଡିଂ ରାଉଟିଂ ନିର୍ଦ୍ଦେଶକୁ ବଜାୟ ରଖେ। ଟପ୍-ଲେଭଲ୍ ନିର୍ଦ୍ଦେଶାବଳୀ ଏବଂ ଟୁଲ୍ ସେଟିଂସମୂହ ସଂରକ୍ଷିତ ରହିଥାଏ। ଏକ ଓମିସନ୍ ମାର୍କର୍ ହଟାଯାଇଥିବା ହିଷ୍ଟ୍ରିକୁ ରେକର୍ଡ କରେ; ଏହା ହେଉଛି ନିର୍ଦ୍ଦିଷ୍ଟ ଟ୍ରିମିଂ (deterministic trimming), ସିମାଣ୍ଟିକ୍ ସାରାଂଶ ନୁହେଁ। ଯଦି ପିନ୍ ହୋଇଥିବା କଣ୍ଟେକ୍ସଟ୍ ଏବେ ବି ବଜେଟ୍ ଅତିକ୍ରମ କରେ, ତେବେ ମଡେଲ ସହିତ ଯୋଗାଯୋଗ କରିବା ପୂର୍ବରୁ ରିକ୍ୱେଷ୍ଟ 413 ଫେରାଇଥାଏ। କମ୍ପାକ୍ସନ୍ ଡିସେବଲ୍ ହୋଇଥିଲେ କିମ୍ବା ଥ୍ରେସହୋଲ୍ଡରୁ କମ୍ ଥିଲେ ରିକ୍ୱେଷ୍ଟ ଅପରିବର୍ତ୍ତିତ ଭାବରେ ପାସ୍ ହୋଇଯାଏ।

ଦ୍ୱିତୀୟ ଟାର୍ଗେଟ୍ ପରେ ଅତିରିକ୍ତ ମଡେଲଗୁଡ଼ିକ ହେଉଛି ଅର୍ଡର୍ ହୋଇଥିବା ଏକ୍ସିକ୍ୟୁଟର ବ୍ୟାକଅପ୍। ଏକ ବିଫଳ HTTP ରିସପନ୍ସ କିମ୍ବା ଟ୍ରାନ୍ସପୋର୍ଟ ଏକ୍ସେପସନ୍ ପରବର୍ତ୍ତୀ ଏକ୍ସିକ୍ୟୁଟରକୁ ଆଗେଇ ଯାଏ, ଯାହା ସମାନ ପ୍ଲାନର ନିଷ୍ପତ୍ତି ଏବଂ ନେଟିଭ୍ ଟୁଲ୍ ବହନ କରେ କିନ୍ତୁ ସେହି ଏକ୍ସିକ୍ୟୁଟରର ନିଜସ୍ୱ ଷ୍ଟେପ୍ ପ୍ରମ୍ପ୍ଟ ଏବଂ ରିଜଲ୍ଭଡ୍ କନେକ୍ସନ୍ ବ୍ୟବହାର କରେ। ପ୍ରଥମ ସଫଳ ରିସପନ୍ସ ଅପରିବର୍ତ୍ତିତ ଭାବରେ ଫେରସ୍ତ କରାଯାଏ, SSE ଷ୍ଟ୍ରିମିଂ ସହିତ; ଏକ ସଫଳ ଷ୍ଟ୍ରିମ୍ ଆରମ୍ଭ ହେବା ପରେ ବିଫଳତାକୁ ଏଠାରେ ପୁନଃପ୍ରୟାସ (retry) କରାଯାଇପାରିବ ନାହିଁ। ଯଦି ସମସ୍ତ ଏକ୍ସିକ୍ୟୁଟର ବିଫଳ ହୁଅନ୍ତି, ତେବେ ଶେଷ ବିଫଳତା ଫେରସ୍ତ କରାଯାଏ। କ୍ଲାଏଣ୍ଟ ଅବର୍ଟ (aborts) ଡିସପ୍ୟାଚ୍ ବନ୍ଦ କରିଦିଏ।

```json

  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],

```

ଏକ୍ସିକ୍ୟୁଟର ଗୋଟିଏ ରିସପନ୍ସରେ ଏକାଧିକ ସ୍ୱାଧୀନ କଲ୍ ନିର୍ଗତ କରିପାରିବ। ନିର୍ଭରଶୀଳ କଲ୍ ଗୁଡ଼ିକ ପରବର୍ତ୍ତୀ କ୍ଲାଏଣ୍ଟ ଟୁଲ୍-ଫଳାଫଳ ଟର୍ନରେ ପରିଚାଳିତ ହୁଏ, ଯେଉଁଠାରେ ପ୍ଲାନର ପ୍ରତ୍ୟେକ ଫଳାଫଳକୁ ସମୀକ୍ଷା କରେ। `maxToolRounds` ଡିଫଲ୍ଟ ଭାବରେ `8` ଏବଂ `1`–`32` ଗ୍ରହଣ କରେ; ଥରେ ପହଞ୍ଚିଗଲେ, ପ୍ଲାନରକୁ ସର୍ବୋତ୍ତମ ଉପଲବ୍ଧ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ପ୍ରଦାନ କରିବାକୁ ପଡିବ। ଆଭ୍ୟନ୍ତରୀଣ ପ୍ଲାନର ନିଷ୍ପତ୍ତିଗୁଡ଼ିକ ବଫର୍ ହୋଇଥାଏ, ଯେତେବେଳେ କି ଚୟନ କରାଯାଇଥିବା କ୍ଲାଏଣ୍ଟ-ଫେସିଂ ରିସପନ୍ସ ମୂଳ ଷ୍ଟ୍ରିମିଂ ପସନ୍ଦକୁ ବଜାୟ ରଖେ।

### `round-robin` ଷ୍ଟିକି ବ୍ୟାଚ୍ ଏବଂ ଆକାଉଣ୍ଟ ଏକ୍ସପାନ୍ସନ୍

Round-robin ବ୍ୟାଚ୍ ହୋଇଥାଏ, ପ୍ରତି-ଷ୍ଟେପ୍-ଏକ-ରିକ୍ୱେଷ୍ଟ ନୁହେଁ:

- `stickyRoundRobinLimit` (କମ୍ବୋ କନଫିଗ୍, ତାପରେ `comboStickyRoundRobinLimit`, ତାପରେ `settings.stickyRoundRobinLimit`, ଡିଫଲ୍ଟ **3**) ରୋଟେଟ୍ କରିବା ପୂର୍ବରୁ ସେତିକି ସଂଖ୍ୟକ କ୍ରମାଗତ ସଫଳତା ପାଇଁ ସମାନ ଟାର୍ଗେଟ୍ ରଖେ। ଗୋଟିଏ-ରିକ୍ୱେଷ୍ଟ ରୋଟେସନ୍ ପାଇଁ କମ୍ବୋ ଓଭରରାଇଡକୁ `1` ରେ ସେଟ୍ କରନ୍ତୁ। କମ୍ବୋ ଏଡିଟର୍ ପ୍ରଭାବଶାଳୀ ମୂଲ୍ୟ ଏବଂ ଏହା କେଉଁ ଲେୟାରରୁ ଆସିଛି ତାହା ଦେଖାଏ।
- `connectionAwareExpansion` (କମ୍ବୋ କନଫିଗ୍, ତାପରେ ସେଟିଂସ, ଡିଫଲ୍ଟ **false**) ରୋଟେସନ୍ ପୂର୍ବରୁ ପ୍ରତ୍ୟେକ ପ୍ରୋଭାଇଡର୍-ଲେଭଲ୍ ଷ୍ଟେପକୁ ପ୍ରତି-ଆକାଉଣ୍ଟ ଟାର୍ଗେଟରେ ବିସ୍ତାର କରେ। Group-B ରଣନୀତି (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) ଏହା ଅନ୍ ନହେବା ପର୍ଯ୍ୟନ୍ତ ଏକ ପ୍ରୋଭାଇଡର୍-ଲେଭଲ୍ ଭ୍ୟୁ ରଖେ। କମ୍ବୋ ଏଡିଟର୍ inherit / on / off ପ୍ରଦର୍ଶନ କରେ; inherit ଗ୍ଲୋବାଲ୍ ଡିଫଲ୍ଟ (off) ବ୍ୟବହାର କରେ।
- Prompt-cache locality routing (`promptCacheAffinityEnabled`, ଡିଫଲ୍ଟ **true**) ପିନ୍ ହୋଇଥିବା କନେକ୍ସନ୍ ଗୁଡ଼ିକୁ ପୁନଃକ୍ରମ କରେ ଯାହାଫଳରେ ମ୍ୟାଚିଂ କ୍ୟାଶ୍ କି (cache keys) ଗୋଟିଏ ଆକାଉଣ୍ଟରେ ରହିବ। ଏହା ପିନ୍ ହୋଇଥିବା ପ୍ରତି-ଆକାଉଣ୍ଟ ଷ୍ଟେପ୍ ଗୁଡ଼ିକରେ round-robin ଏବଂ weighted ରୋଟେସନ୍ ଉପରେ ଅଗ୍ରାଧିକାର ନିଏ। ଯଦି ଆପଣଙ୍କୁ କଠୋର ରୋଟେସନ୍ ଆବଶ୍ୟକ ତେବେ Settings → Combo defaults ଅଧୀନରେ ଏହାକୁ ବନ୍ଦ କରନ୍ତୁ। କୌଣସି ପର-କମ୍ବୋ ଓଭରରାଇଡ୍ ନାହିଁ।

ଗୋଟିଏ ମଡେଲରେ ମଲ୍ଟି-ଆକାଉଣ୍ଟ ରୋଟେସନ୍ ପାଇଁ, ତିନୋଟି ପିନ୍ ହୋଇଥିବା `connectionId` ବଦଳରେ, ଷ୍ଟିକି ଲିମିଟ୍ `1` ସହିତ **ଗୋଟିଏ ଡାଇନାମିକ୍-ଆକାଉଣ୍ଟ ଷ୍ଟେପ୍** (ଖାଲି `connectionId`, ସମ୍ପୂର୍ଣ୍ଣ ପୁଲ୍) ବ୍ୟବହାର କରନ୍ତୁ। RR କାଉଣ୍ଟର୍ ଆଗେଇ ଚାଲିଥିଲେ ମଧ୍ୟ ପିନ୍ ହୋଇଥିବା ଷ୍ଟେପ୍ ଏବଂ ଆଫିନିଟି ସମାନ ଆକାଉଣ୍ଟରେ କଲ୍ୟାପ୍ସ ହୋଇଯାଏ।

## ଫ୍ୟୁଜନ୍ କୌଶଳ

`fusion` ହେଉଛି ଏକମାତ୍ର କୌଶଳ ଯାହା ଗୋଟିଏ ଲକ୍ଷ୍ୟ ଚୟନ କରେ **ନାହିଁ**। ଏହା ପ୍ରମ୍ପ୍ଟକୁ
**ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍ ମଡେଲ୍‌କୁ ସମାନ୍ତରାଳ ଭାବରେ** ପଠାଏ, ତା'ପରେ ଏକ ବିନ୍ୟାସଯୋଗ୍ୟ **ବିଚାରକ ମଡେଲ୍**
ସମସ୍ତ ପ୍ୟାନେଲ୍ ପ୍ରତିକ୍ରିୟାରୁ ଗୋଟିଏ ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ସଂଶ୍ଳେଷଣ କରେ। ଏହାକୁ ଅପ୍‌ଷ୍ଟ୍ରିମ୍ `decolua/9router`
(OpenRouterର Fusion ଡିଜାଇନ୍)ରୁ ପୋର୍ଟ କରାଯାଇଛି; ଏହାର କାର୍ଯ୍ୟାନ୍ୱୟନ `open-sse/services/fusion.ts`ରେ ଅଛି।

ଏହା କିପରି କାମ କରେ:

0. **ଟୁଲ୍-ଯୁକ୍ତ ବାଇପାସ୍** — ଏକ ଅନୁରୋଧରେ ଖାଲି ନଥିବା `tools` ଆରେ ଥିଲେ ଏବଂ
   `tool_choice` ସ୍ପଷ୍ଟ ଭାବରେ `"none"` ନଥିଲେ, ଏହା ପ୍ୟାନେଲ୍‌କୁ ସମ୍ପୂର୍ଣ୍ଣ ଏଡ଼ାଇଯାଏ: ଏହା ସିଧାସଳଖ
   ଗୋଟିଏ ମଡେଲ୍‌କୁ (ବିନ୍ୟାସିତ ବିଚାରକ କିମ୍ବା `panel[0]`) ରୂଟ୍ ହୁଏ ଏବଂ `tools`/`tool_choice`
   କୌଣସି ପରିବର୍ତ୍ତନ ବିନା ପଠାଯାଏ। ପ୍ୟାନେଲ୍ ସଦସ୍ୟମାନଙ୍କ ପାଖରେ ଟୁଲ୍ ଆକ୍ସେସ୍ ନଥାଏ ଏବଂ ବିଚାରକର
   ସଂଶ୍ଳେଷଣ ନିର୍ଦ୍ଦେଶ ଟୁଲ୍-କଲ୍ ନିର୍ଗମନକୁ ନିରୁତ୍ସାହିତ କରେ, ତେଣୁ ଏଜେଣ୍ଟିକ୍/ଟୁଲ୍-କଲିଂ କ୍ଲାଏଣ୍ଟମାନେ
   ସଂଶ୍ଳେଷିତ ଗଦ୍ୟ ପରିବର୍ତ୍ତେ ଏକ ପ୍ରକୃତ ଟୁଲ୍-କଲ୍ ନିଷ୍ପତ୍ତି ପାଆନ୍ତି (#6771)।
1. **ଫ୍ୟାନ୍-ଆଉଟ୍** (କେବଳ ଟୁଲ୍-ବିହୀନ ଅନୁରୋଧ) — ପ୍ରମ୍ପ୍ଟଟିକୁ ଏକାସାଙ୍ଗରେ ପ୍ରତ୍ୟେକ ପ୍ୟାନେଲ୍
   ମଡେଲ୍‌କୁ ପଠାଯାଏ, ଟୁଲ୍‌ଗୁଡ଼ିକୁ ବାଦ ଦେଇ ବାଧ୍ୟତାମୂଳକ ଭାବେ ନନ୍-ଷ୍ଟ୍ରିମିଂ କରାଯାଏ (ସଂଶ୍ଳେଷଣ ପାଇଁ
   ବିଚାରକକୁ ସମ୍ପୂର୍ଣ୍ଣ ଗଦ୍ୟ ଆବଶ୍ୟକ)।
2. **କୋରମ୍-ଗ୍ରେସ୍ ସଂଗ୍ରହ** — `minPanel`ଟି ଉତ୍ତର ପହଞ୍ଚିବା ମାତ୍ରେ ପଛରେ ପଡ଼ିଥିବା
   ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ ଏକ ସ୍ୱଳ୍ପ ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହୁଏ, ତା'ପରେ ଯାହା ସଂଗ୍ରହ ହୋଇଛି ତାହା ସହିତ
   ଫ୍ୟୁଜନ୍ ଆଗକୁ ବଢ଼େ। ଏହା ୱାଲ୍ ଟାଇମ୍‌ରେ ସବୁଠାରୁ ଧୀର ମଡେଲ୍‌ର ବିଳମ୍ବ ପ୍ରଭାବକୁ ସୀମିତ କରେ,
   ଯାହା ଏକ ହାର୍ଡ ଟାଇମ୍‌ଆଉଟ୍‌ରେ ବାନ୍ଧିତ।
3. **ବିଚାରକ ସଂଶ୍ଳେଷଣ** — ପ୍ୟାନେଲ୍ ଉତ୍ତରଗୁଡ଼ିକୁ ଅଜ୍ଞାତକୃତ କରାଯାଏ (`Source 1`, `Source 2`, … — ଯାହାଦ୍ୱାରା
   ବିଚାରକ ମଡେଲ୍ ବ୍ରାଣ୍ଡ ପରିବର୍ତ୍ତେ ବିଷୟବସ୍ତୁକୁ ଗୁରୁତ୍ୱ ଦିଏ) ଏବଂ ବିଚାରକକୁ ଦିଆଯାଏ, ଯିଏ
   ସହମତି / ବିରୋଧାଭାସ / ଆଂଶିକ ପରିସର / ଅନନ୍ୟ ଅନ୍ତର୍ଦୃଷ୍ଟି / ଅଦୃଶ୍ୟ ଦିଗଗୁଡ଼ିକୁ ବିଶ୍ଳେଷଣ କରି,
   **ଗୋଟିଏ** ପ୍ରାମାଣିକ ଉତ୍ତର ଲେଖେ। ବିଚାରକ କଲ୍ କ୍ଲାଏଣ୍ଟର ମୂଳ `stream` ଫ୍ଲାଗ୍ + ଟୁଲ୍‌ଗୁଡ଼ିକୁ
   ଅପରିବର୍ତ୍ତିତ ରଖେ, ଫଳରେ ଷ୍ଟ୍ରିମିଂ ଏବଂ ଡାଉନ୍‌ଷ୍ଟ୍ରିମ୍ ଟୁଲ୍ ବ୍ୟବହାର ଏବେ ମଧ୍ୟ କାମ କରେ।
4. **ସୁଗମ ଅବନତି** — 0ଟି ପ୍ୟାନେଲ୍ ଉତ୍ତର → `503`; ଠିକ୍ 1ଟି ଉତ୍ତର ରହିଲେ → ସେହି ଉତ୍ତର
   ସିଧାସଳଖ ଫେରାଯାଏ (ସଂଯୋଜନ କରିବାକୁ କିଛି ନାହିଁ); ଗୋଟିଏ-ମଡେଲ୍ ପ୍ୟାନେଲ୍ ସିଧାସଳଖ ଉତ୍ତର ଦିଏ।

ଜଣେ ପ୍ୟାନେଲ୍ ସଦସ୍ୟ ଅନ୍ୟ ଏକ କମ୍ବୋକୁ ସନ୍ଦର୍ଭ କରୁଥିବା `combo-ref` ପଦକ୍ଷେପ
(`{kind: "combo-ref", comboName: "..."}`) ମଧ୍ୟ ହୋଇପାରେ — ଏହା **ଗୋଟିଏ ବ୍ଲାକ୍-ବକ୍ସ ପ୍ୟାନେଲ୍ ସ୍ୱର** ଭାବେ
ସମାଧାନ ହୁଏ (ସନ୍ଦର୍ଭିତ କମ୍ବୋର ନିଜସ୍ୱ ଲକ୍ଷ୍ୟଗୁଡ଼ିକର ଫ୍ୟାନ୍-ଆଉଟ୍ ନୁହେଁ, ବରଂ ସେହି କମ୍ବୋ ମଧ୍ୟକୁ
ଏକ ସମ୍ପୂର୍ଣ୍ଣ ପୁନରାବୃତ୍ତିଶୀଳ ଡିସ୍ପାଚ୍), ଏବଂ ଏଥିରେ ପୂର୍ବରୁ ଅନ୍ୟ ସମସ୍ତ combo-ref-ବ୍ୟବହାରକାରୀ
କୌଶଳ ବ୍ୟବହାର କରୁଥିବା ସମାନ ଗଭୀରତା/ଚକ୍ର ସୁରକ୍ଷା ରହିଛି (#6764)।

### ବିନ୍ୟାସ

କମ୍ବୋର `config` ବ୍ଲବ୍‌ରେ ବିନ୍ୟାସ କରାଯାଏ (କୌଣସି ସ୍କିମା ମାଇଗ୍ରେସନ୍ ନାହିଁ — ଏହା ବିଦ୍ୟମାନ
`combos` ଟେବୁଲ୍‌କୁ ପୁନଃବ୍ୟବହାର କରେ):

| କ୍ଷେତ୍ର                                  | ପ୍ରକାର   | ଡିଫଲ୍ଟ               | ଉଦ୍ଦେଶ୍ୟ                                                                            |
| :--------------------------------------- | :------- | :------------------- | :---------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | ପ୍ରଥମ ପ୍ୟାନେଲ୍ ମଡେଲ୍ | ଚୂଡ଼ାନ୍ତ ଉତ୍ତର ସଂଶ୍ଳେଷଣ କରୁଥିବା ମଡେଲ୍                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`                  | ଗ୍ରେସ୍ ଟାଇମର୍ ଆରମ୍ଭ ହେବା ପୂର୍ବରୁ ଆବଶ୍ୟକ ସଫଳ ଉତ୍ତର ସଂଖ୍ୟା (`[2, panelSize]`ରେ ସୀମିତ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | କୋରମ୍ ପୂରଣ ହେବା ପରେ ପଛରେ ପଡ଼ିଥିବା ମଡେଲ୍‌ଗୁଡ଼ିକ ପାଇଁ କେତେ ସମୟ ଅପେକ୍ଷା କରାଯିବ         |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | ଗୋଟିଏ ଅଟକିଥିବା ମଡେଲ୍ ଯେପରି ଅନୁରୋଧକୁ ଅଟକାଇ ନପାରେ, ସେଥିପାଇଁ ସର୍ବାଧିକ ସମୟସୀମା          |

ଡିଫଲ୍ଟଗୁଡ଼ିକ `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`)ରେ ରହିଛି।

### ଉଦାହରଣ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ତା'ପରେ ଅନ୍ୟ ଯେକୌଣସି କମ୍ବୋ ପରି ଏହାକୁ କଲ୍ କରନ୍ତୁ: `{"model":"fusion-panel","messages":[...]}`।

## ଭର୍ଚୁଆଲ୍ ଅଟୋ-କମ୍ବୋ ଫ୍ୟାକ୍ଟରୀ

ଅଟୋ କମ୍ବୋ ଇଞ୍ଜିନ୍‌କୁ ପୂର୍ବ-ନିର୍ଦ୍ଧାରିତ କମ୍ବୋ ଆବଶ୍ୟକ ହୁଏ ନାହିଁ। ଏହା ପରିବର୍ତ୍ତେ, `open-sse/services/autoCombo/virtualFactory.ts` ତତ୍କ୍ଷଣାତ୍ ପ୍ରାର୍ଥୀଗୁଡ଼ିକ ତିଆରି କରେ:

1. `getProviderConnections({ isActive: true })` (ସମସ୍ତ ସକ୍ରିୟ ସଂଯୋଗ) ଆଣେ
2. ବୈଧ ପ୍ରମାଣପତ୍ର ଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ଫିଲ୍ଟର୍ କରେ (API କୀ କିମ୍ବା `hasUsableOAuthToken()` ମାଧ୍ୟମରେ ମିଆଦ ଶେଷ ହୋଇନଥିବା OAuth ଟୋକେନ୍)
3. ମଡେଲ୍ ଉପଲବ୍ଧତା + ମୂଲ୍ୟ ନିର୍ଦ୍ଧାରଣ ପାଇଁ `getProviderRegistry()` ସହିତ କ୍ରସ୍-ରେଫରେନ୍ସ କରେ
4. ପ୍ରତ୍ୟେକ `(provider, model, connection)` ଟ୍ୟୁପଲ୍ ପାଇଁ ଏକ `VirtualAutoComboCandidate` ତିଆରି କରେ
5. ଡିସ୍ପାଚ୍ ଲକ୍ଷ୍ୟ ଭାବରେ `connection.defaultModel` (କିମ୍ବା ରେଜିଷ୍ଟ୍ରିର ପ୍ରଥମ ମଡେଲ୍) ବାଛେ
6. 16-ଫ୍ୟାକ୍ଟର୍ `scorePool()` ଏବଂ ଭାରିଆଣ୍ଟର ୱେଟ୍ ପ୍ୟାକ୍ ବ୍ୟବହାର କରି ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ ସ୍କୋର୍ କରେ
7. `handleComboChat()` ପାଇଁ ଫଳସ୍ୱରୂପ ମିଳିଥିବା ଇନ୍-ମେମୋରୀ `AutoComboConfig` ଫେରାଏ — ଏହା କେବେବି DBରେ ସ୍ଥାୟୀ ଭାବରେ ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ

ଏହାର ଅର୍ଥ ହେଉଛି **`auto/*` ସକ୍ରିୟ ଥିବା ଏକ ନୂଆ ପ୍ରଦାନକାରୀ ଯୋଡ଼ିଲେ ପ୍ରାର୍ଥୀ ପୁଲ୍ ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବିସ୍ତାରିତ ହୁଏ** — ମାନୁଆଲ୍ କମ୍ବୋ ସମ୍ପାଦନା ଆବଶ୍ୟକ ନୁହେଁ। ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ ଭର୍ଚୁଆଲ୍ କମ୍ବୋ ପୁନଃନିର୍ମାଣ ହୁଏ, ତେଣୁ ନୂତନ ଭାବେ ଯୋଡ଼ାଯାଇଥିବା କିମ୍ବା ନୂତନ ଭାବେ ସୁସ୍ଥ ହୋଇଥିବା ସଂଯୋଗଗୁଡ଼ିକୁ ତୁରନ୍ତ ବାଛାଯାଏ।

## ସ୍ୱୟଂ-ପୁନରୁଦ୍ଧାର

- **ଅସ୍ଥାୟୀ ବହିଷ୍କାର**: ସ୍କୋର୍ < 0.2 → 5 ମିନିଟ୍ ପାଇଁ ବହିଷ୍କୃତ (କ୍ରମବର୍ଦ୍ଧିଷ୍ଣୁ ବ୍ୟାକ୍‌ଅଫ୍, ସର୍ବାଧିକ 30 ମିନିଟ୍)
- **ସର୍କିଟ୍ ବ୍ରେକର୍ ସଚେତନତା**: OPEN → ସ୍ୱୟଂଚାଳିତ ଭାବରେ ବହିଷ୍କୃତ; HALF_OPEN → ପ୍ରୋବ୍ ଅନୁରୋଧ
- **ଘଟଣା ମୋଡ୍**: >50% OPEN → ଅନ୍ୱେଷଣ ଅକ୍ଷମ କରି ସ୍ଥିରତାକୁ ସର୍ବାଧିକ କରେ
- **କୁଲ୍‌ଡାଉନ୍ ପୁନରୁଦ୍ଧାର**: ବହିଷ୍କାର ପରେ, ପ୍ରଥମ ଅନୁରୋଧଟି ହ୍ରାସକୃତ ଟାଇମ୍‌ଆଉଟ୍ ସହିତ ଏକ "ପ୍ରୋବ୍" ହୁଏ

## ବ୍ୟାଣ୍ଡିଟ୍ ଅନ୍ୱେଷଣ

5% ଅନୁରୋଧ (ବିନ୍ୟାସଯୋଗ୍ୟ) ଅନ୍ୱେଷଣ ପାଇଁ ଯାଦୃଚ୍ଛିକ ପ୍ରଦାନକାରୀଙ୍କ ନିକଟକୁ ରାଉଟ୍ କରାଯାଏ। ଘଟଣା ମୋଡ୍‌ରେ ଏହା ଅକ୍ଷମ ରହେ।

## API

ଏଠାରେ କୌଣସି **dedicated `POST /api/combos/auto` endpoint ନାହିଁ** — Auto-Combo ଦୁଇଟି ଉପାୟରେ ବ୍ୟବହୃତ ହୁଏ:

1. **Zero-config (ସୁପାରିଶ କରାଯାଇଛି):** `model: "auto"` କିମ୍ବା `model: "auto/<variant>"` ସହିତ ଯେକୌଣସି ଚାଟ୍ କମ୍ପ୍ଲିସନ୍ ଅନୁରୋଧ ପଠାନ୍ତୁ। ଭର୍ଚୁଆଲ୍ ଫ୍ୟାକ୍ଟ୍ରି ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ କମ୍ବୋ ତିଆରି କରେ — କୌଣସି ପର୍ସିଷ୍ଟେନ୍ସ (persistence) କିମ୍ବା API କଲ୍ ଆବଶ୍ୟକ ନାହିଁ।

2. **`strategy: "auto"` ସହିତ ପର୍ସିଷ୍ଟେଡ୍ କମ୍ବୋ:** `POST /api/combos` ମାଧ୍ୟମରେ ଏକ ସାଧାରଣ କମ୍ବୋ ତିଆରି କରନ୍ତୁ ଏବଂ `strategy: "auto"` ସହିତ `config.auto.weights` / `config.auto.candidatePool` ସେଟ୍ କରନ୍ତୁ। ସେହି ସମାନ ସ୍କୋରିଂ ଇଞ୍ଜିନ୍ ବ୍ୟବହୃତ ହୁଏ; କମ୍ବୋଟି `combos` ରେ ସଂରକ୍ଷିତ ହୁଏ ଏବଂ ID ଦ୍ୱାରା ପୁନର୍ବାର ବ୍ୟବହାରଯୋଗ୍ୟ।

ଡିସକଭରି (discovery) ପାଇଁ, `GET /api/combos/auto` ପ୍ରତ୍ୟେକ ଭାରିଆଣ୍ଟକୁ ଏହାର ରିଜଲ୍ଭଡ୍ କ୍ୟାଣ୍ଡିଡେଟ୍ ପୁଲ୍ ସହିତ `context_length` / `max_output_tokens` — କ୍ୟାଣ୍ଡିଡେଟ୍ ପୁଲ୍‌ର ୱିଣ୍ଡୋଗୁଡ଼ିକ ମଧ୍ୟରେ MAX — ତାଲିକାଭୁକ୍ତ କରେ। କ୍ଲାଏଣ୍ଟମାନଙ୍କୁ (ଉଦାହରଣ ସ୍ୱରୂପ opencode ପ୍ଲଗଇନ୍) `0` ପରିବର୍ତ୍ତେ ଏହି ମୂଲ୍ୟଗୁଡ଼ିକୁ ବିଜ୍ଞାପନ କରିବାକୁ ପଡିବ: ଏକ ଜିରୋ କଣ୍ଟେକ୍ସଟ୍ opencode ର ଅଟୋ-କମ୍ପାକ୍ସନ୍‌କୁ ସମ୍ପୂର୍ଣ୍ଣ ରୂପେ ଅକ୍ଷମ କରିଦିଏ, ଯାହା ଗେଟୱେର ହିଷ୍ଟ୍ରି ପର୍ଜ (history purge) କଣ୍ଟେକ୍ସଟ୍‌କୁ ନଷ୍ଟ ନକରିବା ପର୍ଯ୍ୟନ୍ତ ସେସନ୍‌ଗୁଡ଼ିକୁ ବଢିବାକୁ ଦିଏ। MAX ବିଜ୍ଞାପନ କରିବା ନିରାପଦ କାରଣ ଅଟୋ-କମ୍ବୋ କଣ୍ଟେକ୍ସଟ୍ ପ୍ରି-ଫିଲ୍ଟର୍ ଅତ୍ୟଧିକ ବଡ଼ ଅନୁରୋଧଗୁଡ଼ିକୁ ବଡ଼-ୱିଣ୍ଡୋ କ୍ୟାଣ୍ଡିଡେଟ୍‌ମାନଙ୍କ ପାଖକୁ ପଠାଇଥାଏ।

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

ପର୍ସିଷ୍ଟେଡ୍ `strategy: "auto"` କମ୍ବୋଗୁଡ଼ିକ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା `config.auto.routerStrategy`) କୁ ନିମ୍ନଲିଖିତ ମଧ୍ୟରୁ ଗୋଟିଏରେ ସେଟ୍ କରିପାରିବେ:

- `rules` — ଡିଫଲ୍ଟ ୱେଟେଡ୍ ସ୍କୋରିଂ
- `score` — ସର୍ବାଧିକ କନଫିଗର୍ ହୋଇଥିବା ୱେଟେଡ୍ ସ୍କୋର ଚୟନ କରେ। ସଠିକ୍ ଟାଇ (ties) କନଫିଗର୍ ହୋଇଥିବା କ୍ୟାଣ୍ଡିଡେଟ୍ କ୍ରମକୁ ବଜାୟ ରଖେ; ବିଦ୍ୟମାନ `explorationRate` ସମ୍ପୂର୍ଣ୍ଣ ରାଙ୍କଡ୍ ପୁଲ୍‌ରୁ ନମୁନା ନିଏ।
- `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ହେଲଦି ପ୍ରୋଭାଇଡର୍
- `latency` / `fast` — ନିର୍ଭରଯୋଗ୍ୟତା ପେନାଲ୍ଟି ସହିତ ସର୍ବନିମ୍ନ p95 ଲାଟେନ୍ସି
- `sla-aware` / `sla` — p95 ଲାଟେନ୍ସି, ଏରର୍-ରେଟ୍, ଏବଂ ଇଚ୍ଛାଧୀନ କଷ୍ଟ SLO ଗୁଡ଼ିକୁ ପୂରଣ କରୁଥିବା କ୍ୟାଣ୍ଡିଡେଟ୍‌ମାନଙ୍କୁ ପସନ୍ଦ କରେ
- `lkgp` — ଶେଷ ଜଣାଶୁଣା ଭଲ ପ୍ରୋଭାଇଡର୍ ପ୍ରଥମେ
- `nadir` — [Nadir](https://getnadir.com) ର ଡିସିଜନ୍ API କୁ ପଚାରନ୍ତୁ ଯେ ପୁଲ୍‌ରେ କେଉଁ ମଡେଲ୍ ପ୍ରମ୍ପ୍ଟ ପାଇଁ ଆବଶ୍ୟକ; ଅପ୍ଟ-ଇନ୍, `rules` କୁ ଫେଲ୍-ଓପନ୍

### Router strategies in detail

ଅଟୋ-କମ୍ବୋ ଇଞ୍ଜିନ୍ 7ଟି ପ୍ଲଗେବଲ୍ **RouterStrategy** ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ପ୍ରଦାନ କରେ ଯାହାକୁ ଆପଣ `config.routerStrategy` (କିମ୍ବା ପୁରୁଣା `config.auto.routerStrategy`) ମାଧ୍ୟମରେ ସ୍ୱାପ୍ (swap) କରିପାରିବେ। ପ୍ରତ୍ୟେକ ଷ୍ଟ୍ରାଟେଜି ଏକ `RoutingContext` (ଟାସ୍କ ଟାଇପ୍, ଟୁଲ୍/ଭିଜନ୍ ହିଣ୍ଟ୍, ଟୋକନ୍ ଏଷ୍ଟିମେଟ୍, ଇଚ୍ଛାଧୀନ SLA ପଲିସି, ଇଚ୍ଛାଧୀନ ଶେଷ-ଜଣାଶୁଣା-ଭଲ ପ୍ରୋଭାଇଡର୍) ଦିଆଯାଇଥିବା ବେଳେ କ୍ୟାଣ୍ଡିଡେଟ୍ ପୁଲ୍‌ରୁ ଜଣେ ପ୍ରୋଭାଇଡର୍‌କୁ ବାଛିଥାଏ।

#### 1. `rules` (ଡିଫଲ୍ଟ) — 16-ଫ୍ୟାକ୍ଟର୍ ୱେଟେଡ୍ ସ୍କୋରିଂ

ବିଦ୍ୟମାନ ସ୍କୋରିଂ ଇଞ୍ଜିନ୍‌କୁ ରାପ୍ (wrap) କରେ। `OPEN` ସର୍କିଟ୍-ବ୍ରେକର୍ କ୍ୟାଣ୍ଡିଡେଟ୍‌ମାନଙ୍କୁ ଫିଲ୍ଟର୍ କରେ, ତା’ପରେ ବର୍ତ୍ତମାନର ଟାସ୍କ ଟାଇପ୍ ଏବଂ `getTaskFitness()` ସହିତ `scorePool()` ଚଲାଏ, ଏବଂ ସର୍ବାଧିକ ସ୍କୋର କରୁଥିବା ପ୍ରୋଭାଇଡର୍‌କୁ ବାଛିଥାଏ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ଡିଫଲ୍ଟ। ଯେତେବେଳେ ଆପଣ ସମସ୍ତ ସିଗ୍ନାଲ୍ ମଧ୍ୟରେ ଏକ ସନ୍ତୁଳିତ ଟ୍ରେଡ୍-ଅଫ୍ ଚାହାଁନ୍ତି, ସେତେବେଳେ ବ୍ୟବହାର କରନ୍ତୁ।

**Alias**: `rules` (କୌଣସି alias ନାହିଁ)

---

#### 2. `cost` / `eco` — ସବୁଠାରୁ ଶସ୍ତା ହେଲଦି ପ୍ରୋଭାଇଡର୍

କ୍ୟାଣ୍ଡିଡେଟ୍ ପୁଲ୍‌କୁ `costPer1MTokens` (ଆରୋହୀ କ୍ରମରେ) ଅନୁଯାୟୀ ସର୍ଟ କରେ ଏବଂ ସବୁଠାରୁ ଶସ୍ତାଟିକୁ ବାଛିଥାଏ। ପ୍ରଥମେ `OPEN` କ୍ୟାଣ୍ଡିଡେଟ୍‌ମାନଙ୍କୁ ଫିଲ୍ଟର୍ କରେ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: କଷ୍ଟ-ସେନ୍‌ସିଟିଭ୍ ୱାର୍କଲୋଡ୍, ବ୍ୟାଚ୍ ପ୍ରୋସେସିଂ, କିମ୍ବା ବ୍ୟାକଗ୍ରାଉଣ୍ଡ ଜବ୍‌ଗୁଡ଼ିକ ପାଇଁ।

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ନିର୍ଭରଯୋଗ୍ୟତା ପେନାଲ୍ଟି ସହିତ ସର୍ବନିମ୍ନ p95 ଲାଟେନ୍ସି

`p95LatencyMs + (errorRate * 1000)` ଅନୁଯାୟୀ ସର୍ଟ କରେ। ଏରର୍-ରେଟ୍ ପେନାଲ୍ଟି ନିଶ୍ଚିତ କରେ ଯେ ଅବିଶ୍ୱସନୀୟ ପ୍ରୋଭାଇଡର୍‌ମାନେ ନିମ୍ନରେ ରାଙ୍କ୍ ହୁଅନ୍ତି, ଯଦିଓ ସେମାନଙ୍କର ନାମମାତ୍ର ଲାଟେନ୍ସି କମ୍ ଥାଏ।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ରିଅଲ୍-ଟାଇମ୍ ଚାଟ୍, ଅଟୋକମ୍ପ୍ଲିଟ୍, କିମ୍ବା ଇଣ୍ଟରାକ୍ଟିଭ୍ କୋଡିଂ ଆସିଷ୍ଟାଣ୍ଟ ପରି ଲାଟେନ୍ସି-ସେନ୍‌ସିଟିଭ୍ ୱାର୍କଲୋଡ୍ ପାଇଁ।

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ଲାଟେନ୍ସି/ଏରର୍/କଷ୍ଟ SLO କମ୍ପ୍ଲାଏନ୍ସ

ପ୍ରତ୍ୟେକ କ୍ୟାଣ୍ଡିଡେଟ୍ କନଫିଗର୍ ହୋଇଥିବା SLO ପଲିସିକୁ କେତେ ଭଲ ଭାବରେ ପୂରଣ କରୁଛି, ତାହା ଦ୍ୱାରା ସ୍କୋର କରେ:

| Factor          | Weight | Formula                                           |
| --------------- | ------ | ------------------------------------------------- |
| Latency score   | 35%    | `threshold / max(value, ε)`                       |
| Error score     | 35%    | `threshold / max(value, ε)`                       |
| Health score    | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| Cost score      | 10%    | `threshold / max(value, ε)` or inverse normalized |
| Stability score | 5%     | inverse normalized latency stddev                 |

ଯେତେବେଳେ `hardConstraints: true` ଥାଏ, ପ୍ରାର୍ଥୀମାନଙ୍କୁ ପ୍ରାଥମିକ ଭାବରେ **violation score** (ସେମାନେ କେତେ ପରିମାଣରେ SLO ଅତିକ୍ରମ କରୁଛନ୍ତି) ଅନୁଯାୟୀ ସର୍ଟ କରାଯାଏ, ଏବଂ ତା’ପରେ କମ୍ପୋଜିଟ୍ ସ୍କୋର ଅନୁଯାୟୀ। ଅନ୍ୟଥା, ଏହା କେବଳ କମ୍ପୋଜିଟ୍ ସ୍କୋର ଅଟେ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA fields** (କମ୍ବୋ କନଫିଗରେ ସେଟ୍ ହୋଇଛି):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: କଠୋର ଲାଟେନ୍ସି, ଏରର-ରେଟ୍, କିମ୍ବା କଷ୍ଟ ବଜେଟ୍ ଥିବା ପ୍ରଡକ୍ସନ୍ ୱାର୍କଲୋଡ୍ ପାଇଁ।

**Aliases**: `sla-aware`, `sla`

---

#### 5. `lkgp` — last known good provider first

ପ୍ରଥମେ **last known good provider** (ଯଦି ସେଟ୍ ହୋଇଥାଏ) କୁ ଚେଷ୍ଟା କରେ, ତା’ପରେ `rules` ଷ୍ଟ୍ରାଟେଜିକୁ ଫେରିଯାଏ। ସେସନ୍ ଷ୍ଟିକିନେସ୍ ପାଇଁ ଉପଯୋଗୀ — ଗୋଟିଏ କନଭରସେସନରେ ସମାନ ପ୍ରୋଭାଇଡର୍ ଫଲୋ-ଅପ୍ ଅନୁରୋଧଗୁଡ଼ିକୁ ହ୍ୟାଣ୍ଡେଲ କରେ।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**କେବେ ବ୍ୟବହାର କରିବେ**: ମଲ୍ଟି-ଟର୍ନ କନଭରସେସନ୍ ଯେଉଁଠାରେ ଆପଣ ଚାହାଁନ୍ତି ଯେ ସମାନ ପ୍ରୋଭାଇଡର୍ ଫଲୋ-ଅପ୍ ଅନୁରୋଧଗୁଡ଼ିକୁ ହ୍ୟାଣ୍ଡେଲ କରୁ (ଉଦାହରଣ ସ୍ୱରୂପ, କ୍ୟାଚିଂ, କଣ୍ଟେକ୍ସଟ୍ କଣ୍ଟିନ୍ୟୁଟି, କିମ୍ବା ପ୍ରାଇସିଂ କନସିଷ୍ଟେନ୍ସି ପାଇଁ)।

**Alias**: `lkgp` (no alias)

#### 6. `nadir` — prompt-aware model choice via Nadir

ଉପରୋକ୍ତ ପ୍ରତ୍ୟେକ ଷ୍ଟ୍ରାଟେଜି ପ୍ରାର୍ଥୀମାନଙ୍କୁ ସେମାନଙ୍କର ନିଜସ୍ୱ ଟେଲିମେଟ୍ରି ଦ୍ୱାରା ରାଙ୍କ୍ କରେ; ସେମାନଙ୍କ ମଧ୍ୟରୁ କେହି ବି ଅନୁରୋଧକୁ ପଢ଼ନ୍ତି ନାହିଁ। `nadir` ଶେଷ ୟୁଜର୍ ଟର୍ନ ଏବଂ ପୁଲ୍‌ର ମଡେଲ୍ ଆଇଡିଗୁଡ଼ିକୁ [Nadir](https://getnadir.com) ର ଡିସିଜନ୍ API (`POST /v1/bucket`) କୁ ପଠାଏ ଏବଂ ସେହି ମେନୁରୁ Nadir ଯେଉଁ ମଡେଲ୍ ଚୟନ କରେ (`simple` → ସବୁଠାରୁ ଶସ୍ତା ସକ୍ଷମ ମଡେଲ୍, `complex` → ଫ୍ରଣ୍ଟିଅର୍ ମଡେଲ୍) ସେଠାକୁ ରୁଟ୍ କରେ। ସେହି ମଡେଲ୍ ସର୍ଭିସ୍ କରୁଥିବା କନେକ୍ସନ୍ ଏବେ ବି `rules` ଦ୍ୱାରା ଚୟନ କରାଯାଏ, ତେଣୁ କୋଟା, ହେଲଥ୍ ଏବଂ କଷ୍ଟ କେଉଁ ଆକାଉଣ୍ଟ ବ୍ୟବହାର ହେବ ତାହା ନିର୍ଣ୍ଣୟ କରେ।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` ଏବଂ `OMNIROUTE_NADIR_BASE_URL` ହେଉଛି ଦୁଇଟି ଷ୍ଟ୍ରିଙ୍ଗ୍ ପାଇଁ env ଫଲବ୍ୟାକ୍। `baseUrl` କେବଳ ସେଲ୍ଫ-ହୋଷ୍ଟେଡ୍ Nadir ପାଇଁ ଆବଶ୍ୟକ (ଏକ ଟ୍ରେଲିଂ `/v1` ଗ୍ରହଣୀୟ)। Keyless କଲ୍‌ଗୁଡ଼ିକ Nadir ର ଆନୋନିମସ୍ ଟିୟରରେ ପଡ଼େ, ଯାହା ପ୍ରତି IP ରେ ରେଟ୍-ଲିମିଟେଡ୍।

ବକ୍ସରୁ କ’ଣ ବାହାରେ: ଶେଷ ୟୁଜର୍ ମେସେଜ୍‌ର ଟେକ୍ସଟ୍ (ପ୍ରଥମ 16k କ୍ୟାରେକ୍ଟର), ପ୍ରାର୍ଥୀ ମଡେଲ୍ ଆଇଡି ଏବଂ ଏକ `source: "omniroute"` ଚ୍ୟାନେଲ୍ ଟ୍ୟାଗ୍। କୌଣସି ସିଷ୍ଟମ୍ ପ୍ରମ୍ପ୍ଟ, ହିଷ୍ଟ୍ରି, ଟୁଲ୍‌ସ୍ କିମ୍ବା ହେଡର୍ ନୁହେଁ।

ଫେଲିଅର୍ ବିହେଭିୟର୍ ହେଉଛି fail-open: ଏକ ଟାଇମ୍‌ଆଉଟ୍ (ଡିଫଲ୍ଟ 2000 ms), ଏକ non-2xx, ଏକ ଅପହଞ୍ଚ ହୋଷ୍ଟ, ଏକ ମାଲଫର୍ମଡ୍ ରେସପନ୍ସ କିମ୍ବା ପୁଲ୍ ବାହାରେ ଏକ ଚୟନ `rules` ଡିସିଜନ୍‌କୁ ରିଜଲ୍ଭ ହୁଏ ଏବଂ କାରଣଟି `NadirStrategy: fallback (…)` ପ୍ରିଫିକ୍ସ ହୋଇଥାଏ। ଏକ ଫେଲ୍ ହୋଇଥିବା କଲ୍ ପରେ ଷ୍ଟ୍ରାଟେଜି 30 ସେକେଣ୍ଡ ପାଇଁ ନେଟୱାର୍କକୁ ସ୍କିପ୍ କରେ, ତେଣୁ ଏକ ଆଉଟେଜ୍ ପ୍ରତି ଅନୁରୋଧ ପାଇଁ ଗୋଟିଏ ଟାଇମ୍‌ଆଉଟ୍ ବଦଳରେ ପ୍ରତି 30 ସେକେଣ୍ଡରେ ଗୋଟିଏ ଟାଇମ୍‌ଆଉଟ୍ ଖର୍ଚ୍ଚ କରେ। ରୁଟିଂ ଇଭେଣ୍ଟଗୁଡ଼ିକ କେବଳ ସେତେବେଳେ `strategy: "nadir"` ରିପୋର୍ଟ କରେ ଯେତେବେଳେ Nadir ପ୍ରକୃତରେ ଚୟନ କରିଥାଏ।

**କେବେ ବ୍ୟବହାର କରିବେ**: ମିଶ୍ରିତ କଷ୍ଟ ସ୍ତର ଥିବା ପୁଲ୍‌ରେ ମିଶ୍ରିତ-ଅସୁବିଧା ଟ୍ରାଫିକ୍ (ଏକ ସ୍ମଲ୍, ଏକ ମିଡ୍ ଏବଂ ଏକ ଫ୍ରଣ୍ଟିଅର୍ ମଡେଲ୍), ଯେଉଁଠାରେ ସର୍ବଦା-ଫ୍ରଣ୍ଟିଅର୍ ହେଉଛି ସେହି କଷ୍ଟ ଯାହାକୁ ଆପଣ କମ୍ କରିବାକୁ ଚାହାଁନ୍ତି।

**Alias**: `nadir` (no alias)

### କଷ୍ଟମ୍ ରୁଟର୍ ଷ୍ଟ୍ରାଟେଜି

ଆପଣ ପବ୍ଲିକ୍ API ମାଧ୍ୟମରେ ନିଜର `RouterStrategy` ଇମ୍ପ୍ଲିମେଣ୍ଟେସନ୍ ରେଜିଷ୍ଟର୍ କରିପାରିବେ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ତା’ପରେ ଏହାକୁ ବ୍ୟବହାର କରନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## କାର୍ଯ୍ୟ ଉପଯୁକ୍ତତା

6ଟି କାର୍ଯ୍ୟ ପ୍ରକାର (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) ମଧ୍ୟରେ 30+ ମଡେଲ୍‌କୁ ସ୍କୋର୍ କରାଯାଇଛି। ୱାଇଲ୍ଡକାର୍ଡ ପ୍ୟାଟର୍ନଗୁଡ଼ିକୁ ସମର୍ଥନ କରେ (ଉଦାହରଣ ସ୍ୱରୂପ, `*-coder` → ଉଚ୍ଚ କୋଡିଂ ସ୍କୋର୍)।

## Auto ଭାରିଆଣ୍ଟଗୁଡ଼ିକର ସାରାଂଶ

ଡିଫଲ୍ଟ ଖାଲି `auto` ସହିତ `autoPrefix.ts`ରେ ଘୋଷିତ 6ଟି `AutoVariant` ମୂଲ୍ୟକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରି, **7ଟି ଆହ୍ୱାନଯୋଗ୍ୟ ମଡେଲ୍ ID** ଅଛି:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ନିଜେ 6ଟି ମୂଲ୍ୟ ଗଣନା କରେ; 7ମ ବିକଳ୍ପଟି ହେଉଛି "କୌଣସି ଭାରିଆଣ୍ଟ ନାହିଁ" — ଖାଲି `auto` — ଯାହାକୁ `parseAutoPrefix()` ଦ୍ୱାରା `variant: undefined` ଭାବେ ପରିଚାଳନା କରାଯାଏ।)

## ଟିୟରଗୁଡ଼ିକ Auto-Combo ସହିତ କିପରି ଖାପ ଖାଆନ୍ତି

16-ଫ୍ୟାକ୍ଟର ସ୍କୋରିଂ ଫଙ୍କସନ୍ (`open-sse/services/autoCombo/scoring.ts`) ଟିୟର
ସଦସ୍ୟତାକୁ ଦୁଇଟି ସିଗ୍ନାଲ୍ ଭାବେ ବିବେଚନା କରେ: `tierPriority` (0.0476) ଏବଂ `tierAffinity` (0.0476)। ସମ୍ପୂର୍ଣ୍ଣ
`DEFAULT_WEIGHTS` ସେଟ୍ ପାଇଁ ଉପରେ ଥିବା ପ୍ରାମାଣିକ [ସ୍କୋରିଂ ଫ୍ୟାକ୍ଟର୍ ସାରଣୀ](#how-it-works-persisted-auto-combos) ଦେଖନ୍ତୁ —
ପ୍ରତି-ପ୍ୟାକ୍ ଓଭରରାଇଡ୍ଗୁଡ଼ିକ (ship-fast/cost-saver/quality-first/
offline-friendly) "ପ୍ରତି ପ୍ୟାକ୍ର ଓଜନ ପ୍ରୋଫାଇଲ୍" ସାରଣୀରେ ତାଲିକାଭୁକ୍ତ ହୋଇଛି।

କେବଳ ଟିୟର୍ **Tier 1**କୁ ପ୍ରଥମ ସ୍ଥାନରେ ରଖିବାକୁ ବାଧ୍ୟ କରେ ନାହିଁ — ଯଦି Tier 1ର ବିଳମ୍ବତା ଖରାପ ଥାଏ କିମ୍ବା
ମୂଲ୍ୟ-ତୁଳନାରେ-ଗୁଣବତ୍ତା ସର୍ବୋତ୍ତମ ନ ହୁଏ, ତେବେ Tier 2 ବିଜୟୀ ହୁଏ। ଟିୟର୍ କ୍ରମକୁ ବାଧ୍ୟତାମୂଳକ କରିବା ପାଇଁ, କମ୍ବୋ
ଷ୍ଟ୍ରାଟେଜି `priority` ବ୍ୟବହାର କରନ୍ତୁ ଏବଂ ପ୍ରଦାତାମାନଙ୍କୁ ଟିୟର୍ ଅନୁସାରେ ସଜାନ୍ତୁ।

Tier 1 (ସବ୍ସ୍କ୍ରିପ୍ସନ୍)କୁ ଦୃଢ଼ ଭାବରେ ପ୍ରାଧାନ୍ୟ ଦେବା ପାଇଁ, `tierPriority`ର ଓଜନ ବଢ଼ାନ୍ତୁ:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ଟିୟର୍ର ସଂଜ୍ଞା ଏବଂ ପ୍ରଦାତାଙ୍କ ବର୍ଗୀକରଣ ପାଇଁ [`docs/guides/TIERS.md`](../guides/TIERS.md) ଦେଖନ୍ତୁ।

### ନିର୍ଦ୍ଧାରିତ ରାଉଟିଂ-ନିଷ୍ପତ୍ତି ମ୍ୟାଟ୍ରିକ୍ସ (`npm run test:combo:matrix`)

ସାର୍ବଜନୀନ କୌଶଳର ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ ରାଉଟିଂ **ନିଷ୍ପତ୍ତି**କୁ ପ୍ରମାଣ କରେ।
କଭରେଜ୍‌ରେ ଅନ୍ତର୍ଭୁକ୍ତ:

- ସମସ୍ତ 19ଟି `ROUTING_STRATEGY_VALUES` କୌଶଳ (କ୍ରମବଦ୍ଧ, ଓଜନଯୁକ୍ତ, ମୂଲ୍ୟ, ପ୍ରସଙ୍ଗ, ଫ୍ୟୁଜନ୍, …)।
- `quota-share` (ଆଭ୍ୟନ୍ତରୀଣ) ଏଣ୍ଡ-ଟୁ-ଏଣ୍ଡ: ବାସ୍ତବ `selectQuotaShareTarget` ସିମ୍ ମାଧ୍ୟମରେ DRR ନିରପେକ୍ଷତା + ସାଚୁରେସନ୍ ପ୍ରାଥମିକତା ହ୍ରାସ
  (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)।
- ପ୍ରତ୍ୟେକ ଟାର୍ଗେଟ୍ ସଂଖ୍ୟାରେ `context-relay` ସାର୍ବଜନୀନ-ହ୍ୟାଣ୍ଡଅଫ୍ କଭରେଜ୍।

ଏହି ସୁଇଟ୍ CIରେ (`test:integration` ଜବ୍) `--test-concurrency=1` ଏବଂ
`--test-force-exit` ସହିତ ଚାଲେ, ତେଣୁ ଏହା ନିର୍ଦ୍ଧାରିତ ଏବଂ ଲାଇଭ୍ କ୍ରେଡେନ୍ସିଆଲ୍‌ର ଆବଶ୍ୟକତା ନାହିଁ।

### ଗେଟେଡ୍ ଲାଇଭ୍ ସ୍ମୋକ୍ ପରୀକ୍ଷା (CIରେ ନୁହେଁ — ବାସ୍ତବ ପ୍ରଦାତା)

| କମାଣ୍ଡ୍                                | ଏହା କ’ଣ କରେ                                                                               |
| :------------------------------------- | :---------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ସହିତ ଇନ୍-ପ୍ରୋସେସ୍ ବାସ୍ତବ ରାଉଟିଂ; ଏକ ଲାଇଭ୍ OmniRoute DBର ସ୍ନାପ୍‌ସଟ୍ ନିଏ |
| `npm run test:combo:live:vps`          | ଏକ ଲାଇଭ୍ OmniRoute ସର୍ଭର୍ ବିରୁଦ୍ଧରେ HTTP କଲ୍‌ଗୁଡ଼ିକ (`COMBO_LIVE_BASE_URL` ସେଟ୍ କରନ୍ତୁ)   |
| `npm run test:combo:live:vps:failover` | ସମାନ, ଇଚ୍ଛାକୃତ ଫେଲ୍‌ଓଭର୍ ପରିଦୃଶ୍ୟଗୁଡ଼ିକ ସହିତ                                              |

ଏହି ସ୍ମୋକ୍ ପରୀକ୍ଷାଗୁଡ଼ିକ ବାସ୍ତବ ୱାୟାର୍ ପଥ (କମ୍ବୋ → ପ୍ରଦାତା → ସମ୍ପୂର୍ଣ୍ଣତା)କୁ ପରୀକ୍ଷା କରେ। ଏଗୁଡ଼ିକୁ
ଇଚ୍ଛାକୃତ ଭାବେ CIରୁ ବାଦ ଦିଆଯାଇଛି, କାରଣ ଏଗୁଡ଼ିକ ପାଇଁ ଲାଇଭ୍ କ୍ରେଡେନ୍ସିଆଲ୍ ଏବଂ VPS ଆକ୍ସେସ୍ ଆବଶ୍ୟକ।
