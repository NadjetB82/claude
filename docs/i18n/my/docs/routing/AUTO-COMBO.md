## Zero-Config အလိုအလျောက် လမ်းကြောင်းရွေးချယ်ခြင်း (`auto/` ရှေ့ဆက်)

> **အသစ်:** combo ဖန်တီးရန် မလိုအပ်ပါ။ မည်သည့် client တွင်မဆို `auto/` ရှေ့ဆက်ကို တိုက်ရိုက်အသုံးပြုပါ။

### အမြန်နမူနာများ

| Model ID       | မူကွဲ   | လုပ်ဆောင်ပုံ                                                                                          |
| -------------- | ------- | ----------------------------------------------------------------------------------------------------- |
| `auto`         | မူလ     | ချိတ်ဆက်ထားသော provider အားလုံး၊ LKGP နည်းဗျူဟာ၊ ချိန်ညှိထားသော weights                               |
| `auto/coding`  | coding  | အရည်အသွေးဦးစားပေး weights၊ code ထုတ်လုပ်ခြင်းအတွက် သင့်လျော်သည်                                       |
| `auto/fast`    | fast    | latency နည်းသည့် weighted ရွေးချယ်မှု                                                                 |
| `auto/cheap`   | cheap   | ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် လမ်းကြောင်းရွေးချယ်ခြင်း (အနည်းဆုံးကုန်ကျစရိတ်ကို ဦးစွာရွေးသည်)       |
| `auto/offline` | offline | quota ရရှိနိုင်မှု အမြင့်ဆုံး provider များကို ဦးစားပေးသည်                                            |
| `auto/smart`   | smart   | ပိုမိုကောင်းမွန်သော model ရှာဖွေမှုအတွက် အရည်အသွေးဦးစားပေး + ပိုမြင့်သော စမ်းသပ်ရှာဖွေမှုနှုန်း (10%) |
| `auto/lkgp`    | lkgp    | တိကျစွာသတ်မှတ်ထားသော LKGP (မူလ `auto` နှင့် တူညီသည်)                                                  |
| `auto/chaos`   | chaos   | အပြိုင် fan-out၊ provider တစ်ခုလျှင် model တစ်ခု (ချို့ယွင်းချက်ထည့်သွင်းခြင်း မဟုတ်ပါ)               |

### Category × Tier ပေါင်းစပ်မှု (`auto/<category>:<tier>`)

OpenRouter ပုံစံ suffix များသည် **မည်သည့်လမ်းကြောင်းအမျိုးအစားဖြစ်သည်** (category) ကို **မည်သို့ အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်မည်** (tier) နှင့် ခွဲခြားပေးသောကြောင့် ၎င်းတို့ကို လွတ်လပ်စွာ ပေါင်းစပ်နိုင်သည် (#4235 Phase B၊ `open-sse/services/autoCombo/suffixComposition.ts`)：

- **Categories** (စွမ်းဆောင်ရည်အလိုက် ရွေးချယ်နိုင်သော pool ကို စစ်ထုတ်သည်): `coding` · `reasoning` · `vision` · `chat` · `multimodal`။ `vision`/`multimodal` သည် vision စွမ်းရည်ရှိသော model များကို ထိန်းသိမ်းထားပြီး `reasoning` သည် reasoning/thinking model များကို ထိန်းသိမ်းထားသည်။
- **Tiers** (အမှတ်ပေး weights / pool filter ကို ရွေးချယ်သည်): `fast` (လျင်မြန်စွာ ထုတ်ပေးခြင်း) · `cheap` (`floor` ၏ alias၊ ကုန်ကျစရိတ်ချွေတာမှု) · `reliable` (circuit-breaker ကျန်းမာရေး + latency တည်ငြိမ်မှု) · `free` / `pro` (`classifyTier` မှတစ်ဆင့် model tier အလိုက် pool ကို စစ်ထုတ်သည် — free-tier နှင့် premium)။

| နမူနာ                  | ဖြေရှင်းသတ်မှတ်ပုံ                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool၊ latency နည်းသော weights                                                     |
| `auto/coding:cheap`    | coding pool၊ ကုန်ကျစရိတ်အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်ထားသည် (`auto/coding:floor` ၏ alias) |
| `auto/reasoning:pro`   | reasoning/thinking model များသာ၊ premium tier                                            |
| `auto/vision`          | vision စွမ်းရည်ရှိသော model များ (tier မရှိ → ချိန်ညှိထားသော weights)                    |
| `auto/multimodal:free` | multimodal စွမ်းရည်ရှိသော model များ၊ free tier သာ                                       |

တရားဝင်သော `auto/<category>[:<tier>]` မှန်သမျှကို လိုအပ်သည့်အချိန်တွင် ဖြေရှင်းသတ်မှတ်ပေးသည်။ စီစဉ်ရွေးချယ်ထားသော အစုခွဲတစ်ခုကို `/v1/models` နှင့် dashboard တွင် ဖော်ပြထားသည် (`open-sse/services/autoCombo/builtinCatalog.ts` ရှိ `AUTO_SUFFIX_VARIANTS`)။ စစ်ထုတ်ခြင်းသည် **fail-open** ဖြစ်သည် — constraint တစ်ခုနှင့် ကိုက်ညီသော ချိတ်ဆက်ထားသည့် model မရှိပါက လမ်းကြောင်းရွေးချယ်မှု မပျက်စေရန် pool အပြည့်အစုံကို အသုံးပြုသည်။ အဓိက scorer (`combo.ts`) သည် မပြောင်းလဲဘဲ category/tier filter ကို `buildAutoCandidates` တွင် အသုံးချထားသည်။

> **တိုက်ရိုက် model အသိဉာဏ်:** `ARENA_ELO_SYNC_ENABLED` flag ဖွင့်ထားသည့်အခါ အလိုအလျောက်လမ်းကြောင်းရွေးချယ်မှု၏ သင့်လျော်မှုကို တိုက်ရိုက် **Arena ELO** အဆင့်သတ်မှတ်ချက်များ + **models.dev** tier data တို့ဖြင့် ဆုံးဖြတ်သည် (မဟုတ်ပါက static fitness map ကို ပြန်လည်အသုံးပြုသည်)။

**အသုံးပြုနည်း:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**ဖြစ်ပျက်ပုံ:**

1. OmniRoute သည် `src/sse/handlers/chat.ts` တွင် `auto/` ရှေ့ဆက်ကို ရှာဖွေသိရှိသည်
2. database မှ **အသုံးပြုနေသော provider ချိတ်ဆက်မှုများ** အားလုံးကို query ပြုလုပ်သည်
3. တရားဝင် credentials (API key သို့မဟုတ် OAuth token) ရှိသည့်အရာများကို စစ်ထုတ်သည်
4. ချိတ်ဆက်မှုတစ်ခုစီအတွက် model ကို ဆုံးဖြတ်သည် (`connection.defaultModel` သို့မဟုတ် provider ၏ ပထမဆုံး model)
5. memory အတွင်း **virtual combo** တစ်ခုကို တည်ဆောက်သည် (DB တွင် မသိမ်းဆည်းပါ)
6. ရွေးချယ်ထားသော မူကွဲ၏ weight profile + LKGP နည်းဗျူဟာကို အသုံးပြု၍ လမ်းကြောင်းရွေးချယ်သည်

**အဓိကဂုဏ်သတ္တိများ:**

- ✅ **အမြဲဖွင့်ထားသည်:** toggle မလို၊ combo ဖန်တီးရန် မလို၊ configuration မလိုအပ်ပါ
- ✅ **Dynamic:** လက်ရှိချိတ်ဆက်ထားသော provider များကို အလိုအလျောက် ထင်ဟပ်ပေးသည်
- ✅ **Session stickiness:** LKGP သည် နောက်ဆုံးအောင်မြင်ခဲ့သော provider ကို ဦးစားပေးရန် သေချာစေသည်
- ✅ **အကောင့်အများအပြားကို သိရှိစီမံနိုင်သည်:** provider ချိတ်ဆက်မှုတစ်ခုစီသည် သီးခြား candidate တစ်ခု ဖြစ်လာသည်
- ✅ **DB ရေးသားမှုမရှိ:** Virtual combo သည် request အတွက်သာ တည်ရှိပြီး persistence overhead လုံးဝမရှိပါ

### Key တစ်ခုချင်းစီအလိုက် candidate ထိန်းချုပ်မှု (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` နောက်ရှိ suffix သို့မဟုတ်
အခြေခံ channel အတွက် တိုက်ရိုက် `auto`) သည် ရှိပြီးသား resilience reads များကို
ပြန်လည်အသုံးပြုကာ တိုက်ရိုက် reachability ဖြင့် ဖြည့်စွက်ဖော်ပြထားသည့် `auto/*` channel ၏
လက်ရှိ candidate pool ကို စာရင်းပြုစုသော **ဖတ်ရှုရန်သီးသန့်** endpoint ဖြစ်သည် (breaker `state` အကြမ်းကို မည်သည့်အခါမျှ မသုံးပါ):

- provider circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- ချိတ်ဆက်မှု cooldown — ဖြေရှင်းသတ်မှတ်ထားသော `provider_connections` row ရှိ
  `rateLimitedUntil` / `testStatus`
- model lockout — `isModelLocked(provider, connectionId, model)`

Candidate တစ်ခုစီတွင် ဤ API key ၏ `excluded` flag လည်း ပါဝင်သည်။ ဖယ်ထုတ်မှုများကို
API key တစ်ခုချင်းစီအလိုက် သိမ်းဆည်းထားသည် (`auto_candidate_overrides` table၊ migration `128`) — OmniRoute သည်
`users` table မရှိသော single-tenant ဖြစ်သောကြောင့် `apiKeyId` သည် တကယ့် caller တစ်ဦးချင်းစီ၏
identity နှင့် အနီးစပ်ဆုံးဖြစ်သည် — ထို့ပြင် သီးခြားယူနစ်စမ်းသပ်ထားသော
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) မှတစ်ဆင့်
`open-sse/services/autoCombo/virtualFactory.ts` ရှိ candidate-pool chokepoint တွင် အတင်းအကျပ် အသုံးချသည်။
Filter သည် **fail-open** ဖြစ်သည်: apiKeyId/channel ကို မသတ်မှတ်ထားခြင်း သို့မဟုတ် DB lookup ပျက်ကွက်ခြင်း နှစ်မျိုးစလုံးတွင်
pool ကို စစ်ထုတ်ခြင်းမပြုဘဲ ထားရှိသောကြောင့် override များ မစီစဉ်ထားသည့် operator တစ်ဦးသည် ဤ feature မတိုင်မီကနှင့်
byte အဆင့်အထိ တစ်ပုံစံတည်းဖြစ်သော လမ်းကြောင်းရွေးချယ်မှုကို တွေ့မြင်ရသည်။

**နောက်ဆက်တွဲ issue တစ်ခုသို့ ရွှေ့ဆိုင်းထားသည်:** candidate တစ်ခုချင်းစီအလိုက် weight များ + တိကျစွာ သတ်မှတ်ထားသော အစီအစဉ် (Level 3
— လက်ရှိ weighted/priority strategy လမ်းကြောင်းများသို့ ထည့်သွင်းပေးသည်) နှင့် `auto/*` channel တစ်ခုချင်းစီအတွက် သတ်မှတ်ထားသော
`combo.ts` strategy တစ်ခုကို pin လုပ်ခြင်း (Level 4)။ single-tenant model ကို ထည့်သွင်းစဉ်းစားလျှင် override များကို API key တစ်ခုချင်းစီအလိုက် ဆက်လက်ထားရှိသင့်သလား သို့မဟုတ် global အဖြစ် ပြောင်းလဲသင့်သလားဆိုသည့် အဖြေမရှိသေးသော
မေးခွန်းအတွက် #7819 plan ကို ကြည့်ပါ။

**နောက်ကွယ်ရှိ လုပ်ငန်းစဉ်:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**အကောင်အထည်ဖော်မှုဆိုင်ရာ ဖိုင်များ:**

| ဖိုင်                                                     | ရည်ရွယ်ချက်                                        |
| --------------------------------------------------------- | -------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Prefix parser (`parseAutoPrefix`)                  |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Virtual `AutoComboConfig` object များကို ဖန်တီးသည် |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Provider registry ကို mock လုပ်ရန် test hook       |

| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` system entry               |

## အမှန်တကယ်ရှိသော Model Id နှင့် ကိုက်ညီသည့် Combo အမည်များ

`name` သည် bare model id တစ်ခုနှင့် တူညီနေသော combo (ဥပမာ `gpt-5.5` ဟု အမည်ပေးထားသည့် combo) သည် bug မဟုတ်ဘဲ **ရည်ရွယ်ချက်ရှိရှိ ပံ့ပိုးထားသော ပုံစံတစ်ခု** ဖြစ်သည်။ ၎င်းသည် [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) တွင် မှတ်တမ်းတင်ထားသည့် model-id တစ်ခုချင်းအလိုက် provider fallback ပြုလုပ်ရန် ယန္တရားဖြစ်သည်။ Bare-model-id resolution မတိုင်မီ combo resolution ကို စစ်ဆေးသောကြောင့် (`src/sse/services/model.ts` ရှိ `getComboForModel()`) bare id `gpt-5.5` အတွက် request ကို provider တစ်ခုတည်းထံ တိုက်ရိုက်ပို့မည့်အစား combo ၏ targets များ (ဥပမာ `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) မှတစ်ဆင့် route လုပ်သည် — ဤလုပ်ဆောင်ချက်သည် [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) အတွက် တည်ဆောက်ထားသော combo-before-rewrite ဦးစားပေးအစီအစဉ်ကို ပြန်လည်အသုံးပြုထားပြီး `tests/unit/responses-combo-resolution-3227.test.ts` နှင့် `tests/unit/combo-name-codex-responses-rewrite.test.ts` တို့ဖြင့် regression test ပြုလုပ်ထားသည်။

အမှန်တကယ်ရှိသော model id ကို ဖုံးကွယ်သည့် အမည်တစ်ခုဖြင့် combo ဖန်တီးခြင်း သို့မဟုတ် အမည်ပြောင်းခြင်းကို **မည်သည့်အခါမျှ ငြင်းပယ်မည်မဟုတ်ပါ** — ထိုသို့ပြုလုပ်ပါက မှတ်တမ်းတင်ထားသော ဤ workflow ကို ပျက်စီးစေမည်ဖြစ်သည်။ ထိုအစား (#8530)၊ (အသစ်သတ်မှတ်ထားသော) အမည်သည် အမှန်တကယ်ရှိသော model id နှင့် တိုက်ဆိုင်သည့်အခါ `POST /api/combos` နှင့် `PUT /api/combos/[id]` တို့သည် request ကို ပိတ်ဆို့ခြင်းမရှိသော `warning` field တစ်ခုကို response တွင် ထည့်သွင်းပေးသည်-

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

စနစ်စတင်ချိန်တွင် `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) သည် model id ကို ဖုံးကွယ်နေသည့် လက်ရှိ combo တိုင်းကို စာရင်းပြုစုထားသော တစ်ကြောင်းတည်းပါ `[STARTUP]` သတိပေးချက်ကိုလည်း log လုပ်ပေးသည်။ ထို့ကြောင့် #6940 အရ ရည်ရွယ်ချက်ရှိရှိ ပြုလုပ်ခြင်းမဟုတ်ဘဲ မတော်တဆ ကြုံတွေ့ရသော operator များအတွက် သတိပြုနိုင်သည့် အချက်ပြမှုတစ်ခု ရရှိစေသည်။ Detection helper သည် `src/lib/combos/modelNameCollision.ts` တွင် ရှိသည်။

## Client မှ Custom Combo တစ်ခုကို ခေါ်ယူခြင်း

သိမ်းဆည်းထားသော combo များ (Settings → Combos) ကို client က combo ၏ **အမည်အတိအကျ** ကို `model` field တွင် ပို့သည့်အခါမှသာ အသုံးပြုသည် — combo အမည်အတွက် fuzzy သို့မဟုတ် partial matching မရှိသည့်အပြင် `auto/` prefix လည်း မပါဝင်ပါ။ Resolution အစီအစဉ် (`src/sse/services/model.ts` ရှိ `getComboForModel()`)-

1. combo အမည်နှင့် အတိအကျကိုက်ညီမှု (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)။

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

အဖြစ်များသော သတိပြုရမည့်အချက်နှစ်ခု-

- **`auto` သည် သင့် combo များကို အသုံးမပြုပါ။** `auto`/`auto/*` သည် ၎င်းကိုယ်ပိုင် zero-config candidate pool ကို တည်ဆောက်ပြီး `auto` ဟု အမည်အတိအကျ ပေးထားသည့် combo ရှိမှသာ သိမ်းဆည်းထားသော combo များကို အသုံးပြုသည် (မအကြံပြုပါ)။ Combo မှတစ်ဆင့် route လုပ်ရန် `auto` ကို မပို့ဘဲ ၎င်း၏ အမည်အတိအကျကို ပို့ပါ။
- **`openrouter/auto` သည် အမှန်တကယ်ရှိသော အခပေး OpenRouter product** ("Auto Best Available") ဖြစ်ပြီး OmniRoute alias မဟုတ်ပါ။ ၎င်းသည် OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) ၏ တစ်ခုတည်းသော static model entry ဖြစ်ပြီး သီးခြားငွေတောင်းခံသည်။ ၎င်းကို `auto` pools များမှ ဖယ်ထုတ်ရန် Settings → Routing → Hide paid models ကို အသုံးပြုပါ။

ဤမှတ်တမ်းတွင် ရှင်းလင်းထားသော မူလရှုပ်ထွေးမှုအကြောင်းကို [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) နှင့် [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) တို့တွင် ကြည့်ပါ။

## အလုပ်လုပ်ပုံ (Persisted Auto-Combos)

Auto-Combo Engine သည် request တစ်ခုစီအတွက် အကောင်းဆုံး provider/model ကို **16-factor scoring function** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` တွင် သတ်မှတ်ထားသည်) အသုံးပြု၍ dynamic နည်းလမ်းဖြင့် ရွေးချယ်ပေးပါသည်။ မူရင်း weights များ၏ ပေါင်းလဒ်မှာ `1.0` ဖြစ်ပြီး စိတ်ကြိုက်ပြင်ဆင်ထားသော weights များကို `normalizeScoringWeights()` ဖြင့် ပြန်လည်ညှိယူ (renormalize) ပေးပါသည်။ အချက်ဆယ့်ခြောက်ခုအနက် နှစ်ခုဖြစ်သော `cacheAffinity` နှင့် `resetWindowAffinity` တို့သည် မူရင်း weight တန်ဖိုး `0` ရှိပါသည်။ `reliability` ၏ တန်ဖိုးသည် `DEFAULT_WEIGHTS` တွင် `0` ဖြစ်သော်လည်း generic packs များတွင် `0.03` နှင့် `reliability-first` တွင် `0.04` ဖြစ်ပြီး `quality` သည် packs များတွင် `0.02` (`quality-first` တွင် `0.03`) ဖြစ်ပါသည်- ၎င်းတို့ကို candidate တိုင်းအတွက် တွက်ချက်နေဆဲဖြစ်ပြီး `cacheAffinity` သည် score အပြင်ဘက်ရှိ prompt-cache deduplication ကို ထိန်းချုပ်ထားသောကြောင့် မူရင်းတန်ဖိုး သုညဖြစ်နေသော factors များသည် ပုံမှန်အားဖြင့် မဲပေးခြင်းမရှိသော်လည်း packs များတွင် မဲပေးမည်ဖြစ်သည်။

> မည်သည့်အရာမျှ ပြန်မပေးပါက (ရယူမှု မအောင်မြင်ခြင်း၊ credentials ပျောက်ဆုံးနေခြင်း၊ မက်ဆေ့ခ်ျသီးသန့် အသုံးပြုမှုဖြစ်ခြင်း၊ သို့မဟုတ် parse လုပ်နိုင်သော
> `windows` မရှိသည့်အပြင် `percentUsed: null` အပါအဝင် finite `percentUsed` မရှိသော ပျက်ယွင်းနေသည့် snapshot ဖြစ်ခြင်း)၊ ထို candidate သည်
> `quota` ဝင်ရိုးတွင် `0` ရမှတ်ရရှိပြီး ၎င်း၏ နောက်ဆုံးရမှတ်ကို
> connection-status penalty ကဲ့သို့ soft-penalty ပုံစံအတိုင်း `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) ဖြင့်
> မြှောက်ပေးသည်။ မအောင်မြင်သော usage ဖတ်ရှုမှုသည် provider နှင့် မသက်ဆိုင်ဘဲ telemetry ၏ အခြေအနေသာ ဖြစ်သောကြောင့်၊ ၎င်းကို အတည်ပြုပြီးသား ၁၀၀% အသုံးပြုထားသည့်
> တန်ဖိုးအပါအဝင် မည်သည့် အစစ်အမှန်ဖတ်ရှုမှုတန်ဖိုးထက်မဆို အောက်တွင်သာ အဆင့်သတ်မှတ်ထားသော်လည်း၊ မည်သည့်အခါမျှ hard-blocked သို့မဟုတ် ဖယ်ရှားခြင်း (evicted) မပြုလုပ်ပါ။ ကန့်သတ်ချက် (cap) မရှိသော provider တစ်ခုသည် `unlimited: true` အဖြစ် အစီရင်ခံပြီး
> quota အပြည့်အဖြစ် ရမှတ်သတ်မှတ်သည်၊ မှတ်ပုံတင်ထားသော quota fetcher မရှိသော provider တစ်ခုတွင်မူ မည်သည့် telemetry source မျှ လုံးဝမရှိသောကြောင့်
> မူလသတ်မှတ်ချက် `100` ကို ဆက်လက်ထိန်းသိမ်းထားသည်။

**ပေါင်းလဒ်-** `DEFAULT_WEIGHTS` တွင် သတ်မှတ်ထားသည့်အတိုင်း `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` ဖြစ်သည်၊ အသုံးပြုသူစိတ်ကြိုက်ပြင်ဆင်ထားသော weight များကို ရမှတ်မတွက်ချက်မီ `normalizeScoringWeights()` ဖြင့် distribution တစ်ခုအဖြစ် renormalize ပြုလုပ်ပေးသည်။

### `weighted` ၏ အဓိပ္ပာယ်ဖွင့်ဆိုချက်များ

`weighted` ဆိုသည်မှာ **တောင်းဆိုမှုတစ်ခုချင်းစီအတွက် အချိုးကျ ကျပန်းရွေးချယ်ခြင်း** ဖြစ်ပြီး (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)၊ ညီမျှအောင်လုပ်ဆောင်ပေးခြင်း (equalizer) မဟုတ်ပါ:

- တောင်းဆိုမှုတစ်ခုစီသည် `weight / totalWeight` ဖြစ်နိုင်ခြေဖြင့် **အဆင့်တစ်ခု** ကို ရွေးချယ်သည်; ကျန်ရှိသောအဆင့်များကို ထိုတောင်းဆိုမှုအတွက် fallback chain အဖြစ် အလေးချိန်အလိုက် အစဉ်လိုက် စီထားသည်။
- အလေးချိန် `0` ဖြစ်သော (သို့မဟုတ် မရှိသော) အဆင့်ကို အခြားအဆင့်တစ်ခုခုတွင် အလေးချိန် > 0 ရှိနေသရွေ့ **ဘယ်တော့မှ မရွေးချယ်ပါ** — ၎င်းကို ရွေးချယ်ထားသောအဆင့် ပျက်ကွက်မှသာ fallback အဖြစ် အသုံးပြုနိုင်သည်။ အလေးချိန် **အားလုံး** 0 ဖြစ်မှသာ ရွေးချယ်မှုသည် တူညီသွားမည်ဖြစ်သည်။
- Target များ အားလုံး မရရှိနိုင်သော အဆင့်များ — provider circuit breaker `OPEN` ဖြစ်နေခြင်း၊ connection cooldown၊ model lockout — တို့ကို ရွေးချယ်မှုမပြုလုပ်မီ ဖယ်ရှားလိုက်သည် (`open-sse/services/combo/targetResolution.ts`)၊ ထို့ကြောင့် ကျန်းမာသော (အလုပ်လုပ်နိုင်သော) အဆင့်တစ်ခုတည်းက တောင်းဆိုမှုအားလုံးကို ယာယီရရှိသွားနိုင်သည်။
- `stickyWeightedLimit` (combo config, default `1` = off) သည် ရွေးချယ်ထားသောအဆင့်ကို အောင်မြင်မှုအကြိမ်ရေ အတိအကျအထိ ဆက်တိုက် pin လုပ်ထားပြီးမှ ပြန်လည်ရွေးချယ်သည်။

တိကျသော rotation အတွက် `round-robin` ကို အသုံးပြုပါ; `weighted` တွင် အလေးချိန်တူညီခြင်းသည် စာရင်းအင်းဆိုင်ရာ (statistical) မျှတမှုကိုသာ ပေးစွမ်းပြီး တိကျသော (strict) မျှတမှုကို မပေးပါ။

### Agentic pipeline mode

မော်ဒယ်အနည်းဆုံးနှစ်ခုပါဝင်သော `pipeline` combo တစ်ခုသည် `config.agenticOrchestration.enabled` ကို အသုံးပြု၍ planner/executor routing သို့ ရွေးချယ်ဝင်ရောက်နိုင်သည်။ ပထမဆုံး target သည် planning နှင့် နောက်ဆုံးအဖြေများကို တာဝန်ယူပြီး၊ ဒုတိယ target သည် client-native tool calls များကို ထုတ်ပေးသည်။ OmniRoute သည် request protocol မှ tool-result continuations များကို ထောက်လှမ်းပြီး၊ နောက်ထပ် tool round တစ်ခု လိုအပ်မလို planner ကို မေးမြန်းကာ၊ executor သို့မဟုတ် planner ကို client-facing နောက်ဆုံးအဆင့်အဖြစ် တက်ကြွစွာ (dynamically) သတ်မှတ်ပေးသည်။

Tool-result continuations များတွင်၊ ဆက်တိုက်ပြီးဆုံးသွားသော round နှစ်ခုသည် မပြောင်းလဲသော ရလဒ်များဖြင့် တူညီသော tool calls များကို ထပ်ခါတလဲလဲ ပြုလုပ်သည့်အခါ သို့မဟုတ် ဆက်တိုက် round နှစ်ခုတွင် အတိအလင်းဖော်ပြထားသော ရလဒ်တိုင်း ပျက်ကွက်သည့်အခါ OmniRoute သည် execution ကို ရပ်တန့်သည်။ ရလဒ်များ ပြောင်းလဲသွားပါက ထပ်ခါတလဲလဲ ခေါ်ဆိုမှုများကို ခွင့်ပြုသည် (ဥပမာ - polling)။ Guard သည် အသုံးပြုသူ၏ request အသစ်တွင် ပြန်လည်စတင်ပြီး (resets)၊ parallel calls များကို round တစ်ခုတည်းအဖြစ် စုစည်းကာ Anthropic, Chat Completions, Responses နှင့် Gemini histories တို့ကို ပံ့ပိုးပေးသည်။ Planner သည် အကြောင်းရင်းကို လက်ခံရရှိပြီး နောက်ထပ် tool round တစ်ခုကို တောင်းဆိုသော်လည်း နောက်ဆုံးအဖြေအတွက် တာဝန်ယူသည်။

ဒုတိယ target ပြီးနောက်ရှိသော နောက်ထပ်မော်ဒယ်များသည် executor backups များအဖြစ် အစဉ်လိုက်ရှိသည်။ ပျက်ကွက်သွားသော HTTP response သို့မဟုတ် transport exception သည် နောက်ထပ် executor သို့ ပြောင်းရွှေ့သွားပြီး၊ တူညီသော planner ဆုံးဖြတ်ချက်နှင့် native tools များကို သယ်ဆောင်သွားသော်လည်း ထို executor ၏ ကိုယ်ပိုင် step prompt နှင့် resolved connection ကို အသုံးပြုသည်။ ပထမဆုံး အောင်မြင်သော response ကို SSE streaming အပါအဝင် မပြောင်းလဲဘဲ ပြန်ပေးသည်။ အောင်မြင်သော stream တစ်ခု စတင်ပြီးနောက် ဖြစ်ပေါ်လာသော ပျက်ကွက်မှုများကို ဤနေရာတွင် ပြန်လည်ကြိုးစား၍ မရပါ။ Executor အားလုံး ပျက်ကွက်ပါက၊ နောက်ဆုံးဖြစ်ပေါ်သော ပျက်ကွက်မှုကို ပြန်ပေးသည်။ Client မှ ရပ်တန့်လိုက်ပါက dispatch ကို ရပ်တန့်သည်။

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Executor သည် response တစ်ခုတည်းတွင် လွတ်လပ်သော call အများအပြားကို ထုတ်ပေးနိုင်သည်။ မှီခိုနေသော (Dependent) call များကို နောက်ပိုင်း client tool-result အလှည့်များတွင် ကိုင်တွယ်ပြီး၊ planner က ရလဒ်တိုင်းကို ပြန်လည်စစ်ဆေးသည်။ `maxToolRounds` သည် default အားဖြင့် `8` ဖြစ်ပြီး `1`–`32` အထိ လက်ခံသည်။ ထိုပမာဏသို့ ရောက်ရှိပါက၊ planner သည် ရရှိနိုင်သော အကောင်းဆုံး နောက်ဆုံးအဖြေကို ထုတ်ပေးရမည်။ Internal planner ဆုံးဖြတ်ချက်များကို buffer လုပ်ထားပြီး၊ ရွေးချယ်ထားသော client-facing response သည် မူလ streaming preference ကို ထိန်းသိမ်းထားသည်။

### `round-robin` sticky batch နှင့် account expansion

Round-robin သည် batch လုပ်ထားခြင်းဖြစ်ပြီး၊ တစ်ဆင့်ချင်းစီအတွက် request တစ်ခုစီ မဟုတ်ပါ:

- `stickyRoundRobinLimit` (combo config၊ ထို့နောက် `comboStickyRoundRobinLimit`၊ ထို့နောက် `settings.stickyRoundRobinLimit`၊ default **3**) သည် rotating မလုပ်မီ ဆက်တိုက်အောင်မြင်မှုအရေအတွက်အတိုင်း target တစ်ခုတည်းကိုသာ ဆက်လက်ထားရှိသည်။ Request တစ်ခုချင်းစီအတွက် rotation ပြုလုပ်လိုပါက combo override ကို `1` ဟု သတ်မှတ်ပါ။ Combo editor သည် ထိရောက်သောတန်ဖိုး (effective value) နှင့် ၎င်းသည် မည်သည့် layer မှ လာသည်ကို ပြသသည်။
- `connectionAwareExpansion` (combo config၊ ထို့နောက် settings၊ default **false**) သည် rotation မပြုလုပ်မီ provider-level step တစ်ခုစီကို account တစ်ခုချင်းစီ၏ target များအဖြစ် ချဲ့ထွင်သည်။ Group-B strategies များ (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) သည် ဤအရာကို မဖွင့်မချင်း provider-level view ကိုသာ ထိန်းသိမ်းထားသည်။ Combo editor သည် inherit / on / off ကို ဖော်ပြပေးသည်။ inherit သည် global default (off) ကို အသုံးပြုသည်။
- Prompt-cache locality routing (`promptCacheAffinityEnabled`, default **true**) သည် pinned connections များကို ပြန်လည်စီစဉ်ပေးသဖြင့် ကိုက်ညီသော cache keys များသည် account တစ်ခုတည်းတွင် ရှိနေစေသည်။ ၎င်းသည် pinned per-account steps များတစ်လျှောက် round-robin နှင့် weighted rotation ထက် ဦးစားပေးသည်။ တိကျသော rotation လိုအပ်ပါက Settings → Combo defaults အောက်တွင် ၎င်းကို ပိတ်ထားပါ။ Per-combo override မရှိပါ။

မော်ဒယ်တစ်ခုပေါ်တွင် multi-account rotation အတွက်၊ pinned `connectionId` သုံးခုအစား sticky limit `1` ပါသော **one dynamic-account step** (empty `connectionId`, whole pool) ကို ဦးစားပေးပါ။ Pinned steps နှင့် affinity တို့သည် RR counter တိုးလာနေသော်လည်း account တစ်ခုတည်းပေါ်တွင်သာ စုစည်းနေသည်။

## Fusion မဟာဗျူဟာ

`fusion` သည် ပစ်မှတ်တစ်ခုတည်းကို **မရွေးချယ်သည့်** တစ်ခုတည်းသော မဟာဗျူဟာဖြစ်သည်။ ၎င်းသည် prompt ကို
**panel model အားလုံးထံ တစ်ပြိုင်နက်တည်း** ဖြန့်ပို့ပြီးနောက် ပြင်ဆင်သတ်မှတ်နိုင်သော **judge model** က
panel တုံ့ပြန်ချက်အားလုံးမှ နောက်ဆုံးအဖြေတစ်ခုတည်းကို ပေါင်းစပ်ထုတ်ပေးသည်။ မူရင်း `decolua/9router`
(OpenRouter ၏ Fusion ဒီဇိုင်း) မှ ပြောင်းရွှေ့ယူထားပြီး အကောင်အထည်ဖော်မှုမှာ `open-sse/services/fusion.ts` တွင်ရှိသည်။

အလုပ်လုပ်ပုံ-

0. **Tool ပါဝင်သော တောင်းဆိုမှုကို ကျော်လွှားခြင်း** — အလွတ်မဟုတ်သော `tools` array ပါဝင်ပြီး
   `tool_choice` ကို `"none"` ဟု တိတိကျကျ မသတ်မှတ်ထားသော တောင်းဆိုမှုသည် panel ကို လုံးဝကျော်သွားသည်။ ၎င်းကို
   model တစ်ခုတည်း (ပြင်ဆင်သတ်မှတ်ထားသော judge သို့မဟုတ် `panel[0]`) ထံသို့ `tools`/`tool_choice`
   ကို မပြောင်းလဲဘဲ တိုက်ရိုက်လမ်းကြောင်းပေးသည်။ Panel အဖွဲ့ဝင်များသည် tool အသုံးပြုခွင့်မရှိသည့်အပြင် judge ၏
   ပေါင်းစပ်ရေးသားမှု ညွှန်ကြားချက်က tool-call ထုတ်လွှတ်ခြင်းကို အားမပေးသောကြောင့် agentic/tool-calling client များသည်
   ပေါင်းစပ်ရေးသားထားသော စာသားအစား တကယ့် tool-call ဆုံးဖြတ်ချက်ကို ရရှိသည် (#6771)။
1. **ဖြန့်ခွဲပို့ခြင်း** (tool မပါသော တောင်းဆိုမှုများသာ) — prompt ကို panel
   model အားလုံးထံ တစ်ပြိုင်နက်တည်း ပို့ပြီး tools များကို ဖယ်ရှားကာ non-streaming ဖြစ်ရန် အတင်းသတ်မှတ်သည် (judge သည်
   ပေါင်းစပ်ရေးသားရန် စာသားအပြည့်အစုံ လိုအပ်သည်)။
2. **Quorum-grace စုဆောင်းခြင်း** — `minPanel` အဖြေများ ရောက်လာသည်နှင့် ကျန်နေသူများအတွက်
   grace timer အတိုတစ်ခု စတင်ပြီးနောက် ရရှိစုဆောင်းထားသမျှဖြင့် fusion ကို ဆက်လက်လုပ်ဆောင်သည်။
   ဤနည်းဖြင့် အနှေးဆုံး model ကြောင့် wall time တွင် ဖြစ်ပေါ်သော နှောင့်နှေးမှုကို ကန့်သတ်ပေးပြီး hard timeout ဖြင့် အမြင့်ဆုံးကန့်သတ်ထားသည်။
3. **Judge ဖြင့် ပေါင်းစပ်ရေးသားခြင်း** — panel အဖြေများကို အမည်မဖော်ဘဲ (`Source 1`, `Source 2`, … — ထို့ကြောင့်
   judge သည် model အမှတ်တံဆိပ်မဟုတ်ဘဲ အကြောင်းအရာကို အလေးထားသည်) judge ထံ လွှဲပေးသည်။ ထို့နောက် judge က
   သဘောတူညီချက် / ဆန့်ကျင်ကွဲလွဲချက်များ / တစ်စိတ်တစ်ပိုင်းသာ ခြုံငုံမိမှု / ထူးခြားသော ထိုးထွင်းသိမြင်မှုများ / မမြင်မိသော အချက်များကို ခွဲခြမ်းစိတ်ဖြာပြီး
   ယုံကြည်အားထားရသော အဖြေ **တစ်ခုတည်း** ကို ရေးသားသည်။ Judge call သည် client ၏ မူလ
   `stream` flag နှင့် tools များကို ဆက်လက်ထိန်းသိမ်းထားသောကြောင့် streaming နှင့် downstream tool အသုံးပြုမှုတို့ ဆက်လက်အလုပ်လုပ်သည်။
4. **ချောမွေ့စွာ အဆင့်လျှော့လုပ်ဆောင်ခြင်း** — panel အဖြေ 0 ခု → `503`; အဖြေ 1 ခုတည်းသာ ကျန်ရှိခြင်း → ထိုအဖြေကို
   တိုက်ရိုက်ပြန်ပေးသည် (ပေါင်းစပ်စရာမရှိပါ); model တစ်ခုတည်းပါသော panel သည် တိုက်ရိုက်ဖြေဆိုသည်။

Panel အဖွဲ့ဝင်တစ်ခုသည် အခြား combo ကို ရည်ညွှန်းသော `combo-ref` အဆင့် (`{kind: "combo-ref", comboName: "..."}`) လည်း ဖြစ်နိုင်သည် —
၎င်းကို **black-box panel အသံတစ်ခုတည်း** အဖြစ် ဖြေရှင်းသည် (ရည်ညွှန်းထားသော combo သို့ အပြည့်အဝ recursive dispatch လုပ်ခြင်းဖြစ်ပြီး
ထို combo ၏ ကိုယ်ပိုင်ပစ်မှတ်များကို ဖြန့်ခွဲပို့ခြင်းမဟုတ်ပါ)။ ထို့ပြင် အခြား combo-ref အသုံးပြုသည့် မဟာဗျူဟာတိုင်းတွင် ရှိပြီးသား
တူညီသော depth/cycle ကာကွယ်မှုကို အသုံးပြုသည် (#6764)။

### ပြင်ဆင်သတ်မှတ်မှု

Combo ၏ `config` blob တွင် ပြင်ဆင်သတ်မှတ်သည် (schema migration မလိုအပ်ပါ — ရှိပြီးသား
`combos` table ကို ပြန်လည်အသုံးပြုသည်)-

## Virtual Auto-Combo Factory

Auto Combo အင်ဂျင်သည် ကြိုတင်သတ်မှတ်ထားသော combo များကို မလိုအပ်ပါ။ ယင်းအစား `open-sse/services/autoCombo/virtualFactory.ts` သည် candidate များကို လိုအပ်သည့်အချိန်တွင် ချက်ချင်းတည်ဆောက်သည်-

1. `getProviderConnections({ isActive: true })` (ဖွင့်ထားသော connection အားလုံး) ကို ရယူသည်
2. မှန်ကန်သော credential များရှိသည့် connection များကို စစ်ထုတ်သည် (API key သို့မဟုတ် `hasUsableOAuthToken()` မှတစ်ဆင့် သက်တမ်းမကုန်သေးသော OAuth token)
3. Model ရရှိနိုင်မှုနှင့် ဈေးနှုန်းအတွက် `getProviderRegistry()` နှင့် အပြန်အလှန်တိုက်ဆိုင်စစ်ဆေးသည်
4. `(provider, model, connection)` tuple တစ်ခုစီအတွက် `VirtualAutoComboCandidate` တစ်ခု တည်ဆောက်သည်
5. Dispatch target အဖြစ် `connection.defaultModel` (သို့မဟုတ် registry ၏ ပထမဆုံး model) ကို ရွေးချယ်သည်
6. 16-factor `scorePool()` နှင့် variant ၏ weight pack ကို အသုံးပြု၍ candidate တစ်ခုစီကို အမှတ်ပေးသည်
7. `handleComboChat()` အတွက် ရရှိလာသော memory အတွင်းရှိ `AutoComboConfig` ကို ပြန်ပေးသည် — DB ထဲသို့ မည်သည့်အခါမျှ သိမ်းဆည်းထားခြင်းမရှိပါ

ဆိုလိုသည်မှာ **`auto/*` ဖွင့်ထားသော provider အသစ်တစ်ခုကို ထည့်သွင်းခြင်းသည် candidate pool ကို အလိုအလျောက်ချဲ့ထွင်ပေးသည်** — combo ကို ကိုယ်တိုင်ပြင်ဆင်ရန် မလိုအပ်ပါ။ Virtual combo ကို request တစ်ခုစီအတွက် ပြန်လည်တည်ဆောက်သောကြောင့် အသစ်ထည့်ထားသော သို့မဟုတ် ပြန်လည်ကျန်းမာလာသော connection များကို ချက်ချင်းရွေးချယ်နိုင်သည်။

## ကိုယ်တိုင်ပြန်လည်ပြုပြင်ခြင်း

- **ယာယီဖယ်ထုတ်ခြင်း**: Score < 0.2 → 5 min ကြာ ဖယ်ထုတ်မည် (တဖြည်းဖြည်းတိုးလာသော backoff၊ အများဆုံး 30 min)
- **Circuit breaker အခြေအနေကို သိရှိခြင်း**: OPEN → အလိုအလျောက်ဖယ်ထုတ်မည်၊ HALF_OPEN → စမ်းသပ် request များ
- **Incident mode**: >50% OPEN → exploration ကို ပိတ်ပြီး တည်ငြိမ်မှုကို အမြင့်ဆုံးဖြစ်စေမည်
- **Cooldown ပြီးနောက် ပြန်လည်ကောင်းမွန်ခြင်း**: ဖယ်ထုတ်မှုအပြီး ပထမဆုံး request သည် timeout လျှော့ထားသော "probe" တစ်ခုဖြစ်သည်

## Bandit Exploration

Request များ၏ 5% (ပြင်ဆင်သတ်မှတ်နိုင်သည်) ကို exploration အတွက် ကျပန်း provider များထံ လမ်းကြောင်းပြောင်းပို့သည်။ Incident mode တွင် ပိတ်ထားသည်။

## API

**`POST /api/combos/auto` endpoint သီးသန့်မရှိပါ** — Auto-Combo ကို နည်းလမ်းနှစ်မျိုးဖြင့် အသုံးပြုနိုင်သည်-

1. **Zero-config (အကြံပြုထားသည်):** `model: "auto"` သို့မဟုတ် `model: "auto/<variant>"` ပါဝင်သော မည်သည့် chat completion တောင်းဆိုချက်ကိုမဆို ပေးပို့ပါ။ Virtual factory သည် တောင်းဆိုချက်တစ်ခုချင်းစီအတွက် combo ကို တည်ဆောက်ပေးသည် — persistence မလိုပါ၊ API ခေါ်ဆိုမှုများလည်း မလိုအပ်ပါ။

2. **`strategy: "auto"` ဖြင့် Persisted combo:** `POST /api/combos` မှတစ်ဆင့် ပုံမှန် combo တစ်ခုကို ဖန်တီးပြီး `strategy: "auto"` နှင့်အတူ `config.auto.weights` / `config.auto.candidatePool` ကို သတ်မှတ်ပါ။ တူညီသော scoring engine ကို အသုံးပြုထားပြီး combo ကို `combos` တွင် သိမ်းဆည်းထားကာ ID ဖြင့် ပြန်လည်အသုံးပြုနိုင်ပါသည်။

ရှာဖွေတွေ့ရှိနိုင်စေရန်အတွက် `GET /api/combos/auto` သည် variant တစ်ခုချင်းစီကို ၎င်း၏ resolved candidate pool နှင့်အတူ `context_length` / `max_output_tokens` (candidate pool ၏ window များထဲမှ အများဆုံးတန်ဖိုး) ကို စာရင်းပြုစုပေးပါသည်။ Client များ (ဥပမာ- opencode plugin) သည် `0` အစား ဤတန်ဖိုးများကို ကြေညာပေးရပါမည်- context သုညဖြစ်နေပါက opencode ၏ auto-compaction ကို လုံးဝပိတ်ထားသကဲ့သို့ ဖြစ်စေပြီး gateway ၏ history purge မှ context ကို ဖျက်ဆီးသည်အထိ session များ တိုးပွားလာစေမည်ဖြစ်သည်။ Auto-combo context pre-filter သည် အရွယ်အစားကြီးမားသော တောင်းဆိုချက်များကို large-window candidate များထံသို့ လမ်းကြောင်းပေးသောကြောင့် MAX ကို ကြေညာခြင်းသည် ဘေးကင်းပါသည်။

### Auto router strategies

Persisted `strategy: "auto"` combos များသည် `config.routerStrategy` (သို့မဟုတ် legacy `config.auto.routerStrategy`) ကို အောက်ပါတို့ထဲမှ တစ်ခုသို့ သတ်မှတ်နိုင်သည်-

- `rules` — ပုံမှန် weighted scoring
- `score` — အမြင့်ဆုံး သတ်မှတ်ထားသော weighted score ကို ရွေးချယ်သည်။ တူညီနေပါက သတ်မှတ်ထားသော candidate အစဉ်လိုက်အတိုင်း ထိန်းသိမ်းထားမည်ဖြစ်ပြီး ရှိပြီးသား `explorationRate` သည် အဆင့်သတ်မှတ်ထားသော pool တစ်ခုလုံးမှ နမူနာယူပါမည်။
- `cost` / `eco` — အသက်သာဆုံးနှင့် ကျန်းမာသော (healthy) provider
- `latency` / `fast` — ယုံကြည်စိတ်ချရမှုဆိုင်ရာ ပြစ်ဒဏ် (reliability penalty) ပါဝင်သော အနိမ့်ဆုံး p95 latency
- `sla-aware` / `sla` — p95 latency, error-rate နှင့် ရွေးချယ်နိုင်သော cost SLO များကို ပြည့်မီသော candidate များကို ဦးစားပေးသည်
- `lkgp` — နောက်ဆုံးသိရှိထားသော ကောင်းမွန်သည့် provider ကို ဦးစားပေးသည်
- `nadir` — prompt အတွက် pool ထဲမှ မည်သည့် model လိုအပ်သည်ကို [Nadir](https://getnadir.com) ၏ decision API ကို မေးမြန်းသည်; opt-in ဖြစ်ပြီး `rules` သို့ fail-open ဖြစ်သည်

### Router strategies in detail

Auto-combo engine သည် `config.routerStrategy` (သို့မဟုတ် legacy `config.auto.routerStrategy`) မှတစ်ဆင့် သင်လဲလှယ်နိုင်သော pluggable **RouterStrategy** အကောင်အထည်ဖော်မှု ၇ ခုကို ထုတ်ဖော်ပြသထားသည်။ Strategy တစ်ခုချင်းစီသည် `RoutingContext` (task type, tool/vision hints, token estimate, ရွေးချယ်နိုင်သော SLA policy, ရွေးချယ်နိုင်သော last-known-good provider) ကို ပေးထားသည့်အခါ candidate pool မှ provider တစ်ခုကို ရွေးချယ်ပေးသည်။

#### 1. `rules` (default) — 16-factor weighted scoring

ရှိပြီးသား scoring engine ကို ထုပ်ပိုးထားသည်။ `OPEN` circuit-breaker candidate များကို စစ်ထုတ်ပြီးနောက် လက်ရှိ task type နှင့် `getTaskFitness()` ကို အသုံးပြု၍ `scorePool()` ကို လုပ်ဆောင်ကာ အမှတ်အများဆုံးရသော provider ကို ရွေးချယ်သည်။

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**အသုံးပြုရမည့်အချိန်**: ပုံမှန် (Default)။ အချက်ပြမှု (signals) အားလုံးအကြား မျှတသော အပေးအယူ (trade-off) လိုချင်သည့်အခါ အသုံးပြုပါ။

**Alias**: `rules` (alias မရှိပါ)

---

#### 2. `cost` / `eco` — အသက်သာဆုံးနှင့် ကျန်းမာသော provider

Candidate pool ကို `costPer1MTokens` (တိုးစဉ်) အလိုက် စီပြီး အသက်သာဆုံးကို ရွေးချယ်သည်။ `OPEN` candidate များကို ဦးစွာ စစ်ထုတ်သည်။

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုရမည့်အချိန်**: ကုန်ကျစရိတ်ကို အလေးထားရသော လုပ်ငန်းစဉ်များ၊ batch processing သို့မဟုတ် background jobs များအတွက်။

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — ယုံကြည်စိတ်ချရမှုဆိုင်ရာ ပြစ်ဒဏ်ပါဝင်သော အနိမ့်ဆုံး p95 latency

`p95LatencyMs + (errorRate * 1000)` အလိုက် စီသည်။ Error-rate penalty သည် ယုံကြည်စိတ်ချရမှုမရှိသော provider များ၏ nominal latency နည်းနေသော်လည်း အဆင့်နိမ့်သွားစေရန် သေချာစေသည်။

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**အသုံးပြုရမည့်အချိန်**: Real-time chat, autocomplete သို့မဟုတ် interactive coding assistants ကဲ့သို့သော latency ကို အလေးထားရသည့် လုပ်ငန်းစဉ်များအတွက်။

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO လိုက်နာမှု

Candidate တစ်ခုချင်းစီကို သတ်မှတ်ထားသော SLO policy ကို မည်မျှကောင်းမွန်စွာ ဖြည့်ဆည်းပေးနိုင်သည်အပေါ် မူတည်၍ အမှတ်ပေးသည်-

| Factor          | Weight | Formula                                           |
| --------------- | ------ | ------------------------------------------------- |
| Latency score   | 35%    | `threshold / max(value, ε)`                       |
| Error score     | 35%    | `threshold / max(value, ε)`                       |
| Health score    | 15%    | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| Cost score      | 10%    | `threshold / max(value, ε)` or inverse normalized |
| Stability score | 5%     | inverse normalized latency stddev                 |

`hardConstraints: true` ဖြစ်သည့်အခါ၊ ကိုယ်စားလှယ်လောင်းများကို **violation score** (SLO ကို မည်မျှကျော်လွန်သည်) အလိုက် ဦးစွာစီစစ်ပြီးမှ composite score အလိုက် စီစစ်သည်။ မဟုတ်ပါက composite score အလိုက်သာ စီစစ်သည်။

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA fields** (combo config တွင် သတ်မှတ်သည်):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**အသုံးပြုရမည့်အချိန်**: တင်းကျပ်သော latency၊ error-rate သို့မဟုတ် cost ဘတ်ဂျက်များရှိသည့် Production workloads များအတွက်။

**Aliases**: `sla-aware`, `sla`

---

#### 5. `lkgp` — နောက်ဆုံးသိရှိထားသော ကောင်းမွန်သည့် provider ကို ဦးစားပေးခြင်း

**နောက်ဆုံးသိရှိထားသော ကောင်းမွန်သည့် provider** (သတ်မှတ်ထားပါက) ကို ဦးစွာကြိုးစားပြီးမှ `rules` strategy သို့ ပြန်သွားသည်။ Session stickiness အတွက် အသုံးဝင်သည် — စကားပြောဆိုမှုတစ်ခုအတွင်း နောက်ဆက်တွဲတောင်းဆိုချက်များကို provider တစ်ခုတည်းကပင် ကိုင်တွယ်ပေးသည်။

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**အသုံးပြုရမည့်အချိန်**: နောက်ဆက်တွဲတောင်းဆိုချက်များကို provider တစ်ခုတည်းကပင် ကိုင်တွယ်စေလိုသော Multi-turn စကားပြောဆိုမှုများ (ဥပမာ - caching၊ context continuity သို့မဟုတ် pricing consistency အတွက်)။

**Alias**: `lkgp` (alias မရှိပါ)

---

#### 6. `nadir` — Nadir မှတစ်ဆင့် prompt-aware model ရွေးချယ်ခြင်း

အထက်ပါ strategy တိုင်းသည် ကိုယ်စားလှယ်လောင်းများကို ၎င်းတို့၏ telemetry အလိုက် အဆင့်သတ်မှတ်ကြသည်။ မည်သည့် strategy ကမျှ request ကို ဖတ်ရှုခြင်းမရှိပါ။ `nadir` သည် နောက်ဆုံး user turn နှင့် pool ၏ model id များကို [Nadir](https://getnadir.com) ၏ decision API (`POST /v1/bucket`) သို့ ပေးပို့ပြီး ထို menu မှ Nadir ရွေးချယ်သော model သို့ လမ်းကြောင်းပေးသည် (`simple` → စွမ်းဆောင်ရည်ရှိပြီး အသက်သာဆုံး model၊ `complex` → အဆင့်မြင့်ဆုံး model)။ ထို model ကို ဝန်ဆောင်မှုပေးသည့် connection ကို `rules` ကသာ ဆက်လက်ရွေးချယ်သောကြောင့် quota၊ health နှင့် cost တို့က မည်သည့် account ကို သုံးရမည်ကို ဆက်လက်ဆုံးဖြတ်ပေးသည်။

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` နှင့် `OMNIROUTE_NADIR_BASE_URL` တို့သည် ထို string နှစ်ခုအတွက် env fallbacks များဖြစ်သည်။ `baseUrl` ကို self-hosted Nadir အတွက်သာ လိုအပ်သည် (နောက်ဆုံးတွင် `/v1` ပါဝင်ခြင်းကို ခွင့်ပြုသည်)။ Key မပါသော call များသည် Nadir ၏ anonymous tier သို့ ရောက်ရှိသွားပြီး IP တစ်ခုချင်းစီအလိုက် rate-limit သတ်မှတ်ထားသည်။

Box မှ ထွက်သွားသည့်အချက်များမှာ: နောက်ဆုံး user message ၏ စာသား (ပထမဆုံး စာလုံးရေ 16k)၊ candidate model id များ နှင့် `source: "omniroute"` channel tag တို့ဖြစ်သည်။ System prompt၊ history၊ tools သို့မဟုတ် headers များ မပါဝင်ပါ။

Failure behavior သည် fail-open ဖြစ်သည်: timeout (default 2000 ms)၊ non-2xx၊ မရနိုင်သော host၊ ပုံစံမမှန်သော response သို့မဟုတ် pool ပြင်ပမှ ရွေးချယ်မှုတစ်ခုခုဖြစ်ပါက `rules` ဆုံးဖြတ်ချက်အတိုင်း လုပ်ဆောင်ပြီး အကြောင်းပြချက်ကို `NadirStrategy: fallback (…)` ဟု ရှေ့တွင် ထည့်သွင်းပေးသည်။ Call တစ်ခု ပျက်ကွက်ပြီးနောက် strategy သည် 30 စက္ကန့်ကြာ network ကို ကျော်သွားမည်ဖြစ်သောကြောင့် outage တစ်ခုသည် request တစ်ခုချင်းစီအတွက် timeout တစ်ခုအစား 30 စက္ကန့်လျှင် timeout တစ်ခုသာ ကုန်ကျမည်ဖြစ်သည်။ Routing events များသည် Nadir က တကယ်ရွေးချယ်မှသာ `strategy: "nadir"` ဟု ဖော်ပြသည်။

**အသုံးပြုရမည့်အချိန်**: Model tier အမျိုးမျိုး (small, mid နှင့် frontier model) ပါဝင်သော pool တစ်ခုတွင် mixed-difficulty traffic ရှိပြီး၊ always-frontier သည် သင်လျှော့ချလိုသော ကုန်ကျစရိတ်ဖြစ်သည့်အခါ။

**Alias**: `nadir` (alias မရှိပါ)

### Custom router strategies

သင်၏ ကိုယ်ပိုင် `RouterStrategy` implementation ကို public API မှတစ်ဆင့် မှတ်ပုံတင်နိုင်သည်:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ထို့နောက် ၎င်းကို အသုံးပြုပါ:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### Router strategy selection guide

| အသုံးပြုပုံ                   | Strategy    | အကြောင်းရင်း                                              |
| ----------------------------- | ----------- | --------------------------------------------------------- |
| မျှတသော workload              | `rules`     | Default — အချက်အားလုံးကို ထည့်သွင်းစဉ်းစားသည်             |
| ကုန်ကျစရိတ်အနည်းဆုံးဖြစ်စေရန် | `cost`      | အသက်သာဆုံးကို အမြဲရွေးချယ်သည်                             |
| Latency အနည်းဆုံးဖြစ်စေရန်    | `latency`   | အမြန်ဆုံးနှင့် ယုံကြည်စိတ်ချရသော provider ကို ရွေးချယ်သည် |
| တင်းကျပ်သော SLO များ          | `sla-aware` | p95/error/cost thresholds များဖြင့် စစ်ထုတ်သည်            |
| Multi-turn chat               | `lkgp`      | Session stickiness                                        |
| Mixed difficulty              | `nadir`     | Prompt တစ်ခုချင်းစီအလိုက် model tier ကို ရွေးချယ်သည်      |

SLA-aware fields:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## လုပ်ဆောင်ချက်နှင့် ကိုက်ညီမှု

လုပ်ဆောင်ချက်အမျိုးအစား 6 မျိုး (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) အလိုက် မော်ဒယ် 30 ကျော်ကို အမှတ်ပေးထားသည်။ Wildcard pattern များကို ပံ့ပိုးသည် (ဥပမာ၊ `*-coder` → coding အမှတ်မြင့်)။

## Auto Variant များ အကျဉ်းချုပ်

မူရင်းဖြစ်သည့် သီးသန့် `auto` နှင့် `autoPrefix.ts` တွင် ကြေညာထားသော `AutoVariant` တန်ဖိုး 6 ခုအပါအဝင်၊ **ခေါ်ယူအသုံးပြုနိုင်သော model ID 7 ခု** ရှိသည်-

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ကိုယ်တိုင်သည် တန်ဖိုး 6 ခုကို စာရင်းပြုထားသည်။ 7 ခုမြောက်ရွေးချယ်စရာမှာ "variant မရှိခြင်း" — သီးသန့် `auto` — ဖြစ်ပြီး `parseAutoPrefix()` က `variant: undefined` အဖြစ် ကိုင်တွယ်သည်။)

## အဆင့်များသည် Auto-Combo နှင့် မည်သို့ ကိုက်ညီသနည်း

အချက် 16 ချက်ပါ အမှတ်ပေးလုပ်ဆောင်ချက် (`open-sse/services/autoCombo/scoring.ts`) သည် အဆင့်အဖွဲ့ဝင်ဖြစ်မှုကို အချက်ပြမှုနှစ်ခုအဖြစ် သတ်မှတ်သည်- `tierPriority` (0.0476) နှင့် `tierAffinity` (0.0476) တို့ဖြစ်သည်။ `DEFAULT_WEIGHTS` အစုအပြည့်အစုံအတွက် အထက်ပါ စံသတ်မှတ်ထားသော [အမှတ်ပေးအချက်ဇယား](#how-it-works-persisted-auto-combos) ကို ကြည့်ပါ — pack တစ်ခုချင်းစီအလိုက် အစားထိုးသတ်မှတ်ချက်များ (ship-fast/cost-saver/quality-first/
offline-friendly) ကို "Pack တစ်ခုချင်းစီအလိုက် Weight profile များ" ဇယားတွင် ဖော်ပြထားသည်။

အဆင့်တစ်ခုတည်းကြောင့် Tier 1 ကို ဦးစွာအသုံးပြုရန် **အတင်းအကျပ် မသတ်မှတ်ပါ** — Tier 1 ၏ တုံ့ပြန်ကြာချိန် မကောင်းပါက သို့မဟုတ် ကုန်ကျစရိတ်နှင့် အရည်အသွေး အချိုးအစား မသင့်တော်ပါက Tier 2 က ရွေးချယ်ခံရမည်ဖြစ်သည်။ အဆင့်အစဉ်ကို အတင်းအကျပ်သတ်မှတ်ရန် combo မဟာဗျူဟာ `priority` ကို အသုံးပြုပြီး provider များကို အဆင့်အလိုက် စီစဉ်ပါ။

Tier 1 (subscription) ကို အထူးဦးစားပေးရန် `tierPriority` weight ကို တိုးမြှင့်ပါ-

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

အဆင့်သတ်မှတ်ချက်များနှင့် provider အမျိုးအစားခွဲခြားမှုအတွက် [`docs/guides/TIERS.md`](../guides/TIERS.md) ကို ကြည့်ပါ။

### တစ်သမတ်တည်း ရလဒ်ထွက်သည့် routing ဆုံးဖြတ်ချက် matrix (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` သည် အတုယူထားသော upstream နှင့် တကယ့် combo pipeline တစ်လျှောက် public strategy 19 ခုစလုံး၏ routing **ဆုံးဖြတ်ချက်** ကို အစမှအဆုံး အတည်ပြုသည်။
လွှမ်းခြုံမှုတွင် အောက်ပါတို့ ပါဝင်သည်-

- `ROUTING_STRATEGY_VALUES` strategy 19 ခုစလုံး (ordered, weighted, cost, context, fusion, …)။
- `quota-share` (internal) အစမှအဆုံး- တကယ့် `selectQuotaShareTarget` seam (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) မှတစ်ဆင့် DRR မျှတမှု + ပြည့်ဝနေမှုကို ဦးစားပေးမှုလျှော့ချခြင်း။
- Target အရေအတွက်တိုင်းအတွက် `context-relay` universal-handoff လွှမ်းခြုံမှု။

ဤ test suite သည် တစ်သမတ်တည်း ရလဒ်ထွက်စေရန်နှင့် live credential များ မလိုအပ်စေရန် CI (`test:integration` job) တွင် `--test-concurrency=1` နှင့်
`--test-force-exit` တို့ဖြင့် လုပ်ဆောင်သည်။

### ကန့်သတ်ချက်ဖြင့် ဖွင့်ထားသော live smoke (CI တွင် မပါဝင်ပါ — တကယ့် provider များ)

| Command                                | လုပ်ဆောင်ချက်                                                                                                      |
| :------------------------------------- | :----------------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` ဖြင့် process အတွင်း တကယ့် routing ကို လုပ်ဆောင်ပြီး live OmniRoute DB ၏ snapshot ကို ဖန်တီးသည် |
| `npm run test:combo:live:vps`          | Live OmniRoute server သို့ HTTP call များ ပြုလုပ်သည် (`COMBO_LIVE_BASE_URL` ကို သတ်မှတ်ပါ)                         |
| `npm run test:combo:live:vps:failover` | တမင်ဖန်တီးထားသော failover scenario များဖြင့် အထက်ပါအတိုင်း လုပ်ဆောင်သည်                                            |

ဤ smoke test များသည် တကယ့် wire path (combo → provider → completion) ကို စမ်းသပ်သည်။ Live credential များနှင့် VPS access လိုအပ်သောကြောင့် ၎င်းတို့ကို CI မှ ရည်ရွယ်ချက်ရှိရှိ ဖယ်ထုတ်ထားသည်။
