## مسیریابی خودکار بدون پیکربندی (پیشوند `auto/`)

> **جدید:** نیازی به ایجاد combo نیست. پیشوند `auto/` را مستقیماً در هر کلاینتی استفاده کنید.

### مثالهای سریع

| شناسه مدل      | گونه    | رفتار                                                           |
| -------------- | ------- | --------------------------------------------------------------- |
| `auto`         | پیشفرض  | همه ارائهدهندگان متصل، راهبرد LKGP، وزنهای متعادل               |
| `auto/coding`  | کدنویسی | وزنهای مبتنی بر اولویت کیفیت، مناسب برای تولید کد               |
| `auto/fast`    | سریع    | انتخاب وزندار با تأخیر کم                                       |
| `auto/cheap`   | ارزان   | مسیریابی بهینهشده از نظر هزینه (ابتدا کمترین هزینه)             |
| `auto/offline` | آفلاین  | ارائهدهندگانی با بیشترین سهمیه در دسترس را ترجیح میدهد          |
| `auto/smart`   | هوشمند  | اولویت کیفیت + نرخ کاوش بالاتر (10٪) برای کشف بهتر مدلها        |
| `auto/lkgp`    | lkgp    | LKGP صریح (همان `auto` پیشفرض)                                  |
| `auto/chaos`   | آشوب    | توزیع موازی درخواستها، یک مدل برای هر ارائهدهنده (نه تزریق خطا) |

### ترکیب دستهبندی × سطح (`auto/<category>:<tier>`)

پسوندهای سبک OpenRouter، **نوع مسیر** (دستهبندی) را از **نحوه بهینهسازی آن** (سطح) جدا میکنند تا بتوانید آزادانه آنها را ترکیب کنید (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **دستهبندیها** (مجموعه نامزدها را بر اساس قابلیت فیلتر میکنند): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. گزینههای `vision`/`multimodal` مدلهای دارای قابلیت بینایی را نگه میدارند؛ `reasoning` مدلهای استدلال/تفکر را نگه میدارد.
- **سطوح** (وزنهای امتیازدهی / فیلتر مجموعه را انتخاب میکنند): `fast` (عرضه سریع) · `cheap` (نام مستعار `floor`، صرفهجویی در هزینه) · `reliable` (سلامت مدارشکن + پایداری تأخیر) · `free` / `pro` (فیلتر کردن مجموعه بر اساس سطح مدل از طریق `classifyTier` — سطح رایگان در برابر ممتاز).

| مثال                   | نتیجه                                                                  |
| ---------------------- | ---------------------------------------------------------------------- |
| `auto/coding:fast`     | مجموعه کدنویسی، وزنهای با تأخیر کم                                     |
| `auto/coding:cheap`    | مجموعه کدنویسی، بهینهشده از نظر هزینه (نام مستعار `auto/coding:floor`) |
| `auto/reasoning:pro`   | فقط مدلهای استدلال/تفکر، سطح ممتاز                                     |
| `auto/vision`          | مدلهای دارای قابلیت بینایی (بدون سطح ← وزنهای متعادل)                  |
| `auto/multimodal:free` | مدلهای دارای قابلیت چندوجهی، فقط سطح رایگان                            |

هر الگوی معتبر `auto/<category>[:<tier>]` در لحظه تفسیر میشود؛ یک زیرمجموعه منتخب در `/v1/models` و داشبورد اعلام میشود (`AUTO_SUFFIX_VARIANTS` در `open-sse/services/autoCombo/builtinCatalog.ts`). فیلتر کردن بهصورت **fail-open** است — اگر هیچ مدل متصلی با یک محدودیت مطابقت نداشته باشد، از کل مجموعه استفاده میشود تا مسیریابی هرگز مختل نشود. امتیازدهنده اصلی (`combo.ts`) بدون تغییر باقی میماند؛ فیلتر دستهبندی/سطح در `buildAutoCandidates` اعمال میشود.

> **هوشمندی زنده مدل:** تناسب مسیریابی خودکار، هنگامی که پرچم `ARENA_ELO_SYNC_ENABLED` روشن باشد، از رتبهبندیهای زنده **Arena ELO** و دادههای سطح **models.dev** استفاده میکند (در غیر این صورت به نگاشت ایستای تناسب بازمیگردد).

**نحوه استفاده:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**چه اتفاقی میافتد:**

1. OmniRoute پیشوند `auto/` را در `src/sse/handlers/chat.ts` تشخیص میدهد
2. همه **اتصالهای فعال ارائهدهندگان** را از پایگاه داده واکشی میکند
3. مواردی را نگه میدارد که اعتبارنامه معتبر دارند (کلید API یا توکن OAuth)
4. مدل هر اتصال را تعیین میکند (`connection.defaultModel` یا اولین مدل ارائهدهنده)
5. یک **combo مجازی** در حافظه میسازد (در DB ذخیره نمیشود)
6. با استفاده از پروفایل وزن گونه انتخابشده + راهبرد LKGP مسیریابی میکند

**ویژگیهای کلیدی:**

- ✅ **همیشه فعال:** بدون نیاز به کلید تغییر وضعیت، ایجاد combo یا پیکربندی
- ✅ **پویا:** ارائهدهندگان متصل فعلی را بهطور خودکار منعکس میکند
- ✅ **چسبندگی نشست:** LKGP تضمین میکند آخرین ارائهدهنده موفق در اولویت قرار گیرد
- ✅ **آگاه از چند حساب:** هر اتصال ارائهدهنده به یک نامزد جداگانه تبدیل میشود
- ✅ **بدون نوشتن در DB:** combo مجازی فقط برای همان درخواست وجود دارد و سربار ماندگاری آن صفر است

### کنترل نامزدها بهازای هر کلید (#7819، سطح 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = پسوند پس از `auto/`، یا
مقدار لفظی `auto` برای کانال پایه) یک نقطه پایانی **فقط خواندنی** است که مجموعه
نامزدهای فعلی یک کانال `auto/*` را همراه با دسترسپذیری زنده فهرست میکند و
خواندنهای موجود تابآوری را مجدداً بهکار میگیرد (و هرگز `state` خام مدارشکن را نمیخواند):

- مدارشکن ارائهدهنده — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- دوره انتظار اتصال — `rateLimitedUntil` / `testStatus` در ردیف تفسیرشده
  `provider_connections`
- قفل مدل — `isModelLocked(provider, connectionId, model)`

هر نامزد همچنین پرچم `excluded` مربوط به این کلید API را دربر دارد. استثناها
بهازای هر کلید API ذخیره میشوند (جدول `auto_candidate_overrides`، مهاجرت `128`) — OmniRoute
تکمستأجری است و جدول `users` ندارد، بنابراین `apiKeyId` نزدیکترین هویت واقعی
بهازای هر فراخواننده است — و در گلوگاه مجموعه نامزدها در
`open-sse/services/autoCombo/virtualFactory.ts` از طریق تابع خالص و آزمونشده با تست واحد
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`)
اعمال میشوند. این فیلتر بهصورت **fail-open** است: تنظیم نبودن apiKeyId/channel یا شکست
در جستوجوی DB، هر دو مجموعه را بدون فیلتر باقی میگذارند؛ بنابراین اپراتوری که هیچ
نادیدهگیریای برایش پیکربندی نشده باشد، مسیریابیای کاملاً یکسان در سطح بایت با پیش از
این قابلیت مشاهده میکند.

**به یک ایشوی پیگیری موکول شد:** وزندهی به هر کاندیدا + ترتیبدهی صریح (سطح 3
— به مسیرهای راهبرد وزندار/اولویتدار موجود وارد میشود) و پینکردن یک راهبرد مشخص
`combo.ts` برای هر کانال `auto/*` (سطح 4). برای پرسش باز دربارهٔ اینکه با توجه به
مدل تکمستأجری، بازنویسیها باید بهازای هر کلید API باقی بمانند یا سراسری شوند،
به برنامهٔ #7819 مراجعه کنید.

**پشت صحنه:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**فایلهای پیادهسازی:**

| فایل                                                      | هدف                                          |
| --------------------------------------------------------- | -------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | تجزیهکنندهٔ پیشوند (`parseAutoPrefix`)       |
| `open-sse/services/autoCombo/virtualFactory.ts`           | اشیای مجازی `AutoComboConfig` را ایجاد میکند |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | هوک تست برای شبیهسازی رجیستری ارائهدهندگان   |
| `src/sse/handlers/chat.ts`                                | یکپارچهسازی: میانبُر پیشوند خودکار           |
| `src/shared/constants/providers.ts`                       | ورودی سیستمی `SYSTEM_PROVIDERS.auto`         |

## نامهای Combo که با شناسه یک مدل واقعی مطابقت دارند

یک combo که `name` آن با شناسه بدون پیشوند یک مدل یکسان است (برای مثال، comboای با نام
`gpt-5.5`)، یک **الگوی عمدی و پشتیبانیشده** است، نه یک باگ: این همان
سازوکار بازگشت به ارائهدهنده جایگزین برای هر شناسه مدل است که در
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) مستند شده است. از آنجا که
تفکیک combo پیش از تفکیک شناسه بدون پیشوند مدل بررسی میشود
(`getComboForModel()` در `src/sse/services/model.ts`)، درخواست برای شناسه بدون پیشوند
`gpt-5.5` بهجای اینکه مستقیماً به یک ارائهدهنده واحد هدایت شود، از طریق
مقصدهای combo (برای مثال،
`acme-responses/gpt-5.5` و `backup-responses/gpt-5.5`) مسیریابی میشود — این رفتار
از اولویت combo پیش از بازنویسی که برای
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) ساخته شده بود
دوباره استفاده میکند و در برابر رگرسیون توسط `tests/unit/responses-combo-resolution-3227.test.ts` و
`tests/unit/combo-name-codex-responses-rewrite.test.ts` آزمایش میشود.

ایجاد یا تغییر نام یک combo به نامی که شناسه یک مدل واقعی را تحتالشعاع قرار میدهد
**هرگز رد نمیشود** — انجام این کار گردشکار مستندشده را مختل میکند. در عوض
(#8530)، `POST /api/combos` و `PUT /api/combos/[id]` هنگامی که نام (جدید) با شناسه
یک مدل واقعی تداخل داشته باشد، یک فیلد غیرمسدودکننده `warning` به پاسخ اضافه
میکنند:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

هنگام راهاندازی، `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) همچنین یک هشدار تکخطی `[STARTUP]` ثبت میکند که
تمام comboهای موجودی را که یک شناسه مدل را تحتالشعاع قرار میدهند فهرست میکند؛
در نتیجه، اپراتورهایی که بهطور تصادفی با این وضعیت روبهرو شدهاند (و نه بهصورت
عمدی، مطابق #6940)، نشانهای برای تشخیص آن خواهند داشت.
تابع کمکی تشخیص در `src/lib/combos/modelNameCollision.ts` قرار دارد.

## فراخوانی یک Combo سفارشی از یک کلاینت

comboهای ذخیرهشده (Settings → Combos) فقط زمانی استفاده میشوند که کلاینت **نام دقیق** combo را در فیلد `model` ارسال کند — هیچ تطبیق مبهم یا جزئی برای نام combo انجام نمیشود و پیشوند `auto/` نیز در کار نیست. ترتیب تفکیک (`getComboForModel()` در `src/sse/services/model.ts`):

1. تطبیق دقیق نام combo (`model: "my-combo"`)،
2. پیشوند `combo/<name>` (`model: "combo/my-combo"`)،
3. نگاشتهای glob از مدل به combo (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

دو اشتباه رایج:

- **`auto` از comboهای شما استفاده نمیکند.** `auto`/`auto/*` مجموعه کاندیداهای بدون نیاز به پیکربندی خودش را ایجاد میکند و تنها در صورتی comboهای ذخیرهشده را بررسی میکند که یک combo دقیقاً `auto` نام داشته باشد (توصیه نمیشود). برای مسیریابی از طریق یک combo، نام دقیق آن را ارسال کنید — نه `auto`.
- **`openrouter/auto` یک محصول واقعی و پولی OpenRouter است** ("Auto Best Available")، نه یک نام مستعار OmniRoute. این مورد، تنها ورودی مدل ایستای رجیستری OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) است و هزینه آن جداگانه محاسبه میشود. برای حذف آن از مجموعههای `auto`، از Settings → Routing → Hide paid models استفاده کنید.

برای سردرگمی اولیهای که این بخش مستند میکند، به [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) و [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) مراجعه کنید.

## نحوه کارکرد (Auto-Combos پایدار / Persisted)

موتور Auto-Combo Engine با استفاده از یک **تابع امتیازدهی ۱۶ عاملی** (تعریف‌شده در `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`) به‌صورت پویا بهترین ارائه‌دهنده/مدل (provider/model) را برای هر درخواست انتخاب می‌کند. مجموع وزن‌های پیش‌فرض برابر با `1.0` است؛ وزن‌های سفارشی توسط `normalizeScoringWeights()` بازتنظیم (renormalize) می‌شوند. دو عامل از شانزده عامل — `cacheAffinity` و `resetWindowAffinity` — دارای وزن پیش‌فرض `0` هستند؛ `reliability` در `DEFAULT_WEIGHTS` مقدار `0` دارد اما در بسته‌های عمومی (generic packs) مقدار `0.03` و در `reliability-first` مقدار `0.04` دارد، و `quality` در بسته‌ها مقدار `0.02` (در `quality-first` مقدار `0.03`) را حمل می‌کند: این عوامل همچنان برای هر کاندیدا محاسبه می‌شوند، و `cacheAffinity` عمل یکسان‌سازی کش پرامپت (prompt-cache deduplication) را در خارج از امتیاز کنترل می‌کند، بنابراین عوامل با پیش‌فرض صفر صرفاً به‌طور پیش‌فرض رأی نمی‌دهند در حالی که بسته‌ها رأی می‌دهند.

> **سهمیه غیرقابل خواندن (#15347).** هنگامی که یک ارائه‌دهنده دارای واکِش‌گر سهمیه (quota fetcher) است اما هیچ چیز
> قابل خواندنی را برنمی‌گرداند (واکِشی ناموفق، اعتبارنامه‌های مفقود، میزان مصرف فقط-پیامی، یا یک اسنپ‌شات بدفرم فاقد
> `windows` قابل تجزیه و بدون `percentUsed` متناهی، از جمله `percentUsed: null`)، کاندید
> در محور `quota` امتیاز `0` می‌گیرد و امتیاز نهایی آن در
> `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (برابر با 0.5 در `autoStrategy.ts`) ضرب می‌شود؛ یعنی همان الگوی جریمه
> غیراجباری (soft-penalty) مشابه جریمه وضعیت اتصال (connection-status). خواندن ناموفقِ مصرف، شاهدی درباره تله‌متری است
> و نه خود ارائه‌دهنده؛ بنابراین اکیداً پایین‌تر از هر نوع خواندن واقعی، از جمله یک خواندن ۱۰۰٪ مصرف‌شده تأییدشده رتبه‌بندی می‌شود،
> اما هرگز به‌صورت قطعی مسدود یا اخراج نمی‌شود. ارائه‌دهنده‌ای که سقفی ندارد، `unlimited: true` را گزارش می‌کند و
> امتیاز سهمیه کامل را می‌گیرد؛ ارائه‌دهنده‌ای هم که واکِش‌گر سهمیه ثبت‌شده‌ای ندارد، هیچ منبع تله‌متری در اصل ندارد
> و مقدار پیش‌فرض `100` را حفظ می‌کند.

**مجموع:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` همان‌طور که در `DEFAULT_WEIGHTS` اعلام شده است؛ وزن‌های پیکربندی‌شده توسط کاربر پیش از امتیازدهی توسط `normalizeScoringWeights()` مجدداً به صورت یک توزیع نرمال‌سازی می‌شوند.

### کنترلهای هر درخواست (هدرها) — #6023 / #6024 / #6025 / #3470

| `X-OmniRoute-Budget-Fallback` | `cheapest` (پیشفرض، نامهای مستعار: `cheapest-viable`، `soft`) یا `strict` (نامهای مستعار: `block`، `hard`)                                                                                             | `cheapest`: حتی اگر گزینه همچنان از سقف هزینه فراتر برود، به ارزانترین گزینه در کل بازمیگردد (رفتار قدیمی). `strict`: از انتخاب خودداری میکند — درخواست بهجای هزینهکرد بیسروصدا و بیشازحد، بلافاصله با `HTTP 402` شکست میخورد. مقادیر ناشناخته نادیده گرفته میشوند.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `X-OmniRoute-Effort`          | `auto` (سایر مقادیر رزرو شدهاند)                                                                                                                                                                       | بودجهٔ تفکر تطبیقی: وقتی درخواست **هیچ** فیلد استدلالی با هیچ ساختاری (`reasoning_effort`، `reasoning`، `thinking`) نداشته باشد، درگاه مقدار `auto` را بر اساس سیگنالهای قطعیِ ساختار درخواست (طول آخرین پیام کاربر، اندازهٔ زمینه تا آخرین پیام کاربر، نتایج قبلی ابزارها، عمق حلقهٔ ابزار) به `low`/`medium`/`high` تبدیل میکند. سیگنالها به نوبت جاری محدود میشوند — هر چیزی پس از آخرین پیام کاربر نادیده گرفته میشود — بنابراین هر درخواست در یک حلقهٔ ابزار به سطح یکسانی تبدیل میشود (تثبیت بدونحالت در هر نوبت، بدون وضعیت نشست و بدون افزایش سطح در میانهٔ حلقه که پیشوندهای کش پرامپت بالادستی را مختل کند). فیلد استدلال صریح کلاینت همیشه اولویت دارد. این رفتار محدود به درخواستهایی است که ارسال بالادستی آنها به ساختار OpenAI Chat Completions تبدیل میشود (`targetFormat === FORMATS.OPENAI`) — `reasoning_effort` فیلدی با ساختار OpenAI است، بنابراین این هدر در درخواستهای مقصد Claude یا Gemini هیچ اثری ندارد (به `open-sse/handlers/chatCore/adaptiveEffortWiring.ts` مراجعه کنید). |

```bash
# Force the fastest profile, cap this request at $0.05, and hard-block instead of overspending
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OmniRoute-Mode: fast" \
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

تفکیک مقادیر یک تابع خالص است (`open-sse/services/autoCombo/requestControls.ts`)؛
مقادیر تفکیکشده به ورودیهای موجود `config.modePack` / `config.budgetCap` /
`config.budgetFallback` موتور داده میشوند. مقدار ذخیرهشدهٔ `config.budgetFallback` در یک ترکیب ("strict" |
"cheapest") خطمشی پایدار را تعیین میکند؛ هدر آن را برای یک درخواست منفرد بازنویسی میکند.

## تمام استراتژی‌های مسیریابی

موتور ترکیبی OmniRoute از **۲۰ استراتژی مسیریابی** پشتیبانی می‌کند (که در `src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES` تعریف شده‌اند). خود موتور Auto Combo تحت استراتژی `auto` در دسترس است؛ سایر استراتژی‌ها برای ترکیب‌های پایدار (persisted combos) موجود هستند.

| استراتژی            | توضیحات                                                                                                                                                                                            |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `priority`          | لیست مرتب‌شده‌ی اولین هدف با اولویت صریح                                                                                                                                                           |
| `weighted`          | تصادفی وزن‌دار بر اساس وزن هر هدف                                                                                                                                                                  |
| `round-robin`       | چرخش بین اهداف به ترتیب (دسته‌ای؛ در ادامه ببینید)                                                                                                                                                 |
| `context-relay`     | انتقال زمینه (context) بین اهداف (مکالمات طولانی)                                                                                                                                                  |
| `fill-first`        | پر کردن سهمیه هر هدف قبل از رفتن به هدف بعدی                                                                                                                                                       |
| `p2c`               | متعادل‌سازی بار تصادفی با انتخاب از بین دو گزینه (Power-of-2-choices)                                                                                                                              |
| `random`            | انتخاب تصادفی یکنواخت                                                                                                                                                                              |
| `least-used`        | انتخاب هدفی که کمترین بار فعلی را دارد                                                                                                                                                             |
| `cost-optimized`    | بهینه‌سازی هزینه: به حداقل رساندن دلار به ازای هر درخواست با توجه به قیمت‌گذاری کاتالوگ                                                                                                            |
| `reset-aware` ⭐    | اولویت‌بندی بر اساس زمان بازنشانی سهمیه — پنجره‌های بازنشانی کوتاه‌تر رتبه بالاتری دارند                                                                                                           |
| `reset-window`      | ترجیح اهدافی که پنجره سهمیه آن‌ها زودتر بازنشانی می‌شود                                                                                                                                            |
| `headroom`          | انتخاب هدفی که بیشترین فضای سهمیه باقی‌مانده را دارد                                                                                                                                               |
| `quota-weighted`    | پرش از حساب‌های تمام‌شده، سپس انتخاب از بین بقیه به نسبت سهمیه باقی‌مانده تقسیم بر بار در حال اجرا؛ مکالمات موجود پین‌شده باقی می‌مانند                                                            |
| `strict-random`     | تصادفی بدون حذف تکرارها                                                                                                                                                                            |
| `auto`              | استفاده از امتیازدهی Auto Combo (۱۶ عاملی) — **توصیه‌شده**                                                                                                                                         |
| `lkgp`              | مسیر آخرین وضعیت خوب (به آخرین ارائه‌دهنده موفق پین می‌شود، سپس به قوانین بازمی‌گردد)                                                                                                              |
| `context-optimized` | انتخاب هدفی که بهترین تناسب را با اندازه زمینه فعلی دارد                                                                                                                                           |
| `cache-optimized`   | مرتب‌سازی مجدد اهداف بر اساس قرابت کش پرامپت — اتصالی که احتمال بیشتری دارد پیشوند کش‌شده این درخواست را داشته باشد، ابتدا امتحان می‌شود (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | پخش کردن بین گروهی از مدل‌ها به صورت موازی، سپس ترکیب یک پاسخ از طریق یک داور (در ادامه ببینید)                                                                                                    |
| `pipeline`          | اجرای متوالی اهداف، انتقال خروجی هر مرحله به ورودی مرحله بعد؛ فقط پاسخ نهایی بازگردانده می‌شود (#6396)                                                                                             |

⭐ = جدید در v3.8.0 · 🧬 = جدید در v3.8.36

### معناشناسی `weighted`

`weighted` یک **قرعه‌کشی تصادفی متناسب برای هر درخواست** است
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، نه یک متعادل‌کننده:

- هر درخواست **یک** مرحله را با احتمال `weight / totalWeight` انتخاب می‌کند؛ مراحل باقی‌مانده به ترتیب نزولی وزن به عنوان زنجیره بازگشت (fallback) برای آن درخواست مرتب می‌شوند.
- مرحله‌ای که وزن آن `0` (یا ناموجود) است، **هرگز انتخاب نمی‌شود** در حالی که مرحله دیگری با وزن > 0 وجود دارد — این مرحله فقط می‌تواند به عنوان بازگشت (fallback) پس از شکست مرحله انتخاب‌شده عمل کند. تنها زمانی که **تمام** وزن‌ها 0 باشند، انتخاب یکنواخت می‌شود.
- مراحلی که اهداف آن‌ها در دسترس نیستند — مدارشکن ارائه‌دهنده `OPEN`، دوره خنک‌سازی اتصال، قفل شدن مدل — قبل از انجام قرعه‌کشی از آن حذف می‌شوند
  (`open-sse/services/combo/targetResolution.ts`)، بنابراین یک مرحله سالم می‌تواند به طور موقت در هر درخواست برنده شود.
- `stickyWeightedLimit` (پیکربندی combo، پیش‌فرض `1` = خاموش) مرحله انتخاب‌شده را برای آن تعداد موفقیت متوالی پین می‌کند تا دوباره قرعه‌کشی انجام شود.

برای چرخش دقیق از `round-robin` استفاده کنید؛ وزن‌های برابر در `weighted` تعادل آماری — نه دقیق — ایجاد می‌کنند.

### حالت خط لوله (pipeline) عاملی

یک ترکیب `pipeline` با حداقل دو مدل می‌تواند با استفاده از `config.agenticOrchestration.enabled` مسیریابی برنامه‌ریز/اجراکننده (planner/executor) را انتخاب کند. هدف اول مسئول برنامه‌ریزی و پاسخ‌های نهایی است؛ هدف دوم فراخوانی‌های ابزار بومی کلاینت را صادر می‌کند. OmniRoute ادامه نتایج ابزار را از پروتکل درخواست تشخیص می‌دهد، از برنامه‌ریز می‌پرسد که آیا دور دیگری از ابزار نیاز است یا خیر، و به‌صورت پویا یا اجراکننده یا برنامه‌ریز را به عنوان گام نهایی رو به کلاینت تعیین می‌کند.

قابلیت اختیاری `config.agenticOrchestration.contextCompaction` یک بودجه محتوای (payload) جداگانه را قبل از هر ارسال برنامه‌ریز یا اجراکننده اعمال می‌کند. آن را به‌طور صریح فعال کنید:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

این‌ها بودجه‌های کاراکتری JSON سریال‌شده هستند که توسط اپراتور انتخاب می‌شوند، نه پنجره‌های کانتکست توکن یا محدودیت‌های تضمین‌شده بالادستی. شناسه‌های دقیق مدل، پیش‌فرض را لغو می‌کنند. بالاتر از آستانه، فشرده‌سازی تعاریف ابزار یکسان را حذف می‌کند، شواهد ابزار بیش از حد بزرگ را با یک خلاصه (digest) کوتاه می‌کند، و گروه‌های تاریخچه کامل قدیمی را به سمت نسبت هدف حذف می‌کند. این قابلیت دستورالعمل‌های سیستم/توسعه‌دهنده، آخرین درخواست کاربر، آخرین دور ابزار شامل فراخوانی‌ها/نتایج موازی، و دستورالعمل مسیریابی پیشرو Gemini را حفظ می‌کند. دستورالعمل‌های سطح بالا و تنظیمات ابزار حفظ می‌شوند. یک نشانگر حذف، تاریخچه حذف‌شده را ثبت می‌کند؛ این یک کوتاه کردن قطعی (deterministic) است، نه یک خلاصه‌سازی معنایی. اگر کانتکست پین‌شده همچنان از بودجه فراتر رود، درخواست قبل از تماس با مدل، خطای 413 برمی‌گرداند. با غیرفعال بودن فشرده‌سازی یا پایین‌تر بودن از آستانه، درخواست بدون تغییر عبور می‌کند.

مدل‌های اضافی بعد از هدف دوم، پشتیبان‌های اجراکننده مرتب‌شده هستند. یک پاسخ HTTP ناموفق یا استثنای انتقال، به اجراکننده بعدی منتقل می‌شود، که همان تصمیم برنامه‌ریز و ابزارهای بومی را حمل می‌کند اما پرامپت گام و اتصال حل‌شده مختص همان اجراکننده را دارد. اولین پاسخ موفق بدون تغییر برگردانده می‌شود، شامل استریمینگ SSE؛ شکست‌ها پس از شروع یک استریم موفق در اینجا قابل بازتلاش نیستند. اگر همه اجراکننده‌ها شکست بخورند، آخرین شکست برگردانده می‌شود. لغوهای کلاینت، ارسال را متوقف می‌کنند.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

اجراکننده ممکن است چندین فراخوانی مستقل را در یک پاسخ صادر کند. فراخوانی‌های وابسته در دورهای بعدی نتیجه ابزار کلاینت مدیریت می‌شوند، و برنامه‌ریز هر نتیجه را بررسی می‌کند. مقدار پیش‌فرض `maxToolRounds` برابر با `8` است و مقادیر `1` تا `32` را می‌پذیرد؛ پس از رسیدن به این مقدار، برنامه‌ریز باید بهترین پاسخ نهایی موجود را تولید کند. تصمیمات داخلی برنامه‌ریز بافر می‌شوند، در حالی که پاسخ انتخاب‌شده رو به کلاینت، ترجیح استریمینگ اصلی را حفظ می‌کند.

### دسته‌بندی چسبنده (sticky batch) و گسترش حساب `round-robin`

Round-robin به‌صورت دسته‌ای است، نه یک درخواست در هر گام:

- `stickyRoundRobinLimit` (پیکربندی ترکیب، سپس `comboStickyRoundRobinLimit`، سپس `settings.stickyRoundRobinLimit`، پیش‌فرض **3**) همان هدف را برای آن تعداد موفقیت متوالی قبل از چرخش حفظ می‌کند. برای چرخش یک-درخواست، لغو (override) ترکیب را روی `1` تنظیم کنید. ویرایشگر ترکیب، مقدار مؤثر و لایه‌ای که از آن آمده است را نشان می‌دهد.
- `connectionAwareExpansion` (پیکربندی ترکیب، سپس تنظیمات، پیش‌فرض **false**) هر گام در سطح ارائه‌دهنده را قبل از چرخش به اهدافِ هر-حساب گسترش می‌دهد. استراتژی‌های گروه B (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) تا زمانی که این گزینه روشن نباشد، دیدگاه سطح ارائه‌دهنده را حفظ می‌کنند. ویرایشگر ترکیب گزینه‌های inherit / on / off را نمایش می‌دهد؛ inherit از پیش‌فرض جهانی (off) استفاده می‌کند.
- مسیریابی محلی‌سازی کش پرامپت (`promptCacheAffinityEnabled`، پیش‌فرض **true**) اتصالات پین‌شده را دوباره مرتب می‌کند تا کلیدهای کش منطبق روی یک حساب باقی بمانند. این گزینه بر چرخش round-robin و weighted در گام‌های پین‌شده‌ی هر-حساب اولویت دارد. اگر به چرخش دقیق نیاز دارید، آن را در Settings → Combo defaults خاموش کنید. هیچ لغو (override) برای هر ترکیب وجود ندارد.

برای چرخش چند-حسابی روی یک مدل، **یک گام حساب پویا** (بدون `connectionId`، کل استخر) با محدودیت چسبندگی `1` را ترجیح دهید، نه سه `connectionId` پین‌شده. گام‌های پین‌شده به همراه affinity روی همان حساب فرو می‌پاشند (collapse)، حتی زمانی که شمارنده RR پیش می‌رود.

## راهبرد Fusion

`fusion` تنها راهبردی است که یک مقصد واحد را انتخاب **نمیکند**. این راهبرد پرامپت را بهصورت
موازی به **تمام مدلهای پنل** ارسال میکند و سپس یک **مدل داور** قابلپیکربندی، از همه پاسخهای
پنل یک پاسخ نهایی واحد میسازد. این قابلیت از `decolua/9router` بالادستی
(طراحی Fusion متعلق به OpenRouter) منتقل شده است؛ پیادهسازی آن در `open-sse/services/fusion.ts` قرار دارد.

نحوه کار:

0. **عبور مستقیم درخواستهای دارای ابزار** — درخواستی که یک آرایه غیرخالی `tools` داشته باشد و
   مقدار `tool_choice` آن صراحتاً `"none"` نباشد، پنل را کاملاً کنار میگذارد: درخواست مستقیماً به
   یک مدل واحد (داور پیکربندیشده یا `panel[0]`) هدایت میشود و `tools`/`tool_choice`
   بدون تغییر عبور داده میشوند. اعضای پنل به ابزارها دسترسی ندارند و دستورالعمل
   ترکیب پاسخِ داور، تولید فراخوانی ابزار را منع میکند؛ بنابراین کلاینتهای عاملی/فراخواننده ابزار
   بهجای متن ترکیبشده، یک تصمیم واقعی برای فراخوانی ابزار دریافت میکنند (#6771).
1. **ارسال همزمان** (فقط برای درخواستهای بدون ابزار) — پرامپت بهطور همزمان به همه مدلهای
   پنل ارسال میشود؛ حالت غیرجریانی بهاجبار فعال و ابزارها حذف میشوند (داور برای ترکیب پاسخ
   به متن کامل نیاز دارد).
2. **گردآوری با حد نصاب و مهلت** — بهمحض رسیدن `minPanel` پاسخ، یک زمانسنج کوتاه برای
   مدلهای عقبمانده آغاز میشود؛ سپس Fusion با هر تعداد پاسخی که گردآوری شده است ادامه میدهد.
   این کار تأثیر کندترین مدل بر زمان سپریشده را محدود میکند و یک مهلت نهایی سخت نیز آن را
   کراندار نگه میدارد.
3. **ترکیب توسط داور** — پاسخهای پنل ناشناسسازی میشوند (`Source 1`، `Source 2`، … — تا
   داور محتوا را بسنجد، نه برند مدل) و در اختیار داور قرار میگیرند. داور توافقها /
   تناقضها / پوشش ناقص / بینشهای منحصربهفرد / نقاط کور را تحلیل میکند و سپس
   **یک** پاسخ معتبر مینویسد. فراخوانی داور، پرچم اصلی `stream` کلاینت و ابزارها را
   حفظ میکند؛ بنابراین پخش جریانی و استفاده پاییندستی از ابزارها همچنان کار میکنند.
4. **افت تدریجی و کنترلشده** — ۰ پاسخ پنل ← `503`؛ دقیقاً ۱ پاسخ باقیمانده ← همان پاسخ
   مستقیماً برگردانده میشود (چیزی برای ترکیب وجود ندارد)؛ پنلی با یک مدل نیز مستقیماً پاسخ میدهد.

یکی از اعضای پنل میتواند یک مرحله `combo-ref` نیز باشد (`{kind: "combo-ref", comboName: "..."}`) که
به ترکیب دیگری ارجاع میدهد — این مرحله بهعنوان **یک صدای مستقل و جعبهسیاه در پنل** حل میشود
(یک ارسال بازگشتی کامل به ترکیب مورد ارجاع، نه ارسال همزمان به مقصدهای خود آن ترکیب)، با همان
محافظت در برابر عمق/چرخه که همه راهبردهای دیگرِ مصرفکننده combo-ref از آن استفاده میکنند (#6764).

### پیکربندی

پیکربندی در داده `config` ترکیب انجام میشود (بدون مهاجرت طرحواره — از جدول موجود
`combos` دوباره استفاده میکند):

| فیلد                                     | نوع      | پیشفرض        | هدف                                                                             |
| :--------------------------------------- | :------- | :------------ | :------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | اولین مدل پنل | مدلی که پاسخ نهایی را ترکیب میکند                                               |
| `config.fusionTuning.minPanel`           | `number` | `2`           | تعداد پاسخهای موفق لازم پیش از شروع زمانسنج مهلت (محدودشده به `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`        | مدت انتظار برای مدلهای عقبمانده پس از رسیدن به حد نصاب                          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`       | سقف مطلق برای جلوگیری از اینکه یک مدل متوقفشده، درخواست را معطل کند             |

مقادیر پیشفرض در `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) قرار دارند.

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

سپس آن را مانند هر ترکیب دیگری فراخوانی کنید: `{"model":"fusion-panel","messages":[...]}`.

## کارخانهٔ مجازی Auto-Combo

موتور Auto Combo به کمبوهای ازپیشتعریفشده نیازی ندارد. در عوض، `open-sse/services/autoCombo/virtualFactory.ts` کاندیداها را بهصورت پویا میسازد:

1. `getProviderConnections({ isActive: true })` را دریافت میکند (همهٔ اتصالهای فعال)
2. مواردی را که اعتبارنامهٔ معتبر دارند فیلتر میکند (کلید API یا توکن OAuth منقضینشده از طریق `hasUsableOAuthToken()`)
3. برای بررسی دسترسپذیری مدل و قیمتگذاری، آنها را با `getProviderRegistry()` تطبیق میدهد
4. برای هر سهتایی `(provider, model, connection)`، یک `VirtualAutoComboCandidate` میسازد
5. `connection.defaultModel` (یا اولین مدل رجیستری) را بهعنوان مقصد ارسال انتخاب میکند
6. هر کاندیدا را با استفاده از `scorePool()` شانزدهعاملی و بستهٔ وزن آن واریانت امتیازدهی میکند
7. `AutoComboConfig` حاصل را که در حافظه قرار دارد، برای `handleComboChat()` برمیگرداند — و هرگز آن را در DB ذخیره نمیکند

این یعنی **افزودن یک ارائهدهندهٔ جدید که `auto/*` برای آن فعال است، بهطور خودکار مجموعهٔ کاندیداها را گسترش میدهد** — و نیازی به ویرایش دستی کمبو نیست. کمبوی مجازی برای هر درخواست از نو ساخته میشود، بنابراین اتصالهایی که بهتازگی اضافه شدهاند یا دوباره سالم شدهاند، بلافاصله در نظر گرفته میشوند.

## خودترمیمی

- **حذف موقت**: امتیاز < 0.2 ← حذف بهمدت ۵ دقیقه (عقبنشینی تدریجی، حداکثر ۳۰ دقیقه)
- **آگاهی از قطعکنندهٔ مدار**: OPEN ← حذف خودکار؛ HALF_OPEN ← درخواستهای آزمایشی
- **حالت رخداد**: بیش از ۵۰٪ OPEN ← غیرفعالکردن کاوش و بهحداکثررساندن پایداری
- **بازیابی پس از دورهٔ انتظار**: پس از پایان حذف، اولین درخواست یک «آزمایش» با زمانانتظار کاهشیافته است

## کاوش Bandit

۵٪ از درخواستها (قابل پیکربندی) برای کاوش به ارائهدهندگان تصادفی هدایت میشوند. این قابلیت در حالت رخداد غیرفعال است.

## API

هیچ **اندپوینت اختصاصی `POST /api/combos/auto`** وجود ندارد — Auto-Combo به دو روش مصرف می‌شود:

۱. **بدون پیکربندی (توصیه شده):** هر درخواست تکمیل چت (chat completion) را با `model: "auto"` یا `model: "auto/<variant>"` ارسال کنید. کارخانه مجازی (virtual factory) کامبو را برای هر درخواست می‌سازد — بدون نیاز به ماندگاری (persistence) یا فراخوانی‌های API.

۲. **کامبوی ماندگار با `strategy: "auto"`:** یک کامبوی معمولی از طریق `POST /api/combos` ایجاد کنید و `strategy: "auto"` را به همراه `config.auto.weights` / `config.auto.candidatePool` تنظیم کنید. از همان موتور امتیازدهی استفاده می‌شود؛ کامبو در `combos` ذخیره شده و با استفاده از ID قابل استفاده مجدد است.

برای کشف (discovery)، `GET /api/combos/auto` هر واریانت را به همراه مجموعه کاندیداهای حل‌شده‌اش به علاوه `context_length` / `max_output_tokens` فهرست می‌کند — که حداکثر (MAX) مقدار در پنجره‌های مجموعه کاندیداها است. کلاینت‌ها (مثلاً پلاگین opencode) باید این مقادیر را به جای `0` تبلیغ کنند: کانتکست صفر، فشرده‌سازی خودکار opencode را کاملاً غیرفعال می‌کند و اجازه می‌دهد نشست‌ها (sessions) رشد کنند تا زمانی که پاکسازی تاریخچه گیت‌وی، کانتکست را از بین ببرد. تبلیغ مقدار MAX ایمن است زیرا پیش‌فیلتر کانتکست auto-combo، درخواست‌های بیش از حد بزرگ را به کاندیداهای دارای پنجره بزرگ هدایت می‌کند.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### استراتژی‌های روتر خودکار

کامبوهای ماندگار با `strategy: "auto"` می‌توانند `config.routerStrategy` (یا `config.auto.routerStrategy` قدیمی) را روی یکی از موارد زیر تنظیم کنند:

- `rules` — امتیازدهی وزن‌دار پیش‌فرض
- `score` — بالاترین امتیاز وزن‌دار پیکربندی‌شده را انتخاب می‌کند. تساوی‌های دقیق، ترتیب کاندیداهای پیکربندی‌شده را حفظ می‌کنند؛ `explorationRate` موجود از کل مجموعه رتبه‌بندی‌شده نمونه‌برداری می‌کند.
- `cost` / `eco` — ارزان‌ترین ارائه‌دهنده سالم
- `latency` / `fast` — کمترین تأخیر p95 با جریمه قابلیت اطمینان
- `sla-aware` / `sla` — ترجیح کاندیداهایی که تأخیر p95، نرخ خطا و SLOهای هزینه اختیاری را برآورده می‌کنند
- `lkgp` — اولویت با آخرین ارائه‌دهنده خوب شناخته‌شده
- `nadir` — از API تصمیم‌گیری [Nadir](https://getnadir.com) بپرسید که پرامپت به کدام مدل در مجموعه نیاز دارد؛ انتخاب اختیاری (opt-in)، در صورت شکست به `rules` بازمی‌گردد (fail-open)

### جزئیات استراتژی‌های روتر

موتور auto-combo هفت پیاده‌سازی قابل جایگزینی **RouterStrategy** را ارائه می‌دهد که می‌توانید از طریق `config.routerStrategy` (یا `config.auto.routerStrategy` قدیمی) آن‌ها را تغییر دهید. هر استراتژی با دریافت یک `RoutingContext` (نوع وظیفه، نکات ابزار/بینایی، تخمین توکن، سیاست SLA اختیاری، آخرین ارائه‌دهنده خوب شناخته‌شده اختیاری)، یک ارائه‌دهنده را از مجموعه کاندیداها انتخاب می‌کند.

#### ۱. `rules` (پیش‌فرض) — امتیازدهی وزن‌دار ۱۶ عاملی

موتور امتیازدهی موجود را می‌پوشاند (wraps). کاندیداهای دارای مدارشکن (circuit-breaker) در وضعیت `OPEN` را فیلتر می‌کند، سپس `scorePool()` را با نوع وظیفه فعلی و `getTaskFitness()` اجرا کرده و ارائه‌دهنده‌ای که بالاترین امتیاز را دارد انتخاب می‌کند.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: پیش‌فرض. زمانی استفاده کنید که می‌خواهید یک موازنه متعادل بین تمام سیگنال‌ها برقرار کنید.

**نام مستعار**: `rules` (بدون نام مستعار)

---

#### ۲. `cost` / `eco` — ارزان‌ترین ارائه‌دهنده سالم

مجموعه کاندیداها را بر اساس `costPer1MTokens` (صعودی) مرتب کرده و ارزان‌ترین را انتخاب می‌کند. ابتدا کاندیداهای `OPEN` را فیلتر می‌کند.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: بارهای کاری حساس به هزینه، پردازش دسته‌ای (batch)، یا کارهای پس‌زمینه.

**نام‌های مستعار**: `cost`, `eco`

---

#### ۳. `latency` / `fast` — کمترین تأخیر p95 با جریمه قابلیت اطمینان

بر اساس `p95LatencyMs + (errorRate * 1000)` مرتب می‌کند. جریمه نرخ خطا تضمین می‌کند که ارائه‌دهندگان غیرقابل اعتماد حتی اگر تأخیر اسمی آن‌ها کم باشد، در رتبه پایین‌تری قرار گیرند.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**زمان استفاده**: بارهای کاری حساس به تأخیر مانند چت بلادرنگ، تکمیل خودکار، یا دستیارهای کدنویسی تعاملی.

**نام‌های مستعار**: `latency`, `fast`

---

#### ۴. `sla-aware` / `sla` — انطباق با SLO تأخیر/خطا/هزینه

هر کاندیدا را بر اساس میزان برآورده کردن سیاست SLO پیکربندی‌شده امتیازدهی می‌کند:

| فاکتور         | وزن | فرمول                                          |
| -------------- | --- | ---------------------------------------------- |
| امتیاز تأخیر   | ۳۵٪ | `threshold / max(value, ε)`                    |
| امتیاز خطا     | ۳۵٪ | `threshold / max(value, ε)`                    |
| امتیاز سلامت   | ۱۵٪ | `1.0` (بسته) / `0.5` (نیمه‌باز) / `0.0` (باز)  |
| امتیاز هزینه   | ۱۰٪ | `threshold / max(value, ε)` یا نرمال‌شده معکوس |
| امتیاز پایداری | ۵٪  | انحراف معیار تأخیر نرمال‌شده معکوس             |

هنگامی که `hardConstraints: true` باشد، کاندیداها در درجه اول بر اساس **امتیاز تخلف**
(میزان فراتر رفتن از هر SLO) و سپس بر اساس امتیاز ترکیبی مرتب می‌شوند. در غیر این صورت، فقط از
امتیاز ترکیبی استفاده می‌شود.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**فیلدهای SLA** (تنظیم‌شده در پیکربندی ترکیبی):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**زمان استفاده**: بارهای کاری عملیاتی (Production) با بودجه‌های سخت‌گیرانه برای تأخیر، نرخ خطا یا هزینه.

**نام‌های مستعار**: `sla-aware`, `sla`

#### ۵. `lkgp` — ابتدا آخرین ارائه‌دهنده خوب شناخته‌شده

ابتدا **آخرین ارائه‌دهنده خوب شناخته‌شده** (در صورت تنظیم) را امتحان می‌کند، سپس به استراتژی
`rules` بازمی‌گردد. برای چسبندگی نشست (Session stickiness) مفید است — همان ارائه‌دهنده
درخواست‌های بعدی را در یک گفتگو مدیریت می‌کند.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**زمان استفاده**: گفتگوهای چندمرحله‌ای که می‌خواهید همان ارائه‌دهنده درخواست‌های بعدی را مدیریت کند
(مثلاً برای کش کردن، تداوم زمینه، یا ثبات قیمت‌گذاری).

**نام مستعار**: `lkgp` (بدون نام مستعار)

---

#### ۶. `nadir` — انتخاب مدل آگاه از پرامپت از طریق Nadir

تمام استراتژی‌های بالا کاندیداها را بر اساس تله‌متری خود رتبه‌بندی می‌کنند؛ هیچ‌کدام درخواست را
نمی‌خوانند. `nadir` آخرین نوبت کاربر به اضافه شناسه‌های مدل موجود در استخر را به API تصمیم‌گیری
[Nadir](https://getnadir.com) (`POST /v1/bucket`) ارسال می‌کند و به مدلی که Nadir از آن منو
انتخاب می‌کند، مسیریابی می‌کند (`simple` → ارزان‌ترین مدل توانمند، `complex` → مدل پیشرو).
اتصالی که آن مدل را ارائه می‌دهد همچنان توسط `rules` انتخاب می‌شود، بنابراین سهمیه، سلامت و هزینه
همچنان تعیین می‌کنند که کدام حساب استفاده شود.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` و `OMNIROUTE_NADIR_BASE_URL` جایگزین‌های محیطی (env fallbacks) برای این دو
رشته هستند. `baseUrl` فقط برای نسخه خود-میزبانی (self-hosted) Nadir مورد نیاز است (یک `/v1` در
انتها قابل قبول است). تماس‌های بدون کلید به سطح ناشناس Nadir هدایت می‌شوند که محدودیت نرخ
(rate-limit) بر اساس IP دارد.

آنچه از سیستم خارج می‌شود: متن آخرین پیام کاربر (۱۶ هزار کاراکتر اول)، شناسه‌های مدل کاندیدا و یک
تگ کانال `source: "omniroute"`. بدون پرامپت سیستم، تاریخچه، ابزارها یا هدرها.

رفتار در صورت شکست، fail-open است: تایم‌اوت (پیش‌فرض ۲۰۰۰ میلی‌ثانیه)، پاسخ غیر 2xx، میزبان
غیرقابل دسترس، پاسخ ناقص یا انتخابی خارج از استخر، به تصمیم `rules` منجر می‌شود و دلیل آن با پیشوند
`NadirStrategy: fallback (…)` مشخص می‌شود. پس از یک تماس ناموفق، استراتژی به مدت ۳۰ ثانیه شبکه
را نادیده می‌گیرد، بنابراین یک قطعی به جای یک تایم‌اوت در هر درخواست، یک تایم‌اوت در هر ۳۰ ثانیه
هزینه دارد. رویدادهای مسیریابی فقط زمانی `strategy: "nadir"` را گزارش می‌کنند که Nadir واقعاً
انتخاب را انجام داده باشد.

**زمان استفاده**: ترافیک با دشواری ترکیبی روی استخری که شامل سطوح مختلف مدل است (یک مدل کوچک، یک
مدل متوسط و یک مدل پیشرو)، جایی که استفاده همیشگی از مدل پیشرو هزینه‌ای است که می‌خواهید کاهش دهید.

**نام مستعار**: `nadir` (بدون نام مستعار)

### استراتژی‌های مسیریاب سفارشی

شما می‌توانید پیاده‌سازی `RouterStrategy` خود را از طریق API عمومی ثبت کنید:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

سپس از آن استفاده کنید:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### راهنمای انتخاب استراتژی مسیریاب

| مورد استفاده      | استراتژی    | دلیل                                               |
| ----------------- | ----------- | -------------------------------------------------- |
| بار کاری متعادل   | `rules`     | پیش‌فرض — تمام فاکتورها را در نظر می‌گیرد          |
| حداقل‌سازی هزینه  | `cost`      | همیشه ارزان‌ترین را انتخاب می‌کند                  |
| حداقل‌سازی تأخیر  | `latency`   | سریع‌ترین ارائه‌دهنده قابل اعتماد را انتخاب می‌کند |
| SLOهای سخت‌گیرانه | `sla-aware` | فیلتر بر اساس آستانه‌های p95/خطا/هزینه             |
| چت چندمرحله‌ای    | `lkgp`      | چسبندگی نشست                                       |
| دشواری ترکیبی     | `nadir`     | انتخاب سطح مدل برای هر پرامپت                      |

فیلدهای SLA-aware:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## تناسب وظیفه

بیش از ۳۰ مدل در ۶ نوع وظیفه (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`) امتیازدهی شدهاند. از الگوهای wildcard پشتیبانی میشود (برای مثال، `*-coder` → امتیاز بالای کدنویسی).

## مرور گونههای Auto

با احتساب `auto` ساده (پیشفرض) بهعلاوهٔ ۶ مقدار `AutoVariant` تعریفشده در `autoPrefix.ts`، در مجموع **۷ شناسهٔ مدل قابل فراخوانی** وجود دارد:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(`AutoVariant` خود شامل ۶ مقدار است؛ گزینهٔ هفتم «بدون گونه» — یعنی `auto` ساده — است که توسط `parseAutoPrefix()` بهشکل `variant: undefined` مدیریت میشود.)

## جایگاه سطوح در Auto-Combo

تابع امتیازدهی ۱۶عاملی (`open-sse/services/autoCombo/scoring.ts`) عضویت در سطح را بهعنوان دو سیگنال در نظر میگیرد: `tierPriority` (0.0476) و `tierAffinity` (0.0476). برای مشاهده مجموعه کامل `DEFAULT_WEIGHTS`، جدول مرجع [عوامل امتیازدهی](#how-it-works-persisted-auto-combos) در بالا را ببینید — مقادیر بازنویسیشده برای هر بسته (ship-fast/cost-saver/quality-first/
offline-friendly) در جدول «پروفایلهای وزن برای هر بسته» فهرست شدهاند.

سطح بهتنهایی **باعث نمیشود** سطح ۱ در اولویت قرار گیرد — اگر تأخیر سطح ۱ نامطلوب باشد یا
نسبت هزینه به کیفیت بهینه نباشد، سطح ۲ انتخاب میشود. برای اجبار ترتیب سطوح، از استراتژی
`priority` برای ترکیب استفاده کنید و ارائهدهندگان را بر اساس سطح مرتب کنید.

برای ترجیح قوی سطح ۱ (اشتراکی)، وزن `tierPriority` را افزایش دهید:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

برای تعاریف سطوح و دستهبندی ارائهدهندگان، به [`docs/guides/TIERS.md`](../guides/TIERS.md) مراجعه کنید.

## آزمون و پوشش

### ماتریس قطعی تصمیمگیری مسیریابی (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` **تصمیم** مسیریابی هر ۱۹ راهبرد عمومی را بهصورت سرتاسری، از طریق خط لولهٔ واقعی combo و با upstream شبیهسازیشده، اثبات میکند.
پوشش شامل موارد زیر است:

- هر ۱۹ راهبرد `ROUTING_STRATEGY_VALUES` (ordered، weighted، cost، context، fusion، …).
- `quota-share` (داخلی) بهصورت سرتاسری: عدالت DRR + کاهش اولویت هنگام اشباع، از طریق نقطهٔ اتصال واقعی `selectQuotaShareTarget` (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- پوشش واگذاری همگانی `context-relay` برای تمام تعدادهای ممکن هدف.

این مجموعه در CI (کار `test:integration`) با `--test-concurrency=1` و
`--test-force-exit` اجرا میشود؛ بنابراین قطعی است و به اعتبارنامههای زنده نیاز ندارد.

### آزمون دود زندهٔ مشروط (در CI نیست — ارائهدهندگان واقعی)

| فرمان                                  | کاری که انجام میدهد                                                                                 |
| :------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | مسیریابی واقعی درونفرایندی با `RUN_COMBO_LIVE=1`؛ از یک پایگاه دادهٔ زندهٔ OmniRoute اسنپشات میگیرد |
| `npm run test:combo:live:vps`          | فراخوانیهای HTTP علیه یک سرور زندهٔ OmniRoute (`COMBO_LIVE_BASE_URL` را تنظیم کنید)                 |
| `npm run test:combo:live:vps:failover` | همان مورد، همراه با سناریوهای failover عمدی                                                         |

این آزمونهای دود مسیر واقعی ارتباط را آزمایش میکنند (combo → ارائهدهنده → تکمیل). آنها
عمداً از CI کنار گذاشته شدهاند، زیرا به اعتبارنامههای زنده و دسترسی VPS نیاز دارند.
