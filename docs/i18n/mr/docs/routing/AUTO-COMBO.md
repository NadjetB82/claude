## शून्य-कॉन्फिग स्वयं-राउटिंग (`auto/` उपसर्ग)

> **नवीन:** कॉम्बो तयार करण्याची आवश्यकता नाही. कोणत्याही क्लायंटमध्ये थेट `auto/` उपसर्ग वापरा.

### झटपट उदाहरणे

| मॉडेल ID       | प्रकार  | वर्तन                                                                     |
| -------------- | ------- | ------------------------------------------------------------------------- |
| `auto`         | डीफॉल्ट | सर्व कनेक्ट केलेले प्रदाते, LKGP धोरण, संतुलित भार                        |
| `auto/coding`  | कोडिंग  | गुणवत्तेला प्राधान्य देणारे भार, कोड निर्मितीसाठी योग्य                   |
| `auto/fast`    | जलद     | कमी-विलंबाची भारित निवड                                                   |
| `auto/cheap`   | स्वस्त  | खर्च-अनुकूलित राउटिंग (सर्वात कमी खर्च प्रथम)                             |
| `auto/offline` | ऑफलाइन  | सर्वाधिक कोटा उपलब्धता असलेल्या प्रदात्यांना प्राधान्य                    |
| `auto/smart`   | स्मार्ट | गुणवत्तेला प्राधान्य + अधिक चांगल्या मॉडेल शोधासाठी उच्च अन्वेषण दर (10%) |
| `auto/lkgp`    | lkgp    | स्पष्ट LKGP (डीफॉल्ट `auto` प्रमाणेच)                                     |
| `auto/chaos`   | केऑस    | समांतर फॅन-आउट, प्रत्येक प्रदात्यामागे एक मॉडेल (दोष अंतःक्षेपण नाही)     |

### श्रेणी × टियर संयोजन (`auto/<category>:<tier>`)

OpenRouter-शैलीतील प्रत्यय **कोणत्या प्रकारचा मार्ग** (श्रेणी) आणि **तो कसा अनुकूलित करायचा** (टियर) यांना वेगळे करतात, त्यामुळे तुम्ही ते मुक्तपणे एकत्रित करू शकता (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **श्रेण्या** (क्षमतांनुसार उमेदवार पूल फिल्टर करा): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` दृश्य-क्षम मॉडेल कायम ठेवतात; `reasoning` तर्क/विचार करणारी मॉडेल कायम ठेवते.
- **टियर** (स्कोअरिंग भार / पूल फिल्टर निवडा): `fast` (त्वरित वितरण) · `cheap` (`floor` हे उपनाव, खर्च-बचत करणारे) · `reliable` (सर्किट-ब्रेकर आरोग्य + विलंब स्थिरता) · `free` / `pro` (`classifyTier` द्वारे मॉडेल टियरनुसार पूल फिल्टर करा — मोफत टियर विरुद्ध प्रीमियम).

| उदाहरण                 | यामध्ये रूपांतरित होते                                   |
| ---------------------- | -------------------------------------------------------- |
| `auto/coding:fast`     | कोडिंग पूल, कमी-विलंबाचे भार                             |
| `auto/coding:cheap`    | कोडिंग पूल, खर्च-अनुकूलित (`auto/coding:floor` हे उपनाव) |
| `auto/reasoning:pro`   | केवळ तर्क/विचार करणारी मॉडेल, प्रीमियम टियर              |
| `auto/vision`          | दृश्य-क्षम मॉडेल (टियर नाही → संतुलित भार)               |
| `auto/multimodal:free` | बहुपद्धती-क्षम मॉडेल, केवळ मोफत टियर                     |

कोणतेही वैध `auto/<category>[:<tier>]` मागणीनुसार निराकरण केले जाते; काळजीपूर्वक निवडलेला उपसंच `/v1/models` आणि डॅशबोर्डमध्ये (`open-sse/services/autoCombo/builtinCatalog.ts` मधील `AUTO_SUFFIX_VARIANTS`) दर्शविला जातो. फिल्टरिंग **फेल-ओपन** आहे — एखाद्या मर्यादेशी कनेक्ट केलेले कोणतेही मॉडेल जुळत नसल्यास, संपूर्ण पूल वापरला जातो, त्यामुळे राउटिंग कधीही खंडित होत नाही. मुख्य स्कोअरर (`combo.ts`) अपरिवर्तित आहे; श्रेणी/टियर फिल्टर `buildAutoCandidates` मध्ये लागू केला जातो.

> **लाइव्ह मॉडेल इंटेलिजन्स:** `ARENA_ELO_SYNC_ENABLED` फ्लॅग सुरू असताना स्वयं-राउटिंगची उपयुक्तता लाइव्ह **Arena ELO** क्रमवारी + **models.dev** टियर डेटाद्वारे निर्धारित केली जाते (अन्यथा स्थिर उपयुक्तता मॅपचा फॉलबॅक म्हणून वापर केला जातो).

**कसे वापरावे:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**काय घडते:**

1. OmniRoute `src/sse/handlers/chat.ts` मध्ये `auto/` उपसर्ग शोधते
2. डेटाबेसमधून सर्व **सक्रिय प्रदाता कनेक्शन** क्वेरी करते
3. वैध क्रेडेन्शियल्स (API की किंवा OAuth टोकन) असलेली कनेक्शन फिल्टर करते
4. प्रत्येक कनेक्शनसाठी मॉडेल निर्धारित करते (`connection.defaultModel` किंवा प्रदात्याचे पहिले मॉडेल)
5. मेमरीमध्ये **आभासी कॉम्बो** तयार करते (DB मध्ये संग्रहित केला जात नाही)
6. निवडलेल्या प्रकाराचे भार प्रोफाइल + LKGP धोरण वापरून राउट करते

**प्रमुख गुणधर्म:**

- ✅ **नेहमी सुरू:** कोणतेही टॉगल नाही, कॉम्बो निर्मिती नाही, कोणत्याही कॉन्फिगरेशनची आवश्यकता नाही
- ✅ **डायनॅमिक:** सध्या कनेक्ट केलेले प्रदाते आपोआप प्रतिबिंबित करते
- ✅ **सेशन सातत्य:** LKGP मुळे शेवटच्या यशस्वी प्रदात्याला प्राधान्य दिले जाते
- ✅ **एकाधिक खात्यांची जाणीव:** प्रत्येक प्रदाता कनेक्शन स्वतंत्र उमेदवार बनते
- ✅ **DB लेखन नाही:** आभासी कॉम्बो केवळ विनंतीपुरता अस्तित्वात राहतो, सातत्यपूर्ण संचयनाचा शून्य अतिरिक्त भार

### प्रत्येक कीसाठी उमेदवार नियंत्रण (#7819, स्तर 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` नंतरचा प्रत्यय, किंवा
मूलभूत चॅनेलसाठी अक्षरशः `auto`) हा **केवळ-वाचन** एंडपॉइंट आहे, जो विद्यमान
लवचिकता वाचनांचा पुनर्वापर करून, लाइव्ह पोहोचक्षमतेसह सजवलेला `auto/*` चॅनेलचा
सध्याचा उमेदवार पूल सूचीबद्ध करतो (कच्ची ब्रेकर `state` कधीही वापरत नाही):

- प्रदाता सर्किट ब्रेकर — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- कनेक्शन कूलडाउन — निराकरण केलेल्या `provider_connections` पंक्तीवरील
  `rateLimitedUntil` / `testStatus`
- मॉडेल लॉकआउट — `isModelLocked(provider, connectionId, model)`

प्रत्येक उमेदवारासोबत या API कीचा `excluded` फ्लॅगही असतो. वगळण्याची माहिती
प्रत्येक API कीनुसार (`auto_candidate_overrides` तक्ता, माइग्रेशन `128`) संग्रहित
केली जाते — OmniRoute मध्ये `users` तक्ता नसून ते एकल-टेनंट आहे, त्यामुळे
`apiKeyId` ही प्रत्यक्ष प्रत्येक कॉलरसाठीची सर्वात जवळची ओळख आहे — आणि
`open-sse/services/autoCombo/virtualFactory.ts` मधील उमेदवार-पूल चोकपॉइंटवर शुद्ध,
युनिट-चाचणी केलेल्या `filterExcludedCandidates()`
(`open-sse/services/autoCombo/candidateOverrides.ts`) द्वारे तिची अंमलबजावणी केली
जाते. हा फिल्टर **फेल-ओपन** आहे: सेट न केलेले apiKeyId/चॅनेल किंवा DB लुकअप अपयश,
या दोन्ही स्थितींमध्ये पूल फिल्टर न केलेला राहतो, त्यामुळे कोणतेही ओव्हरराइड
कॉन्फिगर न केलेल्या ऑपरेटरला या वैशिष्ट्यापूर्वीप्रमाणेच बाइट-तंतोतंत राउटिंग दिसते.

**पुढील समस्येसाठी पुढे ढकलले आहे:** प्रत्येक उमेदवारासाठी स्वतंत्र वजने + स्पष्ट क्रमवारी (स्तर 3
— विद्यमान भारित/प्राधान्य धोरण मार्गांमध्ये समाविष्ट होते) आणि प्रत्येक `auto/*` चॅनेलसाठी विशिष्ट
`combo.ts` धोरण पिन करणे (स्तर 4). एकल-टेनंट मॉडेलचा विचार करता ओव्हरराइड्स प्रत्येक API कीनुसारच ठेवावेत की ग्लोबल करावेत, या खुल्या
प्रश्नासाठी #7819 योजना पहा.

**पडद्यामागील प्रक्रिया:**

## वास्तविक Model Id शी जुळणारी Combo नावे

ज्या combo चे `name` एखाद्या साध्या model id सारखेच असते (उदा. `gpt-5.5` नावाची combo), तो **हेतुपुरस्सर वापरला जाणारा, समर्थित नमुना** आहे, bug नाही: [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) मध्ये दस्तऐवजीकरण केलेली, प्रत्येक model id साठी provider fallback देणारी ही यंत्रणा आहे. साध्या model-id resolution च्या आधी combo resolution तपासले जात असल्यामुळे (`src/sse/services/model.ts` मधील `getComboForModel()`), साध्या id `gpt-5.5` साठीची विनंती थेट एकाच provider कडे जाण्याऐवजी combo च्या targets मधून (उदा. `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) route केली जाते — यात [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) साठी तयार केलेल्या combo-before-rewrite precedence चा पुनर्वापर होतो आणि `tests/unit/responses-combo-resolution-3227.test.ts` व `tests/unit/combo-name-codex-responses-rewrite.test.ts` द्वारे त्याची regression चाचणी केली जाते.

वास्तविक model id ला झाकणारे नाव असलेली combo तयार करणे किंवा combo चे नाव बदलणे **कधीही नाकारले जात नाही** — तसे केल्याने हा दस्तऐवजीकृत workflow खंडित होईल. त्याऐवजी (#8530), (नवीन) नावाचा वास्तविक model id शी संघर्ष झाल्यास `POST /api/combos` आणि `PUT /api/combos/[id]` response मध्ये अडथळा न आणणारे `warning` field जोडतात:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Boot होताना, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) model id झाकणाऱ्या प्रत्येक विद्यमान combo ची सूची देणारा एका ओळीचा `[STARTUP]` warning देखील log करते, ज्यामुळे हेतुपुरस्सर (#6940 नुसार) असे करण्याऐवजी चुकून या परिस्थितीत आलेल्या operators ना संकेत मिळतो. Detection helper `src/lib/combos/modelNameCollision.ts` मध्ये आहे.

## Client मधून Custom Combo ला Call करणे

Persist केलेल्या combos (Settings → Combos) फक्त तेव्हाच वापरल्या जातात, जेव्हा client `model` field मध्ये combo चे **अचूक नाव** पाठवतो — combo नावासाठी fuzzy किंवा partial matching नसते आणि `auto/` prefix चा संबंधही नसतो. Resolution क्रम (`src/sse/services/model.ts` मधील `getComboForModel()`):

1. combo नावाशी अचूक जुळणी (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

दोन सामान्य अडचणी:

- **`auto` तुमच्या combos वापरत नाही.** `auto`/`auto/*` स्वतःचा zero-config candidate pool तयार करते आणि `auto` नावाची combo अक्षरशः अस्तित्वात असेल तरच persist केलेल्या combos चा विचार करते (याची शिफारस केली जात नाही). combo द्वारे route करण्यासाठी तिचे अचूक नाव पाठवा — `auto` नाही.
- **`openrouter/auto` हे प्रत्यक्ष, सशुल्क OpenRouter product** ("Auto Best Available") आहे, OmniRoute alias नाही. ही OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) मधील एकमेव static model entry आहे आणि तिचे billing स्वतंत्रपणे केले जाते. `auto` pools मधून ती वगळण्यासाठी Settings → Routing → Hide paid models वापरा.

येथे दस्तऐवजीकरण केलेल्या मूळ गोंधळासाठी [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) आणि [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) पहा.

## हे कसे कार्य करते (Persisted Auto-Combos)

Auto-Combo Engine एका **16-factor scoring function** चा वापर करून प्रत्येक विनंतीसाठी (request) सर्वोत्तम provider/model ची डायनॅमिकली निवड करते (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` मध्ये परिभाषित). डीफॉल्ट वजनांची (weights) बेरीज `1.0` होते; कस्टम वजने `normalizeScoringWeights()` द्वारे पुन्हा सामान्यीकृत (renormalized) केली जातात. सोळा घटकांपैकी दोन — `cacheAffinity` आणि `resetWindowAffinity` — यांचे डीफॉल्ट वजन `0` असते; `DEFAULT_WEIGHTS` मध्ये `reliability` चे वजन `0` असते परंतु generic packs मध्ये `0.03` आणि `reliability-first` मध्ये `0.04` असते, तसेच packs मध्ये `quality` चे वजन `0.02` असते (`quality-first` मध्ये `0.03`): त्यांची गणना प्रत्येक उमेदवारासाठी (candidate) केली जाते, आणि `cacheAffinity` स्कोअरच्या बाहेर prompt-cache deduplication नियंत्रित (gate) करते, त्यामुळे शून्य-डीफॉल्ट असलेले घटक डीफॉल्टनुसार मतदान करत नाहीत तर packs करतात.

> पॅटर्न आहे. अयशस्वी वापर वाचन हा टेलिमेट्रीबद्दलचा पुरावा आहे,
> प्रोव्हायडरबद्दल नाही, त्यामुळे तो कोणत्याही वास्तविक वाचनापेक्षा, अगदी निश्चित १००% वापरलेल्या वाचनापेक्षाही पूर्णपणे खाली येतो, परंतु तो कधीही हार्ड-ब्लॉक किंवा बाहेर काढला (evict केला) जात नाही. कोणतीही मर्यादा नसलेला प्रोव्हायडर `unlimited: true` नोंदवतो आणि
> पूर्ण कोटा म्हणून गुण मिळवतो; कोणताही नोंदणीकृत कोटा फेचर नसलेल्या प्रोव्हायडरकडे कोणताही टेलिमेट्री स्त्रोत नसतो
> आणि तो `100` चा डीफॉल्ट कायम ठेवतो.

- **पॅक्समध्ये `quality` आणि `reliability` समाविष्ट असतात** (`quality 0.02`, `quality-first 0.03`; `reliability 0.03`, `reliability-first 0.04`) आणि ते वजन मॅप पूर्णपणे बदलतात (`weights = pack`, मर्ज नव्हे). `DEFAULT_WEIGHTS` मध्ये `quality 0.03 / reliability 0` असते; `balanced`/`default` निवडल्यास ही डीफॉल्ट मूल्ये कायम राहतात, तर पॅक निवडल्यास वरील पॅकची मूल्ये वापरली जातात. कोल्ड पूलवर (अद्याप कोणतीही निरीक्षणे नाहीत, त्यामुळे `quality 0.5` आणि `reliability 1`) हे दोन घटक सामान्य पॅकअंतर्गत `+0.04` (`0.03 + 0.01`), `quality-first` अंतर्गत `+0.045` आणि `reliability-first` अंतर्गत `+0.05` जोडतात.
- प्रत्येक पॅकमध्ये `tierAffinity`, `specificityMatch` आणि `resetWindowAffinity` स्पष्टपणे `0` आहेत.
- एका नजरेत प्रत्येक पॅकचा भर:
  - **ship-fast** → latencyInv 0.3048 + health 0.2667 (कमी विलंबाच्या, सुस्थितीतील जोडण्या)
  - **cost-saver** → costInv 0.3324 (सर्वांत स्वस्त टोकन्स जिंकतात)
  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03, कोणत्याही पॅकपेक्षा सर्वाधिक (कार्याकरिता सर्वोत्तम आणि सुसंगत मॉडेल)
  - **offline-friendly** → quota 0.3324 + health 0.2667 (वेग/खर्च विचारात न घेता कमाल उपलब्ध क्षमता)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04, कोणत्याही पॅकपेक्षा सर्वाधिक (सर्वांत कमी अनपेक्षित परिणाम)
  - **chaos-mode** → health 0.4000 + taskFit 0.1905 (`auto/chaos` वजन पॅक त्याच्या पॅनेल सदस्यांना नेमून देतो ते वजन; समांतर fan-out ही वजने वाचत नाही आणि हे fault-injection प्रोफाइल नाही, [CHAOS-MODE.md](../guides/CHAOS-MODE.md#autochaos-parallel-fan-out) पहा)

### प्रत्येक विनंतीसाठी नियंत्रणे (हेडर्स) — #6023 / #6024 / #6025 / #3470

कॉम्बोच्या संग्रहित कॉन्फिगमध्ये बदल न करता, तीन हेडर्सद्वारे `auto` कॉम्बोला **प्रत्येक विनंतीनुसार** निर्देशित करता येते. हे केवळ `auto` धोरणाला आणि ते हेडर्स असलेल्या विनंतीलाच लागू होतात; हेडर अनुपस्थित असल्यास कॉम्बोची जतन केलेली `modePack`/`budgetCap`/`budgetFallback` मूल्ये वापरली जातात.

`config.budgetFallback` इनपुटना पुरवली जातात. कॉम्बोचे संचयित `config.budgetFallback` ("strict" |
"cheapest") कायमस्वरूपी धोरण ठरवते; हेडर एका विनंतीसाठी ते अधिलिखित करतो.

### `weighted` सिमेंटिक्स

`weighted` हे **प्रति विनंती एक प्रमाणबद्ध रँडम ड्रॉ** आहे
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), इक्वेलायझर नाही:

- प्रत्येक विनंती `weight / totalWeight` संभाव्यतेसह **एक** स्टेप ड्रॉ करते; उर्वरित स्टेप्स त्या विनंतीसाठी फॉलबॅक चेन म्हणून वेटच्या उतरत्या क्रमाने लावल्या जातात.
- ज्या स्टेपचे वेट `0` (किंवा गहाळ) आहे ती **कधीही ड्रॉ केली जात नाही** जोपर्यंत इतर कोणत्याही स्टेपचे वेट > 0 आहे — ती फक्त ड्रॉ केलेली स्टेप अयशस्वी झाल्यावरच फॉलबॅक म्हणून काम करू शकते. जेव्हा **सर्व** वेट्स 0 असतात तेव्हाच निवड युनिफॉर्म होते.
- ज्या स्टेप्सचे टार्गेट्स अनुपलब्ध आहेत — प्रोव्हायडर सर्किट ब्रेकर `OPEN`, कनेक्शन कूलडाउन, मॉडेल लॉकआउट — त्यांना ड्रॉ होण्यापूर्वीच काढून टाकले जाते (`open-sse/services/combo/targetResolution.ts`), त्यामुळे एकच निरोगी स्टेप तात्पुरती प्रत्येक विनंती जिंकू शकते.
- `stickyWeightedLimit` (कॉम्बो कॉन्फिग, डीफॉल्ट `1` = बंद) ड्रॉ केलेली स्टेप पुन्हा ड्रॉ करण्यापूर्वी तितक्या सलग यशांसाठी पिन करते.

कठोर रोटेशनसाठी `round-robin` वापरा; `weighted` वरील समान वेट्स सांख्यिकीय — कठोर नाही — संतुलन देतात.

### एजंटिक पाइपलाइन मोड

किमान दोन मॉडेल्स असलेले `pipeline` कॉम्बो `config.agenticOrchestration.enabled` सह प्लॅनर/एक्झिक्युटर राउटिंगमध्ये निवड करू शकतात. पहिले टार्गेट प्लॅनिंग आणि अंतिम उत्तरांसाठी जबाबदार असते; दुसरे टार्गेट क्लायंट-नेटिव्ह टूल कॉल्स उत्सर्जित करते. OmniRoute विनंती प्रोटोकॉलवरून टूल-रिझल्ट कंटिन्युएशन शोधते, प्लॅनरला विचारते की आणखी एका टूल राउंडची आवश्यकता आहे का, आणि डायनॅमिकरित्या एक्झिक्युटर किंवा प्लॅनरला क्लायंट-फेसिंग अंतिम टप्पा बनवते.

पर्यायी `config.agenticOrchestration.contextCompaction` प्रत्येक प्लॅनर किंवा एक्झिक्युटर डिस्पॅचपूर्वी एक स्वतंत्र पेलोड बजेट लागू करते. ते स्पष्टपणे सक्षम करा:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

हे ऑपरेटरद्वारे निवडलेले सिरियलाइज्ड JSON कॅरेक्टर बजेट आहेत, टोकन कॉन्टेक्स्ट विंडोज किंवा गॅरंटीड अपस्ट्रीम लिमिट्स नाहीत. अचूक मॉडेल IDs डीफॉल्टला ओव्हरराइड करतात. थ्रेशोल्डच्या वर, कॉम्पॅक्शन समान टूल डेफिनिशन्स काढून टाकते, डायजेस्टसह ओव्हरसाईज्ड टूल एविडन्स ट्रिम करते आणि टार्गेट रेशोकडे जुने पूर्ण हिस्ट्री ग्रुप्स काढून टाकते. हे सिस्टम/डेव्हलपर सूचना, नवीनतम वापरकर्ता विनंती, समांतर कॉल्स/रिझल्ट्ससह शेवटचा टूल राउंड आणि Gemini ची लीडिंग राउटिंग सूचना राखून ठेवते. टॉप-लेव्हल सूचना आणि टूल सेटिंग्ज जतन केल्या जातात. एक ओमिशन मार्कर काढलेली हिस्ट्री रेकॉर्ड करतो; हे डिटरमिनिस्टिक ट्रिमिंग आहे, सिमेंटिक सारांश नाही. जर पिन केलेले कॉन्टेक्स्ट अजूनही बजेटपेक्षा जास्त असेल, तर मॉडेलशी संपर्क साधण्यापूर्वी विनंती 413 परत करते. कॉम्पॅक्शन अक्षम असल्यास किंवा थ्रेशोल्डच्या खाली असल्यास विनंती जशीच्या तशी पुढे जाते.

दुसऱ्या टार्गेटनंतरची अतिरिक्त मॉडेल्स ऑर्डर्ड एक्झिक्युटर बॅकअप्स आहेत. अयशस्वी HTTP रिस्पॉन्स किंवा ट्रान्सपोर्ट एक्सेप्शन पुढील एक्झिक्युटरकडे जाते, ज्यामध्ये तोच प्लॅनर निर्णय आणि नेटिव्ह टूल्स असतात परंतु त्या एक्झिक्युटरचा स्वतःचा स्टेप प्रॉम्प्ट आणि रिझॉल्व्ह केलेले कनेक्शन असते. पहिला यशस्वी रिस्पॉन्स जसाच्या तसा परत केला जातो, ज्यामध्ये SSE स्ट्रीमिंग समाविष्ट आहे; यशस्वी स्ट्रीम सुरू झाल्यानंतरचे अपयश येथे पुन्हा प्रयत्न (retry) केले जाऊ शकत नाही. जर सर्व एक्झिक्युटर्स अयशस्वी झाले, तर शेवटचे अपयश परत केले जाते. क्लायंट ॲबॉर्स्ट डिस्पॅच थांबवतात.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

एक्झिक्युटर एका रिस्पॉन्समध्ये अनेक स्वतंत्र कॉल्स उत्सर्जित करू शकतो. अवलंबून असलेले कॉल्स नंतरच्या क्लायंट टूल-रिझल्ट टर्न्समध्ये हाताळले जातात, ज्यामध्ये प्लॅनर प्रत्येक रिझल्टचे पुनरावलोकन करतो. `maxToolRounds` डीफॉल्टनुसार `8` असते आणि `1`–`32` स्वीकारते; एकदा गाठल्यावर, प्लॅनरने सर्वोत्तम उपलब्ध अंतिम उत्तर तयार केले पाहिजे. अंतर्गत प्लॅनर निर्णय बफर केले जातात, तर निवडलेला क्लायंट-फेसिंग रिस्पॉन्स मूळ स्ट्रीमिंग प्राधान्य राखून ठेवतो.

### `round-robin` स्टिकी बॅच आणि अकाउंट एक्सपान्शन

राउंड-रॉबिन बॅच केलेले असते, प्रति-स्टेप एक-विनंती नाही:

- `stickyRoundRobinLimit` (कॉम्बो कॉन्फिग, त्यानंतर `comboStickyRoundRobinLimit`, त्यानंतर `settings.stickyRoundRobinLimit`, डीफॉल्ट **3**) रोटेट करण्यापूर्वी तितक्या सलग यशांसाठी तेच टार्गेट ठेवते. एक-विनंती रोटेशनसाठी कॉम्बो ओव्हरराइड `1` वर सेट करा. कॉम्बो एडिटर प्रभावी मूल्य आणि ते कोणत्या लेयरवरून आले आहे हे दर्शवते.
- `connectionAwareExpansion` (कॉम्बो कॉन्फिग, त्यानंतर सेटिंग्ज, डीफॉल्ट **false**) रोटेशनपूर्वी प्रत्येक प्रोव्हायडर-लेव्हल स्टेपला प्रति-अकाउंट टार्गेट्समध्ये विस्तारित करते. ग्रुप-B धोरणे (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) हे चालू होईपर्यंत प्रोव्हायडर-लेव्हल व्ह्यू ठेवतात. कॉम्बो एडिटर inherit / on / off उघड करतो; inherit जागतिक डीफॉल्ट (off) वापरते.
- प्रॉम्प्ट-कॅशे लोकॅलिटी राउटिंग (`promptCacheAffinityEnabled`, डीफॉल्ट **true**) पिन केलेल्या कनेक्शनची पुनर्रचना करते जेणेकरून जुळणारे कॅशे की एकाच अकाउंटवर राहतील. हे पिन केलेल्या प्रति-अकाउंट स्टेप्सवर राउंड-रॉबिन आणि वेटेड रोटेशनपेक्षा प्राधान्य घेते. जर तुम्हाला कठोर रोटेशनची आवश्यकता असेल तर Settings → Combo defaults अंतर्गत ते बंद करा. कोणतेही प्रति-कॉम्बो ओव्हरराइड नाही.

एका मॉडेलवर मल्टी-अकाउंट रोटेशनसाठी, तीन पिन केलेल्या `connectionId` ऐवजी स्टिकी लिमिट `1` सह **एक डायनॅमिक-अकाउंट स्टेप** (रिकामी `connectionId`, संपूर्ण पूल) ला प्राधान्य द्या. RR काउंटर पुढे जात असतानाही पिन केलेल्या स्टेप्स आणि ॲफिनिटी एकाच अकाउंटवर कोलॅप्स होतात.

## फ्यूजन धोरण

`fusion` हे असे एकमेव धोरण आहे जे एक लक्ष्य निवडत **नाही**. ते प्रॉम्प्ट
**प्रत्येक पॅनेल मॉडेलकडे समांतरपणे** पाठवते आणि त्यानंतर कॉन्फिगर करता येणारे **जज मॉडेल**
सर्व पॅनेल प्रतिसादांमधून एकच अंतिम उत्तर संश्लेषित करते. हे अपस्ट्रीम `decolua/9router`
(OpenRouter ची Fusion रचना) येथून पोर्ट केले आहे; अंमलबजावणी `open-sse/services/fusion.ts` मध्ये आहे.

हे कसे कार्य करते:

0. **टूल असलेल्या विनंत्यांसाठी बायपास** — ज्या विनंतीत रिक्त नसलेला `tools` अॅरे आहे आणि
   `tool_choice` स्पष्टपणे `"none"` वर सेट केलेले नाही, ती विनंती संपूर्ण पॅनेल वगळते: ती
   थेट एका मॉडेलकडे (कॉन्फिगर केलेला जज किंवा `panel[0]`) रूट होते आणि `tools`/`tool_choice`
   कोणताही बदल न करता पुढे पाठवले जातात. पॅनेल सदस्यांना टूल वापरता येत नाहीत आणि जजचा
   संश्लेषण निर्देश टूल-कॉल निर्माण करण्यास परावृत्त करतो, त्यामुळे एजंटिक/टूल-कॉलिंग क्लायंटना
   संश्लेषित गद्याऐवजी प्रत्यक्ष टूल-कॉल निर्णय मिळतो (#6771).
1. **फॅन-आउट** (फक्त टूल नसलेल्या विनंत्यांसाठी) — प्रॉम्प्ट एकाच वेळी प्रत्येक पॅनेल
   मॉडेलकडे पाठवला जातो, टूल काढून टाकून नॉन-स्ट्रीमिंग सक्तीचे केले जाते (संश्लेषणासाठी
   जजला संपूर्ण मजकूर आवश्यक असतो).
2. **कोरम-ग्रेस संकलन** — `minPanel` उत्तरे मिळताच उशिरा प्रतिसाद देणाऱ्यांसाठी एक छोटा
   ग्रेस टाइमर सुरू होतो आणि त्यानंतर जेवढे प्रतिसाद संकलित झाले असतील त्यांसह फ्यूजन पुढे जाते.
   यामुळे सर्वांत धीम्या मॉडेलमुळे एकूण वेळेवर होणारा परिणाम मर्यादित राहतो आणि तो हार्ड टाइमआउटने नियंत्रित केला जातो.
3. **जज संश्लेषण** — पॅनेलची उत्तरे अनामित केली जातात (`Source 1`, `Source 2`, … — जेणेकरून
   जज मॉडेलच्या ब्रँडऐवजी आशयाला महत्त्व देईल) आणि जजकडे दिली जातात; तो सहमती /
   विरोधाभास / अपूर्ण व्याप्ती / वैशिष्ट्यपूर्ण अंतर्दृष्टी / दुर्लक्षित बाबींचे विश्लेषण करून
   **एक** अधिकृत उत्तर लिहितो. जज कॉलमध्ये क्लायंटचा मूळ `stream` फ्लॅग + टूल कायम ठेवले जातात,
   त्यामुळे स्ट्रीमिंग आणि डाउनस्ट्रीम टूल वापर अद्याप कार्य करतात.
4. **सुरळीत अवनती** — पॅनेलची 0 उत्तरे → `503`; नेमका 1 प्रतिसाद टिकून राहिल्यास → ते उत्तर
   थेट परत केले जाते (फ्यूज करण्यासारखे काही नसते); एकाच मॉडेलचे पॅनेल थेट उत्तर देते.

पॅनेल सदस्य हा दुसऱ्या कॉम्बोचा संदर्भ देणारा `combo-ref` टप्पादेखील (`{kind: "combo-ref", comboName: "..."}`)
असू शकतो — तो **एक ब्लॅक-बॉक्स पॅनेल आवाज** म्हणून रिझॉल्व्ह होतो (संदर्भित कॉम्बोमध्ये पूर्ण
रिकर्सिव्ह डिस्पॅच, त्या कॉम्बोच्या स्वतःच्या लक्ष्यांचे फॅन-आउट नाही), आणि इतर प्रत्येक
combo-ref वापरणाऱ्या धोरणात आधीपासून असलेले समान डेप्थ/सायकल संरक्षण वापरतो (#6764).

### कॉन्फिगरेशन

कॉम्बोच्या `config` ब्लॉबवर कॉन्फिगर केले जाते (स्कीमा मायग्रेशन नाही — ते विद्यमान
`combos` टेबलचा पुनर्वापर करते):

| फील्ड                                    | प्रकार   | डीफॉल्ट           | उद्देश                                                                                |
| :--------------------------------------- | :------- | :---------------- | :------------------------------------------------------------------------------------ |
| `config.judgeModel`                      | `string` | पहिले पॅनेल मॉडेल | अंतिम उत्तर संश्लेषित करणारे मॉडेल                                                    |
| `config.fusionTuning.minPanel`           | `number` | `2`               | ग्रेस टाइमर सुरू होण्यापूर्वी आवश्यक यशस्वी उत्तरे (`[2, panelSize]` पर्यंत मर्यादित) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`            | कोरम गाठल्यानंतर उशिरा प्रतिसाद देणाऱ्यांसाठी किती वेळ प्रतीक्षा करायची               |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`           | एखाद्या अडकलेल्या मॉडेलमुळे विनंती थांबू नये म्हणून निरपेक्ष कमाल मर्यादा             |

डीफॉल्ट मूल्ये `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) मध्ये आहेत.

### उदाहरण

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

त्यानंतर इतर कोणत्याही कॉम्बोप्रमाणे त्याला कॉल करा: `{"model":"fusion-panel","messages":[...]}`.

## व्हर्च्युअल ऑटो-कॉम्बो फॅक्टरी

Auto Combo इंजिनला पूर्व-परिभाषित कॉम्बोंची आवश्यकता नसते. त्याऐवजी, `open-sse/services/autoCombo/virtualFactory.ts` तत्काळ उमेदवार तयार करते:

1. `getProviderConnections({ isActive: true })` (सर्व सक्षम कनेक्शन्स) मिळवते
2. वैध क्रेडेन्शियल्स असलेली कनेक्शन्स फिल्टर करते (API की किंवा `hasUsableOAuthToken()` द्वारे कालबाह्य न झालेला OAuth टोकन)
3. मॉडेलची उपलब्धता + किंमत यासाठी `getProviderRegistry()` सोबत क्रॉस-रेफरन्स करते
4. प्रत्येक `(provider, model, connection)` ट्युपलसाठी, एक `VirtualAutoComboCandidate` तयार करते
5. डिस्पॅच लक्ष्य म्हणून `connection.defaultModel` (किंवा रजिस्ट्रीमधील पहिले मॉडेल) निवडते
6. 16-घटकांचे `scorePool()` आणि व्हेरियंटचा वेट पॅक वापरून प्रत्येक उमेदवाराला गुण देते
7. `handleComboChat()` साठी परिणामी इन-मेमरी `AutoComboConfig` परत करते — ते कधीही DB मध्ये कायमस्वरूपी साठवले जात नाही

याचा अर्थ असा की **`auto/*` सक्षम असलेला नवीन प्रोव्हायडर जोडल्याने उमेदवारांचा पूल आपोआप विस्तारित होतो** — कॉम्बोचे मॅन्युअल संपादन आवश्यक नाही. व्हर्च्युअल कॉम्बो प्रत्येक विनंतीसाठी पुन्हा तयार केला जातो, त्यामुळे नव्याने जोडलेली किंवा नव्याने निरोगी झालेली कनेक्शन्स त्वरित निवडली जातात.

## स्वयंचलित पुनर्प्राप्ती

- **तात्पुरते वगळणे**: गुण < 0.2 → 5 मिनिटांसाठी वगळले जाते (प्रगतीशील बॅकऑफ, कमाल 30 मिनिटे)
- **सर्किट ब्रेकरची जाणीव**: OPEN → आपोआप वगळले जाते; HALF_OPEN → प्रोब विनंत्या
- **घटना मोड**: >50% OPEN → एक्सप्लोरेशन अक्षम करा, स्थिरता कमाल करा
- **कूलडाउन पुनर्प्राप्ती**: वगळण्याचा कालावधी संपल्यानंतर, पहिली विनंती कमी टाइमआउटसह "प्रोब" असते

## बँडिट एक्सप्लोरेशन

5% विनंत्या (कॉन्फिगर करण्यायोग्य) एक्सप्लोरेशनसाठी यादृच्छिक प्रोव्हायडर्सकडे रूट केल्या जातात. घटना मोडमध्ये हे अक्षम असते.

## API

**`POST /api/combos/auto`** असा कोणताही समर्पित एंडपॉइंट नाही — Auto-Combo दोन प्रकारे वापरले जाते:

1. **Zero-config (शिफारस केलेले):** `model: "auto"` किंवा `model: "auto/<variant>"` सह कोणतीही चॅट पूर्ण करण्याची विनंती (chat completion request) पाठवा. व्हर्च्युअल फॅक्टरी प्रत्येक विनंतीनुसार कॉम्बो तयार करते — कोणत्याही पर्सिस्टन्सची किंवा API कॉल्सची आवश्यकता नाही.

2. **`strategy: "auto"` सह पर्सिस्टेड कॉम्बो:** `POST /api/combos` द्वारे एक नियमित कॉम्बो तयार करा आणि `strategy: "auto"` तसेच `config.auto.weights` / `config.auto.candidatePool` सेट करा. त्याच स्कोरिंग इंजिनचा वापर केला जातो; कॉम्बो `combos` मध्ये स्टोअर केला जातो आणि ID द्वारे पुन्हा वापरण्यायोग्य असतो.

डिस्कव्हरीसाठी, `GET /api/combos/auto` प्रत्येक व्हेरिएंटची यादी त्याच्या रिझॉल्व्ह केलेल्या कॅंडिडेट पूलसह आणि `context_length` / `max_output_tokens` सह दर्शवते — जे कॅंडिडेट पूलच्या विंडोजमधील MAX मूल्य आहे. क्लायंट्सनी (उदा. opencode प्लगइन) `0` ऐवजी ही मूल्ये ॲडव्हर्टाइज करणे आवश्यक आहे: शून्य कॉन्टेक्स्ट opencode चे ऑटो-कॉम्पॅक्शन पूर्णपणे अक्षम करते, ज्यामुळे गेटवेचे हिस्ट्री पर्ज कॉन्टेक्स्ट नष्ट करेपर्यंत सेशन्स वाढत राहतात. MAX ॲडव्हर्टाइज करणे सुरक्षित आहे कारण ऑटो-कॉम्बो कॉन्टेक्स्ट प्री-फिल्टर ओव्हरसाईज्ड विनंत्यांना मोठ्या-विंडो असलेल्या कॅंडिडेट्सकडे राउट करते.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

पर्सिस्टेड `strategy: "auto"` कॉम्बो `config.routerStrategy` (किंवा लेगसी `config.auto.routerStrategy`) खालीलपैकी एकावर सेट करू शकतात:

- `rules` — डीफॉल्ट वेटेड स्कोरिंग
- `score` — सर्वोच्च कॉन्फिगर केलेले वेटेड स्कोर निवडते. अचूक टाय (ties) असल्यास कॉन्फिगर केलेला कॅंडिडेट क्रम राखला जातो; विद्यमान `explorationRate` पूर्ण रँक केलेल्या पूलधून सॅम्पल घेते.
- `cost` / `eco` — सर्वात स्वस्त हेल्दी प्रोव्हायडर
- `latency` / `fast` — रिलायबिलिटी पेनल्टीसह सर्वात कमी p95 लेटन्सी
- `sla-aware` / `sla` — p95 लेटन्सी, एरर-रेट आणि पर्यायी कॉस्ट SLO पूर्ण करणाऱ्या कॅंडिडेट्सना प्राधान्य देते
- `lkgp` — शेवटचा ज्ञात चांगला (last known good) प्रोव्हायडर प्रथम
- `nadir` — [Nadir](https://getnadir.com) च्या डिसिजन API ला विचारा की पूलमध्ये प्रॉम्प्टला कोणत्या मॉडेलची गरज आहे; ऑप्ट-इन, `rules` वर फेल-ओपन होते

### Router strategies in detail

ऑटो-कॉम्बो इंजिन 7 प्लगेबल **RouterStrategy** इम्प्लिमेंटेशन्स एक्सपोज करते जे तुम्ही `config.routerStrategy` (किंवा लेगसी `config.auto.routerStrategy`) द्वारे स्वॅप करू शकता. प्रत्येक स्ट्रॅटेजी `RoutingContext` (टास्क प्रकार, टूल/व्हिजन हिंट्स, टोकन एस्टिमेट, पर्यायी SLA पॉलिसी, पर्यायी शेवटचा ज्ञात चांगला प्रोव्हायडर) दिल्यावर कॅंडिडेट पूलधून एक प्रोव्हायडर निवडते.

#### 1. `rules` (डीफॉल्ट) — 16-फॅक्टर वेटेड स्कोरिंग

विद्यमान स्कोरिंग इंजिनला रॅप करते. `OPEN` सर्किट-ब्रेकर कॅंडिडेट्सना फिल्टर करते, त्यानंतर सध्याच्या टास्क प्रकारासह आणि `getTaskFitness()` सह `scorePool()` चालवते, आणि टॉप-स्कोरिंग प्रोव्हायडर निवडते.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**कधी वापरावे**: डीफॉल्ट. जेव्हा तुम्हाला सर्व सिग्नल्समध्ये संतुलित ट्रेड-ऑफ हवा असेल तेव्हा वापरा.

**Alias**: `rules` (कोणतेही अलियास नाही)

---

#### 2. `cost` / `eco` — सर्वात स्वस्त हेल्दी प्रोव्हायडर

कॅंडिडेट पूलला `costPer1MTokens` (चढत्या क्रमाने) नुसार सॉर्ट करते आणि सर्वात स्वस्त निवडते. प्रथम `OPEN` कॅंडिडेट्सना फिल्टर करते.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कधी वापरावे**: कॉस्ट-सेन्सिटिव्ह वर्कलोड्स, बॅच प्रोसेसिंग, किंवा बॅकग्राउंड जॉब्स.

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — रिलायबिलिटी पेनल्टीसह सर्वात कमी p95 लेटन्सी

`p95LatencyMs + (errorRate * 1000)` नुसार सॉर्ट करते. एरर-रेट पेनल्टी हे सुनिश्चित करते की अविश्वसनीय प्रोव्हायडर्सना कमी रँक दिली जाते, जरी त्यांची नाममात्र लेटन्सी कमी असली तरीही.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कधी वापरावे**: रिअल-टाइम चॅट, ऑटो-कम्प्लीट, किंवा इंटरअॅक्टिव्ह कोडिंग असिस्टंट्स सारखे लेटन्सी-सेन्सिटिव्ह वर्कलोड्स.

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — लेटन्सी/एरर/कॉस्ट SLO अनुपालन

प्रत्येक कॅंडिडेटने कॉन्फिगर केलेली SLO पॉलिसी किती चांगल्या प्रकारे पूर्ण केली आहे त्यानुसार स्कोर करते:

| घटक               | वजन | सूत्र                                                   |
| ----------------- | --- | ------------------------------------------------------- |
| लेटन्सी स्कोअर    | 35% | `threshold / max(value, ε)`                             |
| एरर स्कोअर        | 35% | `threshold / max(value, ε)`                             |
| हेल्थ स्कोअर      | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)       |
| कॉस्ट स्कोअर      | 10% | `threshold / max(value, ε)` किंवा इन्व्हर्स नॉर्मलाइज्ड |
| स्टॅबिलिटी स्कोअर | 5%  | इन्व्हर्स नॉर्मलाइज्ड लेटन्सी stddev                    |

जेव्हा `hardConstraints: true` असते, तेव्हा उमेदवारांना (candidates) प्रामुख्याने **व्हायोलेशन स्कोअर** (ते कोणत्याही SLO च्या किती पलीकडे जातात) नुसार आणि त्यानंतर कंपोझिट स्कोअरनुसार क्रमवारी लावली जाते. अन्यथा, फक्त कंपोझिट स्कोअर वापरला जातो.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA फील्ड्स** (कॉम्बो कॉन्फिगवर सेट केलेले):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**कधी वापरावे**: कडक लेटन्सी, एरर-रेट किंवा कॉस्ट बजेट असलेले प्रोडक्शन वर्कलोड्स.

**अलायसेस**: `sla-aware`, `sla`

---

#### 5. `lkgp` — शेवटचा ज्ञात चांगला प्रोव्हायडर (last known good provider) प्रथम

**शेवटचा ज्ञात चांगला प्रोव्हायडर** (जर सेट केला असेल तर) प्रथम वापरून पाहतो, त्यानंतर `rules` स्ट्रॅटेजीवर परत येतो. सेशन स्टिकनेससाठी उपयुक्त — संभाषणातील फॉलो-अप विनंत्या एकाच प्रोव्हायडरद्वारे हाताळल्या जातात.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**कधी वापरावे**: मल्टी-टर्न संभाषणे जिथे तुम्हाला फॉलो-अप विनंत्या एकाच प्रोव्हायडरने हाताळाव्यात असे वाटते (उदा. कॅशिंग, संदर्भ सातत्य किंवा किंमतीतील सुसंगततेसाठी).

**अलायस**: `lkgp` (कोणताही अलायस नाही)

---

#### 6. `nadir` — Nadir द्वारे प्रॉम्प्ट-अवेअर मॉडेल निवड

वरील प्रत्येक स्ट्रॅटेजी उमेदवारांना त्यांच्या स्वतःच्या टेलिमेट्रीनुसार रँक करते; त्यापैकी कोणीही विनंती वाचत नाही. `nadir` शेवटचा युजर टर्न आणि पूलचे मॉडेल आयडी [Nadir](https://getnadir.com) च्या डिसिजन API (`POST /v1/bucket`) कडे पाठवते आणि त्या मेनूमधून Nadir ने निवडलेल्या मॉडेलवर रूट करते (`simple` → सर्वात स्वस्त सक्षम मॉडेल, `complex` → फ्रंटियर मॉडेल). त्या मॉडेलला सर्व्ह करणारे कनेक्शन अजूनही `rules` द्वारे निवडले जाते, त्यामुळे कोटा, हेल्थ आणि कॉस्ट हे ठरवत राहतात की कोणते खाते वापरायचे.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` आणि `OMNIROUTE_NADIR_BASE_URL` हे दोन स्ट्रिंग्ससाठी env फॉलबॅक आहेत. `baseUrl` फक्त सेल्फ-होस्टेड Nadir साठी आवश्यक आहे (शेवटी `/v1` चालते). की-लेस कॉल्स Nadir च्या ॲनॉनिमस टियरवर जातात, ज्यावर प्रति IP रेट-लिमिट असते.

बॉक्समधून काय बाहेर जाते: शेवटच्या युजर मेसेजचा मजकूर (पहिले 16k कॅरेक्टर्स), उमेदवार मॉडेल आयडी आणि एक `source: "omniroute"` चॅनेल टॅग. कोणताही सिस्टम प्रॉम्प्ट, इतिहास, टूल्स किंवा हेडर्स नाहीत.

फेल्युअर बिहेवियर फेल-ओपन आहे: टाइमआउट (डिफॉल्ट 2000 ms), नॉन-2xx, न पोहोचता येणारा होस्ट, चुकीचा रिस्पॉन्स किंवा पूलच्या बाहेरील निवड `rules` निर्णयावर रिझॉल्व्ह होते आणि कारणाचे प्रीफिक्स `NadirStrategy: fallback (…)` असे असते. अयशस्वी कॉल नंतर स्ट्रॅटेजी 30 सेकंदांसाठी नेटवर्क वगळते, त्यामुळे आउटेजचा खर्च प्रति विनंती एक टाइमआउट ऐवजी दर 30 सेकंदाला एक टाइमआउट असा होतो. राउटिंग इव्हेंट्स फक्त तेव्हाच `strategy: "nadir"` रिपोर्ट करतात जेव्हा Nadir ने प्रत्यक्ष निवड केली असते.

**कधी वापरावे**: मॉडेल टियर्स (एक लहान, एक मध्यम आणि एक फ्रंटियर मॉडेल) असलेल्या पूलवर मिश्र-कठिणतेचा ट्रॅफिक, जिथे तुम्हाला नेहमी-फ्रंटियरचा खर्च कमी करायचा आहे.

**अलायस**: `nadir` (कोणताही अलायस नाही)

### कस्टम राउटर स्ट्रॅटेजीज

तुम्ही पब्लिक API द्वारे तुमची स्वतःची `RouterStrategy` इम्प्लिमेंटेशन रजिस्टर करू शकता:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

नंतर ते वापरा:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### राउटर स्ट्रॅटेजी निवड मार्गदर्शक

| वापर प्रकरण     | स्ट्रॅटेजी  | कारण                                         |
| --------------- | ----------- | -------------------------------------------- |
| संतुलित वर्कलोड | `rules`     | डिफॉल्ट — सर्व घटक विचारात घेते              |
| खर्च कमी करा    | `cost`      | नेहमी सर्वात स्वस्त निवडते                   |
| लेटन्सी कमी करा | `latency`   | सर्वात वेगवान विश्वासार्ह प्रोव्हायडर निवडते |
| कडक SLOs        | `sla-aware` | p95/एरर/कॉस्ट थ्रेशोल्डनुसार फिल्टर करते     |
| मल्टी-टर्न चॅट  | `lkgp`      | सेशन स्टिकनेस                                |
| मिश्र अडचण      | `nadir`     | प्रति प्रॉम्प्ट मॉडेल टियर निवडते            |

SLA-aware फील्ड्स:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## कार्य अनुरूपता

6 कार्य प्रकारांमध्ये (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) 30+ मॉडेलचे गुणांकन केले आहे. वाइल्डकार्ड पॅटर्नना समर्थन देते (उदा., `*-coder` → उच्च कोडिंग गुण).

## Auto व्हेरिएंटचा आढावा

मूळ `auto` (डीफॉल्ट) आणि `autoPrefix.ts` मध्ये घोषित केलेल्या 6 `AutoVariant` मूल्यांसह, एकूण **7 वापरता येण्याजोगे मॉडेल ID** आहेत:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` मध्ये स्वतः 6 मूल्ये आहेत; 7 वा पर्याय म्हणजे "कोणताही व्हेरिएंट नाही" — मूळ `auto` — जो `parseAutoPrefix()` द्वारे `variant: undefined` म्हणून हाताळला जातो.)

## टियर्स Auto-Combo मध्ये कसे बसतात

16-घटकांचे स्कोअरिंग फंक्शन (`open-sse/services/autoCombo/scoring.ts`) टियर
सदस्यत्वाला दोन सिग्नल्स म्हणून हाताळते: `tierPriority` (0.0476) आणि `tierAffinity` (0.0476). संपूर्ण
`DEFAULT_WEIGHTS` संचासाठी वरील अधिकृत [स्कोअरिंग घटक तक्ता](#how-it-works-persisted-auto-combos) पहा — प्रत्येक पॅकसाठीचे ओव्हरराइड्स (ship-fast/cost-saver/quality-first/
offline-friendly) "प्रत्येक पॅकसाठी वेट प्रोफाइल्स" तक्त्यात दिले आहेत.

केवळ टियरमुळे Tier 1 ला **अनिवार्यपणे** पहिले स्थान मिळत नाही — Tier 1 ची लेटन्सी खराब असल्यास किंवा
किंमत-विरुद्ध-गुणवत्ता इष्टतम नसल्यास, Tier 2 जिंकतो. टियर क्रम अनिवार्य करण्यासाठी, कॉम्बो
स्ट्रॅटेजी `priority` वापरा आणि प्रोव्हायडर्सची टियरनुसार मांडणी करा.

Tier 1 (सबस्क्रिप्शन) ला ठळक प्राधान्य देण्यासाठी, `tierPriority` चे वेट वाढवा:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

टियरच्या व्याख्या आणि प्रोव्हायडर वर्गीकरणासाठी [`docs/guides/TIERS.md`](../guides/TIERS.md) पहा.

## चाचणी आणि कव्हरेज

### निर्धारक राउटिंग-निर्णय मॅट्रिक्स (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` मॉक केलेल्या अपस्ट्रीमसह प्रत्यक्ष कॉम्बो पाइपलाइनद्वारे सर्व 19
सार्वजनिक स्ट्रॅटेजींचा एंड-टू-एंड राउटिंग **निर्णय** सिद्ध करते.
कव्हरेजमध्ये पुढील गोष्टी समाविष्ट आहेत:

- सर्व 19 `ROUTING_STRATEGY_VALUES` स्ट्रॅटेजी (ordered, weighted, cost, context, fusion, …).
- `quota-share` (अंतर्गत) एंड-टू-एंड: प्रत्यक्ष `selectQuotaShareTarget` सीमेद्वारे DRR निष्पक्षता + संपृक्ततेनुसार कमी प्राधान्य
  (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- प्रत्येक लक्ष्य संख्येसाठी `context-relay` युनिव्हर्सल-हँडऑफ कव्हरेज.

हा संच CI मध्ये (`test:integration` जॉब) `--test-concurrency=1` आणि
`--test-force-exit` सह चालतो, त्यामुळे तो निर्धारक असतो आणि त्याला प्रत्यक्ष क्रेडेन्शियल्सची आवश्यकता नसते.

### गेटेड लाइव्ह स्मोक चाचण्या (CI मध्ये नाहीत — प्रत्यक्ष प्रोव्हायडर)

| कमांड                                  | ती काय करते                                                                                 |
| :------------------------------------- | :------------------------------------------------------------------------------------------ |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` सह इन-प्रोसेस प्रत्यक्ष राउटिंग; प्रत्यक्ष OmniRoute DB चा स्नॅपशॉट घेते |
| `npm run test:combo:live:vps`          | प्रत्यक्ष OmniRoute सर्व्हरवर HTTP कॉल (`COMBO_LIVE_BASE_URL` सेट करा)                      |
| `npm run test:combo:live:vps:failover` | तेच, परंतु हेतुपुरस्सर फेलओव्हर परिस्थितींसह                                                |

या स्मोक चाचण्या प्रत्यक्ष वायर मार्गाची (कॉम्बो → प्रोव्हायडर → कम्प्लिशन) चाचणी करतात. त्यांना
प्रत्यक्ष क्रेडेन्शियल्स आणि VPS प्रवेश आवश्यक असल्यामुळे त्या हेतुपुरस्सर CI मधून वगळल्या आहेत.
