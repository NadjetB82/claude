## Автоматично маршрутизиране без конфигурация (префикс `auto/`)

> **НОВО:** Не е необходимо създаване на комбинация. Използвайте префикса `auto/` директно във всеки клиент.

### Бързи примери

| Идентификатор на модел | Вариант         | Поведение                                                                                         |
| ---------------------- | --------------- | ------------------------------------------------------------------------------------------------- |
| `auto`                 | по подразбиране | Всички свързани доставчици, стратегия LKGP, балансирани тегла                                     |
| `auto/coding`          | програмиране    | Тегла с приоритет върху качеството, подходящи за генериране на код                                |
| `auto/fast`            | бърз            | Претеглен избор с ниска латентност                                                                |
| `auto/cheap`           | евтин           | Оптимизирано по цена маршрутизиране (първо най-ниската цена)                                      |
| `auto/offline`         | офлайн          | Предпочита доставчиците с най-висока налична квота                                                |
| `auto/smart`           | интелигентен    | Приоритет върху качеството + по-висока степен на изследване (10%) за по-добро откриване на модели |
| `auto/lkgp`            | lkgp            | Изрично LKGP (същото като стандартното `auto`)                                                    |
| `auto/chaos`           | хаос            | Паралелно разпределяне, по един модел за всеки доставчик (не е инжектиране на неизправности)      |

### Композиция категория × ниво (`auto/<category>:<tier>`)

Суфиксите в стил OpenRouter разделят **какъв вид маршрут** (категория) от **начина на оптимизирането му** (ниво), така че да можете свободно да ги комбинирате (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Категории** (филтрират набора от кандидати според възможностите): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` запазват моделите с възможности за визуална обработка; `reasoning` запазва моделите за логическо разсъждение/мислене.
- **Нива** (избират теглата за оценяване/филтъра на набора): `fast` (бързо изпълнение) · `cheap` (псевдоним `floor`, пестене на разходи) · `reliable` (състояние на прекъсвача на веригата + стабилност на латентността) · `free` / `pro` (филтрират набора според нивото на модела чрез `classifyTier` — безплатно спрямо премиум ниво).

| Пример                 | Резултат                                                                   |
| ---------------------- | -------------------------------------------------------------------------- |
| `auto/coding:fast`     | набор за програмиране, тегла за ниска латентност                           |
| `auto/coding:cheap`    | набор за програмиране, оптимизиран по цена (псевдоним `auto/coding:floor`) |
| `auto/reasoning:pro`   | само модели за логическо разсъждение/мислене, премиум ниво                 |
| `auto/vision`          | модели с възможности за визуална обработка (без ниво → балансирани тегла)  |
| `auto/multimodal:free` | модели с мултимодални възможности, само безплатното ниво                   |

Всяка валидна стойност `auto/<category>[:<tier>]` се разрешава при поискване; подбрано подмножество се обявява в `/v1/models` и таблото за управление (`AUTO_SUFFIX_VARIANTS` в `open-sse/services/autoCombo/builtinCatalog.ts`). Филтрирането е **fail-open** — ако никой свързан модел не отговаря на дадено ограничение, се използва пълният набор, така че маршрутизирането никога да не прекъсва. Основният механизъм за оценяване (`combo.ts`) не е променен; филтърът за категория/ниво се прилага в `buildAutoCandidates`.

> **Актуални данни за моделите:** пригодността за автоматично маршрутизиране се определя от актуалните класации **Arena ELO** + данните за нива от **models.dev**, когато флагът `ARENA_ELO_SYNC_ENABLED` е включен (в противен случай се използва статичната карта за пригодност).

**Начин на използване:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**Какво се случва:**

1. OmniRoute открива префикса `auto/` в `src/sse/handlers/chat.ts`
2. Извлича от базата данни всички **активни връзки към доставчици**
3. Филтрира само тези с валидни идентификационни данни (API ключ или OAuth токен)
4. Определя модела за всяка връзка (`connection.defaultModel` или първия модел на доставчика)
5. Създава **виртуална комбинация** в паметта (не се съхранява в БД)
6. Маршрутизира чрез профила с тегла на избрания вариант + стратегията LKGP

**Основни свойства:**

- ✅ **Винаги активно:** Не са необходими превключвател, създаване на комбинация или конфигуриране
- ✅ **Динамично:** Автоматично отразява текущо свързаните доставчици
- ✅ **Привързаност на сесията:** LKGP гарантира, че последният успешен доставчик е с приоритет
- ✅ **Поддръжка на множество акаунти:** Всяка връзка към доставчик става отделен кандидат
- ✅ **Без запис в БД:** Виртуалната комбинация съществува само за заявката, без допълнителни разходи за съхранение

### Контрол на кандидатите за всеки ключ (#7819, ниво 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = суфиксът след `auto/` или
буквалната стойност `auto` за основния канал) е крайна точка **само за четене**, която изброява
текущия набор от кандидати на даден канал `auto/*`, допълнен с актуални данни за достъпност, като използва повторно
съществуващите механизми за четене на устойчивостта (никога директно полето `state` на прекъсвача):

- прекъсвач на веригата на доставчика — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- период на изчакване на връзката — `rateLimitedUntil` / `testStatus` в разрешения
  ред на `provider_connections`
- блокиране на модела — `isModelLocked(provider, connectionId, model)`

Всеки кандидат съдържа и флага `excluded` за този API ключ. Изключванията се съхраняват
за всеки API ключ поотделно (таблица `auto_candidate_overrides`, миграция `128`) — OmniRoute е
едноинстанционна система без таблица `users`, затова `apiKeyId` е най-близкият реален
идентификатор за отделния извикващ — и се прилагат в общата контролна точка на набора от кандидати в
`open-sse/services/autoCombo/virtualFactory.ts` чрез чистата и покрита с модулни тестове функция
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Филтърът е **fail-open**: липсваща стойност за apiKeyId/канал или грешка при заявка към БД
оставят набора нефилтриран, така че оператор без конфигурирани замествания получава маршрутизиране,
побитово идентично с това отпреди въвеждането на тази функционалност.

**Отложено за последваща задача:** тегла за отделните кандидати + изрично подреждане (Ниво 3
— включва се в съществуващите пътища за стратегии с тегла/приоритети) и фиксиране на конкретна
стратегия от `combo.ts` за всеки канал `auto/*` (Ниво 4). Вижте плана в #7819 за отворения
въпрос дали заместванията трябва да останат за отделен API ключ, или да станат глобални предвид
модела с един клиент.

**Зад кулисите:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

| Файл                                                      | Предназначение                                          |
| --------------------------------------------------------- | ------------------------------------------------------- |

## Имена на комбинации, които съвпадат с реален идентификатор на модел

Комбинация, чието `name` е идентично с непредшестван от префикс идентификатор на модел (напр. комбинация с име
`gpt-5.5`), е **преднамерен и поддържан модел на използване**, а не грешка: това е
механизмът за резервно превключване между доставчици за конкретен идентификатор на модел, документиран в
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Тъй като разрешаването на комбинации
се проверява преди разрешаването на непредшествани от префикс идентификатори на модели
(`getComboForModel()` в `src/sse/services/model.ts`), заявка за непредшествания от префикс
идентификатор `gpt-5.5` се насочва през целите на комбинацията (напр.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), вместо директно към
един доставчик — така се използва приоритетът „комбинация преди пренаписване“, създаден за
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227), а регресионното му тестване се извършва чрез
`tests/unit/responses-combo-resolution-3227.test.ts` и
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Създаването или преименуването на комбинация с име, което засенчва реален идентификатор на модел,
**никога не се отхвърля** — това би нарушило този документиран работен процес. Вместо това
(#8530), `POST /api/combos` и `PUT /api/combos/[id]` добавят неблокиращо
поле `warning` към отговора, когато (новото) име влиза в конфликт с реален
идентификатор на модел:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

При стартиране `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) също записва едноредово предупреждение `[STARTUP]`,
изброяващо всяка съществуваща комбинация, която засенчва идентификатор на модел, така че операторите, които
попаднат на това случайно (вместо преднамерено съгласно #6940), да получат сигнал.
Помощната функция за откриване се намира в `src/lib/combos/modelNameCollision.ts`.

## Извикване на персонализирана комбинация от клиент

Запазените комбинации (Настройки → Комбинации) се използват само когато клиентът изпрати **точното име** на комбинацията в полето `model` — няма приблизително или частично съвпадение на името на комбинацията и не се използва префикс `auto/`. Ред на разрешаване (`getComboForModel()` в `src/sse/services/model.ts`):

1. точно съвпадение с име на комбинация (`model: "my-combo"`),
2. префикс `combo/<name>` (`model: "combo/my-combo"`),
3. glob съпоставяния модел→комбинация (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Два често срещани проблема:

- **`auto` не използва вашите комбинации.** `auto`/`auto/*` изгражда собствен набор от кандидати без необходимост от конфигуриране и използва запазените комбинации само ако дадена комбинация буквално се казва `auto` (не се препоръчва). За насочване през комбинация изпратете точното ѝ име — не `auto`.
- **`openrouter/auto` е реален платен продукт на OpenRouter** („Автоматично най-добрият наличен“), а не псевдоним на OmniRoute. Това е единственият статичен запис за модел в регистъра на OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) и се таксува отделно. Използвайте Настройки → Маршрутизиране → Скриване на платените модели, за да го изключите от наборите на `auto`.

Вижте [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) и [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) за първоначалното объркване, което е документирано тук.

## Как работи (Персистирани Auto-Combos)

Auto-Combo Engine динамично избира най-добрия доставчик/модел за всяка заявка, използвайки **16-факторна функция за оценяване** (дефинирана в `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Теглата по подразбиране дават сбор `1.0`; персонализираните тегла се ренормализират чрез `normalizeScoringWeights()`. Два от шестнадесетте — `cacheAffinity` и `resetWindowAffinity` — имат тегло по подразбиране `0`; `reliability` е с `0` в `DEFAULT_WEIGHTS`, но `0.03` в generic пакетите и `0.04` в `reliability-first`, а `quality` носи `0.02` в пакетите (`0.03` в `quality-first`): те все пак се изчисляват за всеки кандидат, а `cacheAffinity` управлява дедупликацията на prompt-cache извън скора, така че факторите с нула по подразбиране просто не гласуват по подразбиране, докато пакетите го правят.

![Auto-Combo 16-факторно оценяване](../diagrams/exported/auto-combo-scoring.svg)

> Източник: [diagrams/auto-combo-scoring.mmd](../diagrams/auto-combo-scoring.mmd) (прегенерирайте чрез `npm run docs:render-diagrams`). Името на файла е историческо; изходният код и рендерираната диаграма показват всички 16 фактора, декларирани в `DEFAULT_WEIGHTS`.

| :-------------------- | :-------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quota`               | 0.1429                | Оставаща квота / свободен капацитет от rate-limit [0..1]                                                                                                                                                                           |

| `cacheAffinity`       | 0.00                  | Rendezvous-hash афинитет към връзката, за която е най-вероятно вече да съдържа prompt-cache префикса на тази заявка (`open-sse/services/combo/promptCacheAffinity.ts`); изключено по подразбиране (#8008)                          |

| `reliability`         | 0.00                  | Наблюдаван дял на успеваемост, `1 - failureRate`, от 24-часова история на използване с минимум десет извадки (в противен случай метрики в реално време); кандидатите без наблюдения се отчитат като 1.0. Изключено по подразбиране |

> **Нечетима квота (#15347).** Когато даден доставчик има извличащ модул за квота (quota fetcher), но той не връща нищо
> четливо (неуспешно извличане, липсващи идентификационни данни, използване само под формата на съобщение или деформирана моментна снимка без
> валидни за парсване `windows` и без крайна стойност за `percentUsed`, включително `percentUsed: null`), кандидатът
> получава резултат `0` по оста `quota` и крайният му резултат се умножава по
> `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`), по същия модел на мека санкция (soft penalty),
> какъвто е и санкцията за състояние на връзката. Неуспешното отчитане на потреблението е доказателство за телеметрията,
> а не за доставчика, така че той се класира стриктно под всяко реално отчитане, включително потвърдено 100% използвано
> такова, но никога не бива твърдо блокиран или изваден от употреба. Доставчик без лимит отчита `unlimited: true` и
> получава оценка за пълна квота; доставчик без регистриран модул за извличане на квота няма никакъв източник на телеметрия
> и запазва стойността по подразбиране от `100`.

**Сума:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0`, както е декларирано в `DEFAULT_WEIGHTS`; конфигурираните от потребителя тегла се ренормализират в разпределение чрез `normalizeScoringWeights()` преди оценяването.

При студен пул (все още няма наблюдения, така че `quality 0.5` и `reliability 1`) тези два фактора добавят `+0.04` при общ пакет (`0.03 + 0.01`), `+0.045` при `quality-first` и `+0.05` при `reliability-first`.

- Накратко за акцента на всеки пакет:

  - **offline-friendly** → quota 0.3324 + health 0.2667 (максимален наличен резерв независимо от скоростта/цената)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04, най-високата стойност сред всички пакети (най-малко изненади)

"cheapest") на дадена комбинация определя постоянната политика; заглавката я заменя за една отделна заявка.

## Всички стратегии за маршрутизация

Комбо двигателят на OmniRoute поддържа **20 стратегии за маршрутизация** (декларирани в `src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES`). Самият двигател Auto Combo е изложен под стратегията `auto`; останалите са налични за постоянни комбота.

| Стратегия           | Описание                                                                                                                                                                                                            |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `priority`          | Списък с подредени цели с изричен приоритет                                                                                                                                                                         |
| `weighted`          | Претеглен случаен избор според теглото на всяка цел                                                                                                                                                                 |
| `round-robin`       | Циклично преминаване през целите по ред (партидно; виж по-долу)                                                                                                                                                     |
| `context-relay`     | Прехвърляне на контекст между цели (дълги разговори)                                                                                                                                                                |
| `fill-first`        | Запълване на квотата на всяка цел преди преминаване към следващата                                                                                                                                                  |
| `p2c`               | Балансиране на натоварването чрез случаен избор "Power-of-2-choices"                                                                                                                                                |
| `random`            | Равномерен случаен избор                                                                                                                                                                                            |
| `least-used`        | Избор на цел с най-ниско текущо натоварване                                                                                                                                                                         |
| `cost-optimized`    | Минимизиране на $ за заявка спрямо ценоразписа в каталога                                                                                                                                                           |
| `reset-aware` ⭐    | Приоритизиране според времето за нулиране на квотата — кратките прозорци за нулиране са с по-висок ранг                                                                                                             |
| `reset-window`      | Предпочитане на цели, чийто прозорец за квота се нулира най-скоро                                                                                                                                                   |
| `headroom`          | Избор на цел с най-голям оставащ капацитет на квотата                                                                                                                                                               |
| `quota-weighted`    | Пропускане на изчерпаните акаунти, след което избор измежду останалите пропорционално на оставащата квота, разделена на текущото натоварване; съществуващите разговори остават фиксирани                            |
| `strict-random`     | Случаен избор без дедупликация на повторенията                                                                                                                                                                      |
| `auto`              | Използване на оценяване Auto Combo (16-факторно) — **препоръчително**                                                                                                                                               |
| `lkgp`              | Последен известен добър път (фиксира се към последния успешен доставчик, след което преминава към правила)                                                                                                          |
| `context-optimized` | Избор на цел с най-добро съответствие за текущия размер на контекста                                                                                                                                                |
| `cache-optimized`   | Пренареждане на целите според афинитета към кеша на промпта — връзката, която най-вероятно вече съдържа кеширания префикс на тази заявка, се опитва първа (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | Разпръскване към панел от модели паралелно, след което синтезиране на един отговор чрез съдия (виж по-долу)                                                                                                         |
| `pipeline`          | Изпълнение на целите последователно, прехвърляйки изхода на всяка стъпка към входа на следващата; връща се само крайният отговор (#6396)                                                                            |

⭐ = Ново във v3.8.0 · 🧬 = Ново във v3.8.36

### Семантика на `weighted`

`weighted` е **пропорционален случаен избор за всяка заявка**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), а не изравнител:

- Всяка заявка избира **една** стъпка с вероятност `weight / totalWeight`; останалите стъпки
  се подреждат по низходящо тегло като верига за резервен вариант (fallback) за тази заявка.
- Стъпка, чието тегло е `0` (или липсва), **никога не се избира**, докато някоя друга стъпка има
  тегло > 0 — тя може да служи само като резервен вариант, след като избраната стъпка се провали. Само когато **всички**
  тегла са 0, изборът става равномерен.
- Стъпките, чиито цели са недостъпни — прекъсвач на доставчика `OPEN`, охлаждане на връзката,
  блокиране на модела — се премахват от избора, преди той да се случи
  (`open-sse/services/combo/targetResolution.ts`), така че една-единствена здрава стъпка може временно
  да печели всяка заявка.
- `stickyWeightedLimit` (конфигурация на комбо, по подразбиране `1` = изключено) фиксира избраната стъпка за толкова последователни успехи, преди да се извърши нов избор.

За стриктна ротация използвайте `round-robin`; еднаквите тегла при `weighted` дават статистически — не стриктен — баланс.

### Режим на агентен конвейер (Agentic pipeline mode)

Комбинация от тип `pipeline` с поне два модела може да се включи в маршрутизиране тип планировчик/изпълнител (planner/executor) чрез `config.agenticOrchestration.enabled`. Първата цел отговаря за планирането и крайните отговори; втората цел излъчва извиквания на инструменти, специфични за клиента (client-native tool calls). OmniRoute засича продължения на резултати от инструменти от протокола на заявката, пита планировчика дали е необходим още един кръг с инструменти и динамично прави или изпълнителя, или планировчика крайна стъпка към клиента.

Опционалната настройка `config.agenticOrchestration.contextCompaction` прилага отделен бюджет за полезния товар (payload) преди всяко изпращане към планировчика или изпълнителя. Активирайте я изрично:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

Това са бюджети от символи в сериализиран JSON, избрани от оператора, а не прозорци с контекст от токени или гарантирани лимити нагоре по веригата. Точните идентификатори на моделите (model IDs) презаписват настройките по подразбиране. Над прага, компресирането премахва идентични дефиниции на инструменти, подрязва твърде големи доказателства от инструменти с резюме (digest) и премахва стари групи от пълната история, за да се достигне целевото съотношение. То запазва системните/разработчическите инструкции, последната заявка на потребителя, последния кръг с инструменти, включително паралелни извиквания/резултати, и водещата инструкция за маршрутизиране на Gemini. Инструкциите на най-високо ниво и настройките на инструментите се запазват. Маркер за пропуск записва премахнатата история; това е детерминистично подрязване, а не семантично резюме. Ако фиксираният контекст все още надвишава бюджета, заявката връща 413 преди да се свърже с модела. Когато компресирането е деактивирано или е под прага, заявката преминава непроменена.

Допълнителните модели след втората цел са подредени резервни изпълнители. Неуспешен HTTP отговор или транспортно изключение преминава към следващия изпълнител, носейки същото решение на планировчика и нативни инструменти, но със собствения промпт за стъпка и разрешена връзка на този изпълнител. Първият успешен отговор се връща непроменен, включително SSE стрийминг; грешки след стартиране на успешен поток не могат да бъдат повторени тук. Ако всички изпълнители се провалят, се връща последната грешка. Прекъсванията от страна на клиента спират изпращането.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Изпълнителят може да излъчи множество независими извиквания в един отговор. Зависимите извиквания се обработват в по-късни ходове с резултати от инструменти на клиента, като планировчикът преглежда всеки резултат. `maxToolRounds` е по подразбиране `8` и приема стойности от `1` до `32`; след достигане, планировчикът трябва да предостави най-добрия наличен краен отговор. Вътрешните решения на планировчика се буферират, докато избраният отговор към клиента запазва първоначалните предпочитания за стрийминг.

### `round-robin` sticky batch и разширяване на акаунти

Round-robin е на партиди (batched), а не по една заявка на стъпка:

- `stickyRoundRobinLimit` (конфигурация на комбинацията, след това `comboStickyRoundRobinLimit`, след това `settings.stickyRoundRobinLimit`, по подразбиране **3**) запазва същата цел за толкова последователни успехи, преди да се завърти. Задайте презаписването на комбинацията на `1` за ротация с една заявка. Редакторът на комбинации показва ефективната стойност и от кой слой идва тя.
- `connectionAwareExpansion` (конфигурация на комбинацията, след това настройки, по подразбиране **false**) разширява всяка стъпка на ниво доставчик в цели за всеки акаунт преди ротацията. Стратегиите от група B (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) поддържат изглед на ниво доставчик, докато това не е включено. Редакторът на комбинации излага опциите inherit / on / off; inherit използва глобалната настройка по подразбиране (off).
- Маршрутизирането според локалността на кеша на промпта (`promptCacheAffinityEnabled`, по подразбиране **true**) пренарежда фиксираните връзки, така че съвпадащите кеш ключове да останат в един акаунт. То има предимство пред round-robin и weighted ротацията при фиксирани стъпки за всеки акаунт. Изключете го в Settings → Combo defaults, ако се нуждаете от стриктна ротация. Няма презаписване за всяка комбинация (per-combo override).

За ротация между множество акаунти при един модел, предпочитайте **една стъпка с динамичен акаунт** (празен `connectionId`, целия пул) с лимит на лепкавост (sticky limit) `1`, а не три фиксирани `connectionId`s. Фиксираните стъпки плюс афинитета се свиват към един и същ акаунт, дори докато броячът на RR се увеличава.

## Стратегия Fusion

`fusion` е единствената стратегия, която **не** избира една конкретна цел. Тя разпраща подканата
към **всеки модел в панела паралелно**, след което конфигурируем **модел-съдия** синтезира
един окончателен отговор от всички отговори на панела. Пренесена от оригиналния проект `decolua/9router`
(дизайна Fusion на OpenRouter); имплементацията е в `open-sse/services/fusion.ts`.

Как работи:

0. **Заобикаляне при наличие на инструменти** — заявка, която съдържа непразен масив `tools` и
   при която `tool_choice` не е изрично зададено на `"none"`, пропуска изцяло панела: тя се насочва директно към
   един модел (конфигурирания съдия или `panel[0]`), като `tools`/`tool_choice`
   се предават без промени. Членовете на панела нямат достъп до инструменти, а
   директивата за синтез на съдията обезкуражава генерирането на извиквания на инструменти, така че агентните клиенти или клиентите,
   извикващи инструменти, получават реално решение за извикване на инструмент вместо синтезиран текст (#6771).
1. **Паралелно разпращане** (само за заявки без инструменти) — подканата се изпраща едновременно до всеки модел
   в панела, като принудително се изключва поточното предаване и инструментите се премахват (съдията се нуждае от завършен
   текст, за да извърши синтеза).
2. **Събиране с кворум и гратисен период** — веднага щом пристигнат `minPanel` отговора, се стартира кратък гратисен
   таймер за изоставащите, след което Fusion продължава с всичко събрано.
   Това ограничава влиянието на най-бавния модел върху общото време, в рамките на строг краен срок.
3. **Синтез от съдията** — отговорите на панела се анонимизират (`Source 1`, `Source 2`, … — така
   съдията оценява съдържанието, а не марката на модела) и се предават на съдията, който анализира
   съгласуваността / противоречията / частичното покритие / уникалните прозрения / пропуските, след което
   съставя **един** авторитетен отговор. Извикването на съдията запазва оригиналния флаг
   `stream` на клиента + инструментите, така че поточното предаване и последващото използване на инструменти продължават да работят.
4. **Плавно влошаване** — 0 отговора от панела → `503`; точно 1 оцелял отговор → този отговор
   се връща директно (няма какво да се обединява); панел с един модел отговаря директно.

Член на панела може също да бъде стъпка `combo-ref` (`{kind: "combo-ref", comboName: "..."}`), препращаща
към друга комбинация — тя се разрешава като **един непрозрачен глас в панела** (пълно рекурсивно разпределяне към
посочената комбинация, а не паралелно разпращане към собствените ѝ цели), със същата защита от прекомерна дълбочина/цикли,
която вече използва всяка друга стратегия, обработваща `combo-ref` (#6764).

### Конфигурация

Конфигурира се в обекта `config` на комбинацията (без миграция на схемата — използва повторно съществуващата
таблица `combos`):

| Поле                                     | Тип      | По подразбиране        | Предназначение                                                                                       |
| :--------------------------------------- | :------- | :--------------------- | :--------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | първият модел в панела | Моделът, който синтезира окончателния отговор                                                        |
| `config.fusionTuning.minPanel`           | `number` | `2`                    | Необходим брой успешни отговори, преди да стартира гратисният таймер (ограничен до `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`                 | Колко дълго да се изчакват изоставащите след достигане на кворума                                    |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`                | Абсолютно ограничение, така че един блокирал модел да не задържи заявката                            |

Стойностите по подразбиране се намират във `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`).

### Пример

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

След това я извикайте като всяка друга комбинация: `{"model":"fusion-panel","messages":[...]}`.

## Виртуална фабрика за Auto-Combo

Механизмът Auto Combo не изисква предварително дефинирани комбинации. Вместо това `open-sse/services/autoCombo/virtualFactory.ts` създава кандидатите динамично:

1. Извлича `getProviderConnections({ isActive: true })` (всички активирани връзки)
2. Филтрира тези с валидни идентификационни данни (API ключ или неизтекъл OAuth токен чрез `hasUsableOAuthToken()`)
3. Прави кръстосана проверка с `getProviderRegistry()` за наличност на модели и ценообразуване
4. За всеки кортеж `(provider, model, connection)` създава `VirtualAutoComboCandidate`
5. Избира `connection.defaultModel` (или първия модел в регистъра) като цел за изпращане
6. Оценява всеки кандидат чрез 16-факторния `scorePool()` и пакета с тегла на варианта
7. Връща получения в паметта `AutoComboConfig` за `handleComboChat()` — никога не се съхранява в БД

Това означава, че **добавянето на нов доставчик с активирано `auto/*` автоматично разширява набора от кандидати** — не е необходимо ръчно редактиране на комбинацията. Виртуалната комбинация се създава отново при всяка заявка, така че новодобавените или възстановените до изправно състояние връзки се използват незабавно.

## Самовъзстановяване

- **Временно изключване**: Оценка < 0.2 → изключване за 5 мин (прогресивно увеличаване на интервала, максимум 30 мин)
- **Отчитане на прекъсвача на веригата**: OPEN → автоматично изключване; HALF_OPEN → пробни заявки
- **Режим при инцидент**: >50% OPEN → изключване на проучването, максимизиране на стабилността
- **Възстановяване след периода на изчакване**: След изключване първата заявка е „пробна“ с намалено време за изчакване

## Bandit проучване

5% от заявките (стойността може да се конфигурира) се насочват към произволни доставчици с цел проучване. Изключено е в режим при инцидент.

## API

Няма **специализиран `POST /api/combos/auto` endpoint** — Auto-Combo се използва по два начина:

1. **Zero-config (препоръчително):** Изпратете всяка заявка за chat completion с `model: "auto"` или `model: "auto/<variant>"`. Виртуалната фабрика изгражда комбинацията (combo) за всяка заявка — не е необходима постоянна памет (persistence) или API извиквания.

2. **Persisted combo със `strategy: "auto"`:** Създайте обикновена комбинация чрез `POST /api/combos` и задайте `strategy: "auto"` плюс `config.auto.weights` / `config.auto.candidatePool`. Използва се същият механизъм за оценяване; комбинацията се съхранява в `combos` и може да се използва повторно чрез ID.

За откриване (discovery), `GET /api/combos/auto` изброява всеки вариант с неговия разрешен набор от кандидати (candidate pool) плюс `context_length` / `max_output_tokens` — МАКСИМУМЪТ в прозорците на набора от кандидати. Клиентите (напр. плъгинът opencode) трябва да рекламират тези стойности вместо `0`: нулев контекст деактивира напълно автоматичното компресиране (auto-compaction) на opencode, позволявайки на сесиите да растат, докато изчистването на историята на шлюза (gateway) не унищожи контекста. Рекламирането на МАКСИМУМА е безопасно, тъй като предварителният филтър на контекста на auto-combo насочва заявките с превишен размер към кандидати с големи прозорци.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Стратегии за Auto router

Комбинациите с постоянна `strategy: "auto"` могат да зададат `config.routerStrategy` (или наследеното `config.auto.routerStrategy`) на една от следните стойности:

- `rules` — стандартно претеглено оценяване
- `score` — избира най-високия конфигуриран претеглен резултат. При точни равенства се запазва конфигурираният ред на кандидатите; съществуващият `explorationRate` взема проби от пълния класиран набор.
- `cost` / `eco` — най-евтиният изправен (healthy) доставчик
- `latency` / `fast` — най-ниска p95 латентност с наказание за надеждност
- `sla-aware` / `sla` — предпочита кандидати, които отговарят на SLO за p95 латентност, процент на грешки и опционални разходи
- `lkgp` — първо последният известен добър доставчик
- `nadir` — пита API за вземане на решения на [Nadir](https://getnadir.com) кой модел в набора е необходим за промпта; opt-in, fail-open към `rules`

### Подробности за стратегиите на рутера

Механизмът на auto-combo излага 7 pluggable реализации на **RouterStrategy**, които можете да замените чрез `config.routerStrategy` (или наследеното `config.auto.routerStrategy`). Всяка стратегия избира един доставчик от набора от кандидати, като се има предвид `RoutingContext` (тип задача, подсказки за инструменти/зрение, оценка на токени, опционална SLA политика, опционален последен известен добър доставчик).

#### 1. `rules` (по подразбиране) — 16-факторно претеглено оценяване

Обгръща съществуващия механизъм за оценяване. Филтрира кандидатите с `OPEN` прекъсвач (circuit-breaker), след което изпълнява `scorePool()` с текущия тип задача и `getTaskFitness()`, избирайки доставчика с най-висок резултат.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Кога да се използва**: По подразбиране. Използвайте, когато искате балансиран компромис между всички сигнали.

**Псевдоним**: `rules` (няма псевдоним)

---

#### 2. `cost` / `eco` — най-евтиният изправен доставчик

Сортира набора от кандидати по `costPer1MTokens` (възходящо) и избира най-евтиния. Първо филтрира кандидатите с `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Кога да се използва**: Работни натоварвания, чувствителни към разходите, пакетна обработка или фонови задачи.

**Псевдоними**: `cost`, `eco`

---

#### 3. `latency` / `fast` — най-ниска p95 латентност с наказание за надеждност

Сортира по `p95LatencyMs + (errorRate * 1000)`. Наказанието за процент на грешки гарантира, че ненадеждните доставчици се класират по-ниско, дори ако номиналната им латентност е ниска.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Кога да се използва**: Работни натоварвания, чувствителни към латентността, като чат в реално време, автоматично довършване или интерактивни помощници за кодиране.

**Псевдоними**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — съответствие с SLO за латентност/грешки/разходи

Оценява всеки кандидат според това доколко отговаря на конфигурираната SLO политика:

| Фактор               | Тегло | Формула                                                     |
| -------------------- | ----- | ----------------------------------------------------------- |
| Оценка за латентност | 35%   | `threshold / max(value, ε)`                                 |
| Оценка за грешки     | 35%   | `threshold / max(value, ε)`                                 |
| Оценка за състояние  | 15%   | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)           |
| Оценка за разходи    | 10%   | `threshold / max(value, ε)` или обратно нормализирана       |
| Оценка за стабилност | 5%    | обратно нормализирано стандартно отклонение на латентността |

Когато `hardConstraints: true`, кандидатите се сортират основно по **оценка за нарушение**
(доколко надвишават който и да е SLO), а след това по съставна оценка. В противен случай се използва само
съставната оценка.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA полета** (зададени в конфигурацията на combo):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Кога да се използва**: Работни натоварвания в продукция със строги бюджети за латентност, процент грешки или разходи.

**Псевдоними**: `sla-aware`, `sla`

#### 5. `lkgp` — първо последен известен добър доставчик

Опитва първо с **последния известен добър доставчик** (ако е зададен), след което преминава към стратегията
`rules`. Полезно за сесийна устойчивост — един и същ доставчик обработва последващи заявки в рамките на разговор.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**Кога да се използва**: Разговори с множество ходове, където искате един и същ доставчик да обработва
последващите заявки (напр. за кеширане, непрекъснатост на контекста или ценова последователност).

**Псевдоним**: `lkgp` (няма псевдоним)

#### 6. `nadir` — избор на модел, съобразен с промпта, чрез Nadir

Всяка от горните стратегии класира кандидатите според собствената си телеметрия; никоя от тях не чете
заявката. `nadir` изпраща последния ход на потребителя плюс идентификаторите на моделите в пула към API за вземане на решения на
[Nadir](https://getnadir.com) (`POST /v1/bucket`) и насочва към модела, който Nadir избира от това меню
(`simple` → най-евтиният способен модел, `complex` → най-модерният/фронтиер модел). Връзката, обслужваща този модел, все още се избира от `rules`, така че квотата, състоянието и разходите продължават да определят кой акаунт да се използва.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` и `OMNIROUTE_NADIR_BASE_URL` са алтернативи чрез променливи на средата за двата
низа. `baseUrl` е необходим само за самостоятелно хостван Nadir (накрая се толерира `/v1`).
Обажданията без ключ попадат в анонимното ниво на Nadir, което е с ограничена честота на заявките (rate-limited) на IP адрес.

Какво напуска кутията: текстът на последното потребителско съобщение (първите 16k знака), идентификаторите на моделите-кандидати и етикет на канала `source: "omniroute"`. Без системен промпт, история, инструменти или заглавки.

Поведението при отказ е fail-open: изтичане на времето (по подразбиране 2000 ms), отговор, различен от 2xx, недостъпен хост, неправилно форматиран отговор или избор извън пула се разрешават чрез решението на `rules`, а причината се префиксира с `NadirStrategy: fallback (…)`. След неуспешно обаждане стратегията пропуска мрежата за 30 секунди, така че прекъсването струва един таймаут на 30 секунди, вместо по един на заявка. Събитията за маршрутизация отчитат `strategy: "nadir"` само когато Nadir действително е направил избора.

**Кога да се използва**: трафик със смесена трудност върху пул, който обхваща нива на модели (малък, среден и фронтиер модел), където винаги-фронтиер е разходът, който искате да намалите.

**Псевдоним**: `nadir` (няма псевдоним)

### Персонализирани стратегии за рутиране

Можете да регистрирате своя собствена имплементация на `RouterStrategy` чрез публичния API:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

След това я използвайте:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## Пригодност за задачи

Над 30 модела са оценени в 6 типа задачи (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`). Поддържа шаблони със заместващи символи (напр. `*-coder` → висока оценка за програмиране).

## Обобщение на автоматичните варианти

Като се включат базовият `auto` (по подразбиране) и 6-те стойности на `AutoVariant`, декларирани в `autoPrefix.ts`, има **7 идентификатора на модели, които могат да бъдат извикани**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(Самият `AutoVariant` изброява 6 стойности; седмата опция е „без вариант“ — базовият `auto` — обработвана от `parseAutoPrefix()` като `variant: undefined`.)

## Как нивата се вписват в Auto-Combo

Функцията за оценяване с 16 фактора (`open-sse/services/autoCombo/scoring.ts`) разглежда принадлежността към ниво като два сигнала: `tierPriority` (0.0476) и `tierAffinity` (0.0476). Вижте каноничната [таблица с фактори за оценяване](#how-it-works-persisted-auto-combos) по-горе за пълния набор `DEFAULT_WEIGHTS` — заместванията за отделните пакети (ship-fast/cost-saver/quality-first/offline-friendly) са изброени в таблицата „Профили на теглата за всеки пакет“.

Самото ниво **не** налага първо да се използва Ниво 1 — ако латентността на Ниво 1 е висока или съотношението цена-качество не е оптимално, Ниво 2 печели. За да наложите подреждане по нива, използвайте стратегията `priority` за комбинацията и подредете доставчиците по ниво.

За да дадете силно предимство на Ниво 1 (абонамент), увеличете теглото на `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Вижте [`docs/guides/TIERS.md`](../guides/TIERS.md) за дефинициите на нивата и класификацията на доставчиците.

## Тестване и покритие

### Детерминирана матрица за решенията за маршрутизиране (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` доказва **решението** за маршрутизиране на всичките 19 публични стратегии от край до край чрез реалния конвейер за комбинации със симулиран външен доставчик. Покритието включва:

- Всичките 19 стратегии `ROUTING_STRATEGY_VALUES` (подредена, претеглена, по цена, по контекст, сливане, …).
- `quota-share` (вътрешна) от край до край: справедливост чрез DRR + понижаване на приоритета при насищане посредством реалната точка за интеграция `selectQuotaShareTarget` (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`).
- Покритие на универсалното предаване на `context-relay` при всеки брой цели.

Този набор се изпълнява в CI (задачата `test:integration`) с `--test-concurrency=1` и `--test-force-exit`, така че е детерминиран и не изисква реални идентификационни данни.

### Ограничени тестове за бърза проверка в реална среда (НЕ са в CI — реални доставчици)

| Команда                                | Какво прави                                                                                                                 |
| :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Реално маршрутизиране в рамките на процеса с `RUN_COMBO_LIVE=1`; създава моментна снимка на активна база данни на OmniRoute |
| `npm run test:combo:live:vps`          | HTTP извиквания към активен OmniRoute сървър (задайте `COMBO_LIVE_BASE_URL`)                                                |
| `npm run test:combo:live:vps:failover` | Същото, с умишлено зададени сценарии за превключване при отказ                                                              |

Тези тестове за бърза проверка упражняват реалния път на комуникация (комбинация → доставчик → завършване). Те са умишлено изключени от CI, тъй като изискват реални идентификационни данни и достъп до VPS.
