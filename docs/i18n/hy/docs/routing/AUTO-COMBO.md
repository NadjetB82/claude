> Ինքնակառավարվող մոդելային շղթաներ՝ հարմարվողական գնահատմամբ + առանց կազմաձևման ավտոմատ երթուղավորմամբ

## Առանց կազմաձևման ավտոմատ երթուղավորում (`auto/` նախածանց)

> **ՆՈՐՈՒԹՅՈՒՆ․** Կոմբո ստեղծելու կարիք չկա։ Ցանկացած հաճախորդում անմիջապես օգտագործեք `auto/` նախածանցը։

### Արագ օրինակներ

| Մոդելի ID      | Տարբերակ | Վարքագիծ                                                                                                |
| -------------- | -------- | ------------------------------------------------------------------------------------------------------- |
| `auto`         | լռելյայն | Բոլոր միացված մատակարարները, LKGP ռազմավարություն, հավասարակշռված կշիռներ                               |
| `auto/coding`  | coding   | Որակն առաջնահերթ համարող կշիռներ՝ հարմար կոդի գեներացման համար                                          |
| `auto/fast`    | fast     | Ցածր ուշացմամբ կշռված ընտրություն                                                                       |
| `auto/cheap`   | cheap    | Ծախսերի համար օպտիմալացված երթուղավորում (նախ՝ նվազագույն արժեքը)                                       |
| `auto/offline` | offline  | Նախապատվություն է տալիս առավել հասանելի քվոտա ունեցող մատակարարներին                                    |
| `auto/smart`   | smart    | Որակն առաջնահերթ + ուսումնասիրության ավելի բարձր գործակից (10%)՝ մոդելների ավելի լավ հայտնաբերման համար |
| `auto/lkgp`    | lkgp     | Հստակ LKGP (նույնն է, ինչ լռելյայն `auto`-ն)                                                            |
| `auto/chaos`   | chaos    | Զուգահեռ բազմակի ուղարկում՝ մեկ մոդել յուրաքանչյուր մատակարարից (ոչ խափանումների ներարկում)             |

### Կատեգորիա × մակարդակ համադրում (`auto/<category>:<tier>`)

OpenRouter ոճի վերջածանցները տարանջատում են **երթուղու տեսակը** (կատեգորիա) **դրա օպտիմալացման եղանակից** (մակարդակ), որպեսզի կարողանաք դրանք ազատորեն համադրել (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`)․

- **Կատեգորիաները** (թեկնածուների բազմությունը զտում են ըստ հնարավորության)՝ `coding` · `reasoning` · `vision` · `chat` · `multimodal`։ `vision`/`multimodal`-ը պահպանում են տեսողական հնարավորություններ ունեցող մոդելները, իսկ `reasoning`-ը՝ տրամաբանող/մտածող մոդելները։
- **Մակարդակները** (ընտրում են գնահատման կշիռները / բազմության զտիչը)՝ `fast` (արագ թողարկում) · `cheap` (`floor` կեղծանունով, ծախսախնայող) · `reliable` (շղթայի անջատիչի վիճակ + ուշացման կայունություն) · `free` / `pro` (զտում են բազմությունն ըստ մոդելի մակարդակի՝ `classifyTier`-ի միջոցով՝ անվճար մակարդակն ընդդեմ պրեմիումի)։

| Օրինակ                 | Վերածվում է                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `auto/coding:fast`     | coding բազմություն, ցածր ուշացման կշիռներ                                                |
| `auto/coding:cheap`    | coding բազմություն, ծախսերի համար օպտիմալացված (`auto/coding:floor` կեղծանունով)         |
| `auto/reasoning:pro`   | միայն տրամաբանող/մտածող մոդելներ, պրեմիում մակարդակ                                      |
| `auto/vision`          | տեսողական հնարավորություններ ունեցող մոդելներ (առանց մակարդակի → հավասարակշռված կշիռներ) |
| `auto/multimodal:free` | մուլտիմոդալ հնարավորություններ ունեցող մոդելներ, միայն անվճար մակարդակ                   |

Ցանկացած վավեր `auto/<category>[:<tier>]` մշակվում է ըստ պահանջի․ ընտրված ենթաբազմությունը ցուցադրվում է `/v1/models`-ում և կառավարման վահանակում (`AUTO_SUFFIX_VARIANTS`՝ `open-sse/services/autoCombo/builtinCatalog.ts`-ում)։ Զտումն աշխատում է **խափանման դեպքում բաց թողնելու** սկզբունքով․ եթե սահմանափակմանը չի համապատասխանում ոչ մի միացված մոդել, օգտագործվում է ամբողջ բազմությունը, որպեսզի երթուղավորումը երբեք չխափանվի։ Հիմնական գնահատիչը (`combo.ts`) անփոփոխ է․ կատեգորիայի/մակարդակի զտիչը կիրառվում է `buildAutoCandidates`-ում։

> **Մոդելների իրական ժամանակի վերլուծություն․** երբ `ARENA_ELO_SYNC_ENABLED` դրոշը միացված է, ավտոմատ երթուղավորման համապատասխանությունը որոշվում է իրական ժամանակի **Arena ELO** վարկանիշների + **models.dev** մակարդակների տվյալների հիման վրա (հակառակ դեպքում օգտագործվում է համապատասխանության ստատիկ քարտեզը)։

**Օգտագործման եղանակը․**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**Ինչ է տեղի ունենում․**

1. OmniRoute-ը հայտնաբերում է `auto/` նախածանցը `src/sse/handlers/chat.ts`-ում
2. Տվյալների բազայից հարցում է կատարում բոլոր **ակտիվ մատակարարների կապերի** համար
3. Զտում և պահպանում է վավեր հավատարմագրեր ունեցողները (API բանալի կամ OAuth թոքեն)
4. Որոշում է յուրաքանչյուր կապի մոդելը (`connection.defaultModel` կամ մատակարարի առաջին մոդելը)
5. Հիշողության մեջ կառուցում է **վիրտուալ կոմբո** (չի պահպանվում DB-ում)
6. Երթուղավորում է՝ օգտագործելով ընտրված տարբերակի կշիռների պրոֆիլը + LKGP ռազմավարությունը

**Հիմնական հատկություններ․**

- ✅ **Միշտ միացված է․** ոչ մի փոխարկիչ, կոմբոյի ստեղծում կամ կազմաձևում անհրաժեշտ չէ
- ✅ **Դինամիկ է․** ավտոմատ կերպով արտացոլում է ներկայում միացված մատակարարներին
- ✅ **Նիստի կապակցվածություն․** LKGP-ն ապահովում է, որ վերջին հաջող մատակարարին տրվի առաջնահերթություն
- ✅ **Հաշվի է առնում բազմաթիվ հաշիվներ․** մատակարարի յուրաքանչյուր կապ դառնում է առանձին թեկնածու
- ✅ **Առանց DB գրառումների․** վիրտուալ կոմբոն գոյություն ունի միայն հարցման ընթացքում՝ առանց պահպանման հավելյալ ծախսի

### Թեկնածուների կառավարում ըստ բանալու (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/`-ից հետո եկող վերջածանցը կամ
բազային ալիքի համար բառացի `auto`-ն) **միայն կարդալու համար** վերջնակետ է, որը ցուցակագրում է
`auto/*` ալիքի թեկնածուների ընթացիկ բազմությունը՝ լրացված իրական ժամանակի հասանելիության տվյալներով և վերօգտագործելով
կայունության առկա ընթերցումները (երբեք ոչ անջատիչի չմշակված `state`-ը)․

- մատակարարի շղթայի անջատիչ՝ `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- կապի սպասման ժամանակաշրջան՝ `rateLimitedUntil` / `testStatus`՝ որոշված
  `provider_connections` տողում
- մոդելի արգելափակում՝ `isModelLocked(provider, connectionId, model)`

Յուրաքանչյուր թեկնածու նաև պարունակում է այս API բանալու `excluded` դրոշը։ Բացառումները պահվում են
ըստ API բանալու (`auto_candidate_overrides` աղյուսակ, միգրացիա `128`)․ OmniRoute-ը
մեկ վարձակալով է և չունի `users` աղյուսակ, ուստի `apiKeyId`-ն իրական՝ ըստ կանչողի
ինքնությանը ամենամոտ տարբերակն է։ Բացառումները պարտադրվում են թեկնածուների բազմության նեղ անցակետում՝
`open-sse/services/autoCombo/virtualFactory.ts`-ում, մաքուր և միավորային թեստերով ստուգված
`filterExcludedCandidates()`-ի միջոցով (`open-sse/services/autoCombo/candidateOverrides.ts`)։
Զտիչն աշխատում է **խափանման դեպքում բաց թողնելու** սկզբունքով․ չսահմանված apiKeyId/channel-ը կամ DB որոնման ձախողումը
երկուսն էլ բազմությունը թողնում են չզտված, այնպես որ առանց վերագրումների կազմաձևված օպերատորի համար երթուղավորումը
բայթ առ բայթ նույնն է մնում, ինչ այս գործառույթից առաջ։

**Հետաձգված է հետագա խնդրի համար.** յուրաքանչյուր թեկնածուի կշիռներ + հստակ հերթականություն (Մակարդակ 3
— փոխանցվում է կշռված/առաջնահերթ ռազմավարությունների առկա ուղիներին) և որոշակի
`combo.ts` ռազմավարության ամրակցում յուրաքանչյուր `auto/*` ալիքին (Մակարդակ 4)։ Տե՛ս #7819-ի պլանը՝ բաց
հարցի վերաբերյալ, թե արդյոք վերասահմանումները պետք է մնան յուրաքանչյուր API բանալու համար առանձին, թե դառնան գլոբալ՝ հաշվի առնելով
մեկ վարձակալի մոդելը։

**Ներքին աշխատանքային ընթացքը.**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**Իրականացման ֆայլերը.**

| Ֆայլ                                                      | Նպատակ                                          |
| --------------------------------------------------------- | ----------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Նախածանցի վերլուծիչ (`parseAutoPrefix`)         |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Ստեղծում է վիրտուալ `AutoComboConfig` օբյեկտներ |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Մատակարարների ռեեստրի նմանակման թեստային կեռիկ  |
| `src/sse/handlers/chat.ts`                                | Ինտեգրում՝ auto նախածանցի կարճ միացում          |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` համակարգային գրառում    |

## Համակցությունների անուններ, որոնք համընկնում են իրական մոդելի ID-ի հետ

Համակցությունը, որի `name`-ը նույնական է մոդելի պարզ ID-ին (օրինակ՝
`gpt-5.5` անունով համակցությունը), **կանխամտածված և աջակցվող ձևանմուշ է**, ոչ թե վրիպակ․ սա
յուրաքանչյուր մոդելի ID-ի համար մատակարարի պահուստային ընտրության մեխանիզմն է, որը փաստագրված է
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-ում։ Քանի որ համակցության
լուծումը ստուգվում է մոդելի պարզ ID-ի լուծումից առաջ
(`getComboForModel()`՝ `src/sse/services/model.ts`-ում), պարզ
`gpt-5.5` ID-ով հարցումն ուղղորդվում է համակցության թիրախներով (օրինակ՝
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), այլ ոչ թե անմիջապես
մեկ մատակարարի մոտ․ սա կրկին օգտագործում է համակցությունը վերագրումից առաջ մշակելու առաջնահերթությունը, որը ստեղծվել է
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-ի համար և
ռեգրեսիոն եղանակով ստուգվում է `tests/unit/responses-combo-resolution-3227.test.ts` և
`tests/unit/combo-name-codex-responses-rewrite.test.ts` թեստերով։

Իրական մոդելի ID-ն ստվերող անունով համակցության ստեղծումը կամ վերանվանումը
**երբեք չի մերժվում**․ դա կխախտեր այս փաստագրված աշխատանքային հոսքը։ Փոխարենը
(#8530), `POST /api/combos`-ը և `PUT /api/combos/[id]`-ն ավելացնում են չարգելափակող
`warning` դաշտ պատասխանին, երբ (նոր) անունը համընկնում է իրական
մոդելի ID-ի հետ․

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Գործարկման ժամանակ `scanComboModelNameCollisionsAtBoot()`-ը
(`src/instrumentation-node.ts`) նաև գրանցամատյանում ավելացնում է մեկ տողանոց `[STARTUP]` նախազգուշացում՝
թվարկելով մոդելի ID ստվերող բոլոր առկա համակցությունները, որպեսզի այն օպերատորները, որոնք
դրան բախվել են պատահաբար (այլ ոչ թե կանխամտածված՝ համաձայն #6940-ի), ազդանշան ստանան։
Հայտնաբերման օժանդակ գործառույթը գտնվում է `src/lib/combos/modelNameCollision.ts`-ում։

## Հաճախորդից հատուկ համակցության կանչում

Պահպանված համակցությունները (Կարգավորումներ → Համակցություններ) օգտագործվում են միայն այն դեպքում, երբ հաճախորդը `model` դաշտում ուղարկում է համակցության **ճշգրիտ անունը**․ համակցության անվան մոտավոր կամ մասնակի համընկնում չկա, և `auto/` նախածանց չի օգտագործվում։ Լուծման հերթականությունը (`getComboForModel()`՝ `src/sse/services/model.ts`-ում)․

1. համակցության անվան ճշգրիտ համընկնում (`model: "my-combo"`),
2. `combo/<name>` նախածանց (`model: "combo/my-combo"`),
3. model→combo glob համապատասխանեցումներ (`/api/model-combo-mappings`)։

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Երկու տարածված սխալ․

- **`auto`-ն չի օգտագործում ձեր համակցությունները։** `auto`/`auto/*`-ն ստեղծում է իր սեփական՝ զրոյական կազմաձևմամբ թեկնածուների հավաքածուն և պահպանված համակցություններին դիմում է միայն այն դեպքում, երբ որևէ համակցություն բառացիորեն անվանված է `auto` (խորհուրդ չի տրվում)։ Համակցության միջոցով ուղղորդելու համար ուղարկեք դրա ճշգրիտ անունը, ոչ թե `auto`։
- **`openrouter/auto`-ն OpenRouter-ի իրական վճարովի արտադրանք է** («Ավտոմատ կերպով լավագույն հասանելին»), ոչ թե OmniRoute-ի կեղծանուն։ Այն OpenRouter-ի գրանցամատյանի միակ ստատիկ մոդելային գրառումն է (`open-sse/config/providers/registry/openrouter/index.ts`) և առանձին է վճարագրվում։ Օգտագործեք Կարգավորումներ → Ուղղորդում → Թաքցնել վճարովի մոդելները՝ այն `auto` հավաքածուներից բացառելու համար։

Այս փաստաթղթում նկարագրված սկզբնական շփոթության վերաբերյալ տե՛ս [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) և [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111)։

## Ինչպես է այն աշխատում (Persisted Auto-Combos)

Auto-Combo Engine-ը դինամիկ կերպով ընտրում է լավագույն մատակարարին/մոդելը յուրաքանչյուր հարցման համար՝ օգտագործելով **16 գործոնով գնահատման ֆունկցիա** (սահմանված է `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`-ում): Լռելյայն կշիռների գումարը կազմում է `1.0`; հատուկ (custom) կշիռները վերանորմավորվում են `normalizeScoringWeights()`-ի կողմից: Տասնվեցից երկուսը՝ `cacheAffinity`-ն և `resetWindowAffinity`-ն, ունեն `0` լռելյայն կշիռ; `reliability`-ն ունի `0` `DEFAULT_WEIGHTS`-ում, սակայն `0.03`՝ generic փաթեթներում և `0.04`՝ `reliability-first`-ում, իսկ `quality`-ն ունի `0.02` փաթեթներում (`0.03`՝ `quality-first`-ում): Դրանք շարունակում են հաշվարկվել յուրաքանչյուր թեկնածուի համար, իսկ `cacheAffinity`-ն կառավարում է prompt-cache-ի դեդուպլիկացիան միավորների հաշվարկից դուրս, հետևաբար զրոյական լռելյայն գործոնները պարզապես լռելյայն կերպով չեն մասնակցում քվեարկությանը, մինչդեռ փաթեթներում մասնակցում են:

> **Անընթեռնելի քվոտա (#15347):** Երբ մատակարարն (provider) ունի քվոտա ստացող (quota fetcher), բայց այն չի վերադարձնում ոչ մի
> ընթեռնելի բան (ձախողված ստացում, բացակայող վավերացման տվյալներ (credentials), միայն հաղորդագրությամբ օգտագործում կամ սխալ ձևաչափով snapshot՝ առանց
> վերլուծելի (parseable) `windows`-ի և առանց վերջավոր `percentUsed`-ի, ներառյալ `percentUsed: null`), թեկնածուն
> ստանում է `0` միավոր `quota` առանցքի վրա, և նրա վերջնական միավորը բազմապատկվում է
> `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR`-ով (0.5, `autoStrategy.ts`), որը կապի կարգավիճակի (connection-status) տույժի նույն մեղմ տույժի (soft-penalty)
> կաղապարն է: Օգտագործման ձախողված ընթերցումը վկայություն է հեռաչափության (telemetry),
> ոչ թե մատակարարի մասին, ուստի այն դասակարգվում է խստորեն ցանկացած իրական ցուցմունքից ցածր, ներառյալ հաստատված 100% օգտագործվածը,
> բայց երբեք խստորեն չի արգելափակվում կամ հեռացվում (evicted): Առանց սահմանաչափի (cap) մատակարարը հաղորդում է `unlimited: true` և
> գնահատվում է որպես ամբողջական քվոտա. գրանցված quota fetcher չունեցող մատակարարն ընդհանրապես չունի հեռաչափության աղբյուր
> և պահպանում է լռելյայն `100` արժեքը:

**Գումար՝** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` ինչպես հայտարարված է `DEFAULT_WEIGHTS`-ում. օգտատիրոջ կողմից կազմաձևված կշիռները նախքան միավորների հաշվարկը վերանորմավորվում են բաշխման մեջ `normalizeScoringWeights()`-ի միջոցով:

### `weighted` իմաստաբանությունը

`weighted`-ը **համամասնական պատահական ընտրություն է յուրաքանչյուր հարցման համար** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ոչ թե հավասարեցնող.

- Յուրաքանչյուր հարցում ընտրում է **մեկ** քայլ՝ `weight / totalWeight` հավանականությամբ. մնացած քայլերը դասավորվում են ըստ կշռի նվազման կարգի՝ որպես այդ հարցման համար պահուստային շղթա:
- Այն քայլը, որի կշիռը `0` է (կամ բացակայում է), **երբեք չի ընտրվում**, քանի դեռ որևէ այլ քայլ ունի > 0 կշիռ — այն կարող է ծառայել միայն որպես պահուստային տարբերակ՝ ընտրված քայլի ձախողումից հետո: Միայն այն դեպքում, երբ **բոլոր** կշիռները 0 են, ընտրությունը դառնում է համաչափ:
- Այն քայլերը, որոնց թիրախները անհասանելի են — մատակարարի circuit breaker `OPEN`, connection cooldown, model lockout — հեռացվում են ընտրությունից նախքան այն տեղի ունենալը (`open-sse/services/combo/targetResolution.ts`), ուստի մեկ առողջ քայլը կարող է ժամանակավորապես հաղթել յուրաքանչյուր հարցման դեպքում:
- `stickyWeightedLimit` (combo կոնֆիգուրացիա, լռելյայն `1` = անջատված է) ամրագրում է ընտրված քայլը այդքան հաջորդական հաջողությունների համար՝ նախքան նորից ընտրություն կատարելը:

Խիստ հերթափոխի (strict rotation) համար օգտագործեք `round-robin`; `weighted`-ի վրա հավասար կշիռները տալիս են վիճակագրական, ոչ թե խիստ հավասարակշռություն:

### Agentic pipeline ռեժիմ

Առնվազն երկու մոդել ունեցող `pipeline` համակցությունը կարող է ընտրել պլանավորողի/կատարողի (planner/executor) երթուղավորումը `config.agenticOrchestration.enabled`-ի միջոցով: Առաջին թիրախը պատասխանատու է պլանավորման և վերջնական պատասխանների համար. երկրորդ թիրախը թողարկում է հաճախորդի համար նախատեսված գործիքների կանչեր (client-native tool calls): OmniRoute-ը հայտնաբերում է գործիքի արդյունքի շարունակությունները հարցման արձանագրությունից, հարցնում է պլանավորողին, թե արդյոք անհրաժեշտ է գործիքի ևս մեկ փուլ, և դինամիկ կերպով դարձնում է կամ կատարողին, կամ պլանավորողին հաճախորդին ուղղված վերջնական քայլ:

Ընտրովի `config.agenticOrchestration.contextCompaction`-ը կիրառում է առանձին payload բյուջե՝ նախքան պլանավորողի կամ կատարողի յուրաքանչյուր ուղարկումը (dispatch): Միացրեք այն հստակորեն.

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

Սրանք օպերատորի կողմից ընտրված սերիալիզացված JSON նիշերի բյուջեներ են, ոչ թե թոքենների կոնտեքստային պատուհաններ կամ երաշխավորված վերին սահմաններ: Մոդելի ճշգրիտ ID-ները վերասահմանում են լռելյայն արժեքը: Սահմանաչափից վեր, սեղմումը (compaction) հեռացնում է նույնական գործիքների սահմանումները, կրճատում է չափազանց մեծ գործիքների ապացույցները digest-ով և հեռացնում է հին ամբողջական պատմության խմբերը՝ թիրախային հարաբերակցությանը հասնելու համար: Այն պահպանում է համակարգային/մշակողի հրահանգները, օգտատիրոջ վերջին հարցումը, գործիքի վերջին փուլը՝ ներառյալ զուգահեռ կանչերը/արդյունքները, և Gemini-ի առաջատար երթուղավորման հրահանգը: Վերին մակարդակի հրահանգները և գործիքների կարգավորումները պահպանվում են: Բացթողման նշիչը (omission marker) գրանցում է հեռացված պատմությունը. սա դետերմինիստական կրճատում է, ոչ թե իմաստային ամփոփում: Եթե ամրագրված կոնտեքստը դեռ գերազանցում է բյուջեն, հարցումը վերադարձնում է 413՝ նախքան մոդելի հետ կապ հաստատելը: Երբ սեղմումն անջատված է կամ սահմանաչափից ցածր է, հարցումն անցնում է անփոփոխ:

Երկրորդ թիրախից հետո լրացուցիչ մոդելները կատարողի հերթապահ պահուստային տարբերակներ են (executor backups): Ձախողված HTTP պատասխանը կամ տրանսպորտային բացառությունը անցնում է հաջորդ կատարողին՝ կրելով նույն պլանավորողի որոշումը և բնիկ գործիքները, բայց այդ կատարողի սեփական քայլի հուշումը (step prompt) և լուծված կապը: Առաջին հաջող պատասխանը վերադարձվում է անփոփոխ, ներառյալ SSE հոսքը (streaming). հաջող հոսք սկսվելուց հետո ձախողումները այստեղ չեն կարող կրկնվել: Եթե բոլոր կատարողները ձախողվում են, վերադարձվում է վերջին ձախողումը: Հաճախորդի ընդհատումները դադարեցնում են ուղարկումը:

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Կատարողը կարող է մեկ պատասխանում թողարկել բազմաթիվ անկախ կանչեր: Կախյալ կանչերը մշակվում են հաճախորդի գործիքի արդյունքների հետագա փուլերում, ընդ որում պլանավորողը վերանայում է յուրաքանչյուր արդյունք: `maxToolRounds`-ի լռելյայն արժեքը `8` է և ընդունում է `1`–`32` միջակայքը. երբ այն հասնում է սահմանին, պլանավորողը պետք է տրամադրի լավագույն հասանելի վերջնական պատասխանը: Պլանավորողի ներքին որոշումները բուֆերացվում են, մինչդեռ ընտրված հաճախորդին ուղղված պատասխանը պահպանում է հոսքի սկզբնական նախապատվությունը:

### `round-robin` կպչուն խմբաքանակ (sticky batch) և հաշվի ընդլայնում

Round-robin-ը խմբաքանակային է, ոչ թե մեկ հարցում՝ մեկ քայլի համար.

- `stickyRoundRobinLimit` (combo config, այնուհետև `comboStickyRoundRobinLimit`, այնուհետև `settings.stickyRoundRobinLimit`, լռելյայն **3**) պահպանում է նույն թիրախը այդքան հաջորդական հաջողությունների համար՝ նախքան հերթափոխվելը: Սահմանեք combo override-ը `1`-ի՝ մեկ հարցումով հերթափոխի համար: Combo խմբագրիչը ցույց է տալիս արդյունավետ արժեքը և թե որ շերտից է այն եկել:
- `connectionAwareExpansion` (combo config, այնուհետև settings, լռելյայն **false**) ընդլայնում է յուրաքանչյուր մատակարարի մակարդակի քայլը դեպի ըստ հաշվի թիրախների՝ նախքան հերթափոխը: Group-B ռազմավարությունները (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) պահպանում են մատակարարի մակարդակի տեսակետը, քանի դեռ սա միացված չէ: Combo խմբագրիչը ցուցադրում է inherit / on / off; inherit-ը օգտագործում է գլոբալ լռելյայն արժեքը (off):
- Prompt-cache տեղայնության երթուղավորումը (`promptCacheAffinityEnabled`, լռելյայն **true**) վերադասավորում է ամրագրված կապերը, որպեսզի համապատասխան քեշի բանալիները մնան մեկ հաշվի վրա: Այն գերակայում է round-robin-ի և weighted հերթափոխի նկատմամբ ամրագրված ըստ հաշվի քայլերի միջև: Անջատեք այն Settings → Combo defaults-ի տակ, եթե ձեզ անհրաժեշտ է խիստ հերթափոխ: Per-combo override գոյություն չունի:

Մեկ մոդելի վրա բազմահաշիվ հերթափոխի համար նախընտրեք **մեկ դինամիկ հաշվի քայլ** (դատարկ `connectionId`, ամբողջական պուլ) `1` կպչուն սահմանաչափով, ոչ թե երեք ամրագրված `connectionId`-ներ: Ամրագրված քայլերը գումարած affinity-ն կենտրոնանում են (collapse) նույն հաշվի վրա, նույնիսկ երբ RR հաշվիչը առաջ է գնում:

## Միաձուլման ռազմավարություն

`fusion`-ը միակ ռազմավարությունն է, որը **չի** ընտրում մեկ թիրախ։ Այն հարցումը
զուգահեռ ուղարկում է **պանելի բոլոր մոդելներին**, որից հետո կարգավորվող **դատավոր մոդելը**
պանելի բոլոր պատասխաններից սինթեզում է մեկ վերջնական պատասխան։ Փոխադրվել է սկզբնաղբյուր `decolua/9router`-ից
(OpenRouter-ի Fusion նախագծում)․ իրականացումը գտնվում է `open-sse/services/fusion.ts`-ում։

0. **Գործիքներ պարունակող հարցումների շրջանցում** — այն հարցումը, որը պարունակում է ոչ դատարկ `tools` զանգված,
   իսկ `tool_choice`-ը հստակորեն սահմանված չէ որպես `"none"`, ամբողջությամբ շրջանցում է պանելը․ այն անմիջապես ուղղորդվում է
   մեկ մոդելի (կարգավորված դատավորին կամ `panel[0]`-ին), իսկ `tools`/`tool_choice`-ը
   փոխանցվում են առանց փոփոխության։ Պանելի անդամները գործիքների հասանելիություն չունեն, իսկ դատավորի
   սինթեզման հրահանգը խրախուսում է չարտածել գործիքի կանչեր, ուստի գործակալային/գործիք կանչող հաճախորդները
   սինթեզված արձակի փոխարեն ստանում են գործիքի կանչի իրական որոշում (#6771)։
1. **Զուգահեռ բաշխում** (միայն գործիքներ չպարունակող հարցումների համար) — հարցումը միաժամանակ ուղարկվում է պանելի
   բոլոր մոդելներին՝ հարկադրաբար ոչ հոսքային ռեժիմով և հեռացված գործիքներով (սինթեզման համար դատավորին անհրաժեշտ է
   ամբողջական տեքստ)։
2. **Քվորումից հետո արտոնյալ ժամանակով հավաքագրում** — հենց ստացվում է `minPanel` քանակով պատասխան,
   ուշացող մասնակիցների համար գործարկվում է կարճ արտոնյալ ժամանակաչափ, ապա միաձուլումը շարունակվում է հավաքված
   բոլոր պատասխաններով։ Սա սահմանափակում է ամենադանդաղ մոդելի ազդեցությունը ընդհանուր կատարման ժամանակի վրա՝
   կոշտ ժամանակային սահմանաչափի շրջանակում։
3. **Դատավորի սինթեզում** — պանելի պատասխաններն անանունացվում են (`Source 1`, `Source 2`, … — որպեսզի
   դատավորը գնահատի բովանդակությունը, ոչ թե մոդելի ապրանքանիշը) և փոխանցվում դատավորին, որն ուսումնասիրում է
   համաձայնությունը / հակասությունները / մասնակի ընդգրկումը / եզակի դիտարկումները / բացթողումները, ապա
   գրում է **մեկ** հեղինակավոր պատասխան։ Դատավորի կանչը պահպանում է հաճախորդի սկզբնական
   `stream` դրոշը և գործիքները, ուստի հոսքային փոխանցումն ու հետագա գործիքների օգտագործումը շարունակում են աշխատել։
4. **Սահուն վատթարացում** — պանելի 0 պատասխան → `503`; ուղիղ 1 պահպանված պատասխան → այդ պատասխանը
   վերադարձվում է անմիջապես (միաձուլելու ոչինչ չկա)․ մեկ մոդելից բաղկացած պանելն անմիջապես պատասխանում է։

Պանելի անդամը կարող է նաև լինել `combo-ref` քայլ (`{kind: "combo-ref", comboName: "..."}`), որը հղվում է
մեկ այլ կոմբոյի․ այն լուծվում է որպես **մեկ ամբողջական պանելի ձայն** (լիարժեք ռեկուրսիվ ուղղորդում դեպի
հղված կոմբոն, այլ ոչ թե այդ կոմբոյի սեփական թիրախներին զուգահեռ բաշխում)՝ խորությունից/ցիկլերից պաշտպանության
նույն մեխանիզմով, որն արդեն օգտագործում են `combo-ref` կիրառող մյուս բոլոր ռազմավարությունները (#6764)։

### Կազմաձևում

Կարգավորվում է կոմբոյի `config` բլոբում (սխեմայի տեղափոխում չի պահանջվում՝ այն կրկին օգտագործում է գոյություն ունեցող
`combos` աղյուսակը)․

| Դաշտ                                     | Տեսակ    | Լռելյայն             | Նպատակ                                                                                                                     |
| :--------------------------------------- | :------- | :------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | պանելի առաջին մոդելը | Վերջնական պատասխանը սինթեզող մոդել                                                                                         |
| `config.fusionTuning.minPanel`           | `number` | `2`                  | Մինչև արտոնյալ ժամանակաչափի գործարկումը պահանջվող հաջող պատասխանների քանակը (սահմանափակվում է `[2, panelSize]` միջակայքով) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`               | Քվորումի հասնելուց հետո ուշացողներին սպասելու տևողությունը                                                                 |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`              | Բացարձակ սահմանաչափ, որպեսզի կախված մեկ մոդելը չկասեցնի հարցումը                                                           |

Լռելյայն արժեքները գտնվում են `FUSION_DEFAULTS`-ում (`open-sse/services/fusion.ts`)։

### Օրինակ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }

```

Այնուհետև կանչեք այն ինչպես ցանկացած կոմբո՝ `{"model":"fusion-panel","messages":[...]}`։

## Վիրտուալ Auto-Combo գործարան

Auto Combo շարժիչը չի պահանջում նախապես սահմանված կոմբոներ։ Փոխարենը, `open-sse/services/autoCombo/virtualFactory.ts`-ը թեկնածուներ է կառուցում դինամիկ կերպով.

1. Կանչում է `getProviderConnections({ isActive: true })`-ը (բոլոր միացված կապերը)
2. Զտում է՝ թողնելով վավեր հավատարմագրեր ունեցողները (API բանալի կամ `hasUsableOAuthToken()`-ի միջոցով ստուգված՝ ժամկետը չլրացած OAuth թոքեն)
3. Համադրում է `getProviderRegistry()`-ի հետ՝ մոդելների հասանելիության և գնագոյացման համար
4. Յուրաքանչյուր `(provider, model, connection)` եռյակի համար կառուցում է `VirtualAutoComboCandidate`
5. Որպես ուղարկման թիրախ ընտրում է `connection.defaultModel`-ը (կամ ռեեստրի առաջին մոդելը)
6. Գնահատում է յուրաքանչյուր թեկնածուի՝ օգտագործելով 16 գործոնով `scorePool()`-ը և տարբերակի կշիռների փաթեթը
7. Վերադարձնում է ստացված՝ հիշողության մեջ գտնվող `AutoComboConfig`-ը `handleComboChat()`-ի համար՝ այն երբեք չպահպանելով DB-ում

Սա նշանակում է, որ **`auto/*`-ը միացված նոր մատակարարի ավելացումն ինքնաբերաբար ընդլայնում է թեկնածուների բազմությունը**՝ առանց կոմբոն ձեռքով խմբագրելու անհրաժեշտության։ Վիրտուալ կոմբոն վերակառուցվում է յուրաքանչյուր հարցման համար, ուստի նոր ավելացված կամ նորից առողջ դարձած կապերն անմիջապես ներառվում են։

## Ինքնավերականգնում

- **Ժամանակավոր բացառում**․ միավոր < 0.2 → բացառվում է 5 րոպեով (աստիճանական հետաձգում, առավելագույնը՝ 30 րոպե)
- **Circuit breaker-ի վիճակի հաշվառում**․ OPEN → ինքնաբերաբար բացառվում է, HALF_OPEN → փորձնական հարցումներ
- **Միջադեպի ռեժիմ**․ >50% OPEN → անջատել ուսումնասիրումը, առավելագույնի հասցնել կայունությունը
- **Վերականգնում հովացման շրջանից հետո**․ բացառումից հետո առաջին հարցումը «փորձնական» է՝ կրճատված ժամանակային սահմանափակմամբ

## Բանդիտային ուսումնասիրում

Հարցումների 5%-ը (կարգավորվող) ուսումնասիրելու նպատակով ուղղորդվում է պատահական մատակարարների։ Միջադեպի ռեժիմում սա անջատված է։

## API

Գոյություն չունի **առանձին `POST /api/combos/auto` վերջնակետ (endpoint)** — Auto-Combo-ն օգտագործվում է երկու եղանակով.

1. **Zero-config (առաջարկվում է).** Ուղարկեք ցանկացած chat completion հարցում `model: "auto"` կամ `model: "auto/<variant>"` պարամետրով։ Վիրտուալ ֆաբրիկան կառուցում է combo-ն յուրաքանչյուր հարցման համար — պահպանում (persistence) կամ API կանչեր անհրաժեշտ չեն։

2. **Պահպանվող (persisted) combo՝ `strategy: "auto"`-ով.** Ստեղծեք սովորական combo `POST /api/combos`-ի միջոցով և սահմանեք `strategy: "auto"`՝ գումարած `config.auto.weights` / `config.auto.candidatePool`։ Օգտագործվում է նույն գնահատման շարժիչը (scoring engine); combo-ն պահվում է `combos`-ում և կարող է վերաօգտագործվել ըստ ID-ի։

Հայտնաբերման համար `GET /api/combos/auto`-ն թվարկում է յուրաքանչյուր տարբերակ՝ իր լուծված թեկնածուների ֆոնդով (candidate pool), գումարած `context_length` / `max_output_tokens` — թեկնածուների ֆոնդի պատուհանների MAX արժեքը։ Հաճախորդները (օրինակ՝ opencode plugin-ը) պետք է հայտարարեն այս արժեքները `0`-ի փոխարեն. զրոյական կոնտեքստը ամբողջությամբ անջատում է opencode-ի ավտոմատ սեղմումը (auto-compaction), թույլ տալով սեսիաներին մեծանալ այնքան ժամանակ, մինչև gateway-ի պատմության մաքրումը (history purge) ոչնչացնի կոնտեքստը։ MAX-ը անվտանգ է հայտարարել, քանի որ auto-combo կոնտեքստի նախնական ֆիլտրը չափազանց մեծ հարցումները ուղղորդում է դեպի մեծ պատուհան ունեցող թեկնածուներ։

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router-ի ռազմավարություններ

Պահպանվող `strategy: "auto"` combo-ները կարող են սահմանել `config.routerStrategy` (կամ հին `config.auto.routerStrategy`) հետևյալներից մեկին.

- `rules` — լռելյայն կշռված գնահատում
- `score` — ընտրում է ամենաբարձր կազմաձևված կշռված միավորը։ Ճշգրիտ հավասարության դեպքում պահպանվում է թեկնածուների կազմաձևված հերթականությունը. առկա `explorationRate`-ը նմուշառում է կատարում ամբողջ դասակարգված ֆոնդից։
- `cost` / `eco` — ամենաէժան առողջ մատակարարը
- `latency` / `fast` — ամենացածր p95 լատենտությունը՝ հուսալիության տուգանքով
- `sla-aware` / `sla` — նախապատվությունը տալիս է այն թեկնածուներին, որոնք բավարարում են p95 լատենտության, սխալների մակարդակի և կամընտիր ծախսերի SLO-ներին
- `lkgp` — վերջին հայտնի լավ մատակարարը (առաջնահերթ)
- `nadir` — հարցնել [Nadir](https://getnadir.com)-ի որոշումների API-ին, թե ֆոնդի որ մոդելն է անհրաժեշտ հուշման (prompt) համար. opt-in, fail-open դեպի `rules`

### Router-ի ռազմավարությունները մանրամասն

Auto-combo շարժիչը ներկայացնում է 7 միացվող (pluggable) **RouterStrategy** իրականացումներ, որոնք կարող եք փոխել `config.routerStrategy`-ի (կամ հին `config.auto.routerStrategy`-ի) միջոցով։ Յուրաքանչյուր ռազմավարություն ընտրում է մեկ մատակարար թեկնածուների ֆոնդից՝ հաշվի առնելով `RoutingContext`-ը (առաջադրանքի տեսակը, գործիքի/տեսողական հուշումները, թոքենների գնահատականը, կամընտիր SLA քաղաքականությունը, կամընտիր վերջին հայտնի լավ մատակարարը)։

#### 1. `rules` (լռելյայն) — 16-գործոնանի կշռված գնահատում

Փաթեթավորում է առկա գնահատման շարժիչը։ Ֆիլտրում է `OPEN` circuit-breaker ունեցող թեկնածուներին, այնուհետև գործարկում է `scorePool()`-ը ընթացիկ առաջադրանքի տեսակով և `getTaskFitness()`-ով՝ ընտրելով ամենաբարձր միավոր ստացած մատակարարին։

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել.** Լռելյայն։ Օգտագործեք, երբ ցանկանում եք հավասարակշռված փոխզիջում բոլոր ազդանշանների միջև։

**Alias.** `rules` (alias չկա)

#### 2. `cost` / `eco` — ամենաէժան առողջ մատակարարը

Դասավորում է թեկնածուների ֆոնդը ըստ `costPer1MTokens`-ի (աճման կարգով) և ընտրում ամենաէժանը։ Նախ ֆիլտրում է `OPEN` թեկնածուներին։

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել.** Ծախսերի նկատմամբ զգայուն աշխատանքային ծանրաբեռնվածությունների, խմբաքանակի մշակման (batch processing) կամ ֆոնային առաջադրանքների համար։

**Aliases.** `cost`, `eco`

#### 3. `latency` / `fast` — ամենացածր p95 լատենտությունը՝ հուսալիության տուգանքով

Դասավորում է ըստ `p95LatencyMs + (errorRate * 1000)`-ի։ Սխալների մակարդակի տուգանքը ապահովում է, որ անվստահելի մատակարարները ավելի ցածր վարկանիշ ստանան, նույնիսկ եթե նրանց անվանական լատենտությունը ցածր է։

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Երբ օգտագործել.** Լատենտության նկատմամբ զգայուն աշխատանքային ծանրաբեռնվածությունների համար, ինչպիսիք են իրական ժամանակի չաթը, ավտոմատ լրացումը (autocomplete) կամ ինտերակտիվ կոդավորման օգնականները։

**Aliases.** `latency`, `fast`

#### 4. `sla-aware` / `sla` — լատենտության/սխալների/ծախսերի SLO համապատասխանություն

Գնահատում է յուրաքանչյուր թեկնածուի՝ ըստ նրա, թե որքան լավ է այն բավարարում կազմաձևված SLO քաղաքականությանը:

| Գործոն              | Կշիռ | Բանաձև                                                 |
| ------------------- | ---- | ------------------------------------------------------ |
| Հապաղման միավոր     | 35%  | `threshold / max(value, ε)`                            |
| Սխալների միավոր     | 35%  | `threshold / max(value, ε)`                            |
| Առողջության միավոր  | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)      |
| Ծախսերի միավոր      | 10%  | `threshold / max(value, ε)` կամ հակադարձ նորմալացված   |
| Կայունության միավոր | 5%   | հակադարձ նորմալացված հապաղման ստանդարտ շեղում (stddev) |

Երբ `hardConstraints: true` է, թեկնածուները դասավորվում են հիմնականում ըստ **խախտման միավորի**
(որքանով են նրանք գերազանցում որևէ SLO), այնուհետև՝ ըստ համակցված միավորի: Հակառակ դեպքում՝ միայն
համակցված միավորի:

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA դաշտեր** (սահմանվում են combo կոնֆիգուրացիայում):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Երբ օգտագործել**: Արտադրական ծանրաբեռնվածություններ՝ հապաղման, սխալների մակարդակի կամ ծախսերի խիստ բյուջեներով:

**Հոմանիշներ**: `sla-aware`, `sla`

#### 5. `lkgp` — նախկինում հայտնի լավագույն մատակարարը (last known good provider) նախապատվությամբ

Նախ փորձում է **վերջին հայտնի լավագույն մատակարարին** (եթե սահմանված է), այնուհետև անցնում է
`rules` ռազմավարությանը: Օգտակար է սեսիայի կպչունության (session stickiness) համար՝ նույն մատակարարը
սպասարկում է զրույցի շարունակական հարցումները:

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**Երբ օգտագործել**: Բազմաքայլ զրույցներ, որտեղ ցանկանում եք, որ նույն մատակարարը սպասարկի հաջորդող
հարցումները (օրինակ՝ քեշավորման, համատեքստի շարունակականության կամ գնային հետևողականության համար):

**Հոմանիշ**: `lkgp` (հոմանիշ չկա)

#### 6. `nadir` — հարցմանը համապատասխան մոդելի ընտրություն Nadir-ի միջոցով

Վերոնշյալ յուրաքանչյուր ռազմավարություն դասակարգում է թեկնածուներին՝ ըստ իրենց հեռաչափության (telemetry).
դրանցից ոչ մեկը չի կարդում հարցումը: `nadir`-ը ուղարկում է օգտատիրոջ վերջին հաղորդագրությունը և մոդելների
ID-ները [Nadir](https://getnadir.com)-ի որոշումների API-ին (`POST /v1/bucket`) և ուղղորդում է դեպի այն
մոդելը, որն ընտրում է Nadir-ը այդ ցանկից (`simple` → ամենաէժան ունակ մոդելը, `complex` → առաջատար
մոդելը): Այդ մոդելը սպասարկող կապը դեռևս ընտրվում է `rules`-ի կողմից, ուստի քվոտան, առողջությունը և
ծախսերը շարունակում են որոշել, թե որ հաշիվն օգտագործել:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` և `OMNIROUTE_NADIR_BASE_URL`-ը այս երկու տողերի համար նախատեսված շրջակա
միջավայրի (env) պահուստային տարբերակներն են: `baseUrl`-ը անհրաժեշտ է միայն ինքնուրույն հոսթինգի
(self-hosted) Nadir-ի համար (վերջում `/v1` ավելացնելը թույլատրելի է): Առանց բանալու (keyless) զանգերը
հասնում են Nadir-ի անանուն մակարդակին, որը սահմանափակված է ըստ IP-ի:

Ինչ է դուրս գալիս համակարգից. օգտատիրոջ վերջին հաղորդագրության տեքստը (առաջին 16k նիշերը), թեկնածու
մոդելների ID-ները և `source: "omniroute"` ալիքի պիտակը: Ոչ մի համակարգային հուշում (system prompt),
պատմություն, գործիքներ կամ վերնագրեր (headers):

Ձախողման դեպքում վարքագիծը fail-open է. ժամանակի սպառումը (լռելյայն՝ 2000 մվ), ոչ 2xx պատասխանը,
անհասանելի հոսթը, սխալ ձևաչափված պատասխանը կամ լողավազանից (pool) դուրս ընտրությունը հանգեցնում են
`rules` որոշմանը, և պատճառը նախածանցվում է `NadirStrategy: fallback (…)`-ով: Ձախողված զանգից հետո
ռազմավարությունը 30 վայրկյանով բաց է թողնում ցանցային կանչը, ուստի խափանումը արժե մեկ ժամանակի սպառում
յուրաքանչյուր 30 վայրկյանում, այլ ոչ թե մեկը՝ յուրաքանչյուր հարցման համար: Ուղղորդման իրադարձությունները
հաղորդում են `strategy: "nadir"` միայն այն դեպքում, երբ Nadir-ն իրականում կատարել է ընտրությունը:

**Երբ օգտագործել**: Խառը բարդության տրաֆիկ այն լողավազանում (pool), որը ընդգրկում է մոդելների տարբեր
մակարդակներ (փոքր, միջին և առաջատար մոդել), որտեղ միշտ առաջատար մոդել օգտագործելը այն ծախսն է, որը
ցանկանում եք կրճատել:

**Հոմանիշ**: `nadir` (հոմանիշ չկա)

### Պատվերով (Custom) երթուղային ռազմավարություններ

Դուք կարող եք գրանցել ձեր սեփական `RouterStrategy` իրականացումը հանրային API-ի միջոցով:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Այնուհետև օգտագործեք այն.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

### Երթուղային ռազմավարության ընտրության ուղեցույց

| Օգտագործման դեպք                   | Ռազմավարություն | Պատճառ                                     |
| ---------------------------------- | --------------- | ------------------------------------------ |
| Հավասարակշռված ծանրաբեռնվածություն | `rules`         | Լռելյայն — հաշվի է առնում բոլոր գործոնները |
| Ծախսերի նվազեցում                  | `cost`          | Միշտ ընտրում է ամենաէժանը                  |
| Հապաղման նվազեցում                 | `latency`       | Ընտրում է ամենաարագ հուսալի մատակարարին    |
| Խիստ SLO-ներ                       | `sla-aware`     | Ֆիլտրում է ըստ p95/սխալների/ծախսերի շեմերի |
| Բազմաքայլ զրույց                   | `lkgp`          | Սեսիայի կպչունություն                      |
| Խառը բարդություն                   | `nadir`         | Ընտրում է մոդելի մակարդակը ըստ հարցման     |

SLA-aware դաշտեր:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## Առաջադրանքներին համապատասխանություն

30-ից ավելի մոդելներ գնահատվել են առաջադրանքների 6 տեսակների համար (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`)։ Աջակցվում են wildcard ձևանմուշները (օրինակ՝ `*-coder` → կոդավորման բարձր գնահատական)։

## Auto տարբերակների ամփոփում

Ներառյալ պարզ `auto`-ն (կանխադրված) և `autoPrefix.ts`-ում հայտարարված 6 `AutoVariant` արժեքները՝ կան **կանչման ենթակա մոդելների 7 ID-ներ**․

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant`-ն ինքնին թվարկում է 6 արժեք․ 7-րդ տարբերակը «առանց տարբերակի» պարզ `auto`-ն է, որը `parseAutoPrefix()`-ը մշակում է որպես `variant: undefined`։)

## Ինչպես են մակարդակները տեղավորվում Auto-Combo-ում

16 գործոնով գնահատման ֆունկցիան (`open-sse/services/autoCombo/scoring.ts`) մակարդակին պատկանելությունը դիտարկում է որպես երկու ազդանշան՝ `tierPriority` (0.0476) և `tierAffinity` (0.0476)։ `DEFAULT_WEIGHTS`-ի ամբողջական հավաքածուի համար վերևում տե՛ս կանոնական [գնահատման գործոնների աղյուսակը](#how-it-works-persisted-auto-combos). յուրաքանչյուր փաթեթի վերագրումները (ship-fast/cost-saver/quality-first/
offline-friendly) ներկայացված են «Քաշերի պրոֆիլներն ըստ փաթեթի» աղյուսակում։

Միայն մակարդակը **չի** պարտադրում, որ Tier 1-ը լինի առաջինը. եթե Tier 1-ի ուշացումը մեծ է կամ արժեքի և որակի հարաբերակցությունը օպտիմալ չէ, հաղթում է Tier 2-ը։ Մակարդակների հերթականությունը պարտադրելու համար օգտագործեք համակցման `priority` ռազմավարությունը և մատակարարներին դասավորեք ըստ մակարդակի։

Tier 1-ին (բաժանորդագրություն) ընդգծված նախապատվություն տալու համար մեծացրեք `tierPriority`-ի քաշը.

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Մակարդակների սահմանումների և մատակարարների դասակարգման համար տե՛ս [`docs/guides/TIERS.md`](../guides/TIERS.md)։

## Թեստավորում և ծածկույթ

### Ուղղորդման որոշումների դետերմինիստական մատրից (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts`-ը ապացուցում է բոլոր 19
հանրային ռազմավարությունների ուղղորդման **որոշումը**՝ սկզբից մինչև վերջ իրական կոմբո-խողովակաշարի միջոցով՝ ընդօրինակված վերին հոսանքով։
Ծածկույթը ներառում է․

- Բոլոր 19 `ROUTING_STRATEGY_VALUES` ռազմավարությունները (ordered, weighted, cost, context, fusion, …)։
- `quota-share`-ը (ներքին)՝ սկզբից մինչև վերջ․ DRR-ի արդարություն + հագեցվածության դեպքում առաջնահերթության նվազեցում՝ իրական
  `selectQuotaShareTarget` միջերեսի միջոցով (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)։
- `context-relay`-ի համընդհանուր փոխանցման ծածկույթը՝ թիրախների յուրաքանչյուր քանակի համար։

Այս թեստային փաթեթը գործարկվում է CI-ում (`test:integration` առաջադրանք)՝ `--test-concurrency=1` և
`--test-force-exit` դրոշներով, ուստի այն դետերմինիստական է և չի պահանջում իրական հավատարմագրեր։

### Պայմանական իրական smoke թեստեր (CI-ում ՉԵՆ գործարկվում՝ իրական մատակարարներ)

| Հրաման                                 | Ինչ է այն անում                                                                                              |
| :------------------------------------- | :----------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Իրական ուղղորդում նույն գործընթացի ներսում՝ `RUN_COMBO_LIVE=1`-ով․ ստեղծում է գործող OmniRoute DB-ի snapshot |
| `npm run test:combo:live:vps`          | HTTP կանչեր գործող OmniRoute սերվերին (սահմանեք `COMBO_LIVE_BASE_URL`)                                       |
| `npm run test:combo:live:vps:failover` | Նույնը՝ նախապես նախատեսված failover սցենարներով                                                              |

Այս smoke թեստերը ստուգում են իրական հաղորդակցման ուղին (կոմբո → մատակարար → ավարտ)։ Դրանք
միտումնավոր բացառված են CI-ից, քանի որ պահանջում են իրական հավատարմագրեր և VPS հասանելիություն։
