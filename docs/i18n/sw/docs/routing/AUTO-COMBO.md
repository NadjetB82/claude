## Uelekezaji Otomatiki Usiohitaji Usanidi (kiambishi awali `auto/`)

> **MPYA:** Hakuna haja ya kuunda combo. Tumia kiambishi awali `auto/` moja kwa moja katika kiteja chochote.

### Mifano ya Haraka

| Kitambulisho cha Modeli | Kibadala | Tabia                                                                            |
| ----------------------- | -------- | -------------------------------------------------------------------------------- |
| `auto`                  | default  | Watoa huduma wote waliounganishwa, mkakati wa LKGP, uzani uliosawazishwa         |
| `auto/coding`           | coding   | Uzani unaotanguliza ubora, unafaa kwa uzalishaji wa msimbo                       |
| `auto/fast`             | fast     | Uteuzi wenye uzani na muda mfupi wa kusubiri                                     |
| `auto/cheap`            | cheap    | Uelekezaji ulioboreshwa kwa gharama (gharama ya chini kwanza)                    |
| `auto/offline`          | offline  | Hupendelea watoa huduma wenye upatikanaji mkubwa zaidi wa mgao                   |
| `auto/smart`            | smart    | Ubora kwanza + kiwango cha juu cha uchunguzi (10%) kwa ugunduzi bora wa modeli   |
| `auto/lkgp`             | lkgp     | LKGP iliyobainishwa wazi (sawa na `auto` chaguo-msingi)                          |
| `auto/chaos`            | chaos    | Usambazaji sambamba, modeli moja kwa kila mtoa huduma (si uingizaji wa hitilafu) |

### Muundo wa Kategoria × Daraja (`auto/<category>:<tier>`)

Viambishi tamati vya mtindo wa OpenRouter hutenganisha **aina ya njia** (kategoria) na **jinsi ya kuiboresha** (daraja), ili uweze kuviunganisha kwa uhuru (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Kategoria** (chuja kundi la wagombea kulingana na uwezo): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` huhifadhi modeli zenye uwezo wa kuona; `reasoning` huhifadhi modeli za kusababu/kufikiri.
- **Madaraja** (chagua uzani wa upimaji / kichujio cha kundi): `fast` (toleo la haraka) · `cheap` (lakabu `floor`, kuokoa gharama) · `reliable` (afya ya kizuia hitilafu + uthabiti wa muda wa kusubiri) · `free` / `pro` (chuja kundi kulingana na daraja la modeli kupitia `classifyTier` — daraja lisilolipiwa dhidi ya la kulipiwa).

| Mfano                  | Hutatuliwa kuwa                                                          |
| ---------------------- | ------------------------------------------------------------------------ |
| `auto/coding:fast`     | kundi la coding, uzani wa muda mfupi wa kusubiri                         |
| `auto/coding:cheap`    | kundi la coding, lililoboreshwa kwa gharama (lakabu `auto/coding:floor`) |
| `auto/reasoning:pro`   | modeli za kusababu/kufikiri pekee, daraja la kulipiwa                    |
| `auto/vision`          | modeli zenye uwezo wa kuona (hakuna daraja → uzani uliosawazishwa)       |
| `auto/multimodal:free` | modeli zenye uwezo wa multimodal, daraja lisilolipiwa pekee              |

Muundo wowote halali wa `auto/<category>[:<tier>]` hutatuliwa unapohitajika; kikundi kidogo kilichoratibiwa hutangazwa katika `/v1/models` na dashibodi (`AUTO_SUFFIX_VARIANTS` katika `open-sse/services/autoCombo/builtinCatalog.ts`). Uchujaji ni wa **fail-open** — ikiwa kigezo hakilingani na modeli zozote zilizounganishwa, kundi lote hutumiwa ili uelekezaji usikatike kamwe. Kipimaji kikuu (`combo.ts`) hakijabadilishwa; kichujio cha kategoria/daraja hutumika katika `buildAutoCandidates`.

> **Taarifa hai za modeli:** ufaafu wa uelekezaji otomatiki huongozwa na viwango vya moja kwa moja vya **Arena ELO** + data ya madaraja ya **models.dev** wakati alama ya `ARENA_ELO_SYNC_ENABLED` imewashwa (vinginevyo hurudi kutumia ramani tuli ya ufaafu).

**Jinsi ya kutumia:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**Kinachotokea:**

1. OmniRoute hutambua kiambishi awali `auto/` katika `src/sse/handlers/chat.ts`
2. Huuliza **miunganisho yote amilifu ya watoa huduma** kutoka kwenye kanzidata
3. Huchuja na kubakiza ile yenye vitambulisho halali (ufunguo wa API au tokeni ya OAuth)
4. Hubainisha modeli kwa kila muunganisho (`connection.defaultModel` au modeli ya kwanza ya mtoa huduma)
5. Huunda **combo pepe** ndani ya kumbukumbu (haihifadhiwi katika DB)
6. Huelekeza kwa kutumia wasifu wa uzani wa kibadala kilichochaguliwa + mkakati wa LKGP

**Sifa kuu:**

- ✅ **Huwashwa kila wakati:** Hakuna swichi, hakuna uundaji wa combo, hakuna usanidi unaohitajika
- ✅ **Inayobadilika:** Huakisi kiotomatiki watoa huduma waliounganishwa kwa sasa
- ✅ **Uthabiti wa kipindi:** LKGP huhakikisha mtoa huduma aliyefanikiwa mwisho anapewa kipaumbele
- ✅ **Inatambua akaunti nyingi:** Kila muunganisho wa mtoa huduma huwa mgombea tofauti
- ✅ **Hakuna uandishi kwenye DB:** Combo pepe hupatikana kwa ombi hilo pekee, bila kabisa gharama ya ziada ya uhifadhi endelevu

### Udhibiti wa wagombea kwa kila ufunguo (#7819, Kiwango cha 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = kiambishi tamati baada ya `auto/`, au
neno halisi `auto` kwa chaneli msingi) ni endpoint ya **kusoma pekee** inayoorodhesha
kundi la sasa la wagombea la chaneli ya `auto/*`, likiwa limeongezewa hali hai ya kufikika, kwa kutumia tena
usomaji uliopo wa ustahimilivu (kamwe si `state` ghafi ya kizuia hitilafu):

- kizuia hitilafu cha mtoa huduma — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- muda wa kusubiri wa muunganisho — `rateLimitedUntil` / `testStatus` kwenye safu iliyotatuliwa ya
  `provider_connections`
- kufungiwa kwa modeli — `isModelLocked(provider, connectionId, model)`

Kila mgombea pia hubeba alama ya `excluded` ya ufunguo huu wa API. Vilivyoondolewa huhifadhiwa
kwa kila ufunguo wa API (jedwali la `auto_candidate_overrides`, uhamishaji `128`) — OmniRoute ni
ya mpangaji mmoja bila jedwali la `users`, kwa hivyo `apiKeyId` ndiyo utambulisho halisi wa karibu zaidi
kwa kila mwitaji — na hutekelezwa kwenye sehemu finyu ya kundi la wagombea katika
`open-sse/services/autoCombo/virtualFactory.ts` kupitia `filterExcludedCandidates()` safi iliyojaribiwa kwa vipimo vya kitengo
(`open-sse/services/autoCombo/candidateOverrides.ts`).
Kichujio ni cha **fail-open**: apiKeyId/channel ambayo haijawekwa au kushindwa kutafuta kwenye DB
vyote huacha kundi bila kuchujwa, kwa hivyo mwendeshaji ambaye hajasanidi ubatilishaji wowote huona uelekezaji
unaofanana baiti kwa baiti na uliokuwepo kabla ya kipengele hiki.

**Imeahirishwa hadi suala la ufuatiliaji:** uzani wa kila mgombea + mpangilio bayana (Kiwango cha 3
— huingia kwenye njia zilizopo za mikakati ya uzani/kipaumbele) na kubandika mkakati mahususi wa
`combo.ts` kwa kila chaneli ya `auto/*` (Kiwango cha 4). Tazama mpango wa #7819 kuhusu swali lililo wazi
la iwapo ubatilishaji unapaswa kubaki kwa kila ufunguo wa API au kuwa wa kimataifa kwa kuzingatia
muundo wa mpangaji mmoja.

**Kinachotokea nyuma ya pazia:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**Faili za utekelezaji:**

| Faili                                                     | Kusudi                                                     |
| --------------------------------------------------------- | ---------------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Kichanganuzi cha kiambishi awali (`parseAutoPrefix`)       |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Huunda vipengee pepe vya `AutoComboConfig`                 |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Kiunganishi cha majaribio cha kuiga sajili ya watoa huduma |
| `src/sse/handlers/chat.ts`                                | Ujumuishaji: njia ya mkato ya kiambishi awali cha auto     |
| `src/shared/constants/providers.ts`                       | Ingizo la mfumo la `SYSTEM_PROVIDERS.auto`                 |

## Majina ya Combo Yanayolingana na Kitambulisho Halisi cha Modeli

Combo ambayo `name` yake inafanana kabisa na kitambulisho tupu cha modeli (k.m. combo inayoitwa
`gpt-5.5`) ni **muundo wa makusudi unaotumika**, wala si hitilafu: ndiyo
utaratibu wa kutumia mtoa huduma mbadala kwa kila kitambulisho cha modeli, kama ilivyoelezwa katika
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Kwa sababu utatuzi wa combo
hukaguliwa kabla ya utatuzi wa kitambulisho tupu cha modeli
(`getComboForModel()` katika `src/sse/services/model.ts`), ombi la kitambulisho tupu
`gpt-5.5` hupitishwa kupitia malengo ya combo (k.m.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) badala ya kwenda moja kwa moja kwa
mtoa huduma mmoja — hii hutumia tena kipaumbele cha combo-kabla-ya-kuandika-upya kilichoundwa kwa ajili ya
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) na
imejaribiwa dhidi ya hitilafu zinazoweza kujirudia na `tests/unit/responses-combo-resolution-3227.test.ts` pamoja na
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Kuunda au kubadilisha jina la combo kuwa jina linalofunika kitambulisho halisi cha modeli
**hakukataliwi kamwe** — kufanya hivyo kungevunja mtiririko huu wa kazi uliorekodiwa. Badala yake
(#8530), `POST /api/combos` na `PUT /api/combos/[id]` huambatisha sehemu ya
`warning` isiyozuia kwenye jibu wakati jina (jipya) linapogongana na kitambulisho halisi cha
modeli:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Wakati wa kuwasha, `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) pia hurekodi onyo la mstari mmoja la `[STARTUP]`
linaloorodhesha kila combo iliyopo inayofunika kitambulisho cha modeli, ili waendeshaji ambao
wanakumbana na hili kwa bahati mbaya (badala ya kukusudia, kulingana na #6940) wapate ishara.
Kisaidizi cha ugunduzi kinapatikana katika `src/lib/combos/modelNameCollision.ts`.

## Kuita Combo Maalum Kutoka kwa Kiteja

Combo zilizohifadhiwa (Settings → Combos) hutumika tu wakati kiteja kinatuma **jina kamili** la combo katika sehemu ya `model` — hakuna ulinganishaji usio kamili au wa sehemu ya jina la combo, wala hakuna kiambishi awali cha `auto/` kinachohusika. Mpangilio wa utatuzi (`getComboForModel()` katika `src/sse/services/model.ts`):

1. ulinganifu kamili wa jina la combo (`model: "my-combo"`),
2. kiambishi awali cha `combo/<name>` (`model: "combo/my-combo"`),
3. ulinganishaji wa glob wa modeli→combo (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Mitego miwili ya kawaida:

- **`auto` haitumii combo zako.** `auto`/`auto/*` huunda mkusanyiko wake wa wagombea usiohitaji usanidi na huzingatia combo zilizohifadhiwa tu ikiwa combo imepewa jina halisi la `auto` (haipendekezwi). Ili kupitisha ombi kupitia combo, tuma jina lake kamili — si `auto`.
- **`openrouter/auto` ni bidhaa halisi ya kulipia ya OpenRouter** ("Auto Best Available"), wala si jina mbadala la OmniRoute. Ni ingizo moja tuli la modeli katika sajili ya OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) na hutozwa kando. Tumia Settings → Routing → Hide paid models ili kuiondoa kwenye mikusanyiko ya `auto`.

Angalia [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) na [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) kuhusu mkanganyiko wa awali unaofafanuliwa hapa.

### Semantiki za `weighted`

`weighted` ni **uteuzi wa nasibu wa uwiano kwa kila ombi**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), si kisawazishi:

- Kila ombi huchagua hatua **moja** kwa uwezekano wa `weight / totalWeight`; hatua zilizobaki hupangwa kwa uzito wa kushuka kama mnyororo wa kurudi nyuma kwa ombi hilo.
- Hatua ambayo uzito wake ni `0` (au haipo) **haijawahi kuchaguliwa** wakati hatua nyingine yoyote ina uzito > 0 — inaweza tu kutumika kama hatua ya kurudi nyuma baada ya hatua iliyochaguliwa kushindwa. Ni wakati **uzito wote** ni 0 ndipo uteuzi huwa wa sare.
- Hatua ambazo malengo yake yote hayapatikani — mzunguko wa mtoa huduma `OPEN`, muda wa kupoa wa muunganisho, kufungwa kwa modeli — huondolewa kwenye uteuzi kabla haijatokea (`open-sse/services/combo/targetResolution.ts`), kwa hivyo hatua moja yenye afya inaweza kushinda kila ombi kwa muda.
- `stickyWeightedLimit` (usanidi wa combo, chaguo-msingi `1` = imezimwa) hubandika hatua iliyochaguliwa kwa idadi hiyo ya mafanikio mfululizo kabla ya kuchagua tena.

Kwa mzunguko madhubuti tumia `round-robin`; uzito sawa kwenye `weighted` hutoa usawa wa kitakwimu — si madhubuti.

### Hali ya pipeline ya wakala (Agentic pipeline mode)

Combo ya `pipeline` yenye angalau miundo (models) miwili inaweza kuchagua kuelekeza kwa mpangaji/mtendaji (planner/executor) kwa kutumia `config.agenticOrchestration.enabled`. Lengo la kwanza linamiliki upangaji na majibu ya mwisho; lengo la pili hutoa wito wa zana (tool calls) asilia kwa mteja. OmniRoute hutambua mwendelezo wa matokeo ya zana kutoka kwa itifaki ya ombi, humuuliza mpangaji ikiwa raundi nyingine ya zana inahitajika, na kwa nguvu (dynamically) hufanya ama mtendaji au mpangaji kuwa hatua ya mwisho inayomkabili mteja.

Kwenye mwendelezo wa matokeo ya zana, OmniRoute pia husimamisha utekelezaji wakati raundi mbili mfululizo zilizokamilika zinarudia wito uleule wa zana na matokeo yasiyobadilika, au wakati kila matokeo yaliyotiwa alama wazi katika raundi mbili mfululizo yameshindwa. Matokeo yaliyobadilika huruhusu wito wa kurudiwa (kwa mfano, polling). Mlinzi (guard) hujiweka upya kwenye ombi jipya la mtumiaji, huweka wito sambamba katika raundi moja, na inasaidia historia za Anthropic, Chat Completions, Responses na Gemini. Mpangaji hupokea sababu na kumiliki jibu la mwisho hata kama anaomba raundi nyingine ya zana.

Miundo ya ziada baada ya lengo la pili ni nakala za akiba za mtendaji zilizopangwa. Jibu la HTTP lililoshindwa au ubaguzi wa usafirishaji (transport exception) huendelea hadi kwa mtendaji anayefuata, likibeba uamuzi uleule wa mpangaji na zana asilia lakini likiwa na prompt ya hatua ya mtendaji huyo na muunganisho uliotatuliwa. Jibu la kwanza lililofanikiwa hurejeshwa bila kubadilishwa, ikijumuisha utiririshaji wa SSE; kushindwa baada ya mtiririko uliofanikiwa kuanza hakuwezi kujaribiwa tena hapa. Ikiwa watendaji wote watashindwa, kushindwa kwa mwisho hurejeshwa. Usitishaji wa mteja husimamisha utumaji.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Mtendaji anaweza kutoa wito huru nyingi katika jibu moja. Wito tegemezi hushughulikiwa katika zamu za baadaye za matokeo ya zana za mteja, huku mpangaji akipitia kila matokeo. `maxToolRounds` ina thamani ya awali ya `8` na inakubali `1`–`32`; ikishafikiwa, mpangaji lazima atoe jibu bora zaidi la mwisho linalopatikana. Maamuzi ya ndani ya mpangaji huhifadhiwa kwenye buffer, huku jibu lililochaguliwa linalomkabili mteja likihifadhi upendeleo wa awali wa utiririshaji.

### `round-robin` sticky batch na upanuzi wa akaunti

Round-robin imewekwa kwenye kundi (batched), si ombi-moja-kwa-kila-hatua:

- `stickyRoundRobinLimit` (usanidi wa combo, kisha `comboStickyRoundRobinLimit`, kisha `settings.stickyRoundRobinLimit`, chaguo-msingi **3**) huweka lengo lilelile kwa idadi hiyo ya mafanikio mfululizo kabla ya kuzunguka. Weka ubatilishaji wa combo kuwa `1` kwa mzunguko wa ombi-moja. Kihariri cha combo kinaonyesha thamani inayofanya kazi na safu iliyotoka.
- `connectionAwareExpansion` (usanidi wa combo, kisha mipangilio, chaguo-msingi **false**) hupanua kila hatua ya kiwango cha mtoa huduma kuwa malengo ya kila akaunti kabla ya mzunguko. Mikakati ya Group-B (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) huweka mtazamo wa kiwango cha mtoa huduma hadi hii iwe imewashwa. Kihariri cha combo hufichua inherit / on / off; inherit hutumia chaguo-msingi la kimataifa (off).
- Uelekezaji wa eneo la prompt-cache (`promptCacheAffinityEnabled`, chaguo-msingi **true**) hupanga upya miunganisho iliyobandikwa ili funguo za cache zinazolingana zibaki kwenye akaunti moja. Inachukua kipaumbele juu ya mzunguko wa round-robin na weighted katika hatua zilizobandikwa za kila akaunti. Iizime chini ya Settings → Combo defaults ikiwa unahitaji mzunguko madhubuti. Hakuna ubatilishaji wa kila-combo.

Kwa mzunguko wa akaunti nyingi kwenye muundo mmoja, pendelea **hatua moja ya akaunti-dinamiki** (`connectionId` tupu, pool nzima) yenye kikomo cha sticky `1`, si `connectionId` tatu zilizobandikwa. Hatua zilizobandikwa pamoja na affinity huangukia kwenye akaunti ileile hata wakati kaunta ya RR inasonga mbele.

## Mkakati wa Fusion

`fusion` ni mkakati pekee ambao **hauchagui** lengo moja. Husambaza ombi kwa
**kila modeli ya paneli kwa sambamba**, kisha **modeli ya mwamuzi** inayoweza kusanidiwa huunganisha
jibu moja la mwisho kutoka kwa majibu yote ya paneli. Umehamishwa kutoka `decolua/9router`
ya awali (muundo wa Fusion wa OpenRouter); utekelezaji upo katika `open-sse/services/fusion.ts`.

Jinsi unavyofanya kazi:

0. **Kupita moja kwa moja kwa maombi yenye zana** — ombi lenye safu isiyo tupu ya `tools` huku
   `tool_choice` haijawekwa wazi kuwa `"none"` huruka paneli kabisa: huelekezwa moja kwa moja kwa
   modeli moja (mwamuzi aliyesanidiwa, au `panel[0]`) huku `tools`/`tool_choice`
   zikipitishwa bila kubadilishwa. Wanachama wa paneli hawana ufikiaji wa zana na maelekezo ya
   uunganishaji ya mwamuzi hayahimizi utoaji wa miito ya zana, kwa hivyo viteja vya kiwakala/vinavyoita zana
   hupata uamuzi halisi wa kuitwa kwa zana badala ya maandishi yaliyounganishwa (#6771).
1. **Usambazaji mpana** (kwa maombi yasiyo na zana pekee) — ombi hutumwa kwa kila modeli ya
   paneli kwa wakati mmoja, huku utiririshaji ukizimwa kwa lazima na zana zikiondolewa (mwamuzi anahitaji
   maandishi kamili ili kuyaunganisha).
2. **Ukusanyaji wa akidi wenye kipindi cha ziada** — mara tu majibu `minPanel` yanapowasili, kipima muda
   kifupi cha kipindi cha ziada huanza kwa ajili ya waliochelewa, kisha fusion huendelea kwa kutumia chochote kilichokusanywa.
   Hii huweka kikomo kwa athari ya modeli iliyo polepole zaidi kwenye muda halisi, ndani ya kikomo kisichoweza kuvukwa cha muda.
3. **Uunganishaji wa mwamuzi** — majibu ya paneli huondolewa utambulisho (`Chanzo 1`, `Chanzo 2`, … — ili
   mwamuzi apime maudhui, si chapa ya modeli) na kukabidhiwa mwamuzi, ambaye huchanganua
   makubaliano / migongano / ushughulikiaji wa sehemu / maarifa ya kipekee / mambo yaliyopuuzwa, kisha
   huandika jibu **moja** lenye mamlaka. Mwito wa mwamuzi huhifadhi thamani asili ya
   `stream` ya kiteja pamoja na zana, kwa hivyo utiririshaji na matumizi ya zana katika hatua zinazofuata bado hufanya kazi.
4. **Kushuka kwa utendaji kwa ustahimilivu** — majibu 0 ya paneli → `503`; jibu 1 pekee lililosalia → jibu hilo
   hurejeshwa moja kwa moja (hakuna cha kuunganisha); paneli yenye modeli moja hujibu moja kwa moja.

Mwanachama wa paneli anaweza pia kuwa hatua ya `combo-ref` (`{kind: "combo-ref", comboName: "..."}`) inayorejelea
combo nyingine — hutatuliwa kama **sauti moja ya paneli ya kisanduku cheusi** (usambazaji kamili unaojirudia ndani ya
combo inayorejelewa, si usambazaji mpana kwa malengo ya combo hiyo yenyewe), ikiwa na ulinzi uleule wa kina/mizunguko
ambao tayari unatumiwa na kila mkakati mwingine unaotumia combo-ref (#6764).

## Kiwanda Pepe cha Auto-Combo

Injini ya Auto Combo haihitaji combo zilizofafanuliwa mapema. Badala yake, `open-sse/services/autoCombo/virtualFactory.ts` huunda wagombea papo hapo:

1. Huita `getProviderConnections({ isActive: true })` (miunganisho yote iliyowezeshwa)
2. Huchuja na kubakiza ile yenye vitambulisho halali (ufunguo wa API au tokeni ya OAuth ambayo muda wake haujaisha kupitia `hasUsableOAuthToken()`)
3. Hulinganisha na `getProviderRegistry()` ili kupata upatikanaji wa modeli + bei
4. Kwa kila jozi-tatu `(provider, model, connection)`, huunda `VirtualAutoComboCandidate`
5. Huchagua `connection.defaultModel` (au modeli ya kwanza ya sajili) kama lengo la utumaji
6. Hupatia kila mgombea alama kwa kutumia `scorePool()` yenye vipengele 16 na kifurushi cha uzani cha lahaja
7. Hurejesha `AutoComboConfig` iliyotokana na hiyo iliyo kwenye kumbukumbu kwa ajili ya `handleComboChat()` — haihifadhiwi kamwe kwenye DB

Hii inamaanisha kuwa **kuongeza mtoa huduma mpya ambaye `auto/*` imewezeshwa hupanua kundi la wagombea kiotomatiki** — hakuna haja ya kuhariri combo mwenyewe. Combo pepe huundwa upya kwa kila ombi, kwa hivyo miunganisho iliyoongezwa hivi karibuni au iliyorejea katika hali nzuri hutumika mara moja.

## Kujirekebisha

- **Kutengwa kwa muda**: Alama < 0.2 → hutengwa kwa dakika 5 (kuongeza muda wa kusubiri hatua kwa hatua, upeo wa dakika 30)
- **Ufahamu wa circuit breaker**: OPEN → hutengwa kiotomatiki; HALF_OPEN → maombi ya majaribio
- **Hali ya tukio**: >50% OPEN → zima uchunguzi, ongeza uthabiti hadi kiwango cha juu
- **Urejeshaji baada ya muda wa kusubiri**: Baada ya kutengwa, ombi la kwanza huwa "jaribio" lenye muda uliopunguzwa wa kuisha

## Uchunguzi wa Bandit

5% ya maombi (inaweza kusanidiwa) huelekezwa kwa watoa huduma nasibu kwa ajili ya uchunguzi. Huzimwa katika hali ya tukio.

## API

Hakuna **endpoint maalum ya `POST /api/combos/auto`** — Auto-Combo hutumiwa kwa njia mbili:

1. **Zero-config (inayopendekezwa):** Tuma ombi lolote la kukamilisha gumzo (chat completion) ukiwa na `model: "auto"` au `model: "auto/<variant>"`. Kiwanda pepe (virtual factory) hujenga combo kwa kila ombi — hakuna uhifadhi, hakuna haja ya API calls.

2. **Combo iliyohifadhiwa (persisted) na `strategy: "auto"`:** Unda combo ya kawaida kupitia `POST /api/combos` na uweke `strategy: "auto"` pamoja na `config.auto.weights` / `config.auto.candidatePool`. Injini ile ile ya uwekaji alama (scoring engine) hutumika; combo huhifadhiwa kwenye `combos` na inaweza kutumika tena kwa kutumia ID.

Kwa ajili ya ugunduzi, `GET /api/combos/auto` huorodhesha kila variant pamoja na candidate pool iliyosuluhishwa pamoja na `context_length` / `max_output_tokens` — MAX katika madirisha ya candidate pool. Wateja (k.m. opencode plugin) lazima watangaze thamani hizi badala ya `0`: context ya sifuri huzima auto-compaction ya opencode kabisa, ikiruhusu vipindi (sessions) kukua hadi pale ufutaji wa historia wa gateway utakapoharibu context. MAX ni salama kutangazwa kwa sababu pre-filter ya auto-combo context huelekeza maombi makubwa kupita kiasi kwa candidates wenye madirisha makubwa.

```bash
# Zero-config usage (no combo creation)

  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \

```

### Mikakati ya Auto router

Combo za `strategy: "auto"` zilizohifadhiwa zinaweza kuweka `config.routerStrategy` (au `config.auto.routerStrategy` ya zamani) kwa mojawapo ya haya:

- `rules` — uwekaji alama wa uzito chaguo-msingi
- `score` — huchagua alama ya uzito iliyosanidiwa ya juu zaidi. Sare kamili huhifadhi mpangilio wa candidate uliosanidiwa; `explorationRate` iliyopo huchukua sampuli kutoka kwenye pool nzima iliyopangwa.
- `cost` / `eco` — mtoa huduma mwenye afya (healthy) wa bei nafuu zaidi
- `latency` / `fast` — latency ya p95 ya chini zaidi ikiwa na adhabu ya kutokuwa na uhakika (reliability penalty)
- `sla-aware` / `sla` — pendelea candidates wanaokidhi p95 latency, kiwango cha makosa (error-rate), na SLOs za gharama za hiari
- `lkgp` — mtoa huduma wa mwisho aliyejulikana kuwa mzuri kwanza
- `nadir` — uliza API ya maamuzi ya [Nadir](https://getnadir.com) ni model ipi kwenye pool ambayo prompt inahitaji; opt-in, fail-open kwa `rules`

### Mikakati ya Router kwa undani

Injini ya auto-combo hufichua utekelezaji 7 wa **RouterStrategy** unaoweza kuchomekwa (pluggable) ambao unaweza kubadilisha kupitia `config.routerStrategy` (au `config.auto.routerStrategy` ya zamani). Kila mkakati huchagua mtoa huduma mmoja kutoka kwenye candidate pool, ikizingatiwa `RoutingContext` (aina ya kazi, vidokezo vya zana/vision, makadirio ya token, sera ya hiari ya SLA, mtoa huduma wa hiari wa mwisho aliyejulikana kuwa mzuri).

#### 1. `rules` (chaguo-msingi) — uwekaji alama wa uzito wa vipengele 16

Hufunga injini ya uwekaji alama iliyopo. Huchuja candidates wa `OPEN` circuit-breaker, kisha huendesha `scorePool()` na aina ya kazi ya sasa na `getTaskFitness()`, ikichagua mtoa huduma mwenye alama za juu zaidi.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Wakati wa kutumia**: Chaguo-msingi. Tumia wakati unataka uwiano uliosawazishwa katika ishara zote.

**Alias**: `rules` (hakuna alias)

---

#### 2. `cost` / `eco` — mtoa huduma mwenye afya wa bei nafuu zaidi

Hupanga candidate pool kulingana na `costPer1MTokens` (kupanda) na huchagua wa bei nafuu zaidi. Huchuja candidates wa `OPEN` kwanza.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Wakati wa kutumia**: Mizigo ya kazi inayozingatia gharama, usindikaji wa kundi (batch processing), au kazi za usuli (background jobs).

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — latency ya p95 ya chini zaidi ikiwa na adhabu ya kutokuwa na uhakika

Hupanga kulingana na `p95LatencyMs + (errorRate * 1000)`. Adhabu ya kiwango cha makosa (error-rate penalty) huhakikisha watoa huduma wasioaminika wanapangwa chini hata kama latency yao ya kawaida ni ya chini.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Wakati wa kutumia**: Mizigo ya kazi inayozingatia latency kama gumzo la wakati halisi, autocomplete, au wasaidizi wa usimbaji shirikishi.

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — utiifu wa SLO wa latency/makosa/gharama

Hupatia alama kila candidate kulingana na jinsi inavyokidhi sera ya SLO iliyosanidiwa:

| Kigezo            | Uzito | Mfumo                                             |
| ----------------- | ----- | ------------------------------------------------- |
| Alama ya latency  | 35%   | `threshold / max(value, ε)`                       |
| Alama ya hitilafu | 35%   | `threshold / max(value, ε)`                       |
| Alama ya afya     | 15%   | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| Alama ya gharama  | 10%   | `threshold / max(value, ε)` au inverse normalized |
| Alama ya uthabiti | 5%    | inverse normalized latency stddev                 |

Wakati `hardConstraints: true`, wagombea hupangwa kimsingi kwa **alama ya ukiukaji**
(kiasi wanachozidi SLO yoyote), kisha kwa alama ya jumla. Vinginevyo ni
alama ya jumla pekee.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**Sehemu za SLA** (zilizowekwa kwenye usanidi wa combo):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Wakati wa kutumia**: Mizigo ya kazi ya uzalishaji yenye bajeti kali za latency, kiwango cha hitilafu, au gharama.

**Lakabu**: `sla-aware`, `sla`

---

#### 5. `lkgp` — mtoa huduma mzuri anayejulikana wa mwisho kwanza

Hujaribu **mtoa huduma mzuri anayejulikana wa mwisho** (ikiwa amewekwa) kwanza, kisha hurejea kwenye mkakati wa
`rules`. Inafaa kwa uthabiti wa kipindi (session stickiness) — mtoa huduma yuleyule hushughulikia maombi ya ufuatiliaji kwenye mazungumzo.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**Wakati wa kutumia**: Mazungumzo ya zamu nyingi ambapo unataka mtoa huduma yuleyule kushughulikia
maombi ya ufuatiliaji (k.m., kwa ajili ya caching, mwendelezo wa muktadha, au uthabiti wa bei).

**Lakabu**: `lkgp` (hakuna lakabu)

---

#### 6. `nadir` — chaguo la modeli linalozingatia kidokezo kupitia Nadir

Kila mkakati hapo juu hupanga wagombea kulingana na telemetry yao wenyewe; hakuna hata mmoja anayesoma
ombi. `nadir` hutuma zamu ya mwisho ya mtumiaji pamoja na vitambulisho vya modeli vya pool kwenye API ya uamuzi ya
[Nadir](https://getnadir.com) (`POST /v1/bucket`) na kuelekeza kwenye modeli ambayo
Nadir huchagua kutoka kwenye menyu hiyo (`simple` → modeli ya bei nafuu inayoweza kufanya kazi, `complex` → modeli ya kisasa zaidi). Muunganisho unaohudumia modeli hiyo bado huchaguliwa na `rules`, kwa hivyo upendeleo (quota), afya na gharama huendelea kuamua ni akaunti ipi.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` na `OMNIROUTE_NADIR_BASE_URL` ni njia mbadala za mazingira kwa kamba hizo mbili.
`baseUrl` inahitajika tu kwa Nadir inayojiendesha yenyewe (trailing `/v1` inakubalika).
Simu zisizo na ufunguo hutua kwenye tier ya Nadir ya bila utambulisho, ambayo ina kikomo cha kasi kwa kila IP.

Kinachotoka kwenye kisanduku: maandishi ya ujumbe wa mwisho wa mtumiaji (herufi 16k za kwanza), vitambulisho vya modeli za wagombea na lebo ya chaneli ya `source: "omniroute"`. Hakuna kidokezo cha mfumo (system prompt), historia, zana au vichwa vya habari (headers).

Tabia ya kushindwa ni fail-open: muda kuisha (chaguo-msingi 2000 ms), isiyo 2xx, mwenyeji asiyeweza kufikiwa, jibu lililoharibika au uteuzi nje ya pool hutatuliwa kwa uamuzi wa `rules` na sababu huwekwa kiambishi awali `NadirStrategy: fallback (…)`. Baada ya simu iliyoshindwa mkakati huruka mtandao kwa sekunde 30, kwa hivyo hitilafu inagharimu muda mmoja wa kusubiri (timeout) kwa kila sekunde 30 badala ya mmoja kwa kila ombi. Matukio ya uelekezaji huripoti `strategy: "nadir"` pale tu Nadir anapofanya chaguo.

**Wakati wa kutumia**: trafiki ya ugumu mchanganyiko kwenye pool inayozunguka tiers za modeli (ndogo, ya kati na ya kisasa), ambapo kutumia modeli ya kisasa kila wakati ni gharama unayotaka kupunguza.

**Lakabu**: `nadir` (hakuna lakabu)

```ts
import {
  registerStrategy,

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,

      strategy: this.name,
      reason: "MyCustomStrategy: ...",

}
```

## Ufaafu wa Kazi

Zaidi ya modeli 30 zimepewa alama katika aina 6 za kazi (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`). Inatumia ruwaza za wildcard (kwa mfano, `*-coder` → alama ya juu ya coding).

## Muhtasari wa Vibadala vya Auto

Ukijumuisha `auto` tupu (chaguo-msingi) pamoja na thamani 6 za `AutoVariant` zilizotangazwa katika `autoPrefix.ts`, kuna **vitambulisho 7 vya modeli vinavyoweza kuitwa**:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` yenyewe inaorodhesha thamani 6; chaguo la 7 ni "hakuna kibadala" — `auto` tupu — linaloshughulikiwa na `parseAutoPrefix()` kama `variant: undefined`.)

## Jinsi viwango vinavyoendana na Auto-Combo

Kitendakazi cha ukadiriaji chenye vipengele 16 (`open-sse/services/autoCombo/scoring.ts`) huchukulia uanachama wa kiwango kama ishara mbili: `tierPriority` (0.0476) na `tierAffinity` (0.0476). Tazama [jedwali rasmi la vipengele vya ukadiriaji](#how-it-works-persisted-auto-combos) hapo juu kwa seti kamili ya `DEFAULT_WEIGHTS` — ubatilishaji maalum kwa kila kifurushi (ship-fast/cost-saver/quality-first/
offline-friendly) umeorodheshwa katika jedwali la "Wasifu wa uzito kwa kila kifurushi".

Kiwango pekee **hakilazimishi** Kiwango cha 1 kuwa cha kwanza — ikiwa ucheleweshaji wa Kiwango cha 1 ni mbaya au uwiano wa gharama dhidi ya ubora si bora, Kiwango cha 2 hushinda. Ili kulazimisha mpangilio wa viwango, tumia mkakati wa mchanganyiko `priority` na upangilie watoa huduma kulingana na kiwango.

Ili kupendelea sana Kiwango cha 1 (usajili), ongeza uzito wa `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Tazama [`docs/guides/TIERS.md`](../guides/TIERS.md) kwa ufafanuzi wa viwango na uainishaji wa watoa huduma.

## Majaribio na Ufunikaji

### Matriki bainifu ya maamuzi ya uelekezaji (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` huthibitisha **uamuzi** wa uelekezaji wa mikakati yote 19
ya umma kutoka mwanzo hadi mwisho kupitia mchakato halisi wa combo wenye mfumo wa juu ulioigwa.
Ufunikaji unajumuisha:

- Mikakati yote 19 ya `ROUTING_STRATEGY_VALUES` (ordered, weighted, cost, context, fusion, …).
- `quota-share` (ya ndani) kutoka mwanzo hadi mwisho: usawa wa DRR + kupunguza kipaumbele wakati wa kujaa kupitia
  kiungio halisi cha `selectQuotaShareTarget` (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- Ufunikaji wa uhamishaji wa jumla wa `context-relay` katika kila idadi ya malengo.

Seti hii huendeshwa katika CI (kazi ya `test:integration`) ikiwa na `--test-concurrency=1` na
`--test-force-exit` ili iwe bainifu na isihitaji vitambulisho halisi vya uthibitishaji.

### Majaribio ya moja kwa moja yenye kizuizi (SI katika CI — watoa huduma halisi)

| Amri                                   | Inachofanya                                                                                             |
| :------------------------------------- | :------------------------------------------------------------------------------------------------------ |
| `npm run test:combo:live`              | Uelekezaji halisi ndani ya mchakato kwa kutumia `RUN_COMBO_LIVE=1`; hunasa picha ya DB hai ya OmniRoute |
| `npm run test:combo:live:vps`          | Miito ya HTTP dhidi ya seva hai ya OmniRoute (weka `COMBO_LIVE_BASE_URL`)                               |
| `npm run test:combo:live:vps:failover` | Vivyo hivyo, pamoja na hali za makusudi za uhamishaji baada ya hitilafu                                 |

Majaribio haya ya awali hutumia njia halisi ya mawasiliano (combo → mtoa huduma → ukamilishaji). Yameondolewa
kwa makusudi kutoka CI kwa sababu yanahitaji vitambulisho halisi vya uthibitishaji na ufikiaji wa VPS.
