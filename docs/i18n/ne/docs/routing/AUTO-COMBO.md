## शून्य-कन्फिग स्वतः-राउटिङ (`auto/` उपसर्ग)

> **नयाँ:** कम्बो सिर्जना गर्न आवश्यक छैन। कुनै पनि क्लाइन्टमा सीधै `auto/` उपसर्ग प्रयोग गर्नुहोस्।

### द्रुत उदाहरणहरू

| मोडेल ID       | भेरियन्ट       | व्यवहार                                                                     |
| -------------- | -------------- | --------------------------------------------------------------------------- |
| `auto`         | पूर्वनिर्धारित | सबै जडान गरिएका प्रदायकहरू, LKGP रणनीति, सन्तुलित भारहरू                    |
| `auto/coding`  | कोडिङ          | गुणस्तर-प्राथमिक भारहरू, कोड उत्पादनका लागि उपयुक्त                         |
| `auto/fast`    | छिटो           | न्यून-विलम्बता भारित चयन                                                    |
| `auto/cheap`   | सस्तो          | लागत-अनुकूलित राउटिङ (पहिले सबैभन्दा कम लागत)                               |
| `auto/offline` | अफलाइन         | सबैभन्दा बढी कोटा उपलब्धता भएका प्रदायकहरूलाई प्राथमिकता                    |
| `auto/smart`   | स्मार्ट        | गुणस्तर-प्राथमिक + अझ राम्रो मोडेल पहिचानका लागि उच्च अन्वेषण दर (10%)      |
| `auto/lkgp`    | lkgp           | स्पष्ट LKGP (पूर्वनिर्धारित `auto` सरह)                                     |
| `auto/chaos`   | केओस           | समानान्तर फ्यान-आउट, प्रत्येक प्रदायकबाट एउटा मोडेल (त्रुटि इन्जेक्सन होइन) |

### श्रेणी × टियर संयोजन (`auto/<category>:<tier>`)

OpenRouter-शैलीका प्रत्ययहरूले **कस्तो प्रकारको रुट** (श्रेणी) लाई **त्यसलाई कसरी अनुकूलन गर्ने** (टियर) बाट अलग गर्छन्, जसले गर्दा तिनलाई स्वतन्त्र रूपमा संयोजन गर्न सकिन्छ (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **श्रेणीहरू** (क्षमताका आधारमा उम्मेदवार पूल फिल्टर गर्ने): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ले भिजन-सक्षम मोडेलहरू राख्छन्; `reasoning` ले रिजनिङ/थिङ्किङ मोडेलहरू राख्छ।
- **टियरहरू** (स्कोरिङ भारहरू / पूल फिल्टर छनोट गर्ने): `fast` (छिटो डेलिभरी) · `cheap` (उपनाम `floor`, लागत-बचतकर्ता) · `reliable` (सर्किट-ब्रेकर स्वास्थ्य + विलम्बता स्थिरता) · `free` / `pro` (`classifyTier` मार्फत मोडेल टियरअनुसार पूल फिल्टर गर्ने — निःशुल्क-टियर विरुद्ध प्रिमियम)।

| उदाहरण                 | यसमा रूपान्तरण हुन्छ                                 |
| ---------------------- | ---------------------------------------------------- |
| `auto/coding:fast`     | कोडिङ पूल, न्यून-विलम्बता भारहरू                     |
| `auto/coding:cheap`    | कोडिङ पूल, लागत-अनुकूलित (उपनाम `auto/coding:floor`) |
| `auto/reasoning:pro`   | रिजनिङ/थिङ्किङ मोडेलहरू मात्र, प्रिमियम टियर         |
| `auto/vision`          | भिजन-सक्षम मोडेलहरू (टियर छैन → सन्तुलित भारहरू)     |
| `auto/multimodal:free` | मल्टिमोडल-सक्षम मोडेलहरू, निःशुल्क टियर मात्र        |

कुनै पनि मान्य `auto/<category>[:<tier>]` माग हुँदा समाधान हुन्छ; चयनित उपसमूहलाई `/v1/models` र ड्यासबोर्डमा विज्ञापन गरिन्छ (`open-sse/services/autoCombo/builtinCatalog.ts` मा `AUTO_SUFFIX_VARIANTS`)। फिल्टरिङ **फेल-ओपन** हुन्छ — यदि कुनै सर्तसँग जडान भएका कुनै पनि मोडेल मेल खाँदैनन् भने, पूर्ण पूल प्रयोग गरिन्छ, जसले गर्दा राउटिङ कहिल्यै बिग्रँदैन। मूल स्कोरर (`combo.ts`) अपरिवर्तित छ; श्रेणी/टियर फिल्टर `buildAutoCandidates` मा लागू गरिन्छ।

> **लाइभ मोडेल इन्टेलिजेन्स:** `ARENA_ELO_SYNC_ENABLED` फ्ल्याग सक्रिय हुँदा स्वतः-राउटिङको उपयुक्तता लाइभ **Arena ELO** र्याङ्किङ + **models.dev** टियर डेटाबाट निर्देशित हुन्छ (अन्यथा स्थिर फिटनेस म्यापमा फर्कन्छ)।

**प्रयोग गर्ने तरिका:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**के हुन्छ:**

1. OmniRoute ले `src/sse/handlers/chat.ts` मा `auto/` उपसर्ग पत्ता लगाउँछ
2. डेटाबेसबाट सबै **सक्रिय प्रदायक जडानहरू** क्वेरी गर्छ
3. मान्य क्रेडेन्सियलहरू (API कुञ्जी वा OAuth टोकन) भएकाहरू मात्र फिल्टर गर्छ
4. प्रत्येक जडानका लागि मोडेल निर्धारण गर्छ (`connection.defaultModel` वा प्रदायकको पहिलो मोडेल)
5. मेमोरीमा **भर्चुअल कम्बो** निर्माण गर्छ (DB मा भण्डारण गरिँदैन)
6. चयन गरिएको भेरियन्टको भार प्रोफाइल + LKGP रणनीति प्रयोग गरेर राउट गर्छ

**मुख्य विशेषताहरू:**

- ✅ **सधैँ सक्रिय:** कुनै टगल, कम्बो सिर्जना वा कन्फिगरेसन आवश्यक छैन
- ✅ **डायनामिक:** हाल जडान गरिएका प्रदायकहरूलाई स्वचालित रूपमा प्रतिबिम्बित गर्छ
- ✅ **सत्र स्थिरता:** LKGP ले पछिल्लो सफल प्रदायकलाई प्राथमिकता दिइने सुनिश्चित गर्छ
- ✅ **बहु-खाता सचेत:** प्रत्येक प्रदायक जडान छुट्टै उम्मेदवार बन्छ
- ✅ **DB लेखाइ छैन:** भर्चुअल कम्बो अनुरोधका लागि मात्र अस्तित्वमा रहन्छ, कुनै पनि पर्सिस्टेन्स ओभरहेड हुँदैन

### प्रति-कुञ्जी उम्मेदवार नियन्त्रण (#7819, स्तर 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` पछिको प्रत्यय, वा
आधार च्यानलका लागि शाब्दिक `auto`) एउटा **पढ्न-मात्र** एन्डपोइन्ट हो, जसले
अवस्थित रिजिलियन्स रिडहरू पुनः प्रयोग गर्दै, लाइभ पहुँचयोग्यताको विवरणसहित
`auto/*` च्यानलको हालको उम्मेदवार पूल सूचीबद्ध गर्छ (कहिल्यै कच्चा ब्रेकर `state` होइन):

- प्रदायक सर्किट ब्रेकर — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- जडान कुलडाउन — समाधान गरिएको `provider_connections` पङ्क्तिमा रहेको
  `rateLimitedUntil` / `testStatus`
- मोडेल लकआउट — `isModelLocked(provider, connectionId, model)`

प्रत्येक उम्मेदवारमा यस API कुञ्जीको `excluded` फ्ल्याग पनि हुन्छ। बहिष्करणहरू
प्रति-API-कुञ्जी भण्डारण गरिन्छ (`auto_candidate_overrides` तालिका, माइग्रेसन `128`) —
OmniRoute मा `users` तालिका नभएको एकल-टेनेन्ट प्रणाली भएकाले `apiKeyId` नै
वास्तविक प्रति-कलर पहिचानको सबैभन्दा नजिकको विकल्प हो — र यसलाई
`open-sse/services/autoCombo/virtualFactory.ts` को उम्मेदवार-पूल चोकपोइन्टमा
शुद्ध, एकाइ-परीक्षित `filterExcludedCandidates()`
(`open-sse/services/autoCombo/candidateOverrides.ts`) मार्फत लागू गरिन्छ।
फिल्टर **फेल-ओपन** हुन्छ: सेट नगरिएको apiKeyId/channel वा DB लुकअप विफलता दुवैले
पूललाई फिल्टर नगरिएको अवस्थामा छोड्छन्, त्यसैले कुनै ओभरराइड कन्फिगर नगरेको
अपरेटरले यस सुविधाअघिकै बाइट-समान राउटिङ देख्छ।

**फलो-अप मुद्दाका लागि स्थगित:** प्रति-candidate तौलहरू + स्पष्ट क्रम निर्धारण (Level 3
— विद्यमान weighted/priority रणनीति मार्गहरूमा समावेश हुन्छ) र प्रत्येक `auto/*`
च्यानलका लागि विशिष्ट `combo.ts` रणनीति पिन गर्ने (Level 4)। single-tenant मोडेललाई
ध्यानमा राख्दा overrides प्रति-API-key नै रहनुपर्छ वा global बन्नुपर्छ भन्ने खुला
प्रश्नका लागि #7819 योजना हेर्नुहोस्।

**पर्दापछाडि:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## वास्तविक Model Id सँग मेल खाने Combo नामहरू

कुनै combo को `name` ठ्याक्कै bare model id सँग समान हुनु (उदाहरणका लागि, `gpt-5.5` नाम भएको combo) **जानाजानी प्रयोग गरिने, समर्थित ढाँचा** हो, bug होइन: यो [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) मा दस्तावेज गरिएको प्रत्येक model-id का लागि provider fallback संयन्त्र हो। bare-model-id resolution भन्दा पहिले combo resolution जाँचिने भएकाले (`src/sse/services/model.ts` मा `getComboForModel()`), bare id `gpt-5.5` को अनुरोधलाई सिधै एउटै provider तर्फ पठाउनुको सट्टा combo का targets (उदाहरणका लागि, `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) मार्फत route गरिन्छ — यसले [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) का लागि बनाइएको combo-before-rewrite precedence पुनः प्रयोग गर्छ र `tests/unit/responses-combo-resolution-3227.test.ts` तथा `tests/unit/combo-name-codex-responses-rewrite.test.ts` द्वारा regression परीक्षण गरिएको छ।

वास्तविक model id लाई छायामा पार्ने नामसहित combo सिर्जना वा पुनःनामकरण गर्दा त्यसलाई **कहिल्यै अस्वीकार गरिँदैन** — त्यसो गर्दा यो दस्तावेज गरिएको workflow बिग्रन्थ्यो। यसको सट्टा (#8530), (नयाँ) नाम वास्तविक model id सँग बाझिँदा `POST /api/combos` र `PUT /api/combos/[id]` ले response मा non-blocking `warning` field संलग्न गर्छन्:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Boot हुँदा, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ले model id लाई छायामा पार्ने प्रत्येक विद्यमान combo सूचीकृत गर्दै एक-लाइनको `[STARTUP]` warning पनि log गर्छ, जसले जानाजानी (#6940 अनुसार) नभई संयोगवश यस्तो अवस्थामा पुगेका operators लाई संकेत दिन्छ। Detection helper `src/lib/combos/modelNameCollision.ts` मा छ।

## Client बाट Custom Combo कल गर्ने

Persist गरिएका combos (Settings → Combos) client ले `model` field मा combo को **ठ्याक्कै मिल्ने नाम** पठाउँदा मात्र प्रयोग हुन्छन् — combo नामको fuzzy वा partial matching हुँदैन, र `auto/` prefix पनि संलग्न हुँदैन। Resolution क्रम (`src/sse/services/model.ts` मा `getComboForModel()`):

1. combo नामको ठ्याक्कै match (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

दुईवटा सामान्य समस्या:

- **`auto` ले तपाईंका combos प्रयोग गर्दैन।** `auto`/`auto/*` ले आफ्नै zero-config candidate pool बनाउँछ र कुनै combo को नाम अक्षरशः `auto` भएमा मात्र persist गरिएका combos हेर्छ (सिफारिस गरिँदैन)। combo मार्फत route गर्न, त्यसको ठ्याक्कै नाम पठाउनुहोस् — `auto` होइन।
- **`openrouter/auto` एउटा वास्तविक सशुल्क OpenRouter product** ("Auto Best Available") हो, OmniRoute alias होइन। यो OpenRouter registry (`open-sse/config/providers/registry/openrouter/index.ts`) को एकल static model entry हो र यसको billing छुट्टै हुन्छ। यसलाई `auto` pools बाट हटाउन Settings → Routing → Hide paid models प्रयोग गर्नुहोस्।

यहाँ दस्तावेज गरिएको मूल अन्योलबारे [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) र [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) हेर्नुहोस्।

## यसले कसरी काम गर्छ (Persisted Auto-Combos)

Auto-Combo Engine ले प्रत्येक अनुरोधको लागि **16-factor scoring function** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` मा परिभाषित) प्रयोग गरेर गतिशील रूपमा उत्तम प्रदायक/मोडेल चयन गर्दछ। पूर्वनिर्धारित भारहरूको योगफल `1.0` हुन्छ; अनुकूलन भारहरूलाई `normalizeScoringWeights()` द्वारा पुन: सामान्यीकरण (renormalize) गरिन्छ। सोह्रमध्ये दुईवटा — `cacheAffinity` र `resetWindowAffinity` — को पूर्वनिर्धारित भार `0` हुन्छ; `DEFAULT_WEIGHTS` मा `reliability` को भार `0` हुन्छ तर जेनेरिक प्याकहरूमा `0.03` र `reliability-first` मा `0.04` हुन्छ, र `quality` को भार प्याकहरूमा `0.02` (`quality-first` मा `0.03`) हुन्छ: तिनीहरू अझै पनि प्रत्येक उम्मेदवारको लागि गणना गरिन्छ, र `cacheAffinity` ले स्कोर बाहिर प्रम्प्ट-क्यास डुप्लिकेशन नियन्त्रण गर्दछ, त्यसैले शून्य-पूर्वनिर्धारित कारकहरूले केवल पूर्वनिर्धारित रूपमा भोट गर्दैनन् जबकि प्याकहरूले गर्छन्।

> र यसले `100` को पूर्वनिर्धारित मान राख्छ।

- **प्याकहरूले `quality` र `reliability` समावेश गर्छन्** (`quality 0.02`, `quality-first 0.03`; `reliability 0.03`, `reliability-first 0.04`) र तौल नक्सालाई पूर्ण रूपमा प्रतिस्थापन गर्छन् (`weights = pack`, मर्ज होइन)। `DEFAULT_WEIGHTS` मा `quality 0.03 / reliability 0` हुन्छ; `balanced`/`default` चयन गर्दा ती पूर्वनिर्धारित मानहरू कायम रहन्छन्, जबकि कुनै प्याक चयन गर्दा माथिका प्याक मानहरू प्रयोग हुन्छन्। चिसो पूलमा (अझै कुनै अवलोकन नभएकोले `quality 0.5` र `reliability 1`) यी दुई कारकहरूले सामान्य प्याकअन्तर्गत `+0.04` (`0.03 + 0.01`), `quality-first` अन्तर्गत `+0.045` र `reliability-first` अन्तर्गत `+0.05` थप्छन्।
- `tierAffinity`, `specificityMatch` र `resetWindowAffinity` प्रत्येक प्याकमा स्पष्ट रूपमा `0` छन्।
- प्रत्येक प्याकको जोड एक नजरमा:
  - **ship-fast** → latencyInv 0.3048 + health 0.2667 (कम विलम्बता, स्वस्थ जडानहरू)
  - **cost-saver** → costInv 0.3324 (सबैभन्दा सस्ता टोकनहरू विजयी हुन्छन्)
  - **quality-first** → taskFit 0.3524 + stability 0.1429 + quality 0.03, जुन कुनै पनि प्याकमध्ये सबैभन्दा उच्च हो (कार्यका लागि सर्वोत्तम र सुसंगत मोडेल)
  - **offline-friendly** → quota 0.3324 + health 0.2667 (गति/लागतको परवाह नगरी अधिकतम अतिरिक्त क्षमता)

### `weighted` अर्थशास्त्र

`weighted` भनेको प्रति अनुरोध एक समानुपातिक अनियमित ड्र हो (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), इक्वलाइजर होइन:

- प्रत्येक अनुरोधले `weight / totalWeight` सम्भाव्यताको साथ एक चरण ड्र गर्छ; बाँकी चरणहरू त्यो अनुरोधको लागि फलब्याक चेनको रूपमा घट्दो भार (weight) अनुसार क्रमबद्ध हुन्छन्।
- `0` भार (वा हराएको) भएको चरण कहिल्यै ड्र हुँदैन जबसम्म अन्य कुनै चरणको भार `> 0` हुन्छ — यो ड्र गरिएको चरण असफल भएपछि मात्र फलब्याकको रूपमा सेवा गर्न सक्छ। जब सबै भारहरू `0` हुन्छन्, तब मात्र चयन एकसमान हुन्छ।
- जसका लक्ष्यहरू अनुपलब्ध छन् — प्रदायक सर्किट ब्रेकर `OPEN`, जडान कूलडाउन, मोडेल लकआउट — ती चरणहरू ड्र हुनु अघि नै हटाइन्छन् (`open-sse/services/combo/targetResolution.ts`), त्यसैले एउटा मात्र स्वस्थ चरणले अस्थायी रूपमा प्रत्येक अनुरोध जित्न सक्छ।
- `stickyWeightedLimit` (कम्बो कन्फिग, डिफल्ट `1` = बन्द) ले पुन: ड्र गर्नु अघि धेरै लगातार सफलताहरूको लागि ड्र गरिएको चरणलाई पिन गर्दछ।

कडा रोटेशनको लागि `round-robin` प्रयोग गर्नुहोस्; `weighted` मा समान तौलले सांख्यिकीय — कडा होइन — सन्तुलन दिन्छ।

### एजेन्टिक पाइपलाइन मोड

कम्तिमा दुई मोडेलहरू भएको `pipeline` कम्बोले `config.agenticOrchestration.enabled` को साथ प्लानर/एक्जिक्युटर राउटिङमा अप्ट-इन गर्न सक्छ। पहिलो टार्गेटले योजना र अन्तिम उत्तरहरू सम्हाल्छ; दोस्रो टार्गेटले क्लाइन्ट-नेटिभ टूल कलहरू उत्सर्जन गर्छ। OmniRoute ले अनुरोध प्रोटोकलबाट टूल-रिजल्ट निरन्तरताहरू पत्ता लगाउँछ, प्लानरलाई अर्को टूल राउन्ड आवश्यक छ कि छैन भनेर सोध्छ, र गतिशील रूपमा एक्जिक्युटर वा प्लानरलाई क्लाइन्ट-फेसिंग अन्तिम चरण बनाउँछ।

वैकल्पिक `config.agenticOrchestration.contextCompaction` ले प्रत्येक प्लानर वा एक्जिक्युटर डिस्प्याच अघि छुट्टै पेलोड बजेट लागू गर्छ। यसलाई स्पष्ट रूपमा सक्षम गर्नुहोस्:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

यी अपरेटरद्वारा चयन गरिएका सिरियलाइज्ड JSON क्यारेक्टर बजेटहरू हुन्, टोकन कन्टेक्स्ट विन्डोज वा ग्यारेन्टी गरिएको अपस्ट्रिम सीमाहरू होइनन्। सही मोडेल ID हरूले डिफल्टलाई ओभरराइड गर्छन्। थ्रेसहोल्ड भन्दा माथि, कम्प्याक्सनले समान टूल परिभाषाहरू हटाउँछ, डाइजेस्टको साथ ओभरसाइज टूल प्रमाणहरू काट्छ, र टार्गेट अनुपात तर्फ पुराना पूर्ण इतिहास समूहहरू हटाउँछ। यसले सिस्टम/डेभलपर निर्देशनहरू, पछिल्लो प्रयोगकर्ता अनुरोध, समानान्तर कल/रिजल्टहरू सहितको अन्तिम टूल राउन्ड, र Gemini को अग्रणी राउटिङ निर्देशन कायम राख्छ। शीर्ष-स्तरका निर्देशनहरू र टूल सेटिङहरू सुरक्षित राखिन्छन्। एक ओमिशन मार्करले हटाइएको इतिहास रेकर्ड गर्छ; यो डिटरमिनिस्टिक ट्रिमिङ हो, सिमान्टिक सारांश होइन। यदि पिन्ड कन्टेक्स्ट अझै पनि बजेट भन्दा बढी छ भने, अनुरोधले मोडेललाई सम्पर्क गर्नु अघि 413 फिर्ता गर्छ। कम्प्याक्सन असक्षम वा थ्रेसहोल्ड भन्दा तल हुँदा अनुरोध अपरिवर्तित रूपमा पास हुन्छ।

दोस्रो टार्गेट पछिका अतिरिक्त मोडेलहरू अर्डर गरिएका एक्जिक्युटर ब्याकअपहरू हुन्। असफल HTTP प्रतिक्रिया वा ट्रान्सपोर्ट एक्सेप्सन अर्को एक्जिक्युटरमा सर्छ, जसले उही प्लानर निर्णय र नेटिभ टूलहरू बोक्छ तर त्यो एक्जिक्युटरको आफ्नै स्टेप प्रम्प्ट र रिजल्भ गरिएको जडान हुन्छ। पहिलो सफल प्रतिक्रिया अपरिवर्तित रूपमा फिर्ता गरिन्छ, SSE स्ट्रिमिङ सहित; सफल स्ट्रिम सुरु भएपछिका विफलताहरू यहाँ पुन: प्रयास गर्न सकिँदैन। यदि सबै एक्जिक्युटरहरू असफल भएमा, अन्तिम विफलता फिर्ता गरिन्छ। क्लाइन्ट एबोर्टहरूले डिस्प्याच रोक्छन्।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

एक्जिक्युटरले एक प्रतिक्रियामा धेरै स्वतन्त्र कलहरू उत्सर्जन गर्न सक्छ। डिपेन्डेन्ट कलहरू पछिका क्लाइन्ट टूल-रिजल्ट टर्नहरूमा ह्यान्डल गरिन्छन्, जसमा प्लानरले प्रत्येक नतिजाको समीक्षा गर्छ। `maxToolRounds` डिफल्ट रूपमा `8` हुन्छ र `1`–`32` स्वीकार गर्छ; एक पटक पुगेपछि, प्लानरले उपलब्ध उत्तम अन्तिम उत्तर उत्पादन गर्नुपर्छ। आन्तरिक प्लानर निर्णयहरू बफर गरिन्छन्, जबकि चयन गरिएको क्लाइन्ट-फेसिंग प्रतिक्रियाले मूल स्ट्रिमिङ प्राथमिकता कायम राख्छ।

### `round-robin` स्टिकी ब्याच और अकाउन्ट विस्तार

राउन्ड-रोबिन ब्याच गरिएको हुन्छ, प्रति-चरण एक-अनुरोध होइन:

- `stickyRoundRobinLimit` (कम्बो कन्फिग, त्यसपछि `comboStickyRoundRobinLimit`, त्यसपछि `settings.stickyRoundRobinLimit`, डिफल्ट **3**) ले रोटेट हुनु अघि त्यति धेरै लगातार सफलताहरूको लागि उही टार्गेट राख्छ। एक-अनुरोध रोटेशनको लागि कम्बो ओभरराइडलाई `1` मा सेट गर्नुहोस्। कम्बो सम्पादकले प्रभावकारी मान र यो कुन तहबाट आएको हो भनेर देखाउँछ।
- `connectionAwareExpansion` (कम्बो कन्फिग, त्यसपछि सेटिङहरू, डिफल्ट **false**) ले रोटेशन अघि प्रत्येक प्रदायक-स्तरको चरणलाई प्रति-अकाउन्ट टार्गेटहरूमा विस्तार गर्छ। Group-B रणनीतिहरू (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) ले यो अन नभएसम्म प्रदायक-स्तरको दृश्य राख्छन्। कम्बो सम्पादकले inherit / on / off देखाउँछ; inherit ले ग्लोबल डिफल्ट (off) प्रयोग गर्छ।
- प्रम्प्ट-क्यास लोकेलिटी राउटिङ (`promptCacheAffinityEnabled`, डिफल्ट **true**) ले पिन्ड जडानहरूलाई पुन: क्रमबद्ध गर्छ ताकि मिल्दो क्यास कुञ्जीहरू एउटै अकाउन्टमा रहून्। यसले पिन्ड प्रति-अकाउन्ट चरणहरूमा राउन्ड-रोबिन र वेटेड रोटेशन भन्दा प्राथमिकता लिन्छ। यदि तपाईंलाई कडा रोटेशन चाहिन्छ भने Settings → Combo defaults अन्तर्गत यसलाई बन्द गर्नुहोस्। त्यहाँ कुनै प्रति-कम्बो ओभरराइड छैन।

एउटा मोडेलमा बहु-अकाउन्ट रोटेशनको लागि, तीन पिन्ड `connectionId` हरू होइन, स्टिकी लिमिट `1` भएको **एउटा डाइनामिक-अकाउन्ट स्टेप** (खाली `connectionId`, सम्पूर्ण पूल) लाई प्राथमिकता दिनुहोस्। RR काउन्टर अगाडि बढ्दा पनि पिन्ड चरणहरू र एफिनिटी एउटै अकाउन्टमा कोल्याप्स हुन्छन्।

## फ्युजन रणनीति

`fusion` एउटा यस्तो रणनीति हो जसले कुनै एकल लक्ष्य चयन **गर्दैन**। यसले प्रम्प्टलाई
**प्रत्येक प्यानल मोडेलमा समानान्तर रूपमा** पठाउँछ, त्यसपछि कन्फिगर गर्न मिल्ने **निर्णायक मोडेल** ले
सबै प्यानल प्रतिक्रियाबाट एउटा अन्तिम उत्तर संश्लेषण गर्छ। यो upstream `decolua/9router`
(OpenRouter को Fusion डिजाइन) बाट पोर्ट गरिएको हो; यसको कार्यान्वयन `open-sse/services/fusion.ts` मा छ।

यसले कसरी काम गर्छ:

0. **उपकरणयुक्त बाइपास** — गैर-रिक्त `tools` एरे भएको र `tool_choice` लाई स्पष्ट रूपमा
   `"none"` नतोकिएको अनुरोधले प्यानललाई पूर्ण रूपमा छोड्छ: यो अपरिवर्तित रूपमा पास गरिएका
   `tools`/`tool_choice` सहित सिधै एउटा मोडेलमा (कन्फिगर गरिएको निर्णायक, वा `panel[0]`)
   रुट हुन्छ। प्यानल सदस्यहरूसँग उपकरण पहुँच हुँदैन र निर्णायकको संश्लेषण निर्देशनले
   उपकरण-कल उत्सर्जनलाई निरुत्साहित गर्छ, त्यसैले एजेन्टिक/उपकरण-कल गर्ने क्लाइन्टहरूले
   संश्लेषित गद्यको सट्टा वास्तविक उपकरण-कल निर्णय प्राप्त गर्छन् (#6771)।
1. **फ्यान-आउट** (उपकरणरहित अनुरोधहरूमा मात्र) — प्रम्प्टलाई सबै प्यानल
   मोडेलमा एकैपटक पठाइन्छ, उपकरणहरू हटाएर नन-स्ट्रिमिङ हुन बाध्य पारिन्छ (निर्णायकलाई
   संश्लेषण गर्न पूर्ण गद्य चाहिन्छ)।
2. **कोरम-ग्रेस सङ्कलन** — `minPanel` उत्तरहरू प्राप्त हुनेबित्तिकै पछाडि परेकाहरूका लागि
   छोटो ग्रेस टाइमर सुरु हुन्छ, त्यसपछि सङ्कलन भएका उत्तरहरू लिएर फ्युजन अगाडि बढ्छ।
   यसले सबैभन्दा ढिलो मोडेलका कारण कुल प्रतीक्षा समयमा पर्ने असरलाई सीमित गर्छ, जुन
   हार्ड टाइमआउटद्वारा बाँधिएको हुन्छ।
3. **निर्णायक संश्लेषण** — प्यानल उत्तरहरूलाई अज्ञातीकृत गरिन्छ (`Source 1`, `Source 2`, … — ताकि
   निर्णायकले मोडेल ब्रान्ड होइन, विषयवस्तुको महत्त्व मूल्याङ्कन गरोस्) र निर्णायकलाई दिइन्छ, जसले
   सहमति / विरोधाभास / आंशिक समेटाइ / अद्वितीय अन्तर्दृष्टि / छुटेका पक्षहरूको विश्लेषण गर्छ, त्यसपछि
   **एउटा** आधिकारिक उत्तर लेख्छ। निर्णायक कलले क्लाइन्टको मूल
   `stream` फ्ल्याग + उपकरणहरू कायम राख्छ, त्यसैले स्ट्रिमिङ र डाउनस्ट्रिम उपकरण प्रयोग अझै काम गर्छ।
4. **सहज अवनति** — 0 प्यानल उत्तर → `503`; ठ्याक्कै 1 बाँकी उत्तर → त्यो उत्तर
   सिधै फर्काइन्छ (फ्युज गर्न केही हुँदैन); एकल-मोडेल प्यानलले सिधै उत्तर दिन्छ।

प्यानल सदस्य अर्को कम्बोलाई सन्दर्भ गर्ने `combo-ref` चरण (`{kind: "combo-ref", comboName: "..."}`) पनि हुन सक्छ
— यो **एउटा ब्ल्याक-बक्स प्यानल आवाज** का रूपमा समाधान हुन्छ (सन्दर्भित कम्बोमा पूर्ण पुनरावर्ती डिस्प्याच,
त्यस कम्बोका आफ्नै लक्ष्यहरूको फ्यान-आउट होइन), र यसमा अन्य हरेक combo-ref प्रयोग गर्ने रणनीतिले
पहिलेदेखि प्रयोग गर्ने उही गहिराइ/चक्र सुरक्षा लागू हुन्छ (#6764)।

### कन्फिगरेसन

कम्बोको `config` ब्लबमा कन्फिगर गरिन्छ (स्किमा माइग्रेसन आवश्यक छैन — यसले विद्यमान
`combos` तालिका पुनः प्रयोग गर्छ):

| फिल्ड                                    | प्रकार   | पूर्वनिर्धारित     | उद्देश्य                                                                           |
| :--------------------------------------- | :------- | :----------------- | :--------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | पहिलो प्यानल मोडेल | अन्तिम उत्तर संश्लेषण गर्ने मोडेल                                                  |
| `config.fusionTuning.minPanel`           | `number` | `2`                | ग्रेस टाइमर सुरु हुनुअघि आवश्यक सफल उत्तरहरू (`[2, panelSize]` भित्र सीमित गरिन्छ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`             | कोरम पुगेपछि पछाडि परेकाहरूका लागि कति समय पर्खने                                  |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`            | एउटा अड्किएको मोडेलले अनुरोध रोक्न नसकोस् भनेर तोकिएको पूर्ण अधिकतम सीमा           |

पूर्वनिर्धारित मानहरू `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) मा छन्।

### उदाहरण

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

त्यसपछि यसलाई अन्य कुनै कम्बोजस्तै कल गर्नुहोस्: `{"model":"fusion-panel","messages":[...]}`।

## भर्चुअल अटो-कम्बो फ्याक्ट्री

Auto Combo इन्जिनलाई पूर्व-परिभाषित कम्बोहरू आवश्यक पर्दैन। यसको सट्टा, `open-sse/services/autoCombo/virtualFactory.ts` ले तत्कालै उम्मेदवारहरू निर्माण गर्छ:

1. `getProviderConnections({ isActive: true })` (सबै सक्षम जडानहरू) प्राप्त गर्छ
2. वैध क्रेडेन्सियल भएका जडानहरूमा फिल्टर गर्छ (API key वा `hasUsableOAuthToken()` मार्फत म्याद नसकिएको OAuth token)
3. मोडेल उपलब्धता + मूल्य निर्धारणका लागि `getProviderRegistry()` सँग क्रस-रेफरेन्स गर्छ
4. प्रत्येक `(provider, model, connection)` ट्युपलका लागि, एउटा `VirtualAutoComboCandidate` निर्माण गर्छ
5. डिस्प्याच लक्ष्यका रूपमा `connection.defaultModel` (वा registry को पहिलो मोडेल) चयन गर्छ
6. 16-कारक `scorePool()` र भेरियन्टको weight pack प्रयोग गरेर प्रत्येक उम्मेदवारलाई स्कोर गर्छ
7. `handleComboChat()` का लागि नतिजास्वरूप प्राप्त इन-मेमोरी `AutoComboConfig` फर्काउँछ — DB मा कहिल्यै स्थायी रूपमा भण्डारण हुँदैन

यसको अर्थ **`auto/*` सक्षम गरिएको नयाँ provider थप्दा उम्मेदवार पूल स्वतः विस्तार हुन्छ** — म्यानुअल रूपमा कम्बो सम्पादन गर्नुपर्दैन। भर्चुअल कम्बो प्रत्येक अनुरोधमा पुनःनिर्माण हुन्छ, त्यसैले भर्खरै थपिएका वा पुनः स्वस्थ भएका जडानहरू तत्काल समावेश हुन्छन्।

## स्व-उपचार

- **अस्थायी बहिष्करण**: स्कोर < 0.2 → 5 मिनेटका लागि बहिष्कृत (क्रमिक backoff, अधिकतम 30 मिनेट)
- **Circuit breaker सचेतना**: OPEN → स्वतः बहिष्कृत; HALF_OPEN → परीक्षण अनुरोधहरू
- **घटना मोड**: >50% OPEN → अन्वेषण निष्क्रिय गर्ने, स्थिरता अधिकतम बनाउने
- **Cooldown पुनःप्राप्ति**: बहिष्करणपछि, पहिलो अनुरोध घटाइएको timeout सहितको "probe" हुन्छ

## Bandit अन्वेषण

5% अनुरोधहरू (कन्फिगर गर्न मिल्ने) अन्वेषणका लागि अनियमित provider हरूमा रुट गरिन्छन्। घटना मोडमा यो निष्क्रिय हुन्छ।

## API

त्यहाँ कुनै **समर्पित `POST /api/combos/auto` इन्डपोइन्ट छैन** — Auto-Combo दुई तरिकाले प्रयोग गरिन्छ:

1. **Zero-config (सिफारिस गरिएको):** `model: "auto"` वा `model: "auto/<variant>"` को साथ कुनै पनि च्याट कम्प्लिशन अनुरोध पठाउनुहोस्। भर्चुअल फ्याक्ट्रीले प्रति अनुरोध कम्बो निर्माण गर्छ — कुनै पर्सिस्टेन्स (स्थायित्व), कुनै API कल आवश्यक पर्दैन।

2. **`strategy: "auto"` को साथ पर्सिस्टेड कम्बो:** `POST /api/combos` मार्फत नियमित कम्बो सिर्जना गर्नुहोस् र `strategy: "auto"` साथै `config.auto.weights` / `config.auto.candidatePool` सेट गर्नुहोस्। उही स्कोरिङ इन्जिन प्रयोग गरिन्छ; कम्बो `combos` मा भण्डारण गरिन्छ र ID द्वारा पुन: प्रयोग गर्न सकिन्छ।

डिस्कभरीको लागि, `GET /api/combos/auto` ले प्रत्येक भेरियन्टलाई यसको रिजल्भ गरिएको क्यान्डिडेट पूल र `context_length` / `max_output_tokens` — क्यान्डिडेट पूलको विन्डोजहरूमा रहेको MAX — को साथ सूचीबद्ध गर्दछ। क्लाइन्टहरूले (जस्तै opencode प्लगइन) `0` को सट्टा यी मानहरू विज्ञापन गर्नुपर्छ: शून्य कन्टेक्स्टले opencode को अटो-कम्प्याक्सनलाई पूर्ण रूपमा असक्षम पार्छ, जसले गेटवेको हिस्ट्री पर्जले कन्टेक्स्ट नष्ट नगरेसम्म सेसनहरूलाई बढ्न दिन्छ। MAX विज्ञापन गर्न सुरक्षित छ किनभने अटो-कम्बो कन्टेक्स्ट प्रि-फिल्टरले ओभरसाइज अनुरोधहरूलाई ठूलो-विन्डो क्यान्डिडेटहरूमा रूट गर्छ।

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

पर्सिस्टेड `strategy: "auto"` कम्बोहरूले `config.routerStrategy` (वा लिगेसी `config.auto.routerStrategy`) लाई निम्न मध्ये एकमा सेट गर्न सक्छन्:

- `rules` — पूर्वनिर्धारित वेटेड स्कोरिङ
- `score` — उच्चतम कन्फिगर गरिएको वेटेड स्कोर चयन गर्दछ। ठ्याक्कै बराबरी (ties) भएमा कन्फिगर गरिएको क्यान्डिडेट अर्डर कायम रहन्छ; अवस्थित `explorationRate` ले पूर्ण र्याङ्क गरिएको पूलबाट स्याम्पल लिन्छ।
- `cost` / `eco` — सबैभन्दा सस्तो हेल्दी प्रोभाइडर
- `latency` / `fast` — रिलायबिलिटी पेनाल्टीको साथ सबैभन्दा कम p95 लेटन्सी
- `sla-aware` / `sla` — p95 लेटन्सी, एरर-रेट, र वैकल्पिक लागत SLO हरू पूरा गर्ने क्यान्डिडेटहरूलाई प्राथमिकता दिनुहोस्
- `lkgp` — अन्तिम ज्ञात राम्रो (last known good) प्रोभाइडरलाई पहिले
- `nadir` — [Nadir](https://getnadir.com) को डिसिजन API लाई सोध्नुहोस् कि प्रम्प्टलाई पूलमा कुन मोडेल चाहिन्छ; अप्ट-इन, `rules` मा फेल-ओपन

### Router strategies को विस्तृत विवरण

अटो-कम्बो इन्जिनले ७ वटा प्लगेबल **RouterStrategy** कार्यान्वयनहरू एक्सपोज गर्छ जुन तपाईंले `config.routerStrategy` (वा लिगेसी `config.auto.routerStrategy`) मार्फत स्वैप गर्न सक्नुहुन्छ। प्रत्येक रणनीतिले `RoutingContext` (टास्क प्रकार, टूल/भिजन संकेतहरू, टोकन अनुमान, वैकल्पिक SLA नीति, वैकल्पिक अन्तिम-ज्ञात-राम्रो प्रोभाइडर) दिइएको खण्डमा क्यान्डिडेट पूलबाट एउटा प्रोभाइडर छनोट गर्छ।

#### १. `rules` (पूर्वनिर्धारित) — १६-फ्याक्टर वेटेड स्कोरिङ

अवस्थित स्कोरिङ इन्जिनलाई र्‍याप गर्छ। `OPEN` सर्किट-ब्रेकर क्यान्डिडेटहरूलाई फिल्टर गर्छ, त्यसपछि हालको टास्क प्रकार र `getTaskFitness()` को साथ `scorePool()` चलाउँछ, र शीर्ष-स्कोर गर्ने प्रोभाइडर छनोट गर्छ।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: पूर्वनिर्धारित। जब तपाईं सबै सिग्नलहरूमा सन्तुलित ट्रेड-अफ चाहनुहुन्छ तब प्रयोग गर्नुहोस्।

**Alias**: `rules` (कुनै उपनाम छैन)

---

#### २. `cost` / `eco` — सबैभन्दा सस्तो हेल्दी प्रोभाइडर

क्यान्डिडेट पूललाई `costPer1MTokens` (बढ्दो क्रममा) अनुसार क्रमबद्ध गर्छ र सबैभन्दा सस्तो छनोट गर्छ। पहिले `OPEN` क्यान्डिडेटहरूलाई फिल्टर गर्छ।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: लागत-संवेदनशील वर्कलोडहरू, ब्याच प्रोसेसिङ, वा ब्याकग्राउन्ड जबहरू।

**Aliases**: `cost`, `eco`

---

#### ३. `latency` / `fast` — रिलायबिलिटी पेनाल्टीको साथ सबैभन्दा कम p95 लेटन्सी

`p95LatencyMs + (errorRate * 1000)` अनुसार क्रमबद्ध गर्छ। एरर-रेट पेनाल्टीले सुनिश्चित गर्छ कि अविश्वसनीय प्रोभाइडरहरू कम र्याङ्क हुन्छन्, भले पनि तिनीहरूको नाममात्र लेटन्सी कम होस्।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**कहिले प्रयोग गर्ने**: रियल-टाइम च्याट, अटोकमप्लिट, वा अन्तरक्रियात्मक कोडिङ सहायकहरू जस्ता लेटन्सी-संवेदनशील वर्कलोडहरू।

**Aliases**: `latency`, `fast`

---

#### ४. `sla-aware` / `sla` — लेटन्सी/एरर/लागत SLO अनुपालन

प्रत्येक क्यान्डिडेटले कन्फिगर गरिएको SLO नीतिलाई कत्तिको राम्रोसँग पूरा गर्छ भन्ने आधारमा स्कोर गर्छ:

| कारक            | तौल | सूत्र                                             |
| --------------- | --- | ------------------------------------------------- |
| लेटन्सी स्कोर   | 35% | `threshold / max(value, ε)`                       |
| त्रुटि स्कोर    | 35% | `threshold / max(value, ε)`                       |
| स्वास्थ्य स्कोर | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| लागत स्कोर      | 10% | `threshold / max(value, ε)` वा इन्भर्स नर्मालइज्ड |
| स्थिरता स्कोर   | 5%  | इन्भर्स नर्मालइज्ड लेटन्सी stddev                 |

जब `hardConstraints: true` हुन्छ, उम्मेदवारहरूलाई मुख्य रूपमा **उल्लंघन स्कोर** (तिनीहरूले कुनै पनि SLO लाई कति हदसम्म नाघ्छन्) द्वारा क्रमबद्ध गरिन्छ, त्यसपछि कम्पोजिट स्कोरद्वारा। अन्यथा यो केवल कम्पोजिट स्कोर मात्र हुन्छ।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA फिल्डहरू** (कम्बो कन्फिगमा सेट गरिएको):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**कहिले प्रयोग गर्ने**: कडा लेटन्सी, त्रुटि-दर, वा लागत बजेट भएका उत्पादन कार्यभारहरू (Production workloads) को लागि।

**उपनामहरू**: `sla-aware`, `sla`

---

#### 5. `lkgp` — अन्तिम पटक ज्ञात राम्रो प्रदायक (last known good provider) पहिले

**अन्तिम पटक ज्ञात राम्रो प्रदायक** (यदि सेट गरिएको छ भने) लाई पहिले प्रयास गर्दछ, त्यसपछि `rules` रणनीतिमा फर्किन्छ। सत्र स्टिकिनेस (session stickiness) को लागि उपयोगी — एउटै प्रदायकले कुराकानीमा फलो-अप अनुरोधहरू ह्यान्डल गर्दछ।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**कहिले प्रयोग गर्ने**: बहु-टर्न कुराकानीहरू जहाँ तपाईं चाहनुहुन्छ कि एउटै प्रदायकले फलो-अप अनुरोधहरू ह्यान्डल गरोस् (उदाहरणका लागि, क्यासिङ, सन्दर्भ निरन्तरता, वा मूल्य निर्धारण स्थिरताको लागि)।

**उपनाम**: `lkgp` (कुनै उपनाम छैन)

---

#### 6. `nadir` — Nadir मार्फत प्रम्प्ट-सचेत मोडेल छनोट

माथिको प्रत्येक रणनीतिले उम्मेदवारहरूलाई तिनीहरूको आफ्नै टेलिमेट्रीद्वारा क्रमबद्ध गर्दछ; ती मध्ये कसैले पनि अनुरोध पढ्दैनन्। `nadir` ले अन्तिम प्रयोगकर्ता टर्न र पूलको मोडेल आईडीहरू [Nadir](https://getnadir.com) को निर्णय API (`POST /v1/bucket`) मा पठाउँछ र Nadir ले त्यो मेनुबाट छनोट गरेको मोडेलमा रुट गर्छ (`simple` → सबैभन्दा सस्तो सक्षम मोडेल, `complex` → फ्रन्टियर मोडेल)। त्यो मोडेल सेवा गर्ने जडान अझै पनि `rules` द्वारा छनोट गरिन्छ, त्यसैले कोटा, स्वास्थ्य र लागतले कुन खाता प्रयोग गर्ने भन्ने निर्णय गरिरहन्छन्।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` र `OMNIROUTE_NADIR_BASE_URL` दुई स्ट्रिङहरूका लागि env फलब्याकहरू हुन्। `baseUrl` केवल सेल्फ-होस्ट गरिएको Nadir को लागि आवश्यक छ (अन्तमा `/v1` राखिएको खण्डमा पनि स्वीकार्य छ)। की-लेस (Keyless) कलहरू Nadir को अज्ञात टियरमा जान्छन्, जुन प्रति IP दर-सीमित हुन्छ।

बक्सबाट के बाहिर जान्छ: अन्तिम प्रयोगकर्ता सन्देशको पाठ (पहिलो 16k क्यारेक्टरहरू), उम्मेदवार मोडेल आईडीहरू र एक `source: "omniroute"` च्यानल ट्याग। कुनै सिस्टम प्रम्प्ट, इतिहास, उपकरण वा हेडरहरू जाँदैनन्।

विफलता व्यवहार फेल-ओपन (fail-open) हुन्छ: टाइमआउट (पूर्वनिर्धारित 2000 ms), गैर-2xx, पहुँच नभएको होस्ट, खराब ढाँचाको प्रतिक्रिया वा पूल बाहिरको छनोट `rules` निर्णयमा समाधान हुन्छ र कारणमा `NadirStrategy: fallback (…)` उपसर्ग थपिन्छ। असफल कल पछि रणनीतिले 30 सेकेन्डको लागि नेटवर्क छोड्छ, त्यसैले आउटेजले प्रति अनुरोध एकको सट्टा प्रति 30 सेकेन्ड एक टाइमआउट खर्च गर्छ। राउटिङ घटनाहरूले `strategy: "nadir"` रिपोर्ट गर्दछ जब Nadir ले वास्तवमा छनोट गर्छ।

**कहिले प्रयोग गर्ने**: मोडेल टियरहरू (एउटा सानो, एउटा मध्यम र एउटा फ्रन्टियर मोडेल) मा फैलिएको पूलमा मिश्रित-कठिनाई ट्राफिक, जहाँ सधैं-फ्रन्टियर (always-frontier) त्यो लागत हो जुन तपाईं कटौती गर्न चाहनुहुन्छ।

**उपनाम**: `nadir` (कुनै उपनाम छैन)

### कस्टम राउटर रणनीतिहरू

तपाईंले सार्वजनिक API मार्फत आफ्नो आफ्नै `RouterStrategy` कार्यान्वयन दर्ता गर्न सक्नुहुन्छ:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

त्यसपछि यसलाई प्रयोग गर्नुहोस्:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

| ----------------- | ----------- | ------------------------------------------------ |
| सन्तुलित कार्यभार | `rules`     | पूर्वनिर्धारित — सबै कारकहरूलाई विचार गर्दछ      |
| लागत न्यूनीकरण    | `cost`      | सधैं सबैभन्दा सस्तो छनोट गर्दछ                   |
| लेटन्सी न्यूनीकरण | `latency`   | सबैभन्दा छिटो भरपर्दो प्रदायक छनोट गर्दछ         |
| कडा SLO हरू       | `sla-aware` | p95/त्रुटि/लागत थ्रेसहोल्डहरूद्वारा फिल्टर गर्दछ |
| बहु-टर्न च्याट    | `lkgp`      | सत्र स्टिकिनेस                                   |
| मिश्रित कठिनाई    | `nadir`     | प्रति प्रम्प्ट मोडेल टियर छनोट गर्दछ             |

SLA-सचेत फिल्डहरू:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

## कार्य उपयुक्तता

6 प्रकारका कार्यहरू (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) मा 30+ मोडेलहरूको मूल्याङ्कन गरिएको छ। वाइल्डकार्ड ढाँचाहरूलाई समर्थन गर्छ (उदाहरणका लागि, `*-coder` → उच्च कोडिङ स्कोर)।

## Auto भेरियन्टहरूको पुनरावलोकन

मूल `auto` (पूर्वनिर्धारित) सहित `autoPrefix.ts` मा घोषणा गरिएका 6 वटा `AutoVariant` मानहरू जोड्दा, **आह्वान गर्न मिल्ने 7 वटा मोडेल ID** छन्:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` ले आफैंमा 6 वटा मानहरू सूचीबद्ध गर्छ; सातौँ विकल्प "भेरियन्ट छैन" — मूल `auto` — हो, जसलाई `parseAutoPrefix()` ले `variant: undefined` का रूपमा व्यवस्थापन गर्छ।)

## टियरहरू Auto-Combo मा कसरी समाहित हुन्छन्

16-फ्याक्टर स्कोरिङ फङ्सन (`open-sse/services/autoCombo/scoring.ts`) ले टियर
सदस्यतालाई दुई सङ्केतका रूपमा लिन्छ: `tierPriority` (0.0476) र `tierAffinity` (0.0476)। पूर्ण
`DEFAULT_WEIGHTS` सेटका लागि माथिको प्रामाणिक [स्कोरिङ फ्याक्टर तालिका](#how-it-works-persisted-auto-combos) हेर्नुहोस् — प्रति-प्याक ओभरराइडहरू (ship-fast/cost-saver/quality-first/
offline-friendly) "प्रति प्याक तौल प्रोफाइलहरू" तालिकामा सूचीबद्ध छन्।

टियरले मात्र Tier 1 लाई पहिले आउन **बाध्य पार्दैन** — यदि Tier 1 को विलम्बता खराब छ वा
लागत-विरुद्ध-गुणस्तर अनुकूलतम छैन भने, Tier 2 विजयी हुन्छ। टियर क्रम बाध्य पार्न, कम्बो
रणनीति `priority` प्रयोग गर्नुहोस् र प्रदायकहरूलाई टियरअनुसार क्रमबद्ध गर्नुहोस्।

Tier 1 (सदस्यता) लाई बलियो प्राथमिकता दिन, `tierPriority` को तौल बढाउनुहोस्:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

टियरका परिभाषाहरू र प्रदायक वर्गीकरणका लागि [`docs/guides/TIERS.md`](../guides/TIERS.md) हेर्नुहोस्।

## परीक्षण र कभरेज

### निर्धारणात्मक राउटिङ-निर्णय म्याट्रिक्स (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` ले नक्कली अपस्ट्रिमसहितको वास्तविक कम्बो पाइपलाइनमार्फत सबै 19
सार्वजनिक रणनीतिहरूको राउटिङ **निर्णय**लाई सुरुदेखि अन्त्यसम्म प्रमाणित गर्छ।
कभरेजमा निम्न समावेश छन्:

- सबै 19 वटा `ROUTING_STRATEGY_VALUES` रणनीतिहरू (ordered, weighted, cost, context, fusion, …)।
- `quota-share` (आन्तरिक) सुरुदेखि अन्त्यसम्म: वास्तविक `selectQuotaShareTarget` सीम (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) मार्फत DRR निष्पक्षता + संतृप्ति प्राथमिकीकरण न्यूनीकरण।
- प्रत्येक लक्षित सङ्ख्यामा `context-relay` को विश्वव्यापी हस्तान्तरण कभरेज।

यो सुइट CI (`test:integration` कार्य) मा `--test-concurrency=1` र
`--test-force-exit` सहित चल्छ, त्यसैले यो निर्धारणात्मक हुन्छ र यसलाई प्रत्यक्ष प्रमाण-पत्रहरू आवश्यक पर्दैनन्।

### गेट गरिएको प्रत्यक्ष स्मोक परीक्षण (CI मा छैन — वास्तविक प्रदायकहरू)

| आदेश                                   | यसले के गर्छ                                                                                  |
| :------------------------------------- | :-------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` सहित इन-प्रोसेस वास्तविक राउटिङ; प्रत्यक्ष OmniRoute DB को स्न्यापसट लिन्छ |
| `npm run test:combo:live:vps`          | प्रत्यक्ष OmniRoute सर्भरविरुद्ध HTTP कलहरू (`COMBO_LIVE_BASE_URL` सेट गर्नुहोस्)             |
| `npm run test:combo:live:vps:failover` | उही, जानाजानी सिर्जना गरिएका फेलओभर परिदृश्यहरूसहित                                           |

यी स्मोक परीक्षणहरूले वास्तविक वायर पथ (कम्बो → प्रदायक → पूर्णता) प्रयोग गर्छन्। प्रत्यक्ष
प्रमाण-पत्रहरू र VPS पहुँच आवश्यक पर्ने भएकाले तिनीहरूलाई जानाजानी CI बाट बाहिर राखिएको छ।
