## التوجيه التلقائي دون إعداد (`auto/` prefix)

> **جديد:** لا حاجة إلى إنشاء مجموعة. استخدم البادئة `auto/` مباشرةً في أي عميل.

### أمثلة سريعة

| معرّف النموذج  | المتغير   | السلوك                                                       |
| -------------- | --------- | ------------------------------------------------------------ |
| `auto`         | افتراضي   | جميع المزوّدين المتصلين، واستراتيجية LKGP، وأوزان متوازنة    |
| `auto/coding`  | برمجة     | أوزان تعطي الأولوية للجودة، ومناسبة لتوليد الشيفرة البرمجية  |
| `auto/fast`    | سريع      | اختيار موزون بزمن استجابة منخفض                              |
| `auto/cheap`   | رخيص      | توجيه محسّن من حيث التكلفة (الأقل تكلفة أولًا)               |
| `auto/offline` | دون اتصال | يفضّل المزوّدين ذوي أعلى حصة متاحة                           |
| `auto/smart`   | ذكي       | أولوية للجودة + معدل استكشاف أعلى (10%) لاكتشاف أفضل للنماذج |
| `auto/lkgp`    | lkgp      | LKGP صريح (مماثل للإعداد الافتراضي `auto`)                   |
| `auto/chaos`   | chaos     | توزيع متوازٍ، نموذج واحد لكل مزوّد (وليس حقنًا للأعطال)      |

### تركيب الفئة × المستوى (`auto/<category>:<tier>`)

تفصل اللواحق بأسلوب OpenRouter بين **نوع مسار التوجيه** (الفئة) و**كيفية تحسينه** (المستوى)، بحيث يمكنك تركيبهما بحرية (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **الفئات** (تصفية مجموعة المرشحين حسب القدرة): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. تحتفظ `vision`/`multimodal` بالنماذج الداعمة للرؤية؛ بينما تحتفظ `reasoning` بنماذج الاستدلال/التفكير.
- **المستويات** (اختيار أوزان التقييم / عامل تصفية المجموعة): `fast` (إصدار سريع) · `cheap` (اسم بديل `floor`، موفّر للتكلفة) · `reliable` (حالة قاطع الدائرة + استقرار زمن الاستجابة) · `free` / `pro` (تصفية المجموعة حسب مستوى النموذج عبر `classifyTier` — المستوى المجاني مقابل المميز).

| المثال                 | النتيجة                                                                  |
| ---------------------- | ------------------------------------------------------------------------ |
| `auto/coding:fast`     | مجموعة البرمجة، وأوزان بزمن استجابة منخفض                                |
| `auto/coding:cheap`    | مجموعة البرمجة، محسّنة من حيث التكلفة (الاسم البديل `auto/coding:floor`) |
| `auto/reasoning:pro`   | نماذج الاستدلال/التفكير فقط، والمستوى المميز                             |
| `auto/vision`          | نماذج داعمة للرؤية (دون مستوى ← أوزان متوازنة)                           |
| `auto/multimodal:free` | نماذج داعمة للوسائط المتعددة، والمستوى المجاني فقط                       |

يُحل أي نمط صالح من `auto/<category>[:<tier>]` عند الطلب؛ وتُعرض مجموعة فرعية منتقاة في `/v1/models` ولوحة المعلومات (`AUTO_SUFFIX_VARIANTS` في `open-sse/services/autoCombo/builtinCatalog.ts`). تعمل التصفية وفق مبدأ **السماح عند الفشل** — إذا لم يطابق أحد القيود أي نماذج متصلة، تُستخدم المجموعة الكاملة كي لا يتعطل التوجيه مطلقًا. يظل المقيّم الأساسي (`combo.ts`) دون تغيير؛ ويُطبّق عامل تصفية الفئة/المستوى في `buildAutoCandidates`.

> **معلومات مباشرة عن النماذج:** تسترشد ملاءمة التوجيه التلقائي بتصنيفات **Arena ELO** المباشرة + بيانات المستويات من **models.dev** عند تفعيل العلامة `ARENA_ELO_SYNC_ENABLED` (وإلا يُرجع إلى خريطة الملاءمة الثابتة).

**كيفية الاستخدام:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**ما الذي يحدث:**

1. يكتشف OmniRoute البادئة `auto/` في `src/sse/handlers/chat.ts`
2. يستعلم عن جميع **اتصالات المزوّدين النشطة** من قاعدة البيانات
3. يرشّح الاتصالات التي تحتوي على بيانات اعتماد صالحة (مفتاح API أو رمز OAuth)
4. يحدّد النموذج لكل اتصال (`connection.defaultModel` أو النموذج الأول لدى المزوّد)
5. ينشئ **مجموعة افتراضية** في الذاكرة (لا تُخزّن في قاعدة البيانات)
6. يوجّه باستخدام ملف أوزان المتغير المحدد + استراتيجية LKGP

**الخصائص الرئيسية:**

- ✅ **دائم التشغيل:** لا حاجة إلى مفتاح تبديل، أو إنشاء مجموعة، أو أي إعداد
- ✅ **ديناميكي:** يعكس تلقائيًا المزوّدين المتصلين حاليًا
- ✅ **ثبات الجلسة:** يضمن LKGP إعطاء الأولوية لآخر مزوّد نجح
- ✅ **يدعم تعدد الحسابات:** يصبح كل اتصال بمزوّد مرشحًا مستقلًا
- ✅ **دون عمليات كتابة في قاعدة البيانات:** لا توجد المجموعة الافتراضية إلا للطلب، دون أي عبء استمرارية

### التحكم في المرشحين لكل مفتاح (#7819، المستوى 1+2)

تمثل `GET /v1/auto-combo/{channel}/candidates` (`{channel}` = اللاحقة بعد `auto/`، أو
القيمة الحرفية `auto` للقناة الأساسية) نقطة نهاية **للقراءة فقط** تسرد مجموعة
المرشحين الحالية لقناة `auto/*`، مع إضافة معلومات إمكانية الوصول المباشرة إليها، وإعادة استخدام
قراءات المرونة الحالية (وليس `state` الخام لقاطع الدائرة مطلقًا):

- قاطع دائرة المزوّد — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- فترة تهدئة الاتصال — `rateLimitedUntil` / `testStatus` في صف
  `provider_connections` الذي جرى حلّه
- حظر النموذج — `isModelLocked(provider, connectionId, model)`

يحمل كل مرشح أيضًا علامة `excluded` الخاصة بمفتاح API هذا. تُخزّن الاستبعادات
لكل مفتاح API (`auto_candidate_overrides` table، migration `128`) — يعمل OmniRoute
لمستأجر واحد ولا يحتوي على جدول `users`، ولذلك فإن `apiKeyId` هو أقرب هوية فعلية
لكل مستدعٍ — وتُفرض عند نقطة الاختناق الخاصة بمجموعة المرشحين في
`open-sse/services/autoCombo/virtualFactory.ts` عبر
`filterExcludedCandidates()` النقية والخاضعة لاختبارات الوحدات (`open-sse/services/autoCombo/candidateOverrides.ts`).
يعمل عامل التصفية وفق مبدأ **السماح عند الفشل**: يؤدي كل من عدم تعيين apiKeyId/channel أو فشل البحث في قاعدة البيانات
إلى ترك المجموعة دون تصفية، بحيث يرى المشغّل الذي لم يضبط أي تجاوزات عملية توجيه
مطابقة على مستوى البايت لما كانت عليه قبل هذه الميزة.

**مؤجل إلى مشكلة متابعة:** أوزان لكل مرشح + ترتيب صريح (المستوى 3
— يغذي مسارات استراتيجية الأوزان/الأولوية الحالية) وتثبيت استراتيجية محددة من
`combo.ts` لكل قناة `auto/*` (المستوى 4). راجع خطة #7819 للاطلاع على السؤال المفتوح
حول ما إذا كان ينبغي أن تظل التجاوزات خاصة بكل مفتاح API أم تصبح عامة بالنظر إلى
نموذج المستأجر الواحد.

**خلف الكواليس:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**ملفات التنفيذ:**

| الملف                                                     | الغرض                                               |
| --------------------------------------------------------- | --------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | محلل البادئة (`parseAutoPrefix`)                    |
| `open-sse/services/autoCombo/virtualFactory.ts`           | ينشئ كائنات `AutoComboConfig` افتراضية              |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | نقطة ربط للاختبارات لمحاكاة سجل المزودين            |
| `src/sse/handlers/chat.ts`                                | التكامل: اختصار المعالجة عند وجود البادئة التلقائية |
| `src/shared/constants/providers.ts`                       | إدخال النظام `SYSTEM_PROVIDERS.auto`                |

## أسماء المجموعات التي تطابق معرّف نموذج حقيقي

إن المجموعة التي يكون `name` الخاص بها مطابقًا لمعرّف نموذج مجرد (مثل مجموعة باسم
`gpt-5.5`) هي **نمط مقصود ومدعوم** وليست خطأً برمجيًا: فهي الآلية المستخدمة لتوفير
الانتقال الاحتياطي بين المزوّدين لكل معرّف نموذج، كما هو موثق في
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). ولأن التحقق من
المجموعة يسبق تحليل معرّف النموذج المجرّد
(`getComboForModel()` في `src/sse/services/model.ts`)، فإن الطلب الخاص بالمعرّف
المجرّد `gpt-5.5` يُوجَّه عبر أهداف المجموعة (مثل
`acme-responses/gpt-5.5` و`backup-responses/gpt-5.5`) بدلًا من توجيهه مباشرةً إلى
مزوّد واحد — ويعيد هذا استخدام أسبقية المجموعة قبل إعادة الكتابة التي بُنيت من أجل

## استدعاء مجموعة مخصصة من عميل

لا تُستخدم المجموعات المحفوظة (الإعدادات ← المجموعات) إلا عندما يرسل العميل **الاسم المطابق تمامًا** للمجموعة في حقل `model` — فلا توجد مطابقة تقريبية أو جزئية لاسم المجموعة، ولا تُستخدم بادئة `auto/`. ترتيب التحليل (`getComboForModel()` في `src/sse/services/model.ts`):

1. مطابقة اسم المجموعة تمامًا (`model: "my-combo"`)،
2. بادئة `combo/<name>`‏ (`model: "combo/my-combo"`)،
3. تعيينات الأنماط الشاملة من النموذج إلى المجموعة (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

مشكلتان شائعتان:

- **لا يستخدم `auto` مجموعاتك.** يبني `auto`/`auto/*` مجموعة المرشحين الخاصة به من دون إعداد، ولا يرجع إلى المجموعات المحفوظة إلا إذا كانت هناك مجموعة اسمها حرفيًا `auto` (وهذا غير مستحسن). للتوجيه عبر مجموعة، أرسل اسمها المطابق تمامًا — وليس `auto`.
- **يُعد `openrouter/auto` منتجًا حقيقيًا مدفوعًا من OpenRouter** ("أفضل خيار متاح تلقائيًا")، وليس اسمًا مستعارًا في OmniRoute. وهو إدخال النموذج الثابت الوحيد في سجل OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`)، وتُحتسب تكلفته بصورة منفصلة. استخدم الإعدادات ← التوجيه ← إخفاء النماذج المدفوعة لاستبعاده من مجموعات `auto`.

راجع [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) و[#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) للاطلاع على الالتباس الأصلي الذي توضحه هذه الوثائق.

## كيف يعمل (Auto-Combos المحفوظة)

> المتبع كعقوبة لحالة الاتصال. تعد القراءة الفاشلة للاستخدام دليلاً يتعلق بالقياس عن بُعد (telemetry)،
> وليس بالمزود، لذلك يتم تصنيفه بدقة أدنى من أي قراءة فعلية، بما في ذلك القراءة المؤكدة للاستخدام بنسبة 100%،

> درجته كحصة كاملة؛ بينما المزود الذي ليس لديه جالب حصة مسجل لا يمتلك أي مصدر للقياس عن بُعد على الإطلاق
> ويحتفظ بالقيمة الافتراضية `100`.

القيم المحسومة إلى مدخلات المحرك الحالية `config.modePack` / `config.budgetCap` /
`config.budgetFallback`. تحدد قيمة `config.budgetFallback` المخزنة للتوليفة ("strict" |
"cheapest") السياسة الدائمة؛ وتتجاوزها الترويسة لطلب واحد فقط.

## جميع استراتيجيات التوجيه

يدعم محرك التجميع (combo engine) في OmniRoute **20 استراتيجية توجيه** (مُعرفة في `src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES`). يتم عرض محرك التجميع التلقائي (Auto Combo) نفسه تحت استراتيجية `auto`؛ بينما تتوفر الاستراتيجيات الأخرى للتجميعات المستمرة (persisted combos).

| الاستراتيجية        | الوصف                                                                                                                                                                                                                          |
| :------------------ | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `priority`          | قائمة مرتبة حسب الهدف الأول مع أولوية صريحة                                                                                                                                                                                    |
| `weighted`          | عشوائية مرجحة حسب وزن كل هدف                                                                                                                                                                                                   |
| `round-robin`       | التبديل بين الأهداف بالترتيب (على دفعات؛ انظر أدناه)                                                                                                                                                                           |
| `context-relay`     | تسليم السياق عبر الأهداف (للمحادثات الطويلة)                                                                                                                                                                                   |
| `fill-first`        | ملء حصة كل هدف قبل الانتقال إلى التالي                                                                                                                                                                                         |
| `p2c`               | موازنة الحمل العشوائية باستخدام خيار "قوة الاثنين" (Power-of-2-choices)                                                                                                                                                        |
| `random`            | اختيار عشوائي موحد                                                                                                                                                                                                             |
| `least-used`        | اختيار الهدف ذو أقل حمل حالي                                                                                                                                                                                                   |
| `cost-optimized`    | تقليل التكلفة ($) لكل طلب بناءً على أسعار الكتالوج                                                                                                                                                                             |
| `reset-aware` ⭐    | الأولوية حسب وقت إعادة تعيين الحصة — فترات إعادة التعيين القصيرة لها ترتيب أعلى                                                                                                                                                |
| `reset-window`      | تفضيل الأهداف التي تُعاد تعيين نافذة حصتها في أقرب وقت                                                                                                                                                                         |
| `headroom`          | اختيار الهدف الذي يمتلك أكبر قدر متبقي من الحصة                                                                                                                                                                                |
| `quota-weighted`    | تخطي الحسابات المستنفدة، ثم الاختيار من بين البقية بما يتناسب مع الحصة المتبقية مقسومة على الحمل قيد المعالجة؛ تظل المحادثات الحالية مثبتة                                                                                     |
| `strict-random`     | عشوائية بدون إزالة تكرار العناصر المكررة                                                                                                                                                                                       |
| `auto`              | استخدام تسجيل Auto Combo (16 عاملاً) — **موصى به**                                                                                                                                                                             |
| `lkgp`              | المسار الأخير المعروف بأنه جيد (يثبت على آخر مزود ناجح، ثم يعود إلى القواعد)                                                                                                                                                   |
| `context-optimized` | اختيار الهدف الأنسب لحجم السياق الحالي                                                                                                                                                                                         |
| `cache-optimized`   | إعادة ترتيب الأهداف حسب تقارب ذاكرة التخزين المؤقت للمطالبات (prompt-cache) — يتم تجربة الاتصال الأكثر احتمالاً باحتوائه على البادئة المخزنة مؤقتاً لهذا الطلب أولاً (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | التوزيع على مجموعة من النماذج بالتوازي، ثم تجميع إجابة واحدة عبر مُحكِّم (انظر أدناه)                                                                                                                                          |
| `pipeline`          | تشغيل الأهداف بالتسلسل، مع تمرير مخرجات كل خطوة كمدخلات للخطوة التالية؛ يتم إرجاع الإجابة النهائية فقط (#6396)                                                                                                                 |

⭐ = جديد في v3.8.0 · 🧬 = جديد في v3.8.36

### دلالات `weighted`

`weighted` هو **سحب عشوائي نسبي لكل طلب** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، وليس موازنًا:

- يسحب كل طلب خطوة **واحدة** باحتمالية `weight / totalWeight`؛ يتم ترتيب الخطوات المتبقية حسب الوزن التنازلي كسلسلة احتياطية (fallback chain) لهذا الطلب.
- الخطوة التي يكون وزنها `0` (أو مفقود) **لا يتم سحبها أبداً** طالما أن أي خطوة أخرى لها وزن > 0 — يمكنها فقط العمل كخيار احتياطي بعد فشل الخطوة المسحوبة. فقط عندما تكون **جميع** الأوزان 0 يصبح الاختيار موحداً.
- الخطوات التي تكون أهدافها غير متاحة — قاطع دائرة المزود `OPEN`، فترة تهدئة الاتصال، قفل النموذج — تتم إزالتها من السحب قبل حدوثه (`open-sse/services/combo/targetResolution.ts`)، لذا يمكن لخطوة واحدة سليمة أن تفوز مؤقتاً بكل طلب.
- `stickyWeightedLimit` (إعداد التجميع، الافتراضي `1` = إيقاف) يثبت الخطوة المسحوبة لعدد معين من النجاحات المتتالية قبل إعادة السحب.

للدوران الصارم استخدم `round-robin`؛ الأوزان المتساوية في `weighted` تعطي توازناً إحصائياً - وليس صارماً.

### وضع خط أنابيب الوكيل (Agentic pipeline)

يمكن لمجموعة `pipeline` تحتوي على نموذجين على الأقل اختيار توجيه المخطط/المنفذ (planner/executor) باستخدام `config.agenticOrchestration.enabled`. الهدف الأول يتولى التخطيط والإجابات النهائية؛ بينما يصدر الهدف الثاني استدعاءات أدوات أصلية للعميل (client-native tool calls). تكتشف OmniRoute استمرارية نتائج الأدوات من بروتوكول الطلب، وتسأل المخطط عما إذا كانت هناك حاجة لجولة أدوات أخرى، وتجعل ديناميكياً إما المنفذ أو المخطط الخطوة النهائية المواجهة للعميل.

يطبق `config.agenticOrchestration.contextCompaction` الاختياري ميزانية حمولة منفصلة قبل كل إرسال للمخطط أو المنفذ. قم بتمكينه صراحةً:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

هذه ميزانيات أحرف JSON متسلسلة يختارها المشغل، وليست نوافذ سياق الرموز (token context windows) أو حدوداً مضمونة للمنبع (upstream limits). معرفات النماذج الدقيقة تتجاوز القيمة الافتراضية. فوق هذا الحد، تقوم عملية الضغط بإزالة تعريفات الأدوات المتطابقة، وتقليم أدلة الأدوات كبيرة الحجم باستخدام ملخص (digest)، وإزالة مجموعات التاريخ الكاملة القديمة نحو النسبة المستهدفة. إنها تحتفظ بتعليمات النظام/المطور، وطلب المستخدم الأخير، وجولة الأدوات الأخيرة بما في ذلك الاستدعاءات/النتائج المتوازية، وتعليمات التوجيه الرئيسية لـ Gemini. يتم الاحتفاظ بالتعليمات وإعدادات الأدوات ذات المستوى الأعلى. تسجل علامة الحذف التاريخ الذي تمت إزالته؛ هذا تقليم حتمي، وليس ملخصاً دلالياً. إذا كان السياق المثبت لا يزال يتجاوز الميزانية، يعيد الطلب 413 قبل الاتصال بالنموذج. مع تعطيل الضغط أو إذا كان أقل من الحد، يمر الطلب دون تغيير.

النماذج الإضافية بعد الهدف الثاني هي نسخ احتياطية للمنفذ مرتبة. يؤدي استجابة HTTP فاشلة أو استثناء نقل إلى الانتقال إلى المنفذ التالي، مع حمل نفس قرار المخطط والأدوات الأصلية ولكن مع مطالبة الخطوة الخاصة بذلك المنفذ والاتصال الذي تم حله. يتم إرجاع أول استجابة ناجحة دون تغيير، بما في ذلك بث SSE؛ لا يمكن إعادة محاولة حالات الفشل بعد بدء بث ناجح هنا. إذا فشل جميع المنفذين، يتم إرجاع الفشل الأخير. عمليات إلغاء العميل توقف الإرسال.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

قد يصدر المنفذ استدعاءات مستقلة متعددة في استجابة واحدة. تتم معالجة الاستدعاءات التابعة في أدوار نتائج أدوات العميل اللاحقة، مع قيام المخطط بمراجعة كل نتيجة. القيمة الافتراضية لـ `maxToolRounds` هي `8` وتقبل `1`–`32`؛ بمجرد الوصول إليها، يجب على المخطط تقديم أفضل إجابة نهائية متاحة. يتم تخزين قرارات المخطط الداخلية مؤقتاً، بينما تحافظ الاستجابة المختارة المواجهة للعميل على تفضيل البث الأصلي.

### الدفعة اللاصقة (sticky batch) وتوسيع الحساب لـ `round-robin`

`round-robin` يتم على دفعات، وليس طلباً واحداً لكل خطوة:

- يحافظ `stickyRoundRobinLimit` (تكوين المجموعة، ثم `comboStickyRoundRobinLimit`، ثم `settings.stickyRoundRobinLimit`، الافتراضي **3**) على نفس الهدف لعدد النجاحات المتتالية هذا قبل التدوير. اضبط تجاوز المجموعة على `1` لتدوير الطلب الواحد. يعرض محرر المجموعة القيمة الفعلية والطبقة التي جاءت منها.
- يقوم `connectionAwareExpansion` (تكوين المجموعة، ثم الإعدادات، الافتراضي **false**) بتوسيع كل خطوة على مستوى المزود إلى أهداف لكل حساب قبل التدوير. تحافظ استراتيجيات المجموعة ب (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) على عرض على مستوى المزود حتى يتم تشغيل هذا. يكشف محرر المجموعة عن inherit / on / off؛ يستخدم inherit الافتراضي العالمي (off).
- يقوم توجيه محلية ذاكرة التخزين المؤقت للمطالبة (`promptCacheAffinityEnabled`، الافتراضي **true**) بإعادة ترتيب الاتصالات المثبتة بحيث تبقى مفاتيح ذاكرة التخزين المؤقت المطابقة على حساب واحد. له الأولوية على `round-robin` والتدوير الموزون عبر الخطوات المثبتة لكل حساب. قم بإيقاف تشغيله ضمن الإعدادات ← افتراضيات المجموعة (Settings → Combo defaults) إذا كنت بحاجة إلى تدوير صارم. لا يوجد تجاوز لكل مجموعة.

للتدوير متعدد الحسابات على نموذج واحد، يفضل **خطوة حساب ديناميكي واحدة** (`connectionId` فارغ، المجموعة بأكملها) مع حد لاصق `1`، وليس ثلاثة `connectionId`s مثبتة. تنهار الخطوات المثبتة بالإضافة إلى التقارب على نفس الحساب حتى أثناء تقدم عداد RR.

## استراتيجية Fusion

تُعد `fusion` الاستراتيجية الوحيدة التي **لا** تختار هدفًا واحدًا. فهي توزّع الموجّه
على **كل نماذج اللجنة بالتوازي**، ثم يقوم **نموذج حَكَم** قابل للتهيئة بتجميع
إجابة نهائية واحدة من جميع ردود اللجنة. نُقلت من المشروع الأصلي `decolua/9router`
(تصميم Fusion الخاص بـ OpenRouter)؛ والتنفيذ موجود في `open-sse/services/fusion.ts`.

آلية العمل:

0. **تجاوز الطلبات المتضمنة أدوات** — يتخطى الطلب الذي يحمل مصفوفة `tools` غير فارغة، مع
   عدم تعيين `tool_choice` صراحةً إلى `"none"`، اللجنة بالكامل: إذ يُوجَّه مباشرةً إلى
   نموذج واحد (الحَكَم المُهيّأ، أو `panel[0]`) مع تمرير `tools`/`tool_choice`
   دون تعديل. لا يملك أعضاء اللجنة وصولًا إلى الأدوات، كما أن توجيه التجميع الخاص بالحَكَم
   يثبط إصدار استدعاءات الأدوات، وبذلك تحصل التطبيقات العميلة الوكيلة/المستدعية للأدوات
   على قرار حقيقي بشأن استدعاء الأداة بدلًا من نص مُجمَّع (#6771).
1. **التوزيع المتوازي** (للطلبات غير المتضمنة أدوات فقط) — يُرسل الموجّه إلى كل نماذج
   اللجنة دفعةً واحدة، مع فرض عدم استخدام البث وإزالة الأدوات (يحتاج الحَكَم إلى
   نصوص كاملة لتجميعها).
2. **الجمع وفق النصاب وفترة السماح** — بمجرد وصول `minPanel` من الإجابات، يبدأ مؤقت
   سماح قصير للمتأخرين، ثم تتابع Fusion بما جُمع من إجابات.
   يحد ذلك من تأثير أبطأ نموذج على الوقت الإجمالي، ضمن مهلة قصوى صارمة.
3. **تجميع الحَكَم** — تُخفى هويات إجابات اللجنة (`Source 1`، `Source 2`، … — كي
   يقيّم الحَكَم المضمون لا العلامة التجارية للنموذج) وتُسلَّم إلى الحَكَم، الذي يحلل
   التوافق / التناقضات / التغطية الجزئية / الرؤى الفريدة / النقاط العمياء، ثم
   يكتب إجابة موثوقة **واحدة**. يحتفظ استدعاء الحَكَم بقيمة `stream` الأصلية الخاصة
   بالعميل وبالأدوات، لذا يظل البث واستخدام الأدوات في المراحل اللاحقة ممكنين.
4. **التدهور السلس** — 0 من إجابات اللجنة ← `503`؛ ناجٍ واحد فقط ← تُعاد تلك الإجابة
   مباشرةً (فلا يوجد ما يمكن دمجه)؛ واللجنة ذات النموذج الواحد تُجيب مباشرةً.

يمكن أيضًا أن يكون عضو اللجنة خطوة `combo-ref` ‏(`{kind: "combo-ref", comboName: "..."}`) تشير
إلى مجموعة أخرى — وتُحل باعتبارها **صوتًا واحدًا من أصوات اللجنة كصندوق أسود** (عملية توجيه
تكرارية كاملة إلى المجموعة المشار إليها، وليست توزيعًا متوازيًا على أهداف تلك المجموعة)،
مع وسائل الحماية نفسها من العمق/الدورات التي تستخدمها بالفعل كل استراتيجية أخرى تستهلك
combo-ref ‏(#6764).

### التهيئة

تُضبط الإعدادات في كائن `config` الخاص بالمجموعة (دون ترحيل للمخطط — إذ يعيد استخدام
جدول `combos` الحالي):

| الحقل                                    | النوع    | القيمة الافتراضية   | الغرض                                                                              |
| :--------------------------------------- | :------- | :------------------ | :--------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | أول نموذج في اللجنة | النموذج الذي يجمع الإجابة النهائية                                                 |
| `config.fusionTuning.minPanel`           | `number` | `2`                 | عدد الإجابات الناجحة المطلوبة قبل بدء مؤقت السماح (مقيّد بالنطاق `[2, panelSize]`) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`              | مدة انتظار المتأخرين بعد بلوغ النصاب                                               |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`             | حد أقصى مطلق كي لا يتمكن نموذج عالق من تعطيل الطلب                                 |

توجد القيم الافتراضية في `FUSION_DEFAULTS` ‏(`open-sse/services/fusion.ts`).

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ثم استدعِها مثل أي مجموعة أخرى: `{"model":"fusion-panel","messages":[...]}`.

## مصنع Auto-Combo الافتراضي

لا يتطلب محرك Auto Combo مجموعات مُعرَّفة مسبقًا. بدلًا من ذلك، ينشئ `open-sse/services/autoCombo/virtualFactory.ts` المرشحين أثناء التشغيل:

1. يستدعي `getProviderConnections({ isActive: true })` (جميع الاتصالات المُمكَّنة)
2. يرشّح الاتصالات التي لديها بيانات اعتماد صالحة (مفتاح API أو رمز OAuth غير منتهي الصلاحية عبر `hasUsableOAuthToken()`)
3. يقارنها مع `getProviderRegistry()` للتحقق من توافر النماذج والأسعار
4. ينشئ `VirtualAutoComboCandidate` لكل صف `(provider, model, connection)`
5. يختار `connection.defaultModel` (أو النموذج الأول في السجل) بوصفه هدف التوجيه
6. يمنح كل مرشح درجة باستخدام `scorePool()` ذي العوامل الـ16 وحزمة أوزان المتغير
7. يعيد `AutoComboConfig` الناتج والموجود في الذاكرة إلى `handleComboChat()` — ولا يتم حفظه مطلقًا في قاعدة البيانات

يعني هذا أن **إضافة مزود جديد مع تمكين `auto/*` توسّع مجموعة المرشحين تلقائيًا** — دون الحاجة إلى تعديل المجموعة يدويًا. يُعاد إنشاء المجموعة الافتراضية لكل طلب، ولذلك تُلتقط الاتصالات المضافة حديثًا أو التي استعادت حالتها السليمة فورًا.

## التعافي الذاتي

- **الاستبعاد المؤقت**: الدرجة < 0.2 ← الاستبعاد لمدة 5 دقائق (تراجع تدريجي، بحد أقصى 30 دقيقة)
- **مراعاة قاطع الدائرة**: OPEN ← استبعاد تلقائي؛ HALF_OPEN ← طلبات فحص
- **وضع الحوادث**: أكثر من 50% في حالة OPEN ← تعطيل الاستكشاف وتعظيم الاستقرار
- **التعافي بعد فترة التهدئة**: بعد الاستبعاد، يكون الطلب الأول بمثابة "فحص" بمهلة زمنية مخفّضة

## استكشاف Bandit

يتم توجيه 5% من الطلبات (قابلة للتهيئة) إلى مزودين عشوائيين لأغراض الاستكشاف. يُعطَّل ذلك في وضع الحوادث.

## API

لا توجد **نقطة نهاية مخصصة `POST /api/combos/auto`** — يتم استهلاك Auto-Combo بطريقتين:

1. **بدون إعدادات (موصى به):** أرسل أي طلب إكمال محادثة باستخدام `model: "auto"` أو `model: "auto/<variant>"`. يقوم المصنع الافتراضي ببناء الكومبو لكل طلب — لا حاجة إلى استمرارية أو استدعاءات API.

2. **كومبو مستمر مع `strategy: "auto"`:** قم بإنشاء كومبو عادي عبر `POST /api/combos` وقم بتعيين `strategy: "auto"` بالإضافة إلى `config.auto.weights` / `config.auto.candidatePool`. يتم استخدام نفس محرك التسجيل؛ يتم تخزين الكومبو في `combos` ويمكن إعادة استخدامه بواسطة المعرف (ID).

للاكتشاف، تقوم `GET /api/combos/auto` بسرد كل متغير مع مجموعة المرشحين التي تم حلها بالإضافة إلى `context_length` / `max_output_tokens` — وهي القيمة القصوى (MAX) عبر نوافذ مجموعة المرشحين. يجب على العملاء (مثل إضافة opencode) الإعلان عن هذه القيم بدلاً من `0`: حيث يؤدي السياق الصفري إلى تعطيل الضغط التلقائي (auto-compaction) الخاص بـ opencode تماماً، مما يسمح للجلسات بالنمو حتى يقوم مسح السجل الخاص بالبوابة بتدمير السياق. من الآمن الإعلان عن القيمة القصوى (MAX) لأن الفلتر المسبق لسياق auto-combo يوجه الطلبات كبيرة الحجم إلى المرشحين ذوي النوافذ الكبيرة.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### استراتيجيات الموجه التلقائي (Auto router)

يمكن للكومبوهات المستمرة التي تستخدم `strategy: "auto"` تعيين `config.routerStrategy` (أو `config.auto.routerStrategy` القديم) إلى أحد الخيارات التالية:

- `rules` — التسجيل المرجح الافتراضي
- `score` — يختار أعلى درجة مرجحة تم تكوينها. التعادلات الدقيقة تحافظ على ترتيب المرشحين المكون؛ يقوم `explorationRate` الحالي بأخذ عينات من المجموعة المصنفة بالكامل.
- `cost` / `eco` — أرخص مزود سليم
- `latency` / `fast` — أقل زمن انتقال p95 مع عقوبة الموثوقية
- `sla-aware` / `sla` — تفضيل المرشحين الذين يستوفون SLOs الخاصة بزمن الانتقال p95، ومعدل الخطأ، والتكلفة الاختيارية
- `lkgp` — آخر مزود جيد معروف أولاً
- `nadir` — اسأل واجهة برمجة تطبيقات القرار الخاصة بـ [Nadir](https://getnadir.com) عن النموذج الذي تحتاجه المطالبة في المجموعة؛ اختيار الاشتراك (opt-in)، والفشل المفتوح (fail-open) إلى `rules`

### استراتيجيات الموجه بالتفصيل

يكشف محرك auto-combo عن 7 تطبيقات قابلة للتوصيل لـ **RouterStrategy** يمكنك تبديلها عبر `config.routerStrategy` (أو `config.auto.routerStrategy` القديم). تختار كل استراتيجية مزوداً واحداً من مجموعة المرشحين، بناءً على `RoutingContext` (نوع المهمة، تلميحات الأداة/الرؤية، تقدير الرموز، سياسة SLA اختيارية، آخر مزود جيد معروف اختياري).

#### 1. `rules` (افتراضي) — تسجيل مرجح بـ 16 عاملاً

يغلف محرك التسجيل الحالي. يقوم بتصفية المرشحين ذوي قاطع الدائرة (circuit-breaker) في حالة `OPEN`، ثم يقوم بتشغيل `scorePool()` مع نوع المهمة الحالي و `getTaskFitness()`، ويختار المزود صاحب أعلى درجة.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**متى تستخدمه**: افتراضي. استخدمه عندما تريد مقايضة متوازنة عبر جميع الإشارات.

**الاسم المستعار**: `rules` (لا يوجد اسم مستعار)

---

#### 2. `cost` / `eco` — أرخص مزود سليم

يقوم بفرز مجموعة المرشحين حسب `costPer1MTokens` (تصاعدياً) ويختار الأرخص. يقوم بتصفية المرشحين في حالة `OPEN` أولاً.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**متى تستخدمه**: أحمال العمل الحساسة للتكلفة، أو المعالجة الدفعية، أو وظائف الخلفية.

**الأسماء المستعارة**: `cost`, `eco`

---

#### 3. `latency` / `fast` — أقل زمن انتقال p95 مع عقوبة الموثوقية

يقوم بالفرز حسب `p95LatencyMs + (errorRate * 1000)`. تضمن عقوبة معدل الخطأ تصنيف المزودين غير الموثوق بهم في مرتبة أدنى حتى لو كان زمن انتقالهم الاسمي منخفضاً.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**متى تستخدمه**: أحمال العمل الحساسة لزمن الانتقال مثل الدردشة في الوقت الفعلي، أو الإكمال التلقائي، أو مساعدي البرمجة التفاعليين.

**الأسماء المستعارة**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — الامتثال لـ SLO الخاص بزمن الانتقال/الخطأ/التكلفة

يقوم بتسجيل كل مرشح بناءً على مدى تلبيته لسياسة SLO المكونة:

| العامل             | الوزن | الصيغة                                            |
| ------------------ | ----- | ------------------------------------------------- |
| درجة زمن الاستجابة | 35%   | `threshold / max(value, ε)`                       |
| درجة الخطأ         | 35%   | `threshold / max(value, ε)`                       |
| درجة الصحة         | 15%   | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| درجة التكلفة       | 10%   | `threshold / max(value, ε)` أو تطبيع عكسي         |
| درجة الاستقرار     | 5%    | الانحراف المعياري لزمن الاستجابة بالتطبيع العكسي  |

عندما تكون `hardConstraints: true`، يتم فرز المرشحين بشكل أساسي حسب **درجة الانتهاك**
(مدى تجاوزهم لأي SLO)، ثم حسب الدرجة المركبة. بخلاف ذلك، يتم الاعتماد فقط على
الدرجة المركبة.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**حقول SLA** (يتم تعيينها في تكوين combo):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**متى تستخدم**: أحمال العمل الإنتاجية ذات الميزانيات الصارمة لزمن الاستجابة، أو معدل الخطأ، أو التكلفة.

**الأسماء المستعارة**: `sla-aware`, `sla`

---

#### 5. `lkgp` — المزود الأخير المعروف بأنه جيد أولاً

يحاول استخدام **المزود الأخير المعروف بأنه جيد** (إذا تم تعيينه) أولاً، ثم يعود إلى
استراتيجية `rules`. مفيد لثبات الجلسة — حيث يتعامل نفس المزود مع طلبات المتابعة في المحادثة.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**متى تستخدم**: المحادثات متعددة الأدوار حيث تريد أن يتعامل نفس المزود مع طلبات المتابعة
(على سبيل المثال، للتخزين المؤقت، أو استمرارية السياق، أو اتساق التسعير).

**الاسم المستعار**: `lkgp` (لا يوجد اسم مستعار)

#### 6. `nadir` — اختيار النموذج المدرك للمطالبة عبر Nadir

كل استراتيجية أعلاه تصنف المرشحين بناءً على بيانات القياس عن بُعد الخاصة بها؛ لا يقرأ أي منها الطلب.
يرسل `nadir` آخر دور للمستخدم بالإضافة إلى معرفات نماذج المجموعة إلى واجهة برمجة تطبيقات القرار الخاصة بـ
[Nadir](https://getnadir.com) (`POST /v1/bucket`) ويوجه إلى النموذج الذي يختاره Nadir من تلك القائمة
(`simple` ← النموذج الأرخص القادر، `complex` ← النموذج المتطور). لا يزال الاتصال الذي يخدم ذلك النموذج
يتم اختياره بواسطة `rules`، لذا تستمر الحصة والصحة والتكلفة في تحديد الحساب.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` و `OMNIROUTE_NADIR_BASE_URL` هما بدائل بيئة للسلسلتين.
`baseUrl` مطلوبة فقط لـ Nadir المستضاف ذاتياً (يتم التسامح مع `/v1` في النهاية).
المكالمات بدون مفتاح تهبط على مستوى Nadir المجهول، والذي يتم تحديد معدل استخدامه لكل عنوان IP.

ما يخرج من الصندوق: نص رسالة المستخدم الأخيرة (أول 16 ألف حرف)، ومعرفات نماذج المرشحين، وعلامة القناة
`source: "omniroute"`. لا توجد مطالبات نظام، أو سجل، أو أدوات، أو ترويسات.

سلوك الفشل هو الفشل المفتوح (fail-open): مهلة زمنية (افتراضية 2000 مللي ثانية)، أو استجابة غير 2xx،
أو مضيف لا يمكن الوصول إليه، أو استجابة مشوهة، أو اختيار خارج المجموعة يؤدي إلى قرار `rules`
ويتم إضافة بادئة للسبب `NadirStrategy: fallback (...)`. بعد مكالمة فاشلة، تتخطى الاستراتيجية
الشبكة لمدة 30 ثانية، لذا يكلف الانقطاع مهلة واحدة كل 30 ثانية بدلاً من واحدة لكل طلب.
تقارير أحداث التوجيه `strategy: "nadir"` فقط عندما يقوم Nadir بالفعل بإجراء الاختيار.

**متى تستخدم**: حركة المرور ذات الصعوبة المختلطة على مجموعة تمتد عبر مستويات النماذج
(نموذج صغير، متوسط، ومتطور)، حيث يكون "المتطور دائماً" هو التكلفة التي تريد تقليلها.

**الاسم المستعار**: `nadir` (لا يوجد اسم مستعار)

### استراتيجيات الموجه المخصصة

يمكنك تسجيل تنفيذ `RouterStrategy` الخاص بك عبر واجهة برمجة التطبيقات العامة:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ثم استخدمها:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ملاءمة المهام

حصل أكثر من 30 نموذجًا على درجات عبر 6 أنواع من المهام (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`). يدعم أنماط أحرف البدل (مثلًا، `*-coder` ← درجة مرتفعة في البرمجة).

## ملخص المتغيرات التلقائية

باحتساب `auto` المجرّد (الافتراضي) بالإضافة إلى قيم `AutoVariant` الست المعلنة في `autoPrefix.ts`، توجد **7 معرّفات نماذج قابلة للاستدعاء**:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(يسرد `AutoVariant` نفسه 6 قيم؛ أما الخيار السابع فهو «بلا متغير» — أي `auto` المجرّد — وتتعامل معه `parseAutoPrefix()` بوصفه `variant: undefined`.)

## كيف تتكامل المستويات مع Auto-Combo

تتعامل دالة التقييم ذات العوامل الستة عشر (`open-sse/services/autoCombo/scoring.ts`) مع الانتماء إلى المستوى باعتباره إشارتين: `tierPriority` ‏(0.0476) و`tierAffinity` ‏(0.0476). راجع [جدول عوامل التقييم الأساسي](#how-it-works-persisted-auto-combos) أعلاه للاطلاع على مجموعة `DEFAULT_WEIGHTS` الكاملة — أما التجاوزات الخاصة بكل حزمة (ship-fast/cost-saver/quality-first/
offline-friendly) فهي مدرجة في جدول "ملفات تعريف الأوزان لكل حزمة".

لا يفرض المستوى وحده **تقديم المستوى 1** — فإذا كان زمن استجابة المستوى 1 سيئًا أو كانت موازنة التكلفة مقابل الجودة دون المستوى الأمثل، يفوز المستوى 2. لفرض ترتيب المستويات، استخدم استراتيجية التجميع `priority` ورتّب المزوّدين حسب المستوى.

لتفضيل المستوى 1 (الاشتراك) بشدة، زِد وزن `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

راجع [`docs/guides/TIERS.md`](../guides/TIERS.md) للاطلاع على تعريفات المستويات وتصنيف المزوّدين.

## الاختبار والتغطية

### مصفوفة حتمية لقرارات التوجيه (`npm run test:combo:matrix`)

تثبت اختبارات `tests/integration/combo-matrix/*.test.ts` **قرار** التوجيه لجميع
الاستراتيجيات العامة الـ19 من البداية إلى النهاية عبر مسار المجموعة الحقيقي باستخدام خدمة منبع وهمية.
تشمل التغطية:

- جميع استراتيجيات `ROUTING_STRATEGY_VALUES` الـ19 (المرتبة، والموزونة، والتكلفة، والسياق، والدمج، …).
- استراتيجية `quota-share` (داخلية) من البداية إلى النهاية: عدالة DRR + خفض أولوية التشبع عبر
  نقطة التكامل الحقيقية `selectQuotaShareTarget`‏ (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`).
- تغطية التسليم الشامل لاستراتيجية `context-relay` عبر كل عدد ممكن من الأهداف.

تعمل هذه الحزمة في CI (مهمة `test:integration`) باستخدام `--test-concurrency=1` و
`--test-force-exit`، ولذلك فهي حتمية ولا تتطلب بيانات اعتماد حية.

### اختبارات دخانية حية مشروطة (ليست ضمن CI — مزوّدون حقيقيون)

| الأمر                                  | ما يفعله                                                                                     |
| :------------------------------------- | :------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | توجيه حقيقي داخل العملية باستخدام `RUN_COMBO_LIVE=1`؛ يلتقط لقطة لقاعدة بيانات OmniRoute حية |
| `npm run test:combo:live:vps`          | استدعاءات HTTP إلى خادم OmniRoute حي (اضبط `COMBO_LIVE_BASE_URL`)                            |
| `npm run test:combo:live:vps:failover` | الأمر نفسه، مع سيناريوهات تجاوز فشل متعمدة                                                   |

تختبر هذه الاختبارات الدخانية مسار الاتصال الحقيقي (المجموعة ← المزوّد ← الإكمال). وهي
مستبعدة عمدًا من CI لأنها تتطلب بيانات اعتماد حية وإمكانية الوصول إلى VPS.
