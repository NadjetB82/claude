## শূন্য-কনফিগ অটো-রাউটিং (`auto/` প্রিফিক্স)

> **নতুন:** কোনো কম্বো তৈরি করতে হবে না। যেকোনো ক্লায়েন্টে সরাসরি `auto/` প্রিফিক্স ব্যবহার করুন।

### দ্রুত উদাহরণ

| মডেল ID        | ভ্যারিয়েন্ট | আচরণ                                                                    |
| -------------- | ------------ | ----------------------------------------------------------------------- |
| `auto`         | ডিফল্ট       | সংযুক্ত সব প্রোভাইডার, LKGP কৌশল, ভারসাম্যপূর্ণ ওজন                     |
| `auto/coding`  | কোডিং        | গুণমান-প্রথম ওজন, কোড তৈরির জন্য উপযুক্ত                                |
| `auto/fast`    | দ্রুত        | কম-ল্যাটেন্সি ওজনভিত্তিক নির্বাচন                                       |
| `auto/cheap`   | সস্তা        | খরচ-অনুকূলিত রাউটিং (সর্বনিম্ন খরচ প্রথমে)                              |
| `auto/offline` | অফলাইন       | সর্বোচ্চ কোটা-প্রাপ্যতাসম্পন্ন প্রোভাইডারকে অগ্রাধিকার দেয়             |
| `auto/smart`   | স্মার্ট      | আরও ভালো মডেল আবিষ্কারের জন্য গুণমান-প্রথম + উচ্চতর অনুসন্ধান হার (10%) |
| `auto/lkgp`    | lkgp         | সুস্পষ্ট LKGP (ডিফল্ট `auto`-এর সমতুল্য)                                |
| `auto/chaos`   | কেয়স        | সমান্তরাল ফ্যান-আউট, প্রতি প্রোভাইডারে একটি মডেল (ফল্ট ইনজেকশন নয়)     |

### ক্যাটাগরি × টিয়ার কম্পোজিশন (`auto/<category>:<tier>`)

OpenRouter-ধাঁচের সাফিক্সগুলো **কী ধরনের রুট** (ক্যাটাগরি) এবং **কীভাবে সেটি অপ্টিমাইজ করা হবে** (টিয়ার)—এই দুটিকে আলাদা করে, যাতে আপনি সেগুলো স্বাধীনভাবে কম্পোজ করতে পারেন (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ক্যাটাগরি** (সক্ষমতা অনুযায়ী প্রার্থী পুল ফিল্টার করে): `coding` · `reasoning` · `vision` · `chat` · `multimodal`। `vision`/`multimodal` ভিশন-সক্ষম মডেলগুলো রাখে; `reasoning` রিজনিং/থিংকিং মডেলগুলো রাখে।
- **টিয়ার** (স্কোরিং ওজন / পুল ফিল্টার নির্বাচন করে): `fast` (দ্রুত সরবরাহ) · `cheap` (উপনাম `floor`, খরচ-সাশ্রয়ী) · `reliable` (সার্কিট-ব্রেকারের স্বাস্থ্য + ল্যাটেন্সির স্থিতিশীলতা) · `free` / `pro` (`classifyTier`-এর মাধ্যমে মডেল টিয়ার অনুযায়ী পুল ফিল্টার করে—ফ্রি-টিয়ার বনাম প্রিমিয়াম)।

| উদাহরণ                 | যে রূপে সমাধান হয়                                    |
| ---------------------- | ----------------------------------------------------- |
| `auto/coding:fast`     | কোডিং পুল, কম-ল্যাটেন্সি ওজন                          |
| `auto/coding:cheap`    | কোডিং পুল, খরচ-অনুকূলিত (`auto/coding:floor` উপনাম)   |
| `auto/reasoning:pro`   | শুধুমাত্র রিজনিং/থিংকিং মডেল, প্রিমিয়াম টিয়ার       |
| `auto/vision`          | ভিশন-সক্ষম মডেল (কোনো টিয়ার নেই → ভারসাম্যপূর্ণ ওজন) |
| `auto/multimodal:free` | মাল্টিমোডাল-সক্ষম মডেল, শুধুমাত্র ফ্রি টিয়ার         |

যেকোনো বৈধ `auto/<category>[:<tier>]` চাহিদামতো সমাধান করা হয়; এর একটি নির্বাচিত উপসেট `/v1/models` এবং ড্যাশবোর্ডে (`open-sse/services/autoCombo/builtinCatalog.ts`-এ `AUTO_SUFFIX_VARIANTS`) প্রদর্শিত হয়। ফিল্টারিং **ফেইল-ওপেন**—যদি কোনো সীমাবদ্ধতার সঙ্গে সংযুক্ত কোনো মডেল না মেলে, তবে সম্পূর্ণ পুল ব্যবহার করা হয়, যাতে রাউটিং কখনো ব্যর্থ না হয়। মূল স্কোরার (`combo.ts`) অপরিবর্তিত থাকে; ক্যাটাগরি/টিয়ার ফিল্টারটি `buildAutoCandidates`-এ প্রয়োগ করা হয়।

> **লাইভ মডেল ইন্টেলিজেন্স:** `ARENA_ELO_SYNC_ENABLED` ফ্ল্যাগ চালু থাকলে অটো-রাউটিংয়ের উপযুক্ততা লাইভ **Arena ELO** র্যাঙ্কিং + **models.dev** টিয়ার ডেটা দ্বারা নির্ধারিত হয় (অন্যথায় স্ট্যাটিক ফিটনেস ম্যাপ ব্যবহৃত হয়)।

**ব্যবহারের নিয়ম:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**যা ঘটে:**

1. OmniRoute `src/sse/handlers/chat.ts`-এ `auto/` প্রিফিক্স শনাক্ত করে
2. ডেটাবেস থেকে সব **সক্রিয় প্রোভাইডার সংযোগ** অনুসন্ধান করে
3. বৈধ ক্রেডেনশিয়াল (API কী বা OAuth টোকেন) রয়েছে এমন সংযোগগুলো ফিল্টার করে
4. প্রতিটি সংযোগের জন্য মডেল নির্ধারণ করে (`connection.defaultModel` অথবা প্রোভাইডারের প্রথম মডেল)
5. মেমোরিতে একটি **ভার্চুয়াল কম্বো** তৈরি করে (DB-তে সংরক্ষণ করা হয় না)
6. নির্বাচিত ভ্যারিয়েন্টের ওজন প্রোফাইল + LKGP কৌশল ব্যবহার করে রাউট করে

**মূল বৈশিষ্ট্য:**

- ✅ **সর্বদা-সক্রিয়:** কোনো টগল, কম্বো তৈরি বা কনফিগারেশনের প্রয়োজন নেই
- ✅ **ডায়নামিক:** বর্তমান সংযুক্ত প্রোভাইডারগুলো স্বয়ংক্রিয়ভাবে প্রতিফলিত করে
- ✅ **সেশন স্টিকিনেস:** LKGP নিশ্চিত করে যে সর্বশেষ সফল প্রোভাইডার অগ্রাধিকার পাবে
- ✅ **একাধিক অ্যাকাউন্ট সম্পর্কে সচেতন:** প্রতিটি প্রোভাইডার সংযোগ একটি পৃথক প্রার্থী হয়ে ওঠে
- ✅ **কোনো DB রাইট নেই:** ভার্চুয়াল কম্বোটি শুধু অনুরোধের জন্য বিদ্যমান থাকে, ফলে পারসিস্টেন্স ওভারহেড শূন্য

### প্রতি-কী প্রার্থী নিয়ন্ত্রণ (#7819, লেভেল 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/`-এর পরের সাফিক্স, অথবা
বেস চ্যানেলের জন্য আক্ষরিক `auto`) একটি **শুধুমাত্র-পঠনযোগ্য** এন্ডপয়েন্ট, যা বিদ্যমান
রেজিলিয়েন্স রিডগুলো পুনঃব্যবহার করে একটি `auto/*` চ্যানেলের বর্তমান প্রার্থী পুলকে
লাইভ রিচেবিলিটি তথ্যসহ তালিকাভুক্ত করে (কখনোই ব্রেকারের কাঁচা `state` নয়):

- প্রোভাইডার সার্কিট ব্রেকার—`getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- সংযোগ কুলডাউন—সমাধানকৃত `provider_connections` সারির `rateLimitedUntil` / `testStatus`
- মডেল লকআউট—`isModelLocked(provider, connectionId, model)`

প্রতিটি প্রার্থীর সঙ্গে এই API কী-এর `excluded` ফ্ল্যাগও থাকে। এক্সক্লুশনগুলো
প্রতি-API-কী ভিত্তিতে সংরক্ষণ করা হয় (`auto_candidate_overrides` টেবিল, মাইগ্রেশন `128`)—
OmniRoute একক-টেন্যান্ট এবং এতে কোনো `users` টেবিল নেই, তাই `apiKeyId` হলো সবচেয়ে নিকটবর্তী
বাস্তব প্রতি-কলার পরিচয়—এবং বিশুদ্ধ, ইউনিট-পরীক্ষিত
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) ব্যবহার করে
`open-sse/services/autoCombo/virtualFactory.ts`-এর প্রার্থী-পুল চোকপয়েন্টে এটি প্রয়োগ করা হয়।
ফিল্টারটি **ফেইল-ওপেন**: অনির্ধারিত apiKeyId/channel অথবা একটি DB লুকআপ ব্যর্থতা—উভয় ক্ষেত্রেই
পুলটি ফিল্টারহীন থাকে, ফলে কোনো ওভাররাইড কনফিগার না করা অপারেটর এই ফিচারের আগের অবস্থার সঙ্গে
বাইট-অভিন্ন রাউটিং দেখতে পান।

**পরবর্তী ইস্যুতে স্থগিত:** প্রতি-ক্যান্ডিডেট ওজন + সুস্পষ্ট ক্রমবিন্যাস (লেভেল 3
— বিদ্যমান ওজনযুক্ত/অগ্রাধিকার কৌশলের পাথগুলোতে যুক্ত হয়) এবং প্রতি `auto/*` চ্যানেলের জন্য একটি নির্দিষ্ট
`combo.ts` কৌশল পিন করা (লেভেল 4)। সিঙ্গেল-টেন্যান্ট মডেলের প্রেক্ষিতে ওভাররাইডগুলো প্রতি-API-key ভিত্তিক থাকবে নাকি গ্লোবাল হবে—এই অমীমাংসিত
প্রশ্নের জন্য #7819 পরিকল্পনা দেখুন।

**অন্তরালে যা ঘটে:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## বাস্তব Model Id-এর সঙ্গে মিলে যায় এমন Combo নাম

যে combo-র `name` একটি bare model id-এর সঙ্গে অভিন্ন (যেমন `gpt-5.5` নামের একটি combo), সেটি কোনো bug নয়; বরং এটি একটি **ইচ্ছাকৃত ও সমর্থিত pattern**। এটি [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940)-এ নথিভুক্ত প্রতি-model-id provider fallback-এর প্রক্রিয়া। যেহেতু bare-model-id resolution-এর আগে combo resolution পরীক্ষা করা হয় (`src/sse/services/model.ts`-এর `getComboForModel()`), তাই bare id `gpt-5.5`-এর জন্য কোনো request সরাসরি একটি provider-এর কাছে না গিয়ে combo-টির target-গুলোর (যেমন `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) মাধ্যমে route হয়—এটি [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227)-এর জন্য তৈরি combo-before-rewrite precedence পুনরায় ব্যবহার করে এবং `tests/unit/responses-combo-resolution-3227.test.ts` ও `tests/unit/combo-name-codex-responses-rewrite.test.ts` দ্বারা regression-test করা হয়।

বাস্তব model id-কে shadow করে এমন নামে কোনো combo তৈরি করা বা rename করা **কখনোই প্রত্যাখ্যান করা হয় না**—তা করলে এই নথিভুক্ত workflow ভেঙে যাবে। পরিবর্তে (#8530), (নতুন) নামটি কোনো বাস্তব model id-এর সঙ্গে সংঘর্ষ করলে `POST /api/combos` এবং `PUT /api/combos/[id]` response-এ একটি non-blocking `warning` field যুক্ত করে:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Boot-এর সময় `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) একটি এক-লাইনের `[STARTUP]` warning-ও log করে, যেখানে কোনো model id-কে shadow করা প্রতিটি বিদ্যমান combo তালিকাভুক্ত থাকে। ফলে যেসব operator ইচ্ছাকৃতভাবে (#6940 অনুযায়ী) নয়, বরং দুর্ঘটনাক্রমে এই পরিস্থিতির সম্মুখীন হন, তাঁরা একটি সংকেত পান। Detection helper-টি `src/lib/combos/modelNameCollision.ts`-এ রয়েছে।

## Client থেকে একটি Custom Combo কল করা

Persisted combo-গুলো (Settings → Combos) কেবল তখনই ব্যবহৃত হয়, যখন client `model` field-এ combo-টির **হুবহু নাম** পাঠায়—combo নামের কোনো fuzzy বা partial matching নেই এবং এতে কোনো `auto/` prefix-ও জড়িত নয়। Resolution order (`src/sse/services/model.ts`-এর `getComboForModel()`):

1. combo নামের হুবহু মিল (`model: "my-combo"`),
2. `combo/<name>` prefix (`model: "combo/my-combo"`),
3. model→combo glob mapping (`/api/model-combo-mappings`)।

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

দুটি সাধারণ ভুল:

- **`auto` আপনার combo-গুলো ব্যবহার করে না।** `auto`/`auto/*` নিজস্ব zero-config candidate pool তৈরি করে এবং কেবল তখনই persisted combo ব্যবহার করে, যখন কোনো combo-র নাম আক্ষরিক অর্থেই `auto` হয় (প্রস্তাবিত নয়)। কোনো combo-র মাধ্যমে route করতে তার হুবহু নাম পাঠান—`auto` নয়।
- **`openrouter/auto` একটি বাস্তব paid OpenRouter product** ("Auto Best Available"), কোনো OmniRoute alias নয়। এটি OpenRouter registry-র (`open-sse/config/providers/registry/openrouter/index.ts`) একমাত্র static model entry এবং এর জন্য আলাদাভাবে bill করা হয়। এটিকে `auto` pool থেকে বাদ দিতে Settings → Routing → Hide paid models ব্যবহার করুন।

এখানে নথিভুক্ত মূল বিভ্রান্তির জন্য [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) এবং [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) দেখুন।

## এটি কীভাবে কাজ করে (Persisted Auto-Combos)

Auto-Combo Engine প্রতিটি রিকোয়েস্টের জন্য একটি **16-factor scoring function** (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`-এ সংজ্ঞায়িত) ব্যবহার করে সেরা provider/model ডায়নামিকভাবে নির্বাচন করে। ডিফল্ট ওজনগুলির (weights) যোগফল `1.0`; কাস্টম ওজনগুলি `normalizeScoringWeights()` দ্বারা রিনর্মালাইজ করা হয়। ষোলটির মধ্যে দুটি — `cacheAffinity` এবং `resetWindowAffinity` — ডিফল্ট ওজন `0` বহন করে; `reliability` `DEFAULT_WEIGHTS`-এ `0` কিন্তু জেনেরিক প্যাকগুলিতে `0.03` এবং `reliability-first`-এ `0.04` বহন করে, এবং `quality` প্যাকগুলিতে `0.02` বহন করে (`quality-first`-এ `0.03`): এগুলি এখনও প্রতিটি প্রার্থীর জন্য গণনা করা হয়, এবং `cacheAffinity` স্কোরের বাইরে prompt-cache ডিডুপ্লিকেশন নিয়ন্ত্রণ করে, তাই শূন্য-ডিফল্ট ফ্যাক্টরগুলি ডিফল্টভাবে কেবল ভোট দেয় না যেখানে প্যাকগুলি দেয়।

> **অপঠনযোগ্য কোটা (#15347)।** যখন কোনো প্রোভাইডারের একটি কোটা ফেচার থাকে কিন্তু সেটি পড়ার মতো কিছুই রিটার্ন করে না (ব্যর্থ ফেচ, অনুপস্থিত ক্রেডেনশিয়াল, কেবল-বার্তা ব্যবহার, অথবা কোনো পার্সযোগ্য `windows` এবং কোনো সসীম `percentUsed` না থাকা একটি বিকৃত স্ন্যাপশট, যার মধ্যে `percentUsed: null` অন্তর্ভুক্ত), তখন ক্যান্ডিডেটটি `quota` অক্ষে `0` স্কোর পায় এবং এর চূড়ান্ত স্কোরটি `UNREADABLE_QUOTA_SOFT_DEPRIORITIZE_FACTOR` (0.5, `autoStrategy.ts`) দ্বারা গুণ করা হয়, যা সংযোগ-স্থিতি পেনাল্টির মতোই একটি সফট-পেনাল্টি প্যাটার্ন। একটি ব্যর্থ ব্যবহার রিড হলো টেলিমেট্রি সম্পর্কিত প্রমাণ, প্রোভাইডারের নয়, তাই এটি যেকোনো বাস্তব রিডিংয়ের নিচে অবস্থান করে (এমনকি নিশ্চিতভাবে ১০০% ব্যবহৃত রিডিংয়ের নিচেও), কিন্তু এটিকে কখনোই হার্ড-ব্লক বা উচ্ছেদ করা হয় না। কোনো সীমা না থাকা প্রোভাইডার `unlimited: true` রিপোর্ট করে এবং পূর্ণ কোটা হিসেবে স্কোর পায়; কোনো নিবন্ধিত কোটা ফেচার না থাকা প্রোভাইডারের কোনো টেলিমেট্রি উৎসই থাকে না এবং এটি ডিফল্ট `100` মান বজায় রাখে।

**যোগফল:** `0.1429 + 0.1605 + 0.1429 + 0.1143 + 0.0762 + (7 × 0.0476) + 0.00 + 0.00 + 0.03 + 0.00 = 1.0` যা `DEFAULT_WEIGHTS`-এ ঘোষিত হয়েছে; স্কোরিং করার আগে ব্যবহারকারীর কনফিগার করা ওজনগুলো `normalizeScoringWeights()` দ্বারা একটি ডিস্ট্রিবিউশনে পুনর্বিন্যস্ত (renormalized) করা হয়।

"cheapest") স্থায়ী নীতি নির্ধারণ করে; হেডারটি একটি একক অনুরোধের জন্য সেটি ওভাররাইড করে।

## সমস্ত রাউটিং কৌশল

OmniRoute-এর কম্বো ইঞ্জিন **২০টি রাউটিং কৌশল** সমর্থন করে (যা `src/shared/constants/routingStrategies.ts` → `ROUTING_STRATEGY_VALUES`-এ ঘোষিত)। অটো কম্বো ইঞ্জিনটি নিজেই `auto` কৌশলের অধীনে উন্মুক্ত; বাকিগুলো পারসিস্টেড কম্বোর জন্য উপলব্ধ।

| কৌশল                | বিবরণ                                                                                                                                                                                                                   |
| :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `priority`          | প্রথম-টার্গেট ক্রমযুক্ত তালিকা, স্পষ্ট অগ্রাধিকারসহ                                                                                                                                                                     |
| `weighted`          | প্রতি-টার্গেট ওজনের ভিত্তিতে ওজনাঙ্কিত র‍্যান্ডম (Weighted random)                                                                                                                                                      |
| `round-robin`       | ক্রমানুসারে টার্গেটগুলোর মধ্যে চক্রাকার আবর্তন (ব্যাচ করা; নিচে দেখুন)                                                                                                                                                  |
| `context-relay`     | টার্গেটগুলোর মধ্যে কনটেক্সট হস্তান্তর (দীর্ঘ কথোপকথন)                                                                                                                                                                   |
| `fill-first`        | পরবর্তীটিতে যাওয়ার আগে প্রতিটি টার্গেটের কোটা পূরণ করা                                                                                                                                                                  |
| `p2c`               | পাওয়ার-অফ-২-চয়েস র‍্যান্ডম লোড ব্যালেন্সিং                                                                                                                                                                              |
| `random`            | ইউনিফর্ম র‍্যান্ডম নির্বাচন                                                                                                                                                                                             |
| `least-used`        | বর্তমান লোড সবচেয়ে কম এমন টার্গেট নির্বাচন করা                                                                                                                                                                          |
| `cost-optimized`    | ক্যাটালগ প্রাইসিং অনুযায়ী প্রতি রিকোয়েস্টের খরচ কমানো                                                                                                                                                                   |
| `reset-aware` ⭐    | কোটা রিসেট সময়ের ভিত্তিতে অগ্রাধিকার — ছোট রিসেট উইন্ডোগুলোকে উচ্চতর র‍্যাঙ্ক দেওয়া হয়                                                                                                                                  |
| `reset-window`      | যে টার্গেটগুলোর কোটা উইন্ডো দ্রুততম সময়ে রিসেট হয় সেগুলোকে অগ্রাধিকার দেওয়া                                                                                                                                             |
| `headroom`          | সবচেয়ে বেশি অবশিষ্ট কোটা হেডরুম আছে এমন টার্গেট নির্বাচন করা                                                                                                                                                            |
| `quota-weighted`    | নিঃশেষিত অ্যাকাউন্টগুলো বাদ দেওয়া, তারপর অবশিষ্ট কোটাকে ইন-ফ্লাইট লোড দিয়ে ভাগ করে তার অনুপাতে বাকিগুলোর মধ্যে থেকে নির্বাচন করা; বিদ্যমান কথোপকথনগুলো পিন করা থাকে                                                     |
| `strict-random`     | রিপিট ডিডুপ্লিকেশন ছাড়া র‍্যান্ডম নির্বাচন                                                                                                                                                                              |
| `auto`              | অটো কম্বো স্কোরিং (১৬-ফ্যাক্টর) ব্যবহার করা — **প্রস্তাবিত**                                                                                                                                                            |
| `lkgp`              | লাস্ট-নোন-গুড পাথ (সর্বশেষ সফল প্রোভাইডারের সাথে পিন করে, তারপর নিয়মে ফিরে যায়)                                                                                                                                         |
| `context-optimized` | বর্তমান কনটেক্সট সাইজের জন্য সবচেয়ে উপযুক্ত টার্গেট নির্বাচন করা                                                                                                                                                        |
| `cache-optimized`   | প্রম্পট-ক্যাশ অ্যাফিনিটির ভিত্তিতে টার্গেটগুলো পুনরায় সাজানো — যে কানেকশনে এই রিকোয়েস্টের ক্যাশড প্রিফিক্স থাকার সম্ভাবনা সবচেয়ে বেশি, সেটি আগে চেষ্টা করা হয় (`open-sse/services/combo/promptCacheAffinity.ts`, #8008) |
| `fusion` 🧬         | সমান্তরালভাবে মডেলের একটি প্যানেলে ফ্যান আউট করা, তারপর একজন বিচারকের মাধ্যমে একটি উত্তর সংশ্লেষণ করা (নিচে দেখুন)                                                                                                      |
| `pipeline`          | টার্গেটগুলো ধারাবাহিকভাবে চালানো, প্রতিটি ধাপের আউটপুট পরবর্তী ধাপের ইনপুটে যুক্ত করা; শুধুমাত্র চূড়ান্ত উত্তরটি ফেরত দেওয়া হয় (#6396)                                                                                  |

⭐ = v3.8.0-এ নতুন · 🧬 = v3.8.36-এ নতুন

### `weighted` সেমান্টিকস

`weighted` হলো **প্রতি রিকোয়েস্টে একটি আনুপাতিক র‍্যান্ডম ড্র** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), এটি কোনো ইকুয়ালাইজার নয়:

- প্রতিটি রিকোয়েস্ট `weight / totalWeight` সম্ভাব্যতা নিয়ে **একটি** ধাপ ড্র করে; অবশিষ্ট ধাপগুলো সেই রিকোয়েস্টের জন্য ফলব্যাক চেইন হিসেবে ওজনের নিম্নক্রম অনুসারে সাজানো থাকে।
- যে ধাপের ওজন `0` (বা অনুপস্থিত), সেটি **কখনোই ড্র করা হয় না** যদি অন্য কোনো ধাপের ওজন > 0 থাকে — এটি শুধুমাত্র ড্র করা ধাপটি ব্যর্থ হওয়ার পর ফলব্যাক হিসেবে কাজ করতে পারে। শুধুমাত্র যখন **সবগুলো** ওজন 0 হয়, তখনই নির্বাচন ইউনিফর্ম হয়।
- যে ধাপগুলোর টার্গেটগুলো অনুপলব্ধ — প্রোভাইডার সার্কিট ব্রেকার `OPEN`, কানেকশন কুলডাউন, মডেল লকআউট — সেগুলো ড্র হওয়ার আগেই সরিয়ে ফেলা হয় (`open-sse/services/combo/targetResolution.ts`), তাই একটি সুস্থ ধাপ সাময়িকভাবে প্রতিটি রিকোয়েস্টে জয়ী হতে পারে।
- `stickyWeightedLimit` (কম্বো কনফিগ, ডিফল্ট `1` = বন্ধ) পুনরায় ড্র করার আগে টানা কতগুলো সফলতার জন্য ড্র করা ধাপটিকে পিন করে রাখে।

কঠোর রোটেশনের জন্য `round-robin` ব্যবহার করুন; `weighted`-এ সমান ওয়েট পরিসংখ্যানগত — কঠোর নয় — ভারসাম্য প্রদান করে।

### এজেন্টিক পাইপলাইন মোড

অন্তত দুটি মডেলসহ একটি `pipeline` কম্বো `config.agenticOrchestration.enabled`-এর মাধ্যমে প্ল্যানার/এক্সিকিউটর রাউটিং বেছে নিতে পারে। প্রথম টার্গেটটি পরিকল্পনা এবং চূড়ান্ত উত্তরের দায়িত্ব পালন করে; দ্বিতীয় টার্গেটটি ক্লায়েন্ট-নেটিভ টুল কল নির্গত করে। OmniRoute রিকোয়েস্ট প্রোটোকল থেকে টুল-রেজাল্ট কন্টিনিউয়েশন শনাক্ত করে, প্ল্যানারকে জিজ্ঞাসা করে যে অন্য কোনো টুল রাউন্ডের প্রয়োজন আছে কিনা, এবং গতিশীলভাবে এক্সিকিউটর বা প্ল্যানারকে ক্লায়েন্ট-ফেসিং চূড়ান্ত ধাপ হিসেবে নির্ধারণ করে।

টুল-রেজাল্ট কন্টিনিউয়েশনের ক্ষেত্রে, OmniRoute এক্সিকিউশন বন্ধ করে দেয় যখন পরপর দুটি সম্পন্ন রাউন্ড একই টুল কলগুলো অপরিবর্তিত ফলাফলের সাথে পুনরাবৃত্তি করে, অথবা যখন পরপর দুটি রাউন্ডের প্রতিটি স্পষ্টভাবে চিহ্নিত ফলাফল ব্যর্থ হয়। পরিবর্তিত ফলাফল পুনরাবৃত্ত কলগুলোর অনুমতি দেয় (উদাহরণস্বরূপ, পোলিং)। গার্ডটি একটি নতুন ইউজার রিকোয়েস্টে রিসেট হয়, প্যারালাল কলগুলোকে একটি রাউন্ডে গ্রুপ করে, এবং Anthropic, Chat Completions, Responses এবং Gemini হিস্ট্রি সমর্থন করে। প্ল্যানার কারণটি গ্রহণ করে এবং চূড়ান্ত উত্তরের মালিকানা রাখে, এমনকি যদি এটি অন্য কোনো টুল রাউন্ডের অনুরোধও করে।

দ্বিতীয় টার্গেটের পরের অতিরিক্ত মডেলগুলো হলো ক্রমানুসারে সাজানো এক্সিকিউটর ব্যাকআপ। একটি ব্যর্থ HTTP রেসপন্স বা ট্রান্সপোর্ট এক্সেপশন পরবর্তী এক্সিকিউটরে চলে যায়, যা একই প্ল্যানার সিদ্ধান্ত এবং নেটিভ টুলগুলো বহন করে, কিন্তু সেই এক্সিকিউটরের নিজস্ব স্টেপ প্রম্পট এবং রিসলভড কানেকশন ব্যবহার করে। প্রথম সফল রেসপন্সটি অপরিবর্তিতভাবে ফেরত দেওয়া হয়, যার মধ্যে SSE স্ট্রিমিং অন্তর্ভুক্ত; একটি সফল স্ট্রিম শুরু হওয়ার পর ব্যর্থতাগুলো এখানে পুনরায় চেষ্টা (retry) করা যায় না। যদি সব এক্সিকিউটর ব্যর্থ হয়, তবে সর্বশেষ ব্যর্থতাটি ফেরত দেওয়া হয়। ক্লায়েন্ট অ্যাবোর্টগুলো ডিসপ্যাচ বন্ধ করে দেয়।

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

এক্সিকিউটর একটি রেসপন্সে একাধিক স্বাধীন কল নির্গত করতে পারে। ডিপেন্ডেন্ট কলগুলো পরবর্তী ক্লায়েন্ট টুল-রেজাল্ট টার্নগুলোতে হ্যান্ডেল করা হয়, যেখানে প্ল্যানার প্রতিটি ফলাফল পর্যালোচনা করে। `maxToolRounds`-এর ডিফল্ট মান `8` এবং এটি `1`–`32` পর্যন্ত গ্রহণ করে; একবার এই সীমায় পৌঁছে গেলে, প্ল্যানারকে অবশ্যই সেরা উপলব্ধ চূড়ান্ত উত্তরটি প্রদান করতে হবে। অভ্যন্তরীণ প্ল্যানার সিদ্ধান্তগুলো বাফার করা হয়, যেখানে নির্বাচিত ক্লায়েন্ট-ফেসিং রেসপন্সটি মূল স্ট্রিমিং পছন্দ বজায় রাখে।

### `round-robin` স্টিকি ব্যাচ এবং অ্যাকাউন্ট এক্সপ্যানশন

রাউন্ড-রবিন ব্যাচ করা হয়, প্রতি ধাপে একটি রিকোয়েস্ট নয়:

- `stickyRoundRobinLimit` (কম্বো কনফিগ, তারপর `comboStickyRoundRobinLimit`, তারপর `settings.stickyRoundRobinLimit`, ডিফল্ট **3**) রোটেশনের আগে টানা ততগুলো সফলতার জন্য একই টার্গেট বজায় রাখে। ওয়ান-রিকোয়েস্ট রোটেশনের জন্য কম্বো ওভাররাইড `1`-এ সেট করুন। কম্বো এডিটর কার্যকর মান এবং এটি কোন লেয়ার থেকে এসেছে তা দেখায়।
- `connectionAwareExpansion` (কম্বো কনফিগ, তারপর সেটিংস, ডিফল্ট **false**) রোটেশনের আগে প্রতিটি প্রোভাইডার-লেভেল ধাপকে প্রতি-অ্যাকাউন্ট টার্গেটে প্রসারিত করে। গ্রুপ-বি স্ট্র্যাটেজিগুলো (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) এটি চালু না হওয়া পর্যন্ত প্রোভাইডার-লেভেল ভিউ বজায় রাখে। কম্বো এডিটর inherit / on / off প্রকাশ করে; inherit গ্লোবাল ডিফল্ট (off) ব্যবহার করে।
- প্রম্পট-ক্যাশ লোকালিটি রাউটিং (`promptCacheAffinityEnabled`, ডিফল্ট **true**) পিন করা কানেকশনগুলোকে পুনরায় সাজায় যাতে ম্যাচিং ক্যাশ কিগুলো একটি অ্যাকাউন্টে থাকে। এটি পিন করা প্রতি-অ্যাকাউন্ট ধাপগুলোর ক্ষেত্রে রাউন্ড-রবিন এবং ওয়েটেড রোটেশনের চেয়ে অগ্রাধিকার পায়। আপনার যদি কঠোর রোটেশনের প্রয়োজন হয় তবে Settings → Combo defaults-এর অধীনে এটি বন্ধ করুন। কোনো পার-কম্বো ওভাররাইড নেই।

একটি মডেলে মাল্টি-অ্যাকাউন্ট রোটেশনের জন্য, তিনটি পিন করা `connectionId`-এর পরিবর্তে স্টিকি লিমিট `1` সহ **একটি ডাইনামিক-অ্যাকাউন্ট ধাপ** (খালি `connectionId`, পুরো পুল) পছন্দ করুন। পিন করা ধাপগুলো এবং অ্যাফিনিটি একই অ্যাকাউন্টে কলাপ্স করে, এমনকি যখন RR কাউন্টার অগ্রসর হয় তখনও।

## ফিউশন কৌশল

`fusion` হলো একমাত্র কৌশল, যা কোনো একক লক্ষ্য নির্বাচন **করে না**। এটি প্রম্পটটি
**প্রতিটি প্যানেল মডেলে সমান্তরালভাবে** পাঠায়, তারপর কনফিগারযোগ্য একটি **বিচারক মডেল**
প্যানেলের সব প্রতিক্রিয়া থেকে একটি একক চূড়ান্ত উত্তর সংশ্লেষ করে। আপস্ট্রিম `decolua/9router`
(OpenRouter-এর Fusion নকশা) থেকে পোর্ট করা হয়েছে; বাস্তবায়নটি `open-sse/services/fusion.ts`-এ রয়েছে।

এটি যেভাবে কাজ করে:

0. **টুল-সম্বলিত বাইপাস** — যে অনুরোধে একটি খালি নয় এমন `tools` অ্যারে থাকে এবং
   `tool_choice` স্পষ্টভাবে `"none"` হিসেবে নির্ধারিত নয়, সেটি প্যানেল সম্পূর্ণভাবে এড়িয়ে যায়:
   এটি অপরিবর্তিত `tools`/`tool_choice` সহ সরাসরি একটি একক মডেলে (কনফিগার করা বিচারক,
   অথবা `panel[0]`) রাউট করে। প্যানেল সদস্যদের কোনো টুল অ্যাক্সেস নেই এবং বিচারকের
   সংশ্লেষণ নির্দেশনা টুল-কল নির্গমনকে নিরুৎসাহিত করে, ফলে এজেন্টিক/টুল-কলিং ক্লায়েন্টগুলো
   সংশ্লেষিত গদ্যের পরিবর্তে একটি প্রকৃত টুল-কল সিদ্ধান্ত পায় (#6771)।
1. **ফ্যান-আউট** (শুধু টুলবিহীন অনুরোধের জন্য) — প্রম্পটটি একই সঙ্গে প্রতিটি প্যানেল
   মডেলে পাঠানো হয়, টুল বাদ দিয়ে জোরপূর্বক নন-স্ট্রিমিং করা হয় (সংশ্লেষণের জন্য বিচারকের
   সম্পূর্ণ গদ্য প্রয়োজন)।
2. **কোরাম-গ্রেস সংগ্রহ** — `minPanel`টি উত্তর পৌঁছানোর সঙ্গে সঙ্গে পিছিয়ে পড়া
   মডেলগুলোর জন্য একটি সংক্ষিপ্ত গ্রেস টাইমার শুরু হয়, তারপর যতগুলো উত্তর সংগৃহীত হয়েছে
   সেগুলো নিয়েই ফিউশন এগিয়ে যায়। এটি হার্ড টাইমআউটের সীমার মধ্যে, সবচেয়ে ধীর মডেলের
   কারণে মোট অপেক্ষার সময়ের ক্ষতি সীমিত রাখে।
3. **বিচারক সংশ্লেষণ** — প্যানেলের উত্তরগুলো বেনামী করা হয় (`উৎস 1`, `উৎস 2`, … — যাতে
   বিচারক মডেলের ব্র্যান্ড নয়, বরং বিষয়বস্তুর গুরুত্ব মূল্যায়ন করে) এবং বিচারকের কাছে
   পাঠানো হয়। বিচারক ঐকমত্য / পরস্পরবিরোধিতা / আংশিক পরিধি / অনন্য অন্তর্দৃষ্টি / অদেখা
   দিকগুলো বিশ্লেষণ করে, তারপর **একটি** প্রামাণ্য উত্তর লেখে। বিচারক কলটি ক্লায়েন্টের
   মূল `stream` ফ্ল্যাগ + টুলগুলো বজায় রাখে, ফলে স্ট্রিমিং এবং ডাউনস্ট্রিম টুল ব্যবহার
   এখনও কাজ করে।
4. **সাবলীল অবনতি** — প্যানেল থেকে 0টি উত্তর → `503`; ঠিক 1টি উত্তর টিকে থাকলে → সেই
   উত্তরটিই সরাসরি ফেরত দেওয়া হয় (ফিউজ করার মতো কিছু নেই); একক-মডেলের প্যানেল সরাসরি
   উত্তর দেয়।

কোনো প্যানেল সদস্য আরেকটি কম্বোকে উল্লেখকারী একটি `combo-ref` ধাপও হতে পারে
(`{kind: "combo-ref", comboName: "..."}`) — এটি **একটি ব্ল্যাক-বক্স প্যানেল কণ্ঠস্বর** হিসেবে
রিজলভ হয় (উল্লেখিত কম্বোতে একটি পূর্ণাঙ্গ রিকার্সিভ ডিসপ্যাচ, সেই কম্বোর নিজস্ব লক্ষ্যগুলোর
ফ্যান-আউট নয়), এবং অন্য প্রতিটি combo-ref-ব্যবহারকারী কৌশলে ইতিমধ্যে ব্যবহৃত একই
ডেপথ/সাইকেল সুরক্ষা প্রয়োগ করে (#6764)।

### কনফিগারেশন

কম্বোর `config` ব্লবে কনফিগার করা হয় (কোনো স্কিমা মাইগ্রেশন নেই — এটি বিদ্যমান
`combos` টেবিল পুনরায় ব্যবহার করে):

| ফিল্ড                                    | ধরন      | ডিফল্ট             | উদ্দেশ্য                                                                                         |
| :--------------------------------------- | :------- | :----------------- | :----------------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | প্রথম প্যানেল মডেল | চূড়ান্ত উত্তর সংশ্লেষকারী মডেল                                                                  |
| `config.fusionTuning.minPanel`           | `number` | `2`                | গ্রেস টাইমার শুরু হওয়ার আগে প্রয়োজনীয় সফল উত্তরের সংখ্যা (`[2, panelSize]`-এর মধ্যে সীমাবদ্ধ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`             | কোরাম পূরণ হওয়ার পর পিছিয়ে থাকা মডেলগুলোর জন্য যতক্ষণ অপেক্ষা করা হবে                          |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`            | একটি আটকে যাওয়া মডেল যাতে অনুরোধটি থামিয়ে রাখতে না পারে, তার পরম সীমা                          |

ডিফল্টগুলো `FUSION_DEFAULTS`-এ (`open-sse/services/fusion.ts`) রয়েছে।

### উদাহরণ

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

তারপর অন্য যেকোনো কম্বোর মতোই এটি কল করুন: `{"model":"fusion-panel","messages":[...]}`।

## ভার্চুয়াল অটো-কম্বো ফ্যাক্টরি

Auto Combo ইঞ্জিনের জন্য আগে থেকে নির্ধারিত কম্বোর প্রয়োজন হয় না। পরিবর্তে, `open-sse/services/autoCombo/virtualFactory.ts` তাৎক্ষণিকভাবে প্রার্থী তৈরি করে:

1. `getProviderConnections({ isActive: true })` থেকে তথ্য নেয় (সক্রিয় করা সব সংযোগ)
2. বৈধ ক্রেডেনশিয়াল আছে এমন সংযোগগুলো বেছে নেয় (`hasUsableOAuthToken()`-এর মাধ্যমে API key অথবা মেয়াদোত্তীর্ণ নয় এমন OAuth token)
3. মডেলের প্রাপ্যতা + মূল্য নির্ধারণের জন্য `getProviderRegistry()`-এর সঙ্গে ক্রস-রেফারেন্স করে
4. প্রতিটি `(provider, model, connection)` টিউপলের জন্য একটি `VirtualAutoComboCandidate` তৈরি করে
5. ডিসপ্যাচ টার্গেট হিসেবে `connection.defaultModel` (অথবা রেজিস্ট্রির প্রথম মডেল) বেছে নেয়
6. ১৬-ফ্যাক্টরের `scorePool()` এবং ভ্যারিয়েন্টের ওয়েট প্যাক ব্যবহার করে প্রতিটি প্রার্থীর স্কোর নির্ধারণ করে
7. `handleComboChat()`-এর জন্য ফলস্বরূপ ইন-মেমরি `AutoComboConfig` ফেরত দেয় — কখনোই DB-তে সংরক্ষণ করে না

এর অর্থ হলো, **`auto/*` সক্রিয় থাকা নতুন কোনো provider যোগ করলে প্রার্থী পুল স্বয়ংক্রিয়ভাবে প্রসারিত হয়** — ম্যানুয়ালি কম্বো সম্পাদনার প্রয়োজন নেই। প্রতিটি অনুরোধের জন্য ভার্চুয়াল কম্বো পুনর্নির্মাণ করা হয়, তাই নতুন যোগ করা বা সদ্য সুস্থ হয়ে ওঠা সংযোগগুলো তাৎক্ষণিকভাবে অন্তর্ভুক্ত হয়।

## স্বয়ংক্রিয় পুনরুদ্ধার

- **সাময়িকভাবে বাদ দেওয়া**: স্কোর < 0.2 → ৫ মিনিটের জন্য বাদ (ক্রমবর্ধমান ব্যাকঅফ, সর্বোচ্চ ৩০ মিনিট)
- **সার্কিট ব্রেকার সম্পর্কে সচেতনতা**: OPEN → স্বয়ংক্রিয়ভাবে বাদ; HALF_OPEN → প্রোব অনুরোধ
- **ইনসিডেন্ট মোড**: >৫০% OPEN → এক্সপ্লোরেশন বন্ধ করে স্থিতিশীলতা সর্বাধিক করে
- **কুলডাউন পুনরুদ্ধার**: বাদ দেওয়ার সময়সীমা শেষ হলে, প্রথম অনুরোধটি কমানো টাইমআউটসহ একটি "প্রোব" হিসেবে পাঠানো হয়

## ব্যান্ডিট এক্সপ্লোরেশন

এক্সপ্লোরেশনের জন্য ৫% অনুরোধ (কনফিগারযোগ্য) এলোমেলো provider-এ রাউট করা হয়। ইনসিডেন্ট মোডে এটি নিষ্ক্রিয় থাকে।

## API

এখানে **কোনো ডেডিকেটেড `POST /api/combos/auto` এন্ডপয়েন্ট নেই** — Auto-Combo দুটি উপায়ে ব্যবহার করা হয়:

1. **Zero-config (প্রস্তাবিত):** `model: "auto"` বা `model: "auto/<variant>"` সহ যেকোনো চ্যাট কমপ্লিশন রিকোয়েস্ট পাঠান। ভার্চুয়াল ফ্যাক্টরি প্রতিটি রিকোয়েস্টের জন্য কম্বো তৈরি করে — কোনো পারসিস্টেন্স বা API কলের প্রয়োজন নেই।

2. **`strategy: "auto"` সহ পারসিস্টেড কম্বো:** `POST /api/combos` এর মাধ্যমে একটি সাধারণ কম্বো তৈরি করুন এবং `strategy: "auto"` এর সাথে `config.auto.weights` / `config.auto.candidatePool` সেট করুন। একই স্কোরিং ইঞ্জিন ব্যবহৃত হয়; কম্বোটি `combos` এ সংরক্ষিত থাকে এবং ID দ্বারা পুনরায় ব্যবহারযোগ্য।

ডিসকভারির জন্য, `GET /api/combos/auto` প্রতিটি ভেরিয়েন্টকে তার রেজলভড ক্যান্ডিডেট পুল এবং `context_length` / `max_output_tokens` সহ তালিকাভুক্ত করে — যা ক্যান্ডিডেট পুলের উইন্ডোগুলির মধ্যে MAX। ক্লায়েন্টদের (যেমন opencode প্লাগইন) অবশ্যই `0` এর পরিবর্তে এই মানগুলো অ্যাডভার্টাইজ করতে হবে: শূন্য কনটেক্সট opencode-এর অটো-কম্প্যাকশনকে পুরোপুরি নিষ্ক্রিয় করে দেয়, যার ফলে গেটওয়ের হিস্ট্রি পার্জ কনটেক্সট ধ্বংস না করা পর্যন্ত সেশনগুলো বাড়তে থাকে। MAX অ্যাডভার্টাইজ করা নিরাপদ কারণ অটো-কম্বো কনটেক্সট প্রি-ফিল্টার অতিরিক্ত বড় রিকোয়েস্টগুলোকে লার্জ-উইন্ডো ক্যান্ডিডেটদের কাছে রাউট করে।

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

পারসিস্টেড `strategy: "auto"` কম্বোগুলো `config.routerStrategy` (অথবা লিগ্যাসি `config.auto.routerStrategy`) কে নিচের যেকোনো একটিতে সেট করতে পারে:

- `rules` — ডিফল্ট ওয়েটেড স্কোরিং
- `score` — সর্বোচ্চ কনফিগার করা ওয়েটেড স্কোর নির্বাচন করে। সঠিক টাই (ties) হলে কনফিগার করা ক্যান্ডিডেট অর্ডার বজায় থাকে; বিদ্যমান `explorationRate` সম্পূর্ণ র‍্যাঙ্কড পুল থেকে স্যাম্পল নেয়।
- `cost` / `eco` — সবচেয়ে সস্তা হেলদি প্রোভাইডার
- `latency` / `fast` — রিলায়াবিলিটি পেনাল্টি সহ সর্বনিম্ন p95 ল্যাটেন্সি
- `sla-aware` / `sla` — এমন ক্যান্ডিডেটদের অগ্রাধিকার দেয় যারা p95 ল্যাটেন্সি, এরর-রেট এবং ঐচ্ছিক কস্ট SLO পূরণ করে
- `lkgp` — লাস্ট নোন গুড প্রোভাইডারকে প্রথমে রাখে
- `nadir` — [Nadir](https://getnadir.com)-এর ডিসিশন API-কে জিজ্ঞাসা করে যে প্রম্পটের জন্য পুলের কোন মডেলটি প্রয়োজন; অপ্ট-ইন, ব্যর্থ হলে `rules`-এ ফিরে যায় (fail-open)

### Router strategies in detail

অটো-কম্বো ইঞ্জিন ৭টি প্লাগেবল **RouterStrategy** ইমপ্লিমেন্টেশন এক্সপোজ করে যা আপনি `config.routerStrategy` (অথবা লিগ্যাসি `config.auto.routerStrategy`) এর মাধ্যমে অদলবদল করতে পারেন। প্রতিটি স্ট্র্যাটেজি একটি `RoutingContext` (টাস্ক টাইপ, টুল/ভিশন হিন্টস, টোকেন এস্টিমেট, ঐচ্ছিক SLA পলিসি, ঐচ্ছিক লাস্ট-নোন-গুড প্রোভাইডার) এর ভিত্তিতে ক্যান্ডিডেট পুল থেকে একটি প্রোভাইডার নির্বাচন করে।

#### 1. `rules` (ডিফল্ট) — 16-factor ওয়েটেড স্কোরিং

বিদ্যমান স্কোরিং ইঞ্জিনকে র‍্যাপ করে। `OPEN` সার্কিট-ব্রেকার ক্যান্ডিডেটদের ফিল্টার আউট করে, তারপর বর্তমান টাস্ক টাইপ এবং `getTaskFitness()` এর সাথে `scorePool()` রান করে, সর্বোচ্চ স্কোরিং প্রোভাইডারকে বেছে নেয়।

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**কখন ব্যবহার করবেন**: ডিফল্ট। যখন আপনি সমস্ত সিগন্যাল জুড়ে একটি ভারসাম্যপূর্ণ ট্রেড-অফ চান তখন এটি ব্যবহার করুন।

**Alias**: `rules` (কোনো অ্যালিয়াস নেই)

---

#### 2. `cost` / `eco` — সবচেয়ে সস্তা হেলদি প্রোভাইডার

ক্যান্ডিডেট পুলকে `costPer1MTokens` (আরোহী ক্রমে) অনুযায়ী সাজায় এবং সবচেয়ে সস্তাটিকে বেছে নেয়। প্রথমে `OPEN` ক্যান্ডিডেটদের ফিল্টার আউট করে।

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**কখন ব্যবহার করবেন**: খরচ-সংবেদনশীল ওয়ার্কলোড, ব্যাচ প্রসেসিং, বা ব্যাকগ্রাউন্ড জব।

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — রিলায়াবিলিটি পেনাল্টি সহ সর্বনিম্ন p95 ল্যাটেন্সি

`p95LatencyMs + (errorRate * 1000)` অনুযায়ী সাজায়। এরর-রেট পেনাল্টি নিশ্চিত করে যে অবিশ্বস্ত প্রোভাইডারদের র‍্যাঙ্ক নিচে থাকে, এমনকি যদি তাদের নামমাত্র ল্যাটেন্সি কমও হয়।

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**কখন ব্যবহার করবেন**: ল্যাটেন্সি-সংবেদনশীল ওয়ার্কলোড যেমন রিয়েল-টাইম চ্যাট, অটো-কমপ্লিট, বা ইন্টারঅ্যাক্টিভ কোডিং অ্যাসিস্ট্যান্ট।

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — ল্যাটেন্সি/এরর/কস্ট SLO কমপ্লায়েন্স

প্রতিটি ক্যান্ডিডেট কনফিগার করা SLO পলিসি কতটা ভালোভাবে পূরণ করে তার ভিত্তিতে স্কোর করে:

| ফ্যাক্টর           | ওয়েট | সূত্র                                              |
| ------------------ | ---- | -------------------------------------------------- |
| ল্যাটেন্সি স্কোর   | ৩৫%  | `threshold / max(value, ε)`                        |
| এরর স্কোর          | ৩৫%  | `threshold / max(value, ε)`                        |
| হেলথ স্কোর         | ১৫%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)  |
| কস্ট স্কোর         | ১০%  | `threshold / max(value, ε)` অথবা ইনভার্স নরমালাইজড |
| স্ট্যাবিলিটি স্কোর | ৫%   | ইনভার্স নরমালাইজড ল্যাটেন্সি stddev                |

যখন `hardConstraints: true` থাকে, তখন ক্যান্ডিডেটদের প্রাথমিকভাবে **ভায়োলেশন স্কোর** (তারা কতটুকু SLO অতিক্রম করেছে) অনুযায়ী সাজানো হয়, তারপর কম্পোজিট স্কোর অনুযায়ী। অন্যথায়, এটি শুধুমাত্র কম্পোজিট স্কোর।

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ফিল্ডসমূহ** (কম্বো কনফিগারেশনে সেট করা):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**কখন ব্যবহার করবেন**: কঠোর ল্যাটেন্সি, এরর-রেট বা কস্ট বাজেট থাকা প্রোডাকশন ওয়ার্কলোডগুলোর জন্য।

**অ্যালিয়াস**: `sla-aware`, `sla`

---

#### ৫. `lkgp` — লাস্ট নোন গুড প্রোভাইডার ফার্স্ট

**লাস্ট নোন গুড প্রোভাইডার** (যদি সেট করা থাকে) প্রথমে ট্রাই করে, তারপর `rules` স্ট্র্যাটেজিতে ফিরে যায়। সেশন স্টিকিনেসের জন্য দরকারী — একই প্রোভাইডার কথোপকথনের ফলো-আপ রিকোয়েস্টগুলো হ্যান্ডেল করে।

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**কখন ব্যবহার করবেন**: মাল্টি-টার্ন কথোপকথন যেখানে আপনি চান একই প্রোভাইডার ফলো-আপ রিকোয়েস্টগুলো হ্যান্ডেল করুক (যেমন: ক্যাশিং, কনটেক্সট কন্টিনিউটি বা প্রাইসিং কনসিস্টেন্সির জন্য)।

**অ্যালিয়াস**: `lkgp` (কোনো অ্যালিয়াস নেই)

---

#### ৬. `nadir` — Nadir-এর মাধ্যমে প্রম্পট-অ্যাওয়ার মডেল নির্বাচন

উপরের প্রতিটি স্ট্র্যাটেজি তাদের নিজস্ব টেলিমেট্রি অনুযায়ী ক্যান্ডিডেটদের র‍্যাঙ্ক করে; তাদের কেউই রিকোয়েস্ট পড়ে না। `nadir` শেষ ইউজার টার্ন এবং পুলের মডেল আইডিগুলো [Nadir](https://getnadir.com)-এর ডিসিশন API-তে (`POST /v1/bucket`) পাঠায় এবং সেই মেনু থেকে Nadir যে মডেলটি নির্বাচন করে সেখানে রাউট করে (`simple` → সবচেয়ে সস্তা সক্ষম মডেল, `complex` → ফ্রন্টিয়ার মডেল)। সেই মডেলটি সার্ভ করা কানেকশনটি এখনও `rules` দ্বারা বাছাই করা হয়, তাই কোটা, হেলথ এবং কস্ট নির্ধারণ করে কোন অ্যাকাউন্টটি ব্যবহার হবে।

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` এবং `OMNIROUTE_NADIR_BASE_URL` হলো এই দুটি স্ট্রিংয়ের জন্য এনভায়রনমেন্ট ফলব্যাক। `baseUrl` শুধুমাত্র সেলফ-হোস্টেড Nadir-এর জন্য প্রয়োজন (শেষে `/v1` থাকলে তা গ্রহণযোগ্য)। কি-লেস কলগুলো Nadir-এর অ্যানোনিমাস টায়ারে যায়, যা প্রতি IP-তে রেট-লিমিটেড।

যা বক্স থেকে বের হয়: শেষ ইউজার মেসেজের টেক্সট (প্রথম ১৬ হাজার ক্যারেক্টার), ক্যান্ডিডেট মডেল আইডি এবং একটি `source: "omniroute"` চ্যানেল ট্যাগ। কোনো সিস্টেম প্রম্পট, হিস্ট্রি, টুলস বা হেডার নয়।

ফেইলিয়র বিহেভিয়ার হলো ফেইল-ওপেন: একটি টাইমআউট (ডিফল্ট ২০০০ ms), একটি non-2xx, একটি আনরিচেবল হোস্ট, একটি ম্যালফর্মড রেসপন্স বা পুলের বাইরের কোনো সিলেকশন `rules` ডিসিশনে সমাধান হয় এবং কারণটির আগে `NadirStrategy: fallback (…)` প্রিফিক্স যুক্ত থাকে। একটি ফেইলড কলের পর স্ট্র্যাটেজিটি ৩০ সেকেন্ডের জন্য নেটওয়ার্ক এড়িয়ে চলে, তাই একটি আউটেজ প্রতি রিকোয়েস্টের পরিবর্তে প্রতি ৩০ সেকেন্ডে একটি টাইমআউটের খরচ তৈরি করে। রাউটিং ইভেন্টগুলো শুধুমাত্র তখনই `strategy: "nadir"` রিপোর্ট করে যখন Nadir প্রকৃতপক্ষে পছন্দটি করে।

**কখন ব্যবহার করবেন**: এমন পুলে মিশ্র-ডিফিকাল্টির ট্রাফিক যা মডেল টায়ার জুড়ে বিস্তৃত (একটি ছোট, একটি মাঝারি এবং একটি ফ্রন্টিয়ার মডেল), যেখানে অলওয়েজ-ফ্রন্টিয়ার হলো সেই খরচ যা আপনি কমাতে চান।

**অ্যালিয়াস**: `nadir` (কোনো অ্যালিয়াস নেই)

### কাস্টম রাউটার স্ট্র্যাটেজিস

আপনি পাবলিক API-এর মাধ্যমে আপনার নিজস্ব `RouterStrategy` ইমপ্লিমেন্টেশন রেজিস্টার করতে পারেন:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

তারপর এটি ব্যবহার করুন:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

| ব্যালেন্সড ওয়ার্কলোড | `rules`      | ডিফল্ট — সব ফ্যাক্টর বিবেচনা করে             |

| ল্যাটেন্সি কমানো     | `latency`    | সবচেয়ে দ্রুত নির্ভরযোগ্য প্রোভাইডার বেছে নেয় |
| কঠোর SLO             | `sla-aware`  | p95/এরর/কস্ট থ্রেশহোল্ড অনুযায়ী ফিল্টার করে  |

## টাস্ক উপযোগিতা

6টি টাস্কের ধরন (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) জুড়ে 30টিরও বেশি মডেলের স্কোর নির্ধারণ করা হয়েছে। ওয়াইল্ডকার্ড প্যাটার্ন সমর্থন করে (যেমন, `*-coder` → উচ্চ coding স্কোর)।

## Auto ভ্যারিয়েন্টের সারসংক্ষেপ

মূল `auto` (ডিফল্ট) এবং `autoPrefix.ts`-এ ঘোষিত 6টি `AutoVariant` মানসহ, মোট **7টি ব্যবহারযোগ্য মডেল ID** রয়েছে:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` নিজে 6টি মান তালিকাভুক্ত করে; 7ম বিকল্পটি হলো "কোনো ভ্যারিয়েন্ট নয়" — মূল `auto` — যেটিকে `parseAutoPrefix()` দ্বারা `variant: undefined` হিসেবে পরিচালনা করা হয়।)

## Auto-Combo-তে টিয়ার কীভাবে কাজ করে

১৬-ফ্যাক্টরের স্কোরিং ফাংশনটি (`open-sse/services/autoCombo/scoring.ts`) টিয়ারের
সদস্যতাকে দুটি সংকেত হিসেবে বিবেচনা করে: `tierPriority` (0.0476) এবং `tierAffinity` (0.0476)। সম্পূর্ণ
`DEFAULT_WEIGHTS` সেটের জন্য উপরের প্রামাণ্য [স্কোরিং ফ্যাক্টর টেবিলটি](#how-it-works-persisted-auto-combos) দেখুন
— প্রতিটি প্যাকের ওভাররাইড (ship-fast/cost-saver/quality-first/
offline-friendly) "প্রতি প্যাকের ওয়েট প্রোফাইল" টেবিলে তালিকাভুক্ত রয়েছে।

শুধু টিয়ারই **Tier 1**-কে প্রথমে রাখতে বাধ্য করে না — যদি **Tier 1**-এর লেটেন্সি খারাপ হয় বা
খরচের তুলনায় গুণমান অনুকূল না হয়, তাহলে **Tier 2** জয়ী হয়। টিয়ারের ক্রম বাধ্যতামূলক করতে, কম্বো
স্ট্র্যাটেজি `priority` ব্যবহার করুন এবং টিয়ার অনুযায়ী প্রোভাইডারগুলো সাজান।

**Tier 1**-কে (সাবস্ক্রিপশন) জোরালোভাবে অগ্রাধিকার দিতে, `tierPriority`-এর ওয়েট বাড়ান:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

টিয়ারের সংজ্ঞা এবং প্রোভাইডারের শ্রেণিবিভাগের জন্য [`docs/guides/TIERS.md`](../guides/TIERS.md) দেখুন।

## পরীক্ষা ও কভারেজ

### নির্ধারিত রাউটিং-সিদ্ধান্ত ম্যাট্রিক্স (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` একটি মক করা আপস্ট্রিমসহ প্রকৃত কম্বো পাইপলাইনের মধ্য দিয়ে এন্ড-টু-এন্ডভাবে সব 19টি
পাবলিক স্ট্র্যাটেজির রাউটিং **সিদ্ধান্ত** প্রমাণ করে।
কভারেজের অন্তর্ভুক্ত:

- সব 19টি `ROUTING_STRATEGY_VALUES` স্ট্র্যাটেজি (ordered, weighted, cost, context, fusion, …)।
- `quota-share` (অভ্যন্তরীণ) এন্ড-টু-এন্ড: প্রকৃত
  `selectQuotaShareTarget` সীমারেখার (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`) মাধ্যমে DRR ন্যায্যতা + স্যাচুরেশন ডিপ্রায়োরিটাইজেশন।
- প্রতিটি টার্গেট সংখ্যাজুড়ে `context-relay` ইউনিভার্সাল-হ্যান্ডঅফ কভারেজ।

এই স্যুটটি CI-তে (`test:integration` জব) `--test-concurrency=1` এবং
`--test-force-exit` সহ চলে, তাই এটি নির্ধারিত এবং লাইভ ক্রেডেনশিয়ালের প্রয়োজন হয় না।

### শর্তসাপেক্ষ লাইভ স্মোক (CI-তে নয় — প্রকৃত প্রোভাইডার)

| কমান্ড                                 | এটি যা করে                                                                              |
| :------------------------------------- | :-------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` সহ ইন-প্রসেস প্রকৃত রাউটিং; একটি লাইভ OmniRoute DB-এর স্ন্যাপশট নেয় |
| `npm run test:combo:live:vps`          | একটি লাইভ OmniRoute সার্ভারে HTTP কল (`COMBO_LIVE_BASE_URL` সেট করুন)                   |
| `npm run test:combo:live:vps:failover` | একই, তবে ইচ্ছাকৃত ফেইলওভার পরিস্থিতিসহ                                                  |

এই স্মোক টেস্টগুলো প্রকৃত ওয়্যার পাথ (কম্বো → প্রোভাইডার → কমপ্লিশন) অনুশীলন করে। এগুলোকে
ইচ্ছাকৃতভাবে CI থেকে বাদ দেওয়া হয়েছে, কারণ এগুলোর জন্য লাইভ ক্রেডেনশিয়াল এবং VPS অ্যাক্সেস প্রয়োজন।
