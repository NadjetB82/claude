## زیرو-کنفگ آٹو-روٹنگ (`auto/` سابقہ)

> **نیا:** کومبو بنانے کی ضرورت نہیں۔ کسی بھی کلائنٹ میں براہِ راست `auto/` سابقہ استعمال کریں۔

### فوری مثالیں

| ماڈل ID        | ویریئنٹ | طرزِ عمل                                                         |
| -------------- | ------- | ---------------------------------------------------------------- |
| `auto`         | ڈیفالٹ  | تمام منسلک فراہم کنندگان، LKGP حکمتِ عملی، متوازن وزن            |
| `auto/coding`  | کوڈنگ   | معیار کو ترجیح دینے والے وزن، کوڈ بنانے کے لیے موزوں             |
| `auto/fast`    | تیز     | کم تاخیر پر مبنی وزنی انتخاب                                     |
| `auto/cheap`   | سستا    | لاگت کے لیے بہتر بنائی گئی روٹنگ (سب سے کم لاگت پہلے)            |
| `auto/offline` | آف لائن | سب سے زیادہ کوٹہ دستیابی والے فراہم کنندگان کو ترجیح دیتا ہے     |
| `auto/smart`   | اسمارٹ  | معیار کو ترجیح + بہتر ماڈل دریافت کے لیے زیادہ کھوج کی شرح (10%) |
| `auto/lkgp`    | lkgp    | واضح LKGP (ڈیفالٹ `auto` کے مساوی)                               |
| `auto/chaos`   | chaos   | متوازی fan-out، فی فراہم کنندہ ایک ماڈل (fault injection نہیں)   |

### زمرہ × درجہ تشکیل (`auto/<category>:<tier>`)

OpenRouter طرز کے لاحقے **روٹ کی نوعیت** (زمرہ) کو **اسے بہتر بنانے کے طریقے** (درجہ) سے الگ کرتے ہیں، تاکہ آپ انہیں آزادانہ طور پر یکجا کر سکیں (#4235 Phase B، `open-sse/services/autoCombo/suffixComposition.ts`):

- **زمرے** (صلاحیت کے لحاظ سے امیدواروں کے مجموعے کو فلٹر کریں): `coding` · `reasoning` · `vision` · `chat` · `multimodal`۔ `vision`/`multimodal` بصارت کی صلاحیت رکھنے والے ماڈلز برقرار رکھتے ہیں؛ `reasoning` استدلال/تفکر والے ماڈلز برقرار رکھتا ہے۔
- **درجے** (اسکورنگ کے وزن / مجموعے کا فلٹر منتخب کریں): `fast` (فوری ترسیل) · `cheap` (عرف `floor`، لاگت بچانے والا) · `reliable` (circuit-breaker کی صحت + تاخیر کا استحکام) · `free` / `pro` (`classifyTier` کے ذریعے ماڈل کے درجے کے مطابق مجموعے کو فلٹر کریں — مفت درجہ بمقابلہ پریمیم)۔

| مثال                   | نتیجہ                                                                 |
| ---------------------- | --------------------------------------------------------------------- |
| `auto/coding:fast`     | کوڈنگ کا مجموعہ، کم تاخیر والے وزن                                    |
| `auto/coding:cheap`    | کوڈنگ کا مجموعہ، لاگت کے لیے بہتر بنایا گیا (عرف `auto/coding:floor`) |
| `auto/reasoning:pro`   | صرف استدلال/تفکر والے ماڈلز، پریمیم درجہ                              |
| `auto/vision`          | بصارت کی صلاحیت رکھنے والے ماڈلز (کوئی درجہ نہیں → متوازن وزن)        |
| `auto/multimodal:free` | ملٹی موڈل صلاحیت رکھنے والے ماڈلز، صرف مفت درجہ                       |

کوئی بھی درست `auto/<category>[:<tier>]` حسبِ ضرورت resolve ہو جاتا ہے؛ ایک منتخب ذیلی مجموعہ `/v1/models` اور ڈیش بورڈ میں مشتہر کیا جاتا ہے (`open-sse/services/autoCombo/builtinCatalog.ts` میں `AUTO_SUFFIX_VARIANTS`)۔ فلٹرنگ **fail-open** ہے — اگر کوئی شرط کسی منسلک ماڈل سے مماثل نہ ہو تو مکمل مجموعہ استعمال کیا جاتا ہے، تاکہ روٹنگ کبھی ناکام نہ ہو۔ بنیادی اسکورر (`combo.ts`) میں کوئی تبدیلی نہیں کی گئی؛ زمرہ/درجہ فلٹر `buildAutoCandidates` میں لاگو ہوتا ہے۔

> **لائیو ماڈل انٹیلی جنس:** جب `ARENA_ELO_SYNC_ENABLED` فلیگ فعال ہو تو آٹو-روٹنگ کی موزونیت لائیو **Arena ELO** درجہ بندیوں + **models.dev** کے درجہ جاتی ڈیٹا سے متعین ہوتی ہے (بصورتِ دیگر جامد موزونیت میپ استعمال کیا جاتا ہے)۔

**استعمال کا طریقہ:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**کیا ہوتا ہے:**

1. OmniRoute، `src/sse/handlers/chat.ts` میں `auto/` سابقے کا پتہ لگاتا ہے
2. ڈیٹابیس سے تمام **فعال فراہم کنندہ کنکشنز** حاصل کرتا ہے
3. درست اسناد (API key یا OAuth token) رکھنے والے کنکشنز کو فلٹر کرتا ہے
4. ہر کنکشن کے لیے ماڈل کا تعین کرتا ہے (`connection.defaultModel` یا فراہم کنندہ کا پہلا ماڈل)
5. میموری میں ایک **ورچوئل کومبو** بناتا ہے (DB میں محفوظ نہیں کیا جاتا)
6. منتخب ویریئنٹ کے weight profile + LKGP حکمتِ عملی کے ذریعے روٹ کرتا ہے

**اہم خصوصیات:**

- ✅ **ہمیشہ فعال:** کسی toggle، کومبو بنانے یا کنفگریشن کی ضرورت نہیں
- ✅ **متحرک:** موجودہ منسلک فراہم کنندگان کو خودکار طور پر ظاہر کرتا ہے
- ✅ **سیشن کی وابستگی:** LKGP یقینی بناتا ہے کہ آخری کامیاب فراہم کنندہ کو ترجیح دی جائے
- ✅ **متعدد اکاؤنٹس سے آگاہ:** ہر فراہم کنندہ کنکشن ایک علیحدہ امیدوار بن جاتا ہے
- ✅ **DB میں کوئی تحریر نہیں:** ورچوئل کومبو صرف درخواست کے دوران موجود رہتا ہے، persistence کا کوئی اضافی خرچ نہیں

### فی key امیدوار کنٹرول (#7819، سطح 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = `auto/` کے بعد آنے والا لاحقہ، یا
بنیادی چینل کے لیے بعینہٖ `auto`) ایک **صرف پڑھنے کے لیے** endpoint ہے، جو
لائیو رسائی پذیری کی معلومات کے ساتھ `auto/*` چینل کے موجودہ امیدواروں کے مجموعے کی فہرست دیتا ہے اور
موجودہ resilience reads کو دوبارہ استعمال کرتا ہے (خام breaker `state` کبھی استعمال نہیں کرتا):

- فراہم کنندہ circuit breaker — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- کنکشن cooldown — resolve کی گئی `provider_connections` row پر `rateLimitedUntil` / `testStatus`
- ماڈل lockout — `isModelLocked(provider, connectionId, model)`

ہر امیدوار میں اس API key کا `excluded` فلیگ بھی شامل ہوتا ہے۔ استثنا
فی API key محفوظ کیے جاتے ہیں (`auto_candidate_overrides` ٹیبل، migration `128`) — OmniRoute
single-tenant ہے اور اس میں کوئی `users` ٹیبل نہیں، لہٰذا `apiKeyId` فی کالر
حقیقی شناخت کا قریب ترین متبادل ہے — اور انہیں
`open-sse/services/autoCombo/virtualFactory.ts` میں امیدواروں کے مجموعے کے مرکزی کنٹرول مقام پر خالص، unit-tested
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`) کے ذریعے نافذ کیا جاتا ہے۔
فلٹر **fail-open** ہے: غیر متعین apiKeyId/channel یا DB lookup کی ناکامی، دونوں صورتوں میں
مجموعہ بغیر فلٹر کیے رہتا ہے، لہٰذا وہ آپریٹر جس کے لیے کوئی override کنفگر نہ ہو، اس فیچر سے پہلے جیسی
byte-identical روٹنگ دیکھتا ہے۔

**آئندہ فالو اَپ مسئلے کے لیے مؤخر:** فی امیدوار وزن + واضح ترتیب (لیول 3
— موجودہ وزن یافتہ/ترجیحی حکمتِ عملی کے راستوں میں شامل ہوتا ہے) اور ہر `auto/*`
چینل کے لیے ایک مخصوص `combo.ts` حکمتِ عملی کو پن کرنا (لیول 4)۔ اس کھلے سوال کے
لیے #7819 کا منصوبہ دیکھیں کہ آیا واحد کرایہ دار ماڈل کے پیشِ نظر اوور رائیڈز کو فی API کلید
تک محدود رہنا چاہیے یا عالمی بنا دینا چاہیے۔

**پسِ پردہ:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

## ایسے کومبو نام جو کسی حقیقی ماڈل آئی ڈی سے مماثل ہوں

ایسا کومبو جس کا `name` کسی سادہ ماڈل آئی ڈی کے عین مطابق ہو (مثلاً `gpt-5.5` نامی کومبو)، ایک **دانستہ اور معاونت یافتہ پیٹرن** ہے، بگ نہیں: یہ فی ماڈل آئی ڈی پرووائیڈر فال بیک کا طریقۂ کار ہے، جسے [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) میں دستاویزی شکل دی گئی ہے۔ چونکہ کومبو ریزولیوشن کو سادہ ماڈل آئی ڈی ریزولیوشن سے پہلے چیک کیا جاتا ہے (`src/sse/services/model.ts` میں `getComboForModel()`)، اس لیے سادہ آئی ڈی `gpt-5.5` کی درخواست براہِ راست کسی ایک پرووائیڈر کے پاس جانے کے بجائے کومبو کے اہداف (مثلاً `acme-responses/gpt-5.5`، `backup-responses/gpt-5.5`) کے ذریعے روٹ کی جاتی ہے — یہ [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) کے لیے بنائی گئی کومبو-قبل-از-ری رائٹ ترجیح کو دوبارہ استعمال کرتا ہے، اور `tests/unit/responses-combo-resolution-3227.test.ts` اور `tests/unit/combo-name-codex-responses-rewrite.test.ts` کے ذریعے اس کی ریگریشن ٹیسٹنگ کی جاتی ہے۔

کسی ایسے کومبو کو بنانا یا اس کا نام بدلنا جو کسی حقیقی ماڈل آئی ڈی کو شیڈو کرے، **کبھی مسترد نہیں کیا جاتا** — ایسا کرنے سے یہ دستاویزی ورک فلو ٹوٹ جائے گا۔ اس کے بجائے (#8530)، جب (نیا) نام کسی حقیقی ماڈل آئی ڈی سے متصادم ہو تو `POST /api/combos` اور `PUT /api/combos/[id]` ریسپانس کے ساتھ ایک غیر مسدود کرنے والی `warning` فیلڈ منسلک کرتے ہیں:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

بوٹ کے وقت، `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ایک سطر پر مشتمل `[STARTUP]` وارننگ بھی لاگ کرتا ہے، جس میں ایسے تمام موجودہ کومبوز درج ہوتے ہیں جو کسی ماڈل آئی ڈی کو شیڈو کرتے ہیں، تاکہ جن آپریٹرز کو دانستہ طور پر، بمطابق #6940، ایسا کرنے کے بجائے حادثاتی طور پر اس صورتِ حال کا سامنا ہو، انہیں ایک اشارہ مل سکے۔ ڈیٹیکشن ہیلپر `src/lib/combos/modelNameCollision.ts` میں موجود ہے۔

## کسی کلائنٹ سے کسٹم کومبو کو کال کرنا

محفوظ شدہ کومبوز (Settings → Combos) صرف اسی وقت استعمال ہوتے ہیں جب کلائنٹ `model` فیلڈ میں کومبو کا **بالکل درست نام** بھیجے — کومبو نام کی کوئی مبہم یا جزوی میچنگ نہیں ہوتی، اور نہ ہی `auto/` پریفکس شامل ہوتا ہے۔ ریزولیوشن کی ترتیب (`src/sse/services/model.ts` میں `getComboForModel()`):

1. کومبو نام سے بالکل درست میچ (`model: "my-combo"`)،
2. `combo/<name>` پریفکس (`model: "combo/my-combo"`)،
3. ماڈل→کومبو گلوب میپنگز (`/api/model-combo-mappings`)۔

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

دو عام غلط فہمیاں:

- **`auto` آپ کے کومبوز استعمال نہیں کرتا۔** `auto`/`auto/*` اپنا زیرو-کنفیگ امیدوار پول بناتا ہے اور محفوظ شدہ کومبوز سے صرف اس صورت میں رجوع کرتا ہے جب کسی کومبو کا نام حرف بہ حرف `auto` ہو (اس کی سفارش نہیں کی جاتی)۔ کسی کومبو کے ذریعے روٹ کرنے کے لیے اس کا بالکل درست نام بھیجیں — `auto` نہیں۔
- **`openrouter/auto` ایک حقیقی، بامعاوضہ OpenRouter پراڈکٹ** ("Auto Best Available") ہے، OmniRoute کا عرف نہیں۔ یہ OpenRouter رجسٹری (`open-sse/config/providers/registry/openrouter/index.ts`) کا واحد جامد ماڈل اندراج ہے اور اس کی بلنگ الگ سے ہوتی ہے۔ اسے `auto` پولز سے خارج کرنے کے لیے Settings → Routing → Hide paid models استعمال کریں۔

اس دستاویز میں بیان کردہ اصل الجھن کے لیے [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) اور [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) دیکھیں۔

## یہ کیسے کام کرتا ہے (Persisted Auto-Combos)

Auto-Combo Engine ایک **16-factor scoring function** کا استعمال کرتے ہوئے متحرک طور پر ہر درخواست کے لیے بہترین provider/model کا انتخاب کرتا ہے (جو `open-sse/services/autoCombo/scoring.ts` میں → `DEFAULT_WEIGHTS` کے تحت متعین ہے)۔ طے شدہ weights کا مجموعہ `1.0` ہوتا ہے؛ کسٹم weights کو `normalizeScoringWeights()` کے ذریعے دوبارہ نارملائز کیا جاتا ہے۔ سولہ میں سے دو عوامل — `cacheAffinity` اور `resetWindowAffinity` — کا طے شدہ وزن `0` ہوتا ہے؛ `reliability` کا وزن `DEFAULT_WEIGHTS` میں `0` ہوتا ہے لیکن generic packs میں `0.03` اور `reliability-first` میں `0.04` ہوتا ہے، اور `quality` کا وزن packs میں `0.02` ہوتا ہے (`quality-first` میں `0.03`): یہ اب بھی ہر امیدوار کے لیے شمار کیے جاتے ہیں، اور `cacheAffinity` اسکور سے باہر prompt-cache deduplication کا تعین کرتا ہے، لہٰذا صفر ڈیفالٹ والے عوامل عام طور پر ووٹ نہیں دیتے جبکہ packs دیتے ہیں۔

  - **offline-friendly** → quota 0.3324 + health 0.2667 (رفتار/لاگت سے قطع نظر زیادہ سے زیادہ اضافی گنجائش)
  - **reliability-first** → health 0.3524 + stability 0.1905 + reliability 0.04، جو تمام پیکس میں سب سے زیادہ ہے (کم سے کم غیر متوقع نتائج)
  - **chaos-mode** → health 0.4000 + taskFit 0.1905 (وزنی پیک `auto/chaos` اپنے پینل کے اراکین کو یہ وزن تفویض کرتا ہے؛ متوازی فین آؤٹ ان وزنوں کو نہیں پڑھتا، اور یہ فالٹ انجیکشن پروفائل نہیں ہے، [CHAOS-MODE.md](../guides/CHAOS-MODE.md#autochaos-parallel-fan-out) دیکھیں)

### فی درخواست کنٹرولز (ہیڈرز) — #6023 / #6024 / #6025 / #3470

کسی `auto` کومبو کو محفوظ کردہ کنفگ میں تبدیلی کیے بغیر، تین ہیڈرز کے ذریعے **فی درخواست** کنٹرول کیا جا سکتا ہے۔ یہ صرف `auto` حکمتِ عملی اور صرف اس درخواست پر لاگو ہوتے ہیں جس میں یہ موجود ہوں؛ ہیڈر موجود نہ ہونے کی صورت میں کومبو کی محفوظ شدہ `modePack`/`budgetCap`/`budgetFallback` قدریں استعمال ہوتی ہیں۔

| ہیڈر                          | قابلِ قبول اقدار                                                                                                                                                                     | اثر                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| :---------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-Mode`            | ایک پیش سیٹ عرف (`fast`، `balanced`، `quality`، `cheap`، `reliable`، `offline`) یا خام پیک نام (`ship-fast`، `cost-saver`، `quality-first`، `offline-friendly`، `reliability-first`) | اس درخواست کے لیے اسکورنگ کے اوزان کو اوور رائیڈ کرتا ہے۔ `balanced`/`default` طے شدہ اوزان نافذ کرتے ہیں (کوئی پیک نہیں)۔ نامعلوم اقدار نظر انداز کر دی جاتی ہیں (کنفیگریشن برقرار رہتی ہے)۔                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

```bash
# Force the fastest profile, cap this request at $0.05, and hard-block instead of overspending
curl -sS http://localhost:20128/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-OmniRoute-Mode: fast" \
  -H "X-OmniRoute-Budget: 0.05" \
  -H "X-OmniRoute-Budget-Fallback: strict" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hi"}]}'
```

حل شدہ اقدار انجن کے موجودہ `config.modePack` / `config.budgetCap` /
`config.budgetFallback` ان پٹس کو فراہم کی جاتی ہیں۔ کسی کومبو کی محفوظ شدہ `config.budgetFallback` ("strict" |
"cheapest") مستقل پالیسی متعین کرتی ہے؛ ہیڈر ایک واحد درخواست کے لیے اسے اوور رائیڈ کرتا ہے۔

### `weighted` کے معنی

`weighted` فی درخواست ایک **متناسب بے ترتیب قرعہ اندازی** ہے (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`)، نہ کہ برابری کرنے والا (equalizer):

- ہر درخواست `weight / totalWeight` کے امکان کے ساتھ **ایک** مرحلہ منتخب کرتی ہے؛ باقی مراحل اس درخواست کے لیے فال بیک چین کے طور پر وزن کے نزولی ترتیب میں ہوتے ہیں۔
- ایک مرحلہ جس کا وزن `0` (یا غائب) ہے وہ **کبھی منتخب نہیں ہوتا** جب تک کہ کسی دوسرے مرحلے کا وزن > 0 ہو — یہ صرف منتخب کردہ مرحلے کے ناکام ہونے کے بعد فال بیک کے طور پر کام کر سکتا ہے۔ صرف تب جب **تمام** وزن 0 ہوں تو انتخاب یکساں ہو جاتا ہے۔
- وہ مراحل جن کے اہداف دستیاب نہیں ہیں — فراہم کنندہ سرکٹ بریکر `OPEN`، کنکشن کول ڈاؤن، ماڈل لاک آؤٹ — کو قرعہ اندازی سے پہلے ہی ہٹا دیا جاتا ہے (`open-sse/services/combo/targetResolution.ts`)، لہذا ایک واحد صحت مند مرحلہ عارضی طور پر ہر درخواست جیت سکتا ہے۔
- `stickyWeightedLimit` (کومبو کنفیگ، ڈیفالٹ `1` = آف) دوبارہ قرعہ اندازی سے پہلے منتخب کردہ مرحلے کو اتنی مسلسل کامیابیوں کے لیے پن (pin) کر دیتا ہے۔

سخت روٹیشن کے لیے `round-robin` استعمال کریں؛ `weighted` پر مساوی وزن شماریاتی — نہ کہ سخت — توازن فراہم کرتے ہیں۔

### ایجنٹک پائپ لائن موڈ

کم از کم دو ماڈلز کے ساتھ ایک `pipeline` کومبو `config.agenticOrchestration.enabled` کے ساتھ پلانر/ایگزیکیوٹر روٹنگ کا انتخاب کر سکتا ہے۔ پہلا ٹارگٹ پلاننگ اور حتمی جوابات کا ذمہ دار ہوتا ہے؛ دوسرا ٹارگٹ کلائنٹ-نیٹو ٹول کالز جاری کرتا ہے۔ OmniRoute درخواست پروٹوکول سے ٹول-نتیجہ کے تسلسل (continuations) کا پتہ لگاتا ہے، پلانر سے پوچھتا ہے کہ آیا کسی اور ٹول راؤنڈ کی ضرورت ہے، اور متحرک طور پر ایگزیکیوٹر یا پلانر میں سے کسی ایک کو کلائنٹ کے سامنے حتمی مرحلہ بنا دیتا ہے۔

ٹول-نتیجہ کے تسلسل پر، OmniRoute اس وقت بھی ایگزیکیوشن روک دیتا ہے جب دو مسلسل مکمل شدہ راؤنڈز غیر تبدیل شدہ نتائج کے ساتھ وہی ٹول کالز دہراتے ہیں، یا جب دو مسلسل راؤنڈز میں ہر واضح طور پر نشان زد نتیجہ ناکام ہو جاتا ہے۔ تبدیل شدہ نتائج دہرائی گئی کالز کی اجازت دیتے ہیں (مثال کے طور پر، پولنگ)۔ گارڈ ایک نئی صارف درخواست پر ری سیٹ ہو جاتا ہے، متوازی کالز کو ایک راؤنڈ میں گروپ کرتا ہے، اور Anthropic، Chat Completions، Responses اور Gemini ہسٹریز کو سپورٹ کرتا ہے۔ پلانر وجہ وصول کرتا ہے اور حتمی جواب کا مالک ہوتا ہے چاہے وہ کسی اور ٹول راؤنڈ کی درخواست کرے۔

دوسرے ٹارگٹ کے بعد اضافی ماڈلز ترتیب وار ایگزیکیوٹر بیک اپس ہیں۔ ایک ناکام HTTP رسپانس یا ٹرانسپورٹ ایکسیپشن اگلے ایگزیکیوٹر کی طرف بڑھ جاتی ہے، جس میں وہی پلانر فیصلہ اور نیٹو ٹولز ہوتے ہیں لیکن اس ایگزیکیوٹر کا اپنا سٹیپ پرامپٹ اور ریزولوڈ کنکشن ہوتا ہے۔ پہلا کامیاب رسپانس بغیر کسی تبدیلی کے واپس کیا جاتا ہے، بشمول SSE سٹریمنگ؛ کامیاب سٹریم شروع ہونے کے بعد ناکامیوں کو یہاں دوبارہ کوشش (retry) نہیں کیا جا سکتا۔ اگر تمام ایگزیکیوٹرز ناکام ہو جائیں، تو آخری ناکامی واپس کی جاتی ہے۔ کلائنٹ کے ابارٹس (aborts) ڈسپیچ کو روک دیتے ہیں۔

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ایگزیکیوٹر ایک رسپانس میں متعدد آزاد کالز جاری کر سکتا ہے۔ منحصر (dependent) کالز کو بعد کے کلائنٹ ٹول-نتیجہ کے ٹرنز میں ہینڈل کیا جاتا ہے، جس میں پلانر ہر نتیجے کا جائزہ لیتا ہے۔ `maxToolRounds` کا ڈیفالٹ `8` ہے اور یہ `1`–`32` کو قبول کرتا ہے؛ ایک بار پہنچ جانے پر، پلانر کو بہترین دستیاب حتمی جواب تیار کرنا ہوگا۔ اندرونی پلانر کے فیصلے بفر کیے جاتے ہیں، جبکہ منتخب کردہ کلائنٹ کے سامنے والا رسپانس اصل سٹریمنگ ترجیح کو برقرار رکھتا ہے۔

### `round-robin` سٹکی بیچ اور اکاؤنٹ ایکسپینشن

راؤنڈ-روبن بیچڈ ہے، نہ کہ فی سٹیپ ایک درخواست:

- `stickyRoundRobinLimit` (کومبو کنفیگ، پھر `comboStickyRoundRobinLimit`، پھر `settings.stickyRoundRobinLimit`، ڈیفالٹ **3**) روٹیٹ کرنے سے پہلے اتنی مسلسل کامیابیوں کے لیے ایک ہی ٹارگٹ کو برقرار رکھتا ہے۔ ایک-درخواست روٹیشن کے لیے کومبو اووررائیڈ کو `1` پر سیٹ کریں۔ کومبو ایڈیٹر مؤثر ویلیو اور یہ دکھاتا ہے کہ یہ کس لیئر سے آئی ہے۔
- `connectionAwareExpansion` (کومبو کنفیگ، پھر سیٹنگز، ڈیفالٹ **false**) روٹیشن سے پہلے ہر پرووائیڈر-لیول سٹیپ کو فی-اکاؤنٹ ٹارگٹس میں پھیلاتا (expand کرتا) ہے۔ گروپ-B حکمت عملی (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) اس وقت تک پرووائیڈر-لیول ویو رکھتی ہیں جب تک یہ آن نہ ہو۔ کومبو ایڈیٹر inherit / on / off کو ظاہر کرتا ہے؛ inherit گلوبل ڈیفالٹ (off) کا استعمال کرتا ہے۔
- پرامپٹ-کیش لوکیلٹی روٹنگ (`promptCacheAffinityEnabled`، ڈیفالٹ **true**) پن شدہ کنکشنز کو دوبارہ ترتیب دیتی ہے تاکہ مماثل کیش کیز ایک اکاؤنٹ پر رہیں۔ یہ پن شدہ فی-اکاؤنٹ سٹیپس پر راؤنڈ-روبن اور ویٹڈ روٹیشن پر فوقیت رکھتی ہے۔ اگر آپ کو سخت روٹیشن کی ضرورت ہو تو اسے Settings → Combo defaults کے تحت آف کر دیں۔ اس کے لیے کوئی فی-کومبو اووررائیڈ نہیں ہے۔

ایک ماڈل پر ملٹی-اکاؤنٹ روٹیشن کے لیے، **ایک ڈائنامک-اکاؤنٹ سٹیپ** (خالی `connectionId`، پورا پول) کو سٹکی لمٹ `1` کے ساتھ ترجیح دیں، نہ کہ تین پن شدہ `connectionId`s کو۔ پن شدہ سٹیپس جمع ایفینیٹی (affinity) ایک ہی اکاؤنٹ پر گر جاتے ہیں (collapse) حالانکہ RR کاؤنٹر آگے بڑھتا رہتا ہے۔

## فیوژن حکمتِ عملی

`fusion` وہ واحد حکمتِ عملی ہے جو کسی ایک ہدف کو منتخب **نہیں** کرتی۔ یہ پرامپٹ کو
**ہر پینل ماڈل کو متوازی طور پر** بھیجتی ہے، پھر ایک قابلِ تشکیل **جج ماڈل** پینل کے
تمام جوابات سے ایک حتمی جواب مرتب کرتا ہے۔ اسے اپ اسٹریم `decolua/9router`
(OpenRouter کے Fusion ڈیزائن) سے پورٹ کیا گیا ہے؛ نفاذ `open-sse/services/fusion.ts` میں ہے۔

یہ کیسے کام کرتی ہے:

0. **ٹول والی درخواست کا بائی پاس** — ایسی درخواست جس میں ایک غیر خالی `tools` ارے ہو اور
   `tool_choice` کو واضح طور پر `"none"` مقرر نہ کیا گیا ہو، پینل کو مکمل طور پر چھوڑ دیتی ہے:
   یہ `tools`/`tool_choice` کو بغیر تبدیلی کے براہِ راست ایک ماڈل (تشکیل کردہ جج، یا `panel[0]`)
   کی طرف بھیجی جاتی ہے۔ پینل اراکین کو ٹولز تک رسائی حاصل نہیں ہوتی اور جج کی
   ترکیبی ہدایت ٹول کال پیدا کرنے کی حوصلہ شکنی کرتی ہے، اس لیے ایجنٹ پر مبنی/ٹول کال کرنے والے کلائنٹس
   کو ترکیب شدہ نثر کے بجائے حقیقی ٹول کال کا فیصلہ ملتا ہے (#6771)۔
1. **فین آؤٹ** (صرف ٹول کے بغیر درخواستوں کے لیے) — پرامپٹ کو ایک ہی وقت میں ہر پینل
   ماڈل کو بھیجا جاتا ہے، ٹولز ہٹا کر نان اسٹریمنگ کو لازمی بنایا جاتا ہے (جج کو ترکیب کے لیے
   مکمل نثر درکار ہوتی ہے)۔
2. **کورم-گریس کلیکشن** — جیسے ہی `minPanel` جوابات موصول ہوتے ہیں، پیچھے رہ جانے والوں کے لیے
   ایک مختصر گریس ٹائمر شروع ہو جاتا ہے، پھر جو کچھ جمع ہو چکا ہو اس کے ساتھ فیوژن آگے بڑھتا ہے۔
   یہ وال ٹائم پر سب سے سست ماڈل کے جرمانے کو محدود کرتا ہے، جبکہ ایک سخت ٹائم آؤٹ حتمی حد مقرر کرتا ہے۔
3. **جج کی ترکیب** — پینل کے جوابات کو گمنام بنایا جاتا ہے (`Source 1`، `Source 2`، … — تاکہ
   جج ماڈل کے برانڈ کے بجائے مواد کی اہمیت پر غور کرے) اور جج کو دے دیا جاتا ہے، جو
   اتفاقِ رائے / تضادات / جزوی احاطے / منفرد بصیرتوں / نظر انداز پہلوؤں کا تجزیہ کرتا ہے، پھر
   **ایک** مستند جواب لکھتا ہے۔ جج کال کلائنٹ کا اصل
   `stream` فلیگ + ٹولز برقرار رکھتی ہے، اس لیے اسٹریمنگ اور ڈاؤن اسٹریم ٹول کا استعمال بدستور کام کرتے ہیں۔
4. **بتدریج تنزل** — پینل کے 0 جوابات → `503`؛ صرف 1 جواب باقی بچے → وہ جواب
   براہِ راست واپس کر دیا جاتا ہے (ترکیب کرنے کے لیے کچھ نہیں)؛ ایک ماڈل والا پینل براہِ راست جواب دیتا ہے۔

پینل کا کوئی رکن `combo-ref` مرحلہ بھی ہو سکتا ہے (`{kind: "combo-ref", comboName: "..."}`) جو
کسی دوسرے کومبو کا حوالہ دیتا ہے — اسے **ایک بلیک باکس پینل آواز** کے طور پر حل کیا جاتا ہے (حوالہ دیے گئے
کومبو میں مکمل تکراری ڈسپیچ، نہ کہ اس کومبو کے اپنے اہداف کا فین آؤٹ)، اور اس میں وہی گہرائی/چکر کا تحفظ
استعمال ہوتا ہے جو پہلے سے ہر دوسری combo-ref استعمال کرنے والی حکمتِ عملی میں موجود ہے (#6764)۔

### تشکیل

کومبو کے `config` بلاب میں تشکیل کیا جاتا ہے (کسی اسکیما مائیگریشن کی ضرورت نہیں — یہ موجودہ
`combos` ٹیبل کو دوبارہ استعمال کرتا ہے):

| فیلڈ                                     | قسم      | ڈیفالٹ         | مقصد                                                                         |
| :--------------------------------------- | :------- | :------------- | :--------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | پہلا پینل ماڈل | حتمی جواب کی ترکیب کرنے والا ماڈل                                            |
| `config.fusionTuning.minPanel`           | `number` | `2`            | گریس ٹائمر شروع ہونے سے پہلے درکار کامیاب جوابات (`[2, panelSize]` تک محدود) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`         | کورم پورا ہونے کے بعد پیچھے رہ جانے والوں کا کتنی دیر انتظار کیا جائے        |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`        | حتمی مطلق حد، تاکہ ایک معلق ماڈل درخواست کو روک نہ سکے                       |

ڈیفالٹس `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) میں موجود ہیں۔

### مثال

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

پھر اسے کسی بھی کومبو کی طرح کال کریں: `{"model":"fusion-panel","messages":[...]}`۔

## ورچوئل آٹو-کومبو فیکٹری

Auto Combo انجن کو پہلے سے متعین combos کی ضرورت نہیں ہوتی۔ اس کے بجائے، `open-sse/services/autoCombo/virtualFactory.ts` فوری طور پر امیدوار بناتا ہے:

1. `getProviderConnections({ isActive: true })` حاصل کرتا ہے (تمام فعال connections)
2. ان connections تک محدود کرتا ہے جن کے credentials درست ہوں (API key یا `hasUsableOAuthToken()` کے ذریعے غیر زائد المیعاد OAuth token)
3. ماڈل کی دستیابی + قیمتوں کے لیے `getProviderRegistry()` سے تقابل کرتا ہے
4. ہر tuple `(provider, model, connection)` کے لیے ایک `VirtualAutoComboCandidate` بناتا ہے
5. dispatch ہدف کے طور پر `connection.defaultModel` (یا registry کا پہلا ماڈل) منتخب کرتا ہے
6. 16 عوامل والے `scorePool()` اور variant کے weight pack کے ذریعے ہر امیدوار کو اسکور کرتا ہے
7. `handleComboChat()` کے لیے نتیجے میں بننے والا in-memory `AutoComboConfig` واپس کرتا ہے — اسے کبھی DB میں محفوظ نہیں کیا جاتا

اس کا مطلب ہے کہ **`auto/*` فعال رکھنے والا نیا provider شامل کرنے سے امیدواروں کا pool خودکار طور پر وسیع ہو جاتا ہے** — combo میں دستی ترمیم کی ضرورت نہیں ہوتی۔ ورچوئل combo ہر درخواست پر دوبارہ بنایا جاتا ہے، اس لیے نئے شامل کیے گئے یا دوبارہ صحت مند ہونے والے connections فوراً شامل کر لیے جاتے ہیں۔

## خودکار بحالی

- **عارضی اخراج**: اسکور < 0.2 → 5 منٹ کے لیے خارج (تدریجی backoff، زیادہ سے زیادہ 30 منٹ)
- **Circuit breaker سے آگاہی**: OPEN → خودکار طور پر خارج؛ HALF_OPEN → آزمائشی درخواستیں
- **حادثاتی صورتِ حال کا موڈ**: >50% OPEN → exploration غیر فعال، استحکام زیادہ سے زیادہ
- **Cooldown بحالی**: اخراج کے بعد پہلی درخواست کم timeout کے ساتھ ایک "probe" ہوتی ہے

## Bandit Exploration

5% درخواستیں (قابلِ ترتیب) exploration کے لیے بے ترتیب providers کو بھیجی جاتی ہیں۔ حادثاتی صورتِ حال کے موڈ میں یہ غیر فعال ہوتا ہے۔

## API

**`POST /api/combos/auto` کا کوئی مخصوص اینڈ پوائنٹ موجود نہیں ہے** — Auto-Combo کو دو طریقوں سے استعمال کیا جاتا ہے:

1. **Zero-config (تجویز کردہ):** کوئی بھی چیٹ کمپلیشن کی درخواست `model: "auto"` یا `model: "auto/<variant>"` کے ساتھ بھیجیں۔ ورچوئل فیکٹری ہر درخواست پر کومبو بناتی ہے — کسی استقامت (persistence) یا API کالز کی ضرورت نہیں ہے۔

2. **`strategy: "auto"` کے ساتھ پرسسٹڈ کومبو:** `POST /api/combos` کے ذریعے ایک عام کومبو بنائیں اور `strategy: "auto"` کے ساتھ `config.auto.weights` / `config.auto.candidatePool` سیٹ کریں۔ وہی اسکورنگ انجن استعمال ہوتا ہے؛ کومبو `combos` میں محفوظ ہو جاتا ہے اور ID کے ذریعے دوبارہ قابل استعمال ہوتا ہے۔

دریافت کے لیے، `GET /api/combos/auto` ہر ویریئنٹ کو اس کے ریزولوڈ کینڈیڈیٹ پول کے ساتھ، نیز `context_length` / `max_output_tokens` — جو کینڈیڈیٹ پول کی ونڈوز میں MAX ہے — کی فہرست دیتا ہے۔ کلائنٹس (مثال کے طور پر opencode پلگ ان) کو `0` کے بجائے ان اقدار کی تشہیر کرنی چاہیے: صفر کانٹیکسٹ opencode کی آٹو-کمپیکشن کو مکمل طور پر غیر فعال کر دیتا ہے، جس سے سیشنز اس وقت تک بڑھتے رہتے ہیں جب تک گیٹ وے کی ہسٹری پرج (purge) کانٹیکسٹ کو ختم نہ کر دے۔ MAX کی تشہیر کرنا محفوظ ہے کیونکہ آٹو-کومبو کانٹیکسٹ پری-فلٹر بہت بڑی درخواستوں کو بڑی ونڈو والے کینڈیڈیٹس کی طرف بھیج دیتا ہے۔

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

پرسسٹڈ `strategy: "auto"` کومبوز `config.routerStrategy` (یا پرانے `config.auto.routerStrategy`) کو درج ذیل میں سے کسی ایک پر سیٹ کر سکتے ہیں:

- `rules` — ڈیفالٹ ویٹڈ اسکورنگ
- `score` — سب سے زیادہ کنفیگرڈ ویٹڈ اسکور کا انتخاب کرتا ہے۔ بالکل برابر اسکور ہونے کی صورت میں کنفیگرڈ کینڈیڈیٹ آرڈر برقرار رہتا ہے؛ موجودہ `explorationRate` مکمل رینکڈ پول سے نمونے لیتا ہے۔
- `cost` / `eco` — سب سے سستا ہیلتھی پرووائیڈر
- `latency` / `fast` — سب سے کم p95 لیٹنسی مع ریلائبلٹی پینلٹی
- `sla-aware` / `sla` — ان کینڈیڈیٹس کو ترجیح دیں جو p95 لیٹنسی، ایرر ریٹ، اور اختیاری کاسٹ SLOs کو پورا کرتے ہیں
- `lkgp` — آخری معلوم اچھا پرووائیڈر پہلے
- `nadir` — [Nadir](https://getnadir.com) کی ڈیسیژن API سے پوچھیں کہ پول میں موجود کس ماڈل کی پرامپٹ کو ضرورت ہے؛ آپٹ-ان، ناکامی کی صورت میں `rules` پر واپس جائیں

### Router strategies in detail

آٹو-کومبو انجن 7 پلگ ایبل **RouterStrategy** امپلیمنٹیشنز کو ظاہر کرتا ہے جنہیں آپ `config.routerStrategy` (یا پرانے `config.auto.routerStrategy`) کے ذریعے تبدیل کر سکتے ہیں۔ ہر اسٹریٹجی `RoutingContext` (ٹاسک کی قسم، ٹول/ویژن ہنٹس، ٹوکن کا تخمینہ، اختیاری SLA پالیسی، اختیاری آخری معلوم اچھا پرووائیڈر) کو مدنظر رکھتے ہوئے کینڈیڈیٹ پول سے ایک پرووائیڈر کا انتخاب کرتی ہے۔

#### 1. `rules` (ڈیفالٹ) — 16-فیکٹر ویٹڈ اسکورنگ

موجودہ اسکورنگ انجن کو ریپ (wrap) کرتا ہے۔ `OPEN` سرکٹ بریکر کینڈیڈیٹس کو فلٹر آؤٹ کرتا ہے، پھر موجودہ ٹاسک ٹائپ اور `getTaskFitness()` کے ساتھ `scorePool()` چلاتا ہے، اور سب سے زیادہ اسکور کرنے والے پرووائیڈر کا انتخاب کرتا ہے۔

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: ڈیفالٹ۔ تب استعمال کریں جب آپ تمام سگنلز کے درمیان متوازن ٹریڈ آف چاہتے ہیں۔

**عرف (Alias)**: `rules` (کوئی عرف نہیں)

---

#### 2. `cost` / `eco` — سب سے سستا ہیلتھی پرووائیڈر

کینڈیڈیٹ پول کو `costPer1MTokens` (بڑھتی ہوئی ترتیب) کے لحاظ سے ترتیب دیتا ہے اور سب سے سستے کا انتخاب کرتا ہے۔ پہلے `OPEN` کینڈیڈیٹس کو فلٹر آؤٹ کرتا ہے۔

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: لاگت کے لحاظ سے حساس ورک لوڈز، بیچ پروسیسنگ، یا بیک گراؤنڈ جابز۔

**عرف (Aliases)**: `cost`, `eco`

#### 3. `latency` / `fast` — سب سے کم p95 لیٹنسی مع ریلائبلٹی پینلٹی

`p95LatencyMs + (errorRate * 1000)` کے لحاظ سے ترتیب دیتا ہے۔ ایرر ریٹ پینلٹی اس بات کو یقینی بناتی ہے کہ غیر قابل اعتماد پرووائیڈرز کو نیچے رینک کیا جائے، چاہے ان کی برائے نام لیٹنسی کم ہی کیوں نہ ہو۔

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**کب استعمال کریں**: لیٹنسی کے لحاظ سے حساس ورک لوڈز جیسے ریئل ٹائم چیٹ، آٹو مکمل، یا انٹرایکٹو کوڈنگ اسسٹنٹس۔

**عرف (Aliases)**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — لیٹنسی/ایرر/کاسٹ SLO کی تعمیل

ہر کینڈیڈیٹ کو اس بنیاد پر اسکور کرتا ہے کہ وہ کنفیگرڈ SLO پالیسی کو کتنی اچھی طرح پورا کرتا ہے:

| عنصر           | وزن | فارمولا                                           |
| -------------- | --- | ------------------------------------------------- |
| لیٹنسی اسکور   | 35% | `threshold / max(value, ε)`                       |
| ایرر اسکور     | 35% | `threshold / max(value, ε)`                       |
| ہیلتھ اسکور    | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN) |
| کاسٹ اسکور     | 10% | `threshold / max(value, ε)` یا انورس نارملائزڈ    |
| اسٹیبلٹی اسکور | 5%  | انورس نارملائزڈ لیٹنسی stddev                     |

جب `hardConstraints: true` ہو، تو امیدواروں کو بنیادی طور پر **وائلیشن اسکور** (وہ SLO سے کتنا تجاوز کرتے ہیں) کے لحاظ سے ترتیب دیا جاتا ہے، اور پھر کمپوزٹ اسکور کے لحاظ سے۔ بصورت دیگر یہ صرف کمپوزٹ اسکور ہوتا ہے۔

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA فیلڈز** (کومبو کنفیگ پر سیٹ کی گئی):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**کب استعمال کریں**: پروڈکشن ورک لوڈز جن میں سخت لیٹنسی، ایرر ریٹ، یا کاسٹ بجٹ ہوں۔

**عرفی نام (Aliases)**: `sla-aware`, `sla`

#### 5. `lkgp` — آخری معلوم اچھا پرووائیڈر پہلے

**آخری معلوم اچھے پرووائیڈر** (اگر سیٹ ہو) کو پہلے آزماتا ہے، پھر `rules` حکمت عملی پر واپس آ جاتا ہے۔ سیشن اسٹیکینس کے لیے مفید ہے — ایک ہی پرووائیڈر گفتگو میں فالو اپ درخواستوں کو ہینڈل کرتا ہے۔

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**کب استعمال کریں**: ملٹی ٹرن گفتگو جہاں آپ چاہتے ہیں کہ ایک ہی پرووائیڈر فالو اپ درخواستوں کو ہینڈل کرے (مثال کے طور پر، کیشنگ، سیاق و سباق کے تسلسل، یا قیمتوں میں مستقل مزاجی کے لیے)۔

**عرفی نام (Alias)**: `lkgp` (کوئی عرفی نام نہیں)

#### 6. `nadir` — Nadir کے ذریعے پرامپٹ سے آگاہ ماڈل کا انتخاب

اوپر دی گئی ہر حکمت عملی امیدواروں کو ان کی اپنی ٹیلی میٹری کے لحاظ سے درجہ بندی کرتی ہے؛ ان میں سے کوئی بھی درخواست کو نہیں پڑھتی۔ `nadir` آخری صارف کی باری اور پول کے ماڈل آئی ڈیز کو [Nadir](https://getnadir.com) کی ڈیسیژن API (`POST /v1/bucket`) پر بھیجتا ہے اور اس ماڈل کی طرف روٹ کرتا ہے جسے Nadir اس مینو سے منتخب کرتا ہے (`simple` → سب سے سستا قابل ماڈل، `complex` → فرنٹیئر ماڈل)۔ اس ماڈل کو پیش کرنے والا کنکشن اب بھی `rules` کے ذریعے منتخب کیا جاتا ہے، لہذا کوٹہ، ہیلتھ اور کاسٹ یہ فیصلہ کرتے رہتے ہیں کہ کون سا اکاؤنٹ استعمال کرنا ہے۔

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` اور `OMNIROUTE_NADIR_BASE_URL` ان دو اسٹرنگز کے لیے env فال بیکس ہیں۔ `baseUrl` صرف سیلف ہوسٹڈ Nadir کے لیے درکار ہے (آخر میں `/v1` کی اجازت ہے)۔ بغیر کلید والی کالز Nadir کے گمنام ٹیر پر جاتی ہیں، جو فی IP ریٹ لمیٹڈ ہوتی ہے۔

باکس سے کیا باہر جاتا ہے: آخری صارف کے پیغام کا متن (پہلے 16k حروف)، امیدوار ماڈل آئی ڈیز اور ایک `source: "omniroute"` چینل ٹیگ۔ کوئی سسٹم پرامپٹ، ہسٹری، ٹولز یا ہیڈرز نہیں۔

ناکامی کا رویہ fail-open ہے: ٹائم آؤٹ (ڈیفالٹ 2000 ms)، نان-2xx، ناقابل رسائی ہوسٹ، خراب رسپانس یا پول سے باہر کا انتخاب `rules` کے فیصلے پر حل ہوتا ہے اور وجہ کا سابقہ `NadirStrategy: fallback (…)` ہوتا ہے۔ ناکام کال کے بعد حکمت عملی 30 سیکنڈ کے لیے نیٹ ورک کو چھوڑ دیتی ہے، لہذا آؤٹیج کی قیمت فی درخواست ایک کے بجائے ہر 30 سیکنڈ میں ایک ٹائم آؤٹ ہوتی ہے۔ روٹنگ ایونٹس صرف تب `strategy: "nadir"` رپورٹ کرتے ہیں جب Nadir نے واقعی انتخاب کیا ہو۔

**کب استعمال کریں**: ایسے پول پر مخلوط مشکل والا ٹریفک جو ماڈل ٹیرز پر محیط ہو (ایک چھوٹا، ایک درمیانہ اور ایک فرنٹیئر ماڈل)، جہاں ہمیشہ فرنٹیئر ماڈل استعمال کرنا وہ قیمت ہے جسے آپ کم کرنا چاہتے ہیں۔

**عرفی نام (Alias)**: `nadir` (کوئی عرفی نام نہیں)

### کسٹم روٹر حکمت عملیاں

آپ پبلک API کے ذریعے اپنی `RouterStrategy` امپلیمنٹیشن رجسٹر کر سکتے ہیں:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

پھر اسے استعمال کریں:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## ٹاسک کی موزونیت

6 ٹاسک اقسام (`coding`، `review`، `planning`، `analysis`، `debugging`، `documentation`) میں 30+ ماڈلز کو اسکور کیا گیا ہے۔ وائلڈ کارڈ پیٹرنز کی معاونت موجود ہے (مثلاً، `*-coder` → کوڈنگ کا بلند اسکور)۔

## خودکار ویریئنٹس کا خلاصہ

بنیادی `auto` (ڈیفالٹ) اور `autoPrefix.ts` میں اعلان کردہ 6 `AutoVariant` اقدار سمیت، **7 قابلِ استعمال ماڈل IDs** ہیں:

`auto`، `auto/coding`، `auto/fast`، `auto/cheap`، `auto/offline`، `auto/smart`، `auto/lkgp`

(`AutoVariant` بذاتِ خود 6 اقدار شمار کرتا ہے؛ ساتواں آپشن "کوئی ویریئنٹ نہیں" — بنیادی `auto` — ہے، جسے `parseAutoPrefix()`، `variant: undefined` کے طور پر ہینڈل کرتا ہے۔)

## ٹئیرز Auto-Combo میں کیسے فٹ ہوتے ہیں

16 عوامل پر مشتمل اسکورنگ فنکشن (`open-sse/services/autoCombo/scoring.ts`) ٹئیر کی
رکنیت کو دو سگنلز کے طور پر استعمال کرتا ہے: `tierPriority` (0.0476) اور `tierAffinity` (0.0476)۔ مکمل
`DEFAULT_WEIGHTS` سیٹ کے لیے اوپر دی گئی مستند [اسکورنگ عوامل کی جدول](#how-it-works-persisted-auto-combos) دیکھیں — ہر پیک کی مخصوص ترتیبات (ship-fast/cost-saver/quality-first/
offline-friendly) "ہر پیک کے لیے ویٹ پروفائلز" کی جدول میں درج ہیں۔

صرف ٹئیر کی بنیاد پر **لازماً** Tier 1 کو پہلی ترجیح نہیں دی جاتی — اگر Tier 1 کی لیٹنسی خراب ہو یا
لاگت بمقابلہ معیار غیر موزوں ہو، تو Tier 2 ترجیح حاصل کرتا ہے۔ ٹئیر کی ترتیب لازمی کرنے کے لیے، کومبو
حکمتِ عملی `priority` استعمال کریں اور فراہم کنندگان کو ٹئیر کے مطابق ترتیب دیں۔

Tier 1 (سبسکرپشن) کو بھرپور ترجیح دینے کے لیے، `tierPriority` کا ویٹ بڑھائیں:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ٹئیر کی تعریفوں اور فراہم کنندگان کی درجہ بندی کے لیے [`docs/guides/TIERS.md`](../guides/TIERS.md) دیکھیں۔

## ٹیسٹنگ اور کوریج

### قطعی روٹنگ-فیصلہ میٹرکس (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts`، فرضی اپ اسٹریم کے ساتھ حقیقی کومبو پائپ لائن کے ذریعے تمام 19
عوامی حکمتِ عملیوں کے روٹنگ **فیصلے** کو ابتدا سے انتہا تک ثابت کرتا ہے۔
کوریج میں شامل ہیں:

- تمام 19 `ROUTING_STRATEGY_VALUES` حکمتِ عملیاں (ترتیب یافتہ، وزن دار، لاگت، سیاق، فیوژن، …)۔
- `quota-share` (اندرونی) ابتدا سے انتہا تک: حقیقی `selectQuotaShareTarget` جوڑ کے ذریعے DRR کی منصفانہ تقسیم + سچوریشن پر ترجیح میں کمی (`registerQuotaFetcher` / `setLKGP` /
  `__setHeadroomSaturationFetcherForTests`)۔
- اہداف کی ہر تعداد میں `context-relay` یونیورسل-ہینڈ آف کوریج۔

یہ سویٹ CI (`test:integration` جاب) میں `--test-concurrency=1` اور
`--test-force-exit` کے ساتھ چلتا ہے، لہٰذا یہ قطعی ہے اور اسے لائیو اسناد درکار نہیں ہوتیں۔

### مشروط لائیو اسموک ٹیسٹس (CI میں نہیں — حقیقی پرووائیڈرز)

| کمانڈ                                  | یہ کیا کرتی ہے                                                                             |
| :------------------------------------- | :----------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | `RUN_COMBO_LIVE=1` کے ساتھ اِن-پروسیس حقیقی روٹنگ؛ لائیو OmniRoute DB کا اسنیپ شاٹ لیتی ہے |
| `npm run test:combo:live:vps`          | لائیو OmniRoute سرور کے خلاف HTTP کالز (`COMBO_LIVE_BASE_URL` سیٹ کریں)                    |

یہ اسموک ٹیسٹس حقیقی وائر پاتھ (کومبو → پرووائیڈر → تکمیل) کو آزماتے ہیں۔ انہیں
جان بوجھ کر CI سے خارج رکھا گیا ہے کیونکہ انہیں لائیو اسناد اور VPS رسائی درکار ہوتی ہے۔
