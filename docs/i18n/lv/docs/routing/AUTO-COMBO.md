## Automātiskā maršrutēšana bez konfigurācijas (`auto/` prefikss)

> **JAUNUMS:** Kombinācija nav jāveido. Izmantojiet `auto/` prefiksu tieši jebkurā klientā.

### Īsi piemēri

| Modeļa ID      | Variants | Darbība                                                                             |
| -------------- | -------- | ----------------------------------------------------------------------------------- |
| `auto`         | default  | Visi pievienotie nodrošinātāji, LKGP stratēģija, līdzsvaroti svari                  |
| `auto/coding`  | coding   | Uz kvalitāti orientēti svari, piemēroti koda ģenerēšanai                            |
| `auto/fast`    | fast     | Svērta atlase ar zemu latentumu                                                     |
| `auto/cheap`   | cheap    | Izmaksu ziņā optimizēta maršrutēšana (vispirms zemākās izmaksas)                    |
| `auto/offline` | offline  | Dod priekšroku nodrošinātājiem ar vislielāko pieejamo kvotu                         |
| `auto/smart`   | smart    | Prioritāte kvalitātei + lielāks izpētes koeficients (10%) labākai modeļu atklāšanai |
| `auto/lkgp`    | lkgp     | Nepārprotams LKGP (tas pats, kas noklusējuma `auto`)                                |
| `auto/chaos`   | chaos    | Paralēla izsūtīšana, viens modelis katram nodrošinātājam (nevis kļūmju injicēšana)  |

### Kategorijas × līmeņa kompozīcija (`auto/<category>:<tier>`)

OpenRouter stila sufiksi nodala **maršruta veidu** (kategoriju) no **tā optimizācijas veida** (līmeņa), tāpēc tos var brīvi kombinēt (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Kategorijas** (filtrē kandidātu kopu pēc iespējām): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` saglabā modeļus ar attēlu apstrādes iespējām; `reasoning` saglabā spriešanas/domāšanas modeļus.
- **Līmeņi** (izvēlas vērtēšanas svarus / kopas filtru): `fast` (ātra piegāde) · `cheap` (aizstājvārds `floor`, izmaksu taupīšana) · `reliable` (ķēdes pārtraucēja stāvoklis + latentuma stabilitāte) · `free` / `pro` (filtrē kopu pēc modeļa līmeņa, izmantojot `classifyTier` — bezmaksas līmenis pret premium līmeni).

| Piemērs                | Tiek atrisināts kā                                                              |
| ---------------------- | ------------------------------------------------------------------------------- |
| `auto/coding:fast`     | programmēšanas kopa, zema latentuma svari                                       |
| `auto/coding:cheap`    | programmēšanas kopa, optimizēta pēc izmaksām (aizstājvārds `auto/coding:floor`) |
| `auto/reasoning:pro`   | tikai spriešanas/domāšanas modeļi, premium līmenis                              |
| `auto/vision`          | modeļi ar attēlu apstrādes iespējām (bez līmeņa → līdzsvaroti svari)            |
| `auto/multimodal:free` | modeļi ar multimodālām iespējām, tikai bezmaksas līmenis                        |

Jebkurš derīgs `auto/<category>[:<tier>]` tiek atrisināts pēc pieprasījuma; rūpīgi atlasīta apakškopa tiek piedāvāta `/v1/models` un informācijas panelī (`AUTO_SUFFIX_VARIANTS` failā `open-sse/services/autoCombo/builtinCatalog.ts`). Filtrēšana ir **kļūmju gadījumā atvērta** — ja nevienam pievienotajam modelim ierobežojums neatbilst, tiek izmantota pilnā kopa, lai maršrutēšana nekad nepārtrūktu. Pamatvērtētājs (`combo.ts`) nav mainīts; kategorijas/līmeņa filtrs tiek lietots funkcijā `buildAutoCandidates`.

> **Aktuāla modeļu informācija:** automātiskās maršrutēšanas piemērotības novērtēšanai tiek izmantoti aktuālie **Arena ELO** reitingi un **models.dev** līmeņu dati, ja ir ieslēgts karogs `ARENA_ELO_SYNC_ENABLED` (pretējā gadījumā tiek izmantota statiskā piemērotības karte).

**Lietošana:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**Kas notiek:**

1. OmniRoute nosaka `auto/` prefiksu failā `src/sse/handlers/chat.ts`
2. No datubāzes izgūst visus **aktīvos nodrošinātāju savienojumus**
3. Atlasa savienojumus ar derīgiem akreditācijas datiem (API atslēgu vai OAuth pilnvaru)
4. Nosaka katra savienojuma modeli (`connection.defaultModel` vai nodrošinātāja pirmo modeli)
5. Atmiņā izveido **virtuālu kombināciju** (tā netiek glabāta DB)
6. Maršrutē, izmantojot izvēlētā varianta svaru profilu un LKGP stratēģiju

**Galvenās īpašības:**

- ✅ **Vienmēr ieslēgts:** Nav nepieciešams slēdzis, kombinācijas izveide vai konfigurācija
- ✅ **Dinamisks:** Automātiski atspoguļo pašlaik pievienotos nodrošinātājus
- ✅ **Sesijas piesaiste:** LKGP nodrošina, ka prioritāte tiek piešķirta pēdējam veiksmīgajam nodrošinātājam
- ✅ **Vairāku kontu atbalsts:** Katrs nodrošinātāja savienojums kļūst par atsevišķu kandidātu
- ✅ **Nav DB ierakstu:** Virtuālā kombinācija pastāv tikai pieprasījuma laikā, neradot nekādas pastāvīgas glabāšanas papildu izmaksas

### Kandidātu pārvaldība katrai atslēgai (#7819, Level 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = sufikss pēc `auto/` vai
literālā vērtība `auto` pamata kanālam) ir **tikai lasāms** galapunkts, kas uzskaita
`auto/*` kanāla pašreizējo kandidātu kopu, papildinātu ar aktuālo sasniedzamības
informāciju un atkārtoti izmantojot esošos noturības nolasījumus (nekad neapstrādāto
pārtraucēja `state`):

- nodrošinātāja ķēdes pārtraucējs — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- savienojuma gaidīšanas periods — `rateLimitedUntil` / `testStatus` atrisinātajā
  `provider_connections` rindā
- modeļa bloķēšana — `isModelLocked(provider, connectionId, model)`

Katram kandidātam ir arī šīs API atslēgas karogs `excluded`. Izņēmumi tiek glabāti
katrai API atslēgai atsevišķi (`auto_candidate_overrides` tabula, migrācija `128`) — OmniRoute ir
viena nomnieka sistēma bez `users` tabulas, tāpēc `apiKeyId` ir tuvākā reālā identitāte
katram izsaucējam — un tie tiek piemēroti kandidātu kopas kontroles punktā
`open-sse/services/autoCombo/virtualFactory.ts`, izmantojot tīro, ar vienībtestiem pārbaudīto
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Filtrs ir **kļūmju gadījumā atvērts**: neiestatīts apiKeyId/kanāls vai DB uzmeklēšanas kļūme
abos gadījumos atstāj kopu nefiltrētu, tāpēc operators bez konfigurētiem izņēmumiem saņem
maršrutēšanu, kas baitu līmenī ir identiska darbībai pirms šīs funkcijas ieviešanas.

**Atlikts uz vēlāku papildu uzdevumu:** katra kandidāta svari + skaidri noteikta secība (3. līmenis
— izmanto esošos svērto/prioritāro stratēģiju ceļus), kā arī konkrētas
`combo.ts` stratēģijas piesaiste katram `auto/*` kanālam (4. līmenis). Skatiet #7819 plānu par neatrisināto
jautājumu, vai viena nomnieka modeļa dēļ ignorēšanas iestatījumiem būtu jāpaliek katrai API atslēgai atsevišķi vai jākļūst globāliem.

**Aizkulisēs:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**Implementācijas faili:**

| Fails                                                     | Nolūks                                                   |
| --------------------------------------------------------- | -------------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Prefiksa parsētājs (`parseAutoPrefix`)                   |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Izveido virtuālus `AutoComboConfig` objektus             |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Testēšanas āķis nodrošinātāju reģistra imitēšanai        |
| `src/sse/handlers/chat.ts`                                | Integrācija: automātiskā prefiksa priekšlaicīga apstrāde |
| `src/shared/constants/providers.ts`                       | `SYSTEM_PROVIDERS.auto` sistēmas ieraksts                |

## Kombināciju nosaukumi, kas atbilst reāliem modeļa identifikatoriem

Kombinācija, kuras `name` ir identisks vienkāršam modeļa identifikatoram (piemēram, kombinācija ar nosaukumu `gpt-5.5`), ir **apzināts un atbalstīts modelis**, nevis kļūda: tas ir mehānisms katra modeļa identifikatora pakalpojumu sniedzēja rezerves risinājumam, kas aprakstīts [sadaļā #6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Tā kā kombinācijas risināšana tiek pārbaudīta pirms vienkārša modeļa identifikatora risināšanas (`getComboForModel()` failā `src/sse/services/model.ts`), pieprasījums vienkāršajam identifikatoram `gpt-5.5` tiek novirzīts caur kombinācijas mērķiem (piemēram, `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`), nevis tieši uz vienu pakalpojumu sniedzēju — tas atkārto kombinācijas-pirms-pārrakstīšanas prioritāti, kas izveidota [sadaļā #3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227), un to pārbauda regresijas testi `tests/unit/responses-combo-resolution-3227.test.ts` un `tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Kombinācijas izveidošana vai pārdēvēšana uz nosaukumu, kas pārklājas ar reālu modeļa identifikatoru, **nekad netiek noraidīta** — tā rīcība pārtrauktu šo dokumentēto darboplastu. Tā vietā (#8530) `POST /api/combos` un `PUT /api/combos/[id]` pievieno atbildei bloķējošu `warning` lauku, kad (jaunais) nosaukums pārklājas ar reālu modeļa identifikatoru:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Palaižot sistēmu, `scanComboModelNameCollisionsAtBoot()` (failā `src/instrumentation-node.ts`) arī reģistrē vienrindiņas `[STARTUP]` brīdinājumu, uzskaitot katru esošo kombināciju, kas pārklājas ar modeļa identifikatoru, lai operatori, kas to nejauši sastop (nevis apzinīgi, kā #6940 norāda), saņemtu signālu. Noteikšanas palīdzības rīks atrodas failā `src/lib/combos/modelNameCollision.ts`.

## Pielāgotas kombinācijas izsaukšana no klienta

Saglabātās kombinācijas (Iestatījumi → Kombinācijas) tiek izmantotas tikai tad, kad klients komandas laukā `model` nosūta kombinācijas **precīzo nosaukumu** — kombinācijas nosaukumam nav nepilnīgas vai daļējas atbilstības, un netiek izmantots prefikss `auto/`. Risināšanas secība (`getComboForModel()` failā `src/sse/services/model.ts`):

1. precīza kombinācijas nosaukuma atbilstība (`model: "my-combo"`),
2. `combo/<nosaukums>` prefikss (`model: "combo/my-combo"`),
3. modeļa→kombinācijas glob kartēšanas (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Divas biežās kļūdas:

- **`auto` neizmanto jūsu kombinācijas.** `auto`/`auto/*` veido savu bezkonfigurācijas kandidātu kopu un konsultējas ar saglabātajām kombinācijām tikai tad, ja kombinācijas nosaukums ir burtiski `auto` (nav ieteicams). Lai novirzītu caur kombināciju, nosūtiet tās precīzo nosaukumu — ne `auto`.
- **`openrouter/auto` ir reāls apmaksāts OpenRouter produkts** ("Auto Best Available"), nevis OmniRoute aizstājvārds. Tas ir OpenReģistra (`open-sse/config/providers/registry/openrouter/index.ts`) vienīgais statiskais modeļa ieraksts, un par to tiek atsevišķi iekasēta maksa. Lai izslēgtu to no `auto` kopām, izmantojiet Iestatījumi → Maršrutēšana → Slēgt apmaksātus modeļus.

Skatīt [sadaļu #7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) un [sadaļu #7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) par sākotnējo pārpratumu, ko šis dokuments apraksta.

## Kā tas darbojas (Saglabātie Auto-Combos)

Auto-Combo dzinējs dinamiski izvēlas labāko nodrošinātāju/modeli katram pieprasījumam, izmantojot **16 faktoru novērtēšanas funkciju** (definēta `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Noklusējuma svaru summa ir `1.0`; pielāgotos svarus renormalizē `normalizeScoringWeights()`. ### `weighted` semantika

`weighted` ir **proporcionāla nejauša izloze katram pieprasījumam**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), nevis izlīdzinātājs:

- Katrs pieprasījums izlozē **vienu** soli ar varbūtību `weight / totalWeight`; atlikušie soļi
  tiek sakārtoti pēc dilstoša svara kā rezerves ķēde šim pieprasījumam.
- Solis, kura svars ir `0` (vai trūkst), **nekad netiek izlozēts**, kamēr jebkuram citam solim ir
  svars > 0 — tas var kalpot tikai kā rezerve pēc tam, kad izlozētais solis neizdodas. Tikai tad, kad **visu**
  svars ir 0, izvēle kļūst vienmērīga.
- Soļi, kuru mērķi nav pieejami — pakalpojumu sniedzēja ķēdes pārtraucējs `OPEN`,
  savienojuma dzesēšanas periods, modeļa bloķēšana — tiek noņemti no izlozes pirms tās sākuma
  (`open-sse/services/combo/targetResolution.ts`), tāpēc viens veselīgs solis var īslaicīgi
  uzvarēt katrā pieprasījumā.
- `stickyWeightedLimit` (combo konfigurācija, noklusējums `1` = izslēgts) piesaista izlozēto soli tik daudz secīgiem panākumiem pirms atkārtotas izlozes.

Lai nodrošinātu stingru rotāciju, izmantojiet `round-robin`; vienādi svari `weighted` režīmā nodrošina statistisku — nevis stingru — līdzsvaru.

### Aģentu konveijera (pipeline) režīms

`pipeline` kombinācija ar vismaz diviem modeļiem var izvēlēties plānotāja/izpildītāja maršrutēšanu, izmantojot `config.agenticOrchestration.enabled`. Pirmais mērķis veic plānošanu un sniedz galīgās atbildes; otrais mērķis izsauc klienta vietējos rīkus (tool calls). OmniRoute nosaka rīka rezultātu turpinājumus no pieprasījuma protokola, jautā plānotājam, vai ir nepieciešams vēl viens rīka izsaukuma cikls, un dinamiski padara vai nu izpildītāju, vai plānotāju par klientam redzamo pēdējo soli.

Izvēles `config.agenticOrchestration.contextCompaction` piemēro atsevišķu datu apjoma (payload) budžetu pirms katras plānotāja vai izpildītāja nosūtīšanas. Iespējojiet to nepārprotami:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

Šie ir operatora izvēlēti serializēti JSON rakstzīmju budžeti, nevis marķieru (token) konteksta logi vai garantēti augšupējie limiti. Precīzi modeļu ID ignorē noklusējuma iestatījumus. Virs sliekšņa kompaktēšana noņem identiskus rīku definējumus, apgriež pārāk lielus rīku pierādījumus ar kopsavilkumu (digest) un noņem vecas pilnīgas vēstures grupas, lai sasniegtu mērķa attiecību. Tā saglabā sistēmas/izstrādātāja instrukcijas, jaunāko lietotāja pieprasījumu, pēdējo rīku ciklu, ieskaitot paralēlos izsaukumus/rezultātus, un Gemini vadošo maršrutēšanas instrukciju. Augstākā līmeņa instrukcijas un rīku iestatījumi tiek saglabāti. Izlaišanas marķieris reģistrē noņemto vēsturi; šī ir deterministiska apgriešana, nevis semantisks kopsavilkums. Ja piespraustais (pinned) konteksts joprojām pārsniedz budžetu, pieprasījums atgriež 413 pirms sazināšanās ar modeli. Ja kompaktēšana ir atspējota vai ja tas ir zem sliekšņa, pieprasījums tiek izlaists cauri nemainīts.

Papildu modeļi pēc otrā mērķa ir sakārtoti izpildītāja dublējumi. Neveiksmīga HTTP atbilde vai transporta izņēmums pāriet uz nākamo izpildītāju, pārnesot to pašu plānotāja lēmumu un vietējos rīkus, bet izmantojot šī izpildītāja paša soļa uzvedni (prompt) un atrisināto savienojumu. Pirmā veiksmīgā atbilde tiek atgriezta nemainīta, ieskaitot SSE straumēšanu; kļūdas pēc veiksmīgas straumes sākuma šeit nevar tikt mēģinātas atkārtoti. Ja visi izpildītāji neizdodas, tiek atgriezta pēdējā kļūda. Klienta pārtraukumi aptur nosūtīšanu.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Izpildītājs vienā atbildē var izsūtīt vairākus neatkarīgus izsaukumus. Atkarīgie izsaukumi tiek apstrādāti vēlākos klienta rīka rezultātu pagriezienos, plānotājam pārskatot katru rezultātu. `maxToolRounds` noklusējuma vērtība ir `8`, un tas pieņem vērtības no `1` līdz `32`; kad šis limits ir sasniegts, plānotājam ir jāsniedz labākā pieejamā galīgā atbilde. Iekšējie plānotāja lēmumi tiek buferēti, savukārt izvēlētā klientam redzamā atbilde saglabā sākotnējo straumēšanas preferenci.

### `round-robin` "lipīgā" (sticky) pakešu apstrāde un konta paplašināšana

Round-robin ir pakešu veidā, nevis viens pieprasījums uz soli:

- `stickyRoundRobinLimit` (kombinācijas konfigurācija, tad `comboStickyRoundRobinLimit`, tad `settings.stickyRoundRobinLimit`, noklusējums **3**) saglabā to pašu mērķi tik daudziem secīgiem panākumiem pirms rotācijas. Iestatiet kombinācijas ignorēšanu (override) uz `1` vienas pieprasījuma rotācijas veikšanai. Kombināciju redaktors parāda efektīvo vērtību un to, no kura slāņa tā nākusi.
- `connectionAwareExpansion` (kombinācijas konfigurācija, tad iestatījumi, noklusējums **false**) paplašina katru pakalpojumu sniedzēja līmeņa soli uz mērķiem katram kontam pirms rotācijas. B grupas stratēģijas (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) saglabā pakalpojumu sniedzēja līmeņa skatu, līdz šis ir ieslēgts. Kombināciju redaktors atklāj inherit / on / off; inherit izmanto globālo noklusējumu (off).
- Prompt-cache lokalitātes maršrutēšana (`promptCacheAffinityEnabled`, noklusējums **true**) pārkārto piespraustos savienojumus tā, lai atbilstošās kešatmiņas atslēgas paliktu vienā kontā. Tai ir prioritāte pār round-robin un weighted rotāciju starp piespraustiem soļiem katram kontam. Izslēdziet to sadaļā Settings → Combo defaults, ja jums ir nepieciešama stingra rotācija. Nav iespējams ignorēt iestatījumus katrai kombinācijai atsevišķi.

Daudzkontu rotācijai vienā modelī dodiet priekšroku **vienam dinamiskā konta solim** (tukšs `connectionId`, viss kopums) ar "lipīgo" limitu `1`, nevis trim piespraustiem `connectionId`. Piespraustie soļi kopā ar afinitāti (affinity) saplūst uz to pašu kontu, pat kamēr RR skaitītājs virzās uz priekšu.

## Fusijas stratēģija

`fusion` ir vienīgā stratēģija, kas **neizvēlas vienu mērķi**. Tā vienlaikus izplata pieprasījumu
**visām paneļa modeļiem paralēli**, pēc tam konfigurējams **tiesnesis模型is** sintezē
vienīgo galīgo atbildi no visām paneļa atbildēm. Portēts no augšējā līmeņa `decolua/9router`
(OpenRouter Fusijas dizains); implementācija `open-sse/services/fusion.ts`.

Kā tas darbojas:

0. **Rīku nesēju apietšana** — pieprasījums, kas satur nepukstošu `tools` masīvu ar
   `tool_choice`, kas nav skaidri norādīts `"none"`, pilnībā izlaiž paneli: tas tieši novirzās uz
   vienu modeli (konfigurēto tiesnesi vai `panel[0]`) ar `tools`/`tool_choice`
   nemainīti nodotiem. Paneļa dalībniekiem nav piekļuves rīkiem, un tiesnesa sintēzes
   direktīja attur no rīku izsaukumu ģenerēšanas, tāpēc aģentu/rīku izsaukumu klienti
   saņem īstu rīku izsaukuma lēmumu, nevis sintezētu prozu (#6771).
1. **Izplatīšana** (tikai pieprasījumiem bez rīkiem) — pieprasījums tiek nosūtīts uz katru paneļa
   modeli uzreiz, ar piespiedu nestreamingu un izņemtiem rīkiem (tiesnesim vajag pilnu
   prozu sintēzei).
2. **Kvorumā žēlastības savākšana** — tiklīdz ir saņemtas `minPanel` atbildes, sākas
   īsa žēlastības taimerīša gaidīšana novēlošanām, pēc tam fusija turpinās ar visu, kas savākts.
   Tas ierobežo lēnākā modeļa sodu par faktisko laiku, ar cieto taimautu kā robežu.
3. **Tiesnesa sintēze** — paneļa atbildes tiek anonimizētas (`Avots 1`, `Avots 2`, … — lai
   tiesnesis vērtētu saturu, nevis modeļa zīmolu) un nodotas tiesnesim, kas analizē
   vienprātības / pretrunas / daļēju pārklājumu / unikālās atziņas / neredzamās vietas, pēc tam
   uzraksta **vienīgo** autoritatīvo atbildi. Tiesnesa izsaukums saglabā klienta sākotnējo
   `stream` karogu + rīkus, tāpēc straumēšana un lejupējā rīku izmantošana joprojām darbojas.
4. **Vienmērīga degradācija** — 0 paneļa atbildes → `503`; tieši 1 izdzīvotājs → tā atbilde
   tiek atgriezta tieši (nav nekā ko sintezēt); viena modeļa panelis atbild tieši.

Paneļa dalībnieks var būt arī `combo-ref` solis (`{kind: "combo-ref", comboName: "..."}`), kas atsaucas
uz citu kombināciju — tas tiek atrisināts kā **viens melnā kastes paneļa balss** (pilna rekursīva nosūtīšana uz
atsaukto kombināciju, nevis šīs kombinācijas pašu mērķu izplatīšana), ar vienādu dziļuma/cikla aizsardzību,
kādu izmanto jebkura cita stratēģija, kas patērē combo-ref (#6764).

### Konfigurācija

Konfigurēts kombinācijas `config` blobā (nav shēmas migrācijas — tas atkārtoti izmanto esošo
`combos` tabulu):

## Virtuālā Auto-Kombināciju Fabrika

Auto Kombināciju dzinējam nav nepieciešamas iepriekš definētas kombinācijas. Tā vietā `open-sse/services/autoCombo/virtualFactory.ts` veido kandidātus dinamiski:

1. Iegūst `getProviderConnections({ isActive: true })` (visas aktivētās savienojumus)
2. Filtrē pēc derīgiem akreditācijas datiem (API atslēga vai nebeidzis OAuth tokens, izmantojot `hasUsableOAuthToken()`)
3. Krustodzēš ar `getProviderRegistry()`, lai iegūtu modeļu pieejamību + cenu noteikšanu
4. Katram kopa `(provider, model, connection)` izveido `VirtualAutoComboCandidate`
5. Izvēlas `connection.defaultModel` (vai reģistra pirmo modeli) kā izsūtīšanas mērķi
6. Vērtē katru kandidātu, izmantojot 16 faktoru `scorePool()` un varianta svaru pakotni
7. Atgriež rezultātā iegūto atmiņā esošo `AutoComboConfig` priekš `handleComboChat()` — nekad netiek saglabāts datubāzē

Tas nozīmē, ka **jauna pakalpojumu sniedzēja pievienošana ar `auto/*` iespējotu automātiski paplašina kandidātu kopienu** — nav nepieciešama manuāla kombināciju rediģēšana. Virtuālā kombinācija tiek pārbūvēta katram pieprasījumam, tāpēc jaunpievienotie vai jaunā veselības stāvokļa savienojumi tiek iekļauti uzreiz.

## Pašdziedināšanās

- **Pagaidu izslēgšana**: Vērtējums < 0.2 → izslēgts uz 5 minūtēm (progresīva atkāpšanās, maks. 30 min)
- **Apļa pārtraucēja apzināšanās**: ATVĒRTS → automātiski izslēgts; PUSATVĒRTS → izmeklēšanas pieprasījumi
- **Incidenta režīms**: >50% ATVĒRTS → atspējot izpēti, maksimizēt stabilitāti
- **Atdzišanas atgūšana**: Pēc izslēgšanas pirmais pieprasījums ir "izmeklēšana" ar samazinātu taimautu

## Bandītu izpēte

5% pieprasījumu (konfigurējams) tiek novirzīti uz nejaušiem pakalpojumu sniedzējiem izpētei. Atspējots incidenta režīmā.

## API

Nav **īpaša `POST /api/combos/auto` galapunkta** — Auto-Combo tiek izmantots divos veidos:

1. **Zero-config (ieteicams):** Nosūtiet jebkuru tērzēšanas pabeigšanas pieprasījumu ar `model: "auto"` vai `model: "auto/<variant>"`. Virtuālā rūpnīca izveido kombināciju katram pieprasījumam — nav nepieciešama saglabāšana vai API izsaukumi.

2. **Saglabāta kombinācija ar `strategy: "auto"`:** Izveidojiet parastu kombināciju, izmantojot `POST /api/combos`, un iestatiet `strategy: "auto"`, kā arī `config.auto.weights` / `config.auto.candidatePool`. Tiek izmantots tas pats vērtēšanas dzinējs; kombinācija tiek saglabāta `combos` un ir atkārtoti izmantojama pēc ID.

Lai veiktu atklāšanu, `GET /api/combos/auto` uzskaita katru variantu ar tā atrisināto kandidātu kopu, kā arī `context_length` / `max_output_tokens` — MAKSIMĀLO vērtību visos kandidātu kopas logos. Klientiem (piemēram, opencode spraudnim) ir jāreklamē šīs vērtības, nevis `0`: nulle kontekstā pilnībā atspējo opencode automātisko saspiešanu, ļaujot sesijām augt, līdz vārtejas vēstures tīrīšana iznīcina kontekstu. MAKSIMĀLO vērtību ir droši reklamēt, jo auto-combo konteksta iepriekšējais filtrs novirza pārāk lielus pieprasījumus uz kandidātiem ar lieliem logiem.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto maršrutētāja stratēģijas

Saglabātās `strategy: "auto"` kombinācijas var iestatīt `config.routerStrategy` (vai mantoto `config.auto.routerStrategy`) uz vienu no:

- `rules` — noklusējuma svērtā vērtēšana
- `score` — atlasa augstāko konfigurēto svērto punktu skaitu. Precīzi neizšķirti saglabā konfigurēto kandidātu secību; esošais `explorationRate` veic izlasi no pilnas sarindotās kopas.
- `cost` / `eco` — lētākais veselīgais pakalpojumu sniedzējs
- `latency` / `fast` — zemākā p95 latentums ar uzticamības sodu
- `sla-aware` / `sla` — dod priekšroku kandidātiem, kas atbilst p95 latentuma, kļūdu līmeņa un izvēles izmaksu SLO
- `lkgp` — vispirms pēdējais zināmais labais pakalpojumu sniedzējs
- `nadir` — jautāt [Nadir](https://getnadir.com) lēmumu API, kurš modelis kopā ir nepieciešams uzvednei; izvēles iespēja, kļūmes gadījumā atgriežas pie `rules`

### Maršrutētāja stratēģijas detalizēti

Auto-combo dzinējs piedāvā 7 pievienojamas **RouterStrategy** ieviešanas, kuras varat mainīt, izmantojot `config.routerStrategy` (vai mantoto `config.auto.routerStrategy`). Katra stratēģija izvēlas vienu pakalpojumu sniedzēju no kandidātu kopas, ņemot vērā `RoutingContext` (uzdevuma veids, rīku/redzes mājieni, žetonu aprēķins, izvēles SLA politika, izvēles pēdējais zināmais labais pakalpojumu sniedzējs).

#### 1. `rules` (noklusējums) — 16 faktoru svērtā vērtēšana

Ietver esošo vērtēšanas dzinēju. Filtrē `OPEN` ķēdes pārtraucēja kandidātus, pēc tam palaiž `scorePool()` ar pašreizējo uzdevuma veidu un `getTaskFitness()`, izvēloties visaugstāk novērtēto pakalpojumu sniedzēju.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Kad izmantot**: Noklusējums. Izmantojiet, kad vēlaties līdzsvarotu kompromisu starp visiem signāliem.

**Aizstājvārds**: `rules` (nav aizstājvārda)

---

#### 2. `cost` / `eco` — lētākais veselīgais pakalpojumu sniedzējs

Kārto kandidātu kopu pēc `costPer1MTokens` (augošā secībā) un izvēlas lētāko. Vispirms filtrē `OPEN` kandidātus.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kad izmantot**: Izmaksu ziņā jutīgas darba slodzes, pakešapstrāde vai fona darbi.

**Aizstājvārdi**: `cost`, `eco`

---

#### 3. `latency` / `fast` — zemākā p95 latentums ar uzticamības sodu

Kārto pēc `p95LatencyMs + (errorRate * 1000)`. Kļūdu līmeņa sods nodrošina, ka neuzticami pakalpojumu sniedzēji tiek sarindoti zemāk, pat ja to nominālais latentums ir zems.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kad izmantot**: Latentuma ziņā jutīgas darba slodzes, piemēram, reāllaika tērzēšana, automātiskā pabeigšana vai interaktīvi kodēšanas palīgi.

**Aizstājvārdi**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latentuma/kļūdu/izmaksu SLO atbilstība

Novērtē katru kandidātu pēc tā, cik labi tas atbilst konfigurētajai SLO politikai:

| Faktors               | Svars | Formula                                               |
| --------------------- | ----- | ----------------------------------------------------- |
| Latentuma rādītājs    | 35%   | `threshold / max(value, ε)`                           |
| Kļūdu rādītājs        | 35%   | `threshold / max(value, ε)`                           |
| Veselības rādītājs    | 15%   | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)     |
| Izmaksu rādītājs      | 10%   | `threshold / max(value, ε)` vai apgriezti normalizēts |
| Stabilitātes rādītājs | 5%    | apgriezta normalizēta latentuma standartnovirze       |

Kad `hardConstraints: true`, kandidāti tiek kārtoti galvenokārt pēc **pārkāpumu rādītāja**
(cik lielā mērā tie pārsniedz jebkuru SLO), pēc tam pēc kopējā rādītāja. Pretējā gadījumā tas ir tikai
kopējais rādītājs.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA lauki** (iestatīti kombinētajā konfigurācijā):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Kad izmantot**: Produkcijas darba slodzes ar stingriem latentuma, kļūdu līmeņa vai izmaksu budžetiem.

**Aizstājvārdi**: `sla-aware`, `sla`

---

#### 5. `lkgp` — vispirms pēdējais zināmais labais pakalpojumu sniedzējs

Vispirms mēģina izmantot **pēdējo zināmo labo pakalpojumu sniedzēju** (ja iestatīts), pēc tam atgriežas pie
`rules` stratēģijas. Noderīgi sesijas noturībai — viens un tas pats pakalpojumu sniedzējs apstrādā
turpmākos pieprasījumus sarunā.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**Kad izmantot**: Vairāku pagriezienu sarunas, kurās vēlaties, lai viens un tas pats pakalpojumu sniedzējs apstrādātu
turpmākos pieprasījumus (piemēram, kešatmiņai, konteksta nepārtrauktībai vai cenu konsekvencei).

**Aizstājvārds**: `lkgp` (nav aizstājvārda)

---

#### 6. `nadir` — uz uzvedni balstīta modeļa izvēle, izmantojot Nadir

Katra iepriekš minētā stratēģija sarindo kandidātus pēc savas telemetrijas; neviena no tām nelasa
pieprasījumu. `nadir` nosūta pēdējo lietotāja pagriezienu un kopas modeļu ID uz
[Nadir](https://getnadir.com) lēmumu API (`POST /v1/bucket`) un novirza uz modeli, ko
Nadir izvēlas no šīs izvēlnes (`simple` → lētākais spējīgais modelis, `complex` → progresīvākais modelis).
Savienojumu, kas apkalpo šo modeli, joprojām izvēlas `rules`, tāpēc kvota, veselība un izmaksas turpina
noteikt, kurš konts tiks izmantots.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` un `OMNIROUTE_NADIR_BASE_URL` ir vides mainīgo rezerves varianti šīm divām
virknēm. `baseUrl` ir nepieciešams tikai pašmitinātam Nadir (beigu `/v1` tiek pieļauts).
Zvani bez atslēgas nonāk Nadir anonīmajā līmenī, kuram ir ātruma ierobežojums uz IP adresi.

Kas tiek nosūtīts: pēdējā lietotāja ziņojuma teksts (pirmās 16k rakstzīmes), kandidātu modeļu ID un
`source: "omniroute"` kanāla tags. Nav sistēmas uzvednes, vēstures, rīku vai galveņu.

Kļūmes uzvedība ir fail-open: noildze (noklusējuma 2000 ms), non-2xx atbilde, nesasniedzams resursdators,
nepareizi formatēta atbilde vai izvēle ārpus kopas tiek atrisināta ar `rules` lēmumu, un iemeslam tiek
pievienots prefikss `NadirStrategy: fallback (…)`. Pēc neveiksmīga zvana stratēģija izlaiž tīklu uz 30 sekundēm,
tāpēc darbības pārtraukums izmaksā vienu noildzi ik pēc 30 sekundēm, nevis vienu uz katru pieprasījumu.
Maršrutēšanas notikumi ziņo `strategy: "nadir"` tikai tad, kad Nadir faktiski izdarīja izvēli.

**Kad izmantot**: jaukta sarežģītības līmeņa trafika kopā, kas aptver modeļu līmeņus (mazs, vidējs un
progresīvs modelis), kur vienmēr-progresīvs ir izmaksas, kuras vēlaties samazināt.

**Aizstājvārds**: `nadir` (nav aizstājvārda)

### Pielāgotas maršrutētāja stratēģijas

Jūs varat reģistrēt savu `RouterStrategy` ieviešanu, izmantojot publisko API:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

Pēc tam izmantojiet to:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

Ieskaitot tukšo `auto` (noklusējuma) un 6 `AutoVariant` vērtības, kas deklarētas `autoPrefix.ts`, kopā ir **7 izsaucamu modeļu ID**:

## Kā līmeņi iekļaujas Auto-Combo

16 faktoru vērtēšanas funkcija (`open-sse/services/autoCombo/scoring.ts`) līmeņa
piederību izmanto kā divus signālus: `tierPriority` (0.0476) un `tierAffinity` (0.0476). Pilnu
`DEFAULT_WEIGHTS` kopu skatiet iepriekš esošajā kanoniskajā [vērtēšanas faktoru tabulā](#how-it-works-persisted-auto-combos) —
atsevišķu pakotņu pārrakstījumi (ship-fast/cost-saver/quality-first/
offline-friendly) ir norādīti tabulā "Svaru profili katrai pakotnei".

Līmenis pats par sevi **nenodrošina**, ka 1. līmenis būs pirmais — ja 1. līmeņa latentums ir pārāk liels vai
izmaksu un kvalitātes attiecība nav optimāla, uzvar 2. līmenis. Lai uzspiestu līmeņu secību, izmantojiet kombinācijas
stratēģiju `priority` un sakārtojiet nodrošinātājus pēc līmeņa.

Lai izteikti dotu priekšroku 1. līmenim (abonementam), palieliniet `tierPriority` svaru:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Līmeņu definīcijas un nodrošinātāju klasifikāciju skatiet failā [`docs/guides/TIERS.md`](../guides/TIERS.md).
