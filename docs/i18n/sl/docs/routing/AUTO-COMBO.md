## Samodejno usmerjanje brez konfiguracije (predpona `auto/`)

> **NOVO:** Ustvarjanje kombinacij ni potrebno. Predpono `auto/` uporabite neposredno v katerem koli odjemalcu.

### Hitri primeri

| ID modela      | Različica | Delovanje                                                                           |
| -------------- | --------- | ----------------------------------------------------------------------------------- |
| `auto`         | privzeto  | Vsi povezani ponudniki, strategija LKGP, uravnotežene uteži                         |
| `auto/coding`  | coding    | Uteži s prednostjo kakovosti, primerno za ustvarjanje kode                          |
| `auto/fast`    | fast      | Utežena izbira z nizko zakasnitvijo                                                 |
| `auto/cheap`   | cheap     | Stroškovno optimizirano usmerjanje (najprej najnižji strošek)                       |
| `auto/offline` | offline   | Daje prednost ponudnikom z največjo razpoložljivostjo kvote                         |
| `auto/smart`   | smart     | Prednost kakovosti + višja stopnja raziskovanja (10 %) za boljše odkrivanje modelov |
| `auto/lkgp`    | lkgp      | Izrecni LKGP (enako kot privzeti `auto`)                                            |
| `auto/chaos`   | chaos     | Vzporedna razpršitev, en model na ponudnika (ne gre za vnašanje napak)              |

### Sestava kategorije × ravni (`auto/<category>:<tier>`)

Pripone v slogu OpenRouter ločujejo **vrsto poti** (kategorijo) od **načina njene optimizacije** (ravni), zato jih lahko poljubno sestavljate (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **Kategorije** (filtriranje nabora kandidatov glede na zmožnosti): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` ohranita modele, ki podpirajo vid; `reasoning` ohrani modele za sklepanje/razmišljanje.
- **Ravni** (izbira uteži ocenjevanja oziroma filtra nabora): `fast` (hitro pošiljanje) · `cheap` (vzdevek `floor`, varčevanje s stroški) · `reliable` (stanje odklopnika + stabilnost zakasnitve) · `free` / `pro` (filtriranje nabora glede na raven modela prek `classifyTier` — brezplačna raven v primerjavi s premijsko).

| Primer                 | Razreši se v                                                                 |
| ---------------------- | ---------------------------------------------------------------------------- |
| `auto/coding:fast`     | nabor za programiranje, uteži z nizko zakasnitvijo                           |
| `auto/coding:cheap`    | nabor za programiranje, stroškovno optimiziran (vzdevek `auto/coding:floor`) |
| `auto/reasoning:pro`   | samo modeli za sklepanje/razmišljanje, premijska raven                       |
| `auto/vision`          | modeli, ki podpirajo vid (brez ravni → uravnotežene uteži)                   |
| `auto/multimodal:free` | modeli z večmodalnimi zmožnostmi, samo brezplačna raven                      |

Vsak veljaven `auto/<category>[:<tier>]` se razreši na zahtevo; skrbno izbran podnabor je objavljen v `/v1/models` in na nadzorni plošči (`AUTO_SUFFIX_VARIANTS` v `open-sse/services/autoCombo/builtinCatalog.ts`). Filtriranje je **odporno na neuspeh** — če omejitev ne ustreza nobenemu povezanemu modelu, se uporabi celoten nabor, tako da se usmerjanje nikoli ne prekine. Jedrni ocenjevalnik (`combo.ts`) ostane nespremenjen; filter kategorije/ravni se uporabi v `buildAutoCandidates`.

> **Podatki o modelih v živo:** primernost samodejnega usmerjanja določajo sprotne lestvice **Arena ELO** in podatki o ravneh iz **models.dev**, ko je zastavica `ARENA_ELO_SYNC_ENABLED` vključena (sicer se uporabi statični zemljevid primernosti).

**Uporaba:**

```bash
# Any IDE or CLI tool that supports OpenAI format
Base URL: http://localhost:20128/v1
API Key:  <your-endpoint-key>

# In your code/config, set model to:
model: "auto"                 # balanced default
model: "auto/coding"          # best for coding tasks
model: "auto/fast"            # fastest available
model: "auto/cheap"           # cheapest per token
```

**Kaj se zgodi:**

1. OmniRoute zazna predpono `auto/` v `src/sse/handlers/chat.ts`
2. V zbirki podatkov poišče vse **aktivne povezave ponudnikov**
3. Omeji jih na povezave z veljavnimi poverilnicami (ključ API ali žeton OAuth)
4. Določi model za vsako povezavo (`connection.defaultModel` ali prvi model ponudnika)
5. V pomnilniku zgradi **navidezno kombinacijo** (ni shranjena v zbirki podatkov)
6. Usmerja z uporabo profila uteži izbrane različice in strategije LKGP

**Ključne lastnosti:**

- ✅ **Vedno vklopljeno:** Preklop, ustvarjanje kombinacij ali konfiguracija niso potrebni
- ✅ **Dinamično:** Samodejno odraža trenutno povezane ponudnike
- ✅ **Lepljivost seje:** LKGP zagotavlja, da ima zadnji uspešni ponudnik prednost
- ✅ **Podpora za več računov:** Vsaka povezava ponudnika postane ločen kandidat
- ✅ **Brez zapisov v zbirko podatkov:** Navidezna kombinacija obstaja samo za zahtevo, brez dodatnih stroškov trajnega shranjevanja

### Nadzor kandidatov za posamezni ključ (#7819, raven 1+2)

`GET /v1/auto-combo/{channel}/candidates` (`{channel}` = pripona za `auto/` ali
dobesedni `auto` za osnovni kanal) je končna točka **samo za branje**, ki prikaže
trenutni nabor kandidatov kanala `auto/*`, dopolnjen s sprotnimi podatki o dosegljivosti,
pri čemer ponovno uporabi obstoječe odčitke odpornosti (nikoli neobdelanega `state`
odklopnika):

- odklopnik ponudnika — `getCircuitBreaker(provider).getStatus()` / `.canExecute()`
- obdobje mirovanja povezave — `rateLimitedUntil` / `testStatus` v razrešeni vrstici
  `provider_connections`
- blokada modela — `isModelLocked(provider, connectionId, model)`

Vsak kandidat vsebuje tudi zastavico `excluded` tega ključa API. Izključitve so shranjene
za posamezni ključ API (tabela `auto_candidate_overrides`, migracija `128`) — OmniRoute
je rešitev za enega najemnika brez tabele `users`, zato je `apiKeyId` najbližja dejanska
identiteta posameznega klicatelja — in se uveljavljajo na zožitveni točki nabora kandidatov v
`open-sse/services/autoCombo/virtualFactory.ts` prek čiste, z enotnimi testi preizkušene funkcije
`filterExcludedCandidates()` (`open-sse/services/autoCombo/candidateOverrides.ts`).
Filter je **odporen na neuspeh**: nenastavljen apiKeyId/kanal ali neuspešno iskanje v zbirki podatkov
pustita nabor nefiltriran, zato skrbnik brez konfiguriranih preglasitev vidi usmerjanje,
ki je na ravni bajtov povsem enako kot pred uvedbo te funkcije.

**Preloženo na nadaljnjo težavo:** uteži posameznih kandidatov + izrecno razvrščanje (3. raven
— vključuje se v obstoječe poti strategij uteževanja/prednosti) in pripenjanje določene
strategije `combo.ts` posameznemu kanalu `auto/*` (4. raven). Glejte načrt #7819 glede odprtega
vprašanja, ali naj preglasitve glede na model z enim najemnikom ostanejo vezane na posamezni ključ API ali postanejo globalne.

**V ozadju:**

```txt
Request: { model: "auto/coding" }
   ↓
src/sse/handlers/chat.ts detects prefix
   ↓
createVirtualAutoCombo('coding') → candidatePool from active connections
   ↓
handleComboChat (same engine as persisted combos)
   ↓
Auto-scoring selects best provider/model per request
```

**Datoteke implementacije:**

| Datoteka                                                  | Namen                                               |
| --------------------------------------------------------- | --------------------------------------------------- |
| `open-sse/services/autoCombo/autoPrefix.ts`               | Razčlenjevalnik predpone (`parseAutoPrefix`)        |
| `open-sse/services/autoCombo/virtualFactory.ts`           | Ustvari navidezne objekte `AutoComboConfig`         |
| `open-sse/services/autoCombo/providerRegistryAccessor.ts` | Testna kljuka za simuliranje registra ponudnikov    |
| `src/sse/handlers/chat.ts`                                | Integracija: takojšnja obravnava samodejne predpone |
| `src/shared/constants/providers.ts`                       | Sistemski vnos `SYSTEM_PROVIDERS.auto`              |

## Imena kombinacij, ki se ujemajo z dejanskim ID-jem modela

Kombinacija, katere `name` je enak samostojnemu ID-ju modela (npr. kombinacija z imenom
`gpt-5.5`), je **nameren in podprt vzorec**, ne napaka: to je
mehanizem za nadomestnega ponudnika za posamezen ID modela, dokumentiran v
[#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940). Ker se
razreševanje kombinacij preveri pred razreševanjem samostojnega ID-ja modela
(`getComboForModel()` v `src/sse/services/model.ts`), je zahteva za samostojni
ID `gpt-5.5` usmerjena prek ciljev kombinacije (npr.
`acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) namesto neposredno k
enemu ponudniku — s tem se ponovno uporabi prednost kombinacije pred prepisovanjem, uvedena za
[#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227), delovanje pa je
regresijsko preizkušeno v `tests/unit/responses-combo-resolution-3227.test.ts` in
`tests/unit/combo-name-codex-responses-rewrite.test.ts`.

Ustvarjanje ali preimenovanje kombinacije v ime, ki prekriva dejanski ID modela,
**ni nikoli zavrnjeno** — zavrnitev bi prekinila ta dokumentirani potek dela. Namesto tega
(#8530) `POST /api/combos` in `PUT /api/combos/[id]` odgovoru dodata neblokirajoče
polje `warning`, kadar je (novo) ime v navzkrižju z dejanskim
ID-jem modela:

```json
{ "warning": { "code": "COMBO_NAME_SHADOWS_MODEL", "modelId": "gpt-5.5", "providerId": "openai" } }
```

Ob zagonu `scanComboModelNameCollisionsAtBoot()`
(`src/instrumentation-node.ts`) prav tako zabeleži enovrstično opozorilo `[STARTUP]`,
ki našteje vse obstoječe kombinacije, ki prekrivajo ID modela, tako da imajo upravljavci,
ki to povzročijo pomotoma (in ne namerno, kot je opisano v #6940), na voljo opozorilni signal.
Pomožna funkcija za zaznavanje je v `src/lib/combos/modelNameCollision.ts`.

## Klicanje kombinacije po meri iz odjemalca

Shranjene kombinacije (Nastavitve → Kombinacije) se uporabijo samo, kadar odjemalec v polju `model` pošlje **točno ime** kombinacije — mehko ali delno ujemanje imena kombinacije ni podprto, prav tako ni vključena predpona `auto/`. Vrstni red razreševanja (`getComboForModel()` v `src/sse/services/model.ts`):

1. natančno ujemanje z imenom kombinacije (`model: "my-combo"`),
2. predpona `combo/<name>` (`model: "combo/my-combo"`),
3. preslikave model→kombinacija z vzorci glob (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

Dve pogosti pasti:

- **`auto` ne uporablja vaših kombinacij.** `auto`/`auto/*` ustvari lasten nabor kandidatov brez potrebe po konfiguraciji in shranjene kombinacije upošteva samo, če je kombinacija dobesedno poimenovana `auto` (ni priporočljivo). Za usmerjanje prek kombinacije pošljite njeno točno ime — ne `auto`.
- **`openrouter/auto` je dejanski plačljivi izdelek OpenRouter** (»Auto Best Available«), ne vzdevek OmniRoute. Je edini statični vnos modela v registru OpenRouter (`open-sse/config/providers/registry/openrouter/index.ts`) in se obračunava ločeno. Če ga želite izključiti iz naborov `auto`, uporabite Nastavitve → Usmerjanje → Skrij plačljive modele.

Za prvotno zmedo, ki jo ta dokumentacija pojasnjuje, glejte [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) in [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111).

## Kako deluje (Persisted Auto-Combos)

Pogon Auto-Combo dinamično izbere najboljšega ponudnika/model za vsako zahtevo z uporabo **funkcije točkovanja s 16 dejavniki** (opredeljene v `open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS`). Dva od šestnajstih — `cacheAffinity` in `resetWindowAffinity` — imata privzeto utež `0`; `reliability` ima `0` v `DEFAULT_WEIGHTS`, vendar `0.03` v generičnih paketih in `0.04` v `reliability-first`, `quality` pa ima `0.02` v paketih (`0.03` v `quality-first`): še vedno se izračunavata za vsakega kandidata, `cacheAffinity` pa nadzoruje deduplikacijo predpomnilnika pozivov (prompt-cache) zunaj točkovanja, zato dejavniki s privzeto vrednostjo nič preprosto ne glasujejo privzeto, medtem ko paketi glasujejo.

### Semantika `weighted`

`weighted` je **sorazmerno naključno žrebanje na zahtevo**
(`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), ne izenačevalnik:

- Vsaka zahteva izžreba **en** korak z verjetnostjo `weight / totalWeight`; preostali koraki
  so razvrščeni po padajoči uteži kot nadomestna veriga za to zahtevo.
- Korak, katerega utež je `0` (ali manjka), **ni nikoli izžreban**, dokler ima kateri koli drug korak
  utež > 0 — služi lahko le kot nadomestek, potem ko izžrebani korak odpove. Šele ko so **vse**
  uteži 0, postane izbira enakomerna.
- Koraki, katerih cilji so nedostopni — prekinjevalec tokokroga ponudnika `OPEN`, ohlajanje povezave,
  zaklepanje modela — se pred žrebanjem odstranijo
  (`open-sse/services/combo/targetResolution.ts`), zato lahko en sam zdrav korak začasno
  zmaga pri vsaki zahtevi.
- `stickyWeightedLimit` (combo konfiguracija, privzeto `1` = izklopljeno) pripne izžrebani korak za toliko
  zaporednih uspehov, preden ponovno žreba.

Za strogo rotacijo uporabite `round-robin`; enake uteži pri `weighted` zagotavljajo statistično — ne strogo — ravnovesje.

### Način agentic pipeline

Kombinacija `pipeline` z vsaj dvema modeloma se lahko odloči za usmerjanje načrtovalec/izvajalec s `config.agenticOrchestration.enabled`. Prvi cilj upravlja načrtovanje in končne odgovore; drugi cilj oddaja izvorne orodne klice odjemalca. OmniRoute zazna nadaljevanja rezultatov orodij iz protokola zahteve, vpraša načrtovalca, ali je potreben še en krog orodij, in dinamično določi bodisi izvajalca bodisi načrtovalca kot končni korak, ki je viden odjemalcu.

Pri nadaljevanjih rezultatov orodij OmniRoute tudi ustavi izvajanje, ko dva zaporedna zaključena kroga ponovita iste klice orodij z nespremenjenimi rezultati ali ko vsak izrecno označen rezultat v dveh zaporednih krogih ne uspe. Spremenjeni rezultati dovoljujejo ponovljene klice (na primer, anketiranje). Varovalo se ponastavi ob novi uporabniški zahtevi, združi vzporedne klice v en krog in podpira zgodovine Anthropic, Chat Completions, Responses in Gemini. Načrtovalec prejme razlog in upravlja končni odgovor, tudi če zahteva še en krog orodij.

Dodatni modeli za drugim ciljem so urejene varnostne kopije izvajalca. Neuspešen HTTP odziv ali transportna izjema napreduje do naslednjega izvajalca, pri čemer nosi isto odločitev načrtovalca in izvorna orodja, vendar z lastnim pozivom koraka in razrešeno povezavo tega izvajalca. Prvi uspešen odziv se vrne nespremenjen, vključno s SSE pretakanjem; napak po začetku uspešnega pretoka tukaj ni mogoče ponovno poskusiti. Če vsi izvajalci odpovejo, se vrne zadnja napaka. Prekinitve s strani odjemalca ustavijo pošiljanje.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

Izvajalec lahko v enem odzivu odda več neodvisnih klicev. Odvisni klici se obravnavajo v kasnejših obratih rezultatov orodij odjemalca, pri čemer načrtovalec pregleda vsak rezultat. `maxToolRounds` ima privzeto vrednost `8` in sprejema `1`–`32`; ko je dosežena, mora načrtovalec pripraviti najboljši možni končni odgovor. Notranje odločitve načrtovalca so medpomnjene, medtem ko izbrani odziv, viden odjemalcu, ohranja prvotno nastavitev pretakanja.

### `round-robin` lepljiva serija in širitev računa

Round-robin je serijski, ne ena-zahteva-na-korak:

- `stickyRoundRobinLimit` (konfiguracija combo, nato `comboStickyRoundRobinLimit`, nato `settings.stickyRoundRobinLimit`, privzeto **3**) ohrani isti cilj za toliko zaporednih uspehov, preden se zavrti. Nastavite preglasitev combo na `1` za rotacijo po eni zahtevi. Urejevalnik combo prikazuje dejansko vrednost in plast, iz katere izvira.
- `connectionAwareExpansion` (konfiguracija combo, nato nastavitve, privzeto **false**) razširi vsak korak na ravni ponudnika v cilje na račun pred rotacijo. Strategije skupine B (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) ohranjajo pogled na ravni ponudnika, dokler to ni vklopljeno. Urejevalnik combo izpostavlja inherit / on / off; inherit uporablja globalno privzeto vrednost (off).
- Usmerjanje lokalnosti predpomnilnika pozivov (`promptCacheAffinityEnabled`, privzeto **true**) prerazporedi pripete povezave tako, da ujemajoči se ključi predpomnilnika ostanejo na enem računu. Ima prednost pred rotacijo round-robin in weighted pri pripetih korakih na račun. Izklopite ga v Settings → Combo defaults, če potrebujete strogo rotacijo. Ni preglasitve na combo.

Za rotacijo med več računi na enem modelu raje uporabite **en korak dinamičnega računa** (prazen `connectionId`, celoten nabor) z lepljivo omejitvijo `1`, ne treh pripetih `connectionId`-jev. Pripeti koraki skupaj z afiniteto se zrušijo na isti račun, tudi ko se števec RR premika naprej.

## Strategija Fusion

`fusion` je edina strategija, ki **ne** izbere enega samega cilja. Poziv razpošlje
**vsem modelom panela vzporedno**, nato pa nastavljiv **model razsodnika** iz vseh
odgovorov panela sintetizira en sam končni odgovor. Preneseno iz izvornega projekta
`decolua/9router` (OpenRouterjeva zasnova Fusion); implementacija je v `open-sse/services/fusion.ts`.

Kako deluje:

0. **Obhod pri uporabi orodij** — zahteva, ki vsebuje neprazno polje `tools`, pri čemer
   `tool_choice` ni izrecno nastavljen na `"none"`, v celoti preskoči panel: usmerjena je
   neposredno v en sam model (nastavljenega razsodnika ali `panel[0]`), pri čemer sta
   `tools`/`tool_choice` nespremenjeno posredovana naprej. Člani panela nimajo dostopa
   do orodij, navodilo za sintezo razsodniku pa odsvetuje ustvarjanje klicev orodij, zato
   odjemalci z agentskim delovanjem oziroma klicanjem orodij namesto sintetiziranega
   besedila prejmejo pravo odločitev o klicu orodja (#6771).
1. **Razpošiljanje** (samo za zahteve brez orodij) — poziv je hkrati poslan vsakemu
   modelu panela, pri čemer je vsiljen način brez pretočnega prenosa in so orodja
   odstranjena (razsodnik za sintezo potrebuje celotno besedilo).
2. **Zbiranje s kvorumom in dodatnim časom** — takoj ko prispe `minPanel` odgovorov,
   se za zamudnike zažene kratko obdobje dodatnega čakanja, nato pa se sinteza izvede
   z vsemi do tedaj zbranimi odgovori. Tako je vpliv najpočasnejšega modela na skupni
   čas omejen, zgornjo mejo pa določa stroga časovna omejitev.
3. **Sinteza razsodnika** — odgovori panela so anonimizirani (`Source 1`, `Source 2`, … —
   tako razsodnik presoja vsebino in ne znamke modela) ter posredovani razsodniku, ki
   analizira soglasje / protislovja / delno pokritost / edinstvene ugotovitve / slepe
   pege, nato pa napiše **en** avtoritativen odgovor. Klic razsodnika ohrani izvorno
   odjemalčevo zastavico `stream` in orodja, zato pretočni prenos in nadaljnja uporaba
   orodij še vedno delujeta.
4. **Postopno zmanjševanje zmogljivosti** — 0 odgovorov panela → `503`; natanko 1
   preživeli odgovor → ta odgovor se vrne neposredno (ni ničesar za združiti); panel
   z enim samim modelom odgovori neposredno.

Član panela je lahko tudi korak `combo-ref` (`{kind: "combo-ref", comboName: "..."}`), ki se sklicuje
na drugo kombinacijo — razreši se kot **en samostojen glas panela** (popolna rekurzivna usmeritev v
navedeno kombinacijo, ne razpošiljanje njenim lastnim ciljem), z enako zaščito pred preveliko globino
in cikli, kot jo že uporablja vsaka druga strategija, ki obdeluje `combo-ref` (#6764).

## Navidezna tovarna Auto-Combo

Mehanizem Auto Combo ne zahteva vnaprej določenih kombinacij. Namesto tega `open-sse/services/autoCombo/virtualFactory.ts` sproti gradi kandidate:

1. Pridobi `getProviderConnections({ isActive: true })` (vse omogočene povezave)
2. Filtrira tiste z veljavnimi poverilnicami (ključ API ali žeton OAuth, ki še ni potekel, prek `hasUsableOAuthToken()`)
3. Podatke navzkrižno primerja z `getProviderRegistry()` glede razpoložljivosti modelov in cen
4. Za vsako trojico `(provider, model, connection)` zgradi `VirtualAutoComboCandidate`
5. Kot cilj usmerjanja izbere `connection.defaultModel` (ali prvi model v registru)
6. Vsakega kandidata oceni s 16-faktorsko funkcijo `scorePool()` in paketom uteži različice
7. Vrne nastali pomnilniški `AutoComboConfig` za `handleComboChat()` — nikoli se ne shrani v podatkovno zbirko

To pomeni, da **dodajanje novega ponudnika z omogočenim `auto/*` samodejno razširi nabor kandidatov** — ročno urejanje kombinacij ni potrebno. Navidezna kombinacija se znova zgradi ob vsaki zahtevi, zato so na novo dodane ali na novo delujoče povezave upoštevane takoj.

## Samozdravljenje

- **Začasna izključitev**: Ocena < 0.2 → izključitev za 5 min (progresivno podaljševanje, največ 30 min)
- **Upoštevanje odklopnika**: OPEN → samodejno izključen; HALF_OPEN → poskusne zahteve
- **Način incidenta**: >50 % OPEN → onemogoči raziskovanje, poveča stabilnost
- **Obnovitev po obdobju ohlajanja**: Po izključitvi je prva zahteva »poskusna« z zmanjšano časovno omejitvijo

## Raziskovanje z večrokim razbojnikom

5 % zahtev (nastavljivo) je zaradi raziskovanja usmerjenih k naključnim ponudnikom. V načinu incidenta je to onemogočeno.

## API

Ne obstaja **noben namenski končni točki `POST /api/combos/auto`** — Auto-Combo se uporablja na dva načina:

1. **Brez konfiguracije (priporočeno):** Pošljite katero koli zahtevo za dokončanje klepeta z `model: "auto"` ali `model: "auto/<variant>"`. Navidezna tovarna zgradi kombinacijo za vsako zahtevo — brez trajnega shranjevanja, brez potrebnih klicev API.

2. **Trajno shranjena kombinacija s `strategy: "auto"`:** Ustvarite običajno kombinacijo prek `POST /api/combos` in nastavite `strategy: "auto"` ter `config.auto.weights` / `config.auto.candidatePool`. Uporabljen je enak mehanizem točkovanja; kombinacija je shranjena v `combos` in jo je mogoče ponovno uporabiti z ID-jem.

Za odkrivanje `GET /api/combos/auto` navede vsako različico z njenim razrešenim naborom kandidatov ter `context_length` / `max_output_tokens` — NAJVEČJO vrednost v oknih nabora kandidatov. Odjemalci (npr. vtičnik opencode) morajo oglaševati te vrednosti namesto `0`: ničelni kontekst popolnoma onemogoči samodejno stiskanje vtičnika opencode, kar omogoča, da se seje povečujejo, dokler čiščenje zgodovine prehoda ne uniči konteksta. NAJVEČJO vrednost je varno oglaševati, ker predfilter konteksta auto-combo usmeri prevelike zahteve h kandidatom z velikimi okni.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \

```

### Strategije samodejnega usmerjevalnika

Trajno shranjene kombinacije s `strategy: "auto"` lahko nastavijo `config.routerStrategy` (ali starejši `config.auto.routerStrategy`) na eno od naslednjih:

- `rules` — privzeto uteženo točkovanje
- `score` — izbere najvišjo konfigurirano uteženo oceno. Pri natančnih izenačenjih se ohrani konfigurirani vrstni red kandidatov; obstoječa `explorationRate` vzorči iz celotnega razvrščenega nabora.
- `cost` / `eco` — najcenejši zdravi ponudnik
- `latency` / `fast` — najnižja zakasnitev p95 s kaznijo za zanesljivost
- `sla-aware` / `sla` — daje prednost kandidatom, ki izpolnjujejo SLO-je za zakasnitev p95, stopnjo napak in neobvezne stroške
- `lkgp` — najprej zadnji znani dobri ponudnik
- `nadir` — vpraša API za odločanje [Nadir](https://getnadir.com), kateri model v naboru poziv potrebuje; opt-in, ob napaki preklopi na `rules`

### Podrobnosti o strategijah usmerjevalnika

Mehanizem auto-combo izpostavlja 7 vtičnih implementacij **RouterStrategy**, ki jih lahko zamenjate prek `config.routerStrategy` (ali starejše `config.auto.routerStrategy`). Vsaka strategija izbere enega ponudnika iz nabora kandidatov, glede na `RoutingContext` (vrsta naloge, namigi za orodja/vid, ocena žetonov, neobvezna politika SLA, neobvezni zadnji znani dobri ponudnik).

#### 1. `rules` (privzeto) — 16-faktorsko uteženo točkovanje

Zavije obstoječi mehanizem točkovanja. Filtrira kandidate s stanjem `OPEN` odklopnika, nato zažene `scorePool()` s trenutno vrsto naloge in `getTaskFitness()`, pri čemer izbere najbolje ocenjenega ponudnika.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**Kdaj uporabiti**: Privzeto. Uporabite, ko želite uravnotežen kompromis med vsemi signali.

**Alias**: `rules` (brez aliasa)

---

#### 2. `cost` / `eco` — najcenejši zdravi ponudnik

Razvrsti nabor kandidatov po `costPer1MTokens` (naraščajoče) in izbere najcenejšega. Najprej filtrira kandidate s stanjem `OPEN`.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kdaj uporabiti**: Delovne obremenitve, občutljive na stroške, paketna obdelava ali opravila v ozadju.

**Aliasi**: `cost`, `eco`

---

#### 3. `latency` / `fast` — najnižja zakasnitev p95 s kaznijo za zanesljivost

Razvrsti po `p95LatencyMs + (errorRate * 1000)`. Kazen za stopnjo napak zagotavlja, da so nezanesljivi ponudniki uvrščeni nižje, tudi če je njihova nominalna zakasnitev nizka.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**Kdaj uporabiti**: Delovne obremenitve, občutljive na zakasnitev, kot so klepet v realnem času, samodejno dokončanje ali interaktivni pomočniki za kodiranje.

**Aliasi**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — skladnost s SLO za zakasnitev/napake/stroške

Ocenjuje vsakega kandidata glede na to, kako dobro izpolnjuje konfigurirano politiko SLO:

| Dejavnik          | Teža | Formula                                                |
| ----------------- | ---- | ------------------------------------------------------ |
| Ocena zakasnitve  | 35%  | `threshold / max(value, ε)`                            |
| Ocena napak       | 35%  | `threshold / max(value, ε)`                            |
| Ocena stanja      | 15%  | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)      |
| Ocena stroškov    | 10%  | `threshold / max(value, ε)` ali inverzno normalizirano |
| Ocena stabilnosti | 5%   | inverzno normaliziran standardni odklon zakasnitve     |

Ko je `hardConstraints: true`, so kandidati razvrščeni primarno po **oceni kršitev**
(kako daleč presegajo kateri koli SLO), nato po sestavljeni oceni. V nasprotnem primeru gre le za
sestavljeno oceno.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**Polja SLA** (nastavljena v konfiguraciji combo):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**Kdaj uporabiti**: Produkcijske obremenitve s strogimi proračuni za zakasnitev, stopnjo napak ali stroške.

**Aliasi**: `sla-aware`, `sla`

---

#### 5. `lkgp` — najprej zadnji znani dobri ponudnik

Najprej poskusi z **zadnjim znanim dobrim ponudnikom** (če je nastavljen), nato se vrne na
strategijo `rules`. Uporabno za vztrajnost seje — isti ponudnik obravnava
nadaljnje zahteve v pogovoru.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**Kdaj uporabiti**: Pogovori z več izmenjavami, kjer želite, da isti ponudnik obravnava
nadaljnje zahteve (npr. za predpomnjenje, kontinuiteto konteksta ali doslednost cen).

**Alias**: `lkgp` (brez aliasa)

---

#### 6. `nadir` — izbira modela glede na poziv prek Nadir

Vsaka strategija zgoraj razvršča kandidate po lastni telemetriji; nobena od njih ne bere
zahteve. `nadir` pošlje zadnji uporabnikov obrat plus ID-je modelov v naboru na odločitveni API
[Nadir](https://getnadir.com) (`POST /v1/bucket`) in usmeri na model, ki ga Nadir
izbere iz tega menija (`simple` → najcenejši zmogljiv model, `complex` → najnaprednejši model).
Povezavo, ki streže ta model, še vedno izbere `rules`, zato kvota, zdravje in stroški še naprej
odločajo, kateri račun se uporabi.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` in `OMNIROUTE_NADIR_BASE_URL` sta okoljski povratni vrednosti za ta dva
niza. `baseUrl` je potreben le za Nadir, ki ga gostite sami (končna `/v1` je dovoljena).
Klici brez ključa pristanejo na Nadirjevem anonimnem nivoju, ki je omejen glede na IP.

Kaj zapusti škatlo: besedilo zadnjega uporabniškega sporočila (prvih 16k znakov), ID-ji
kandidatnih modelov in oznaka kanala `source: "omniroute"`. Brez sistemskega poziva,
zgodovine, orodij ali glav.

Vedenje ob napaki je fail-open: časovna omejitev (privzeto 2000 ms), odgovor, ki ni 2xx,
nedosegljiv gostitelj, napačno oblikovan odgovor ali izbira zunaj nabora se razreši v odločitev
`rules`, razlog pa dobi predpono `NadirStrategy: fallback (…)`. Po neuspešnem klicu
strategija preskoči omrežje za 30 s, tako da izpad stane eno časovno omejitev na 30 s namesto
ene na zahtevo. Usmerjevalni dogodki poročajo `strategy: "nadir"` le, ko je Nadir dejansko
opravil izbiro.

**Kdaj uporabiti**: promet mešane zahtevnosti v naboru, ki zajema nivoje modelov (majhen,
srednji in najnaprednejši model), kjer je vedno-najnaprednejši strošek, ki ga želite zmanjšati.

**Alias**: `nadir` (brez aliasa)

## Kako se ravni vključujejo v Auto-Combo

Funkcija ocenjevanja s 16 dejavniki (`open-sse/services/autoCombo/scoring.ts`) obravnava
pripadnost ravni kot dva signala: `tierPriority` (0.0476) in `tierAffinity` (0.0476). Za celoten
nabor `DEFAULT_WEIGHTS` glejte zgornjo kanonično [tabelo dejavnikov ocenjevanja](#how-it-works-persisted-auto-combos) —
preglasitve za posamezne pakete (ship-fast/cost-saver/quality-first/
offline-friendly) so navedene v tabeli »Profili uteži po paketih«.

Sama raven **ne** zagotavlja, da bo raven 1 prva — če je zakasnitev ravni 1 velika ali
je razmerje med stroški in kakovostjo neoptimalno, zmaga raven 2. Če želite vsiliti vrstni red
ravni, uporabite strategijo kombiniranja `priority` in razvrstite ponudnike po ravneh.

Če želite močno prednost dati ravni 1 (naročnina), povečajte utež `tierPriority`:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

Za opredelitve ravni in razvrstitev ponudnikov glejte [`docs/guides/TIERS.md`](../guides/TIERS.md).

## Testiranje in pokritost

### Deterministična matrika odločitev usmerjanja (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` preverja **odločitev** usmerjanja za vseh 19 javnih strategij od začetka do konca prek dejanskega cevovoda kombiniranja s simuliranim nadrejenim ponudnikom. Pokritost vključuje:

- Vseh 19 strategij `ROUTING_STRATEGY_VALUES` (ordered, weighted, cost, context, fusion, …).
- Celovito testiranje interne strategije `quota-share`: pravičnost DRR in znižanje prednosti ob nasičenosti prek dejanske testne točke `selectQuotaShareTarget` (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`).
- Pokritost univerzalne predaje `context-relay` za vsako število ciljev.

Ta zbirka testov se izvaja v CI (opravilo `test:integration`) z možnostma `--test-concurrency=1` in `--test-force-exit`, zato je deterministična in ne zahteva dejanskih poverilnic.

### Pogojni preizkus delovanja v živo (NI v CI — dejanski ponudniki)

| Ukaz                                   | Kaj naredi                                                                                                |
| :------------------------------------- | :-------------------------------------------------------------------------------------------------------- |
| `npm run test:combo:live`              | Dejansko usmerjanje znotraj procesa z `RUN_COMBO_LIVE=1`; ustvari posnetek žive zbirke podatkov OmniRoute |
| `npm run test:combo:live:vps`          | Klici HTTP do živega strežnika OmniRoute (nastavite `COMBO_LIVE_BASE_URL`)                                |
| `npm run test:combo:live:vps:failover` | Enako, z namerno sproženimi scenariji preklopa ob odpovedi                                                |

Ti preizkusi delovanja preverjajo dejansko komunikacijsko pot (kombinacija → ponudnik → dokončanje). Namenoma so izključeni iz CI, ker zahtevajo dejanske poverilnice in dostop do VPS-ja.
