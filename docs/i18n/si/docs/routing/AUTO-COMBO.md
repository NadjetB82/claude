## ශුන්ය-වින්යාස ස්වයංක්රීය මාර්ගගත කිරීම (`auto/` උපසර්ගය)

> **නව:** combo සෑදීම අවශ්ය නොවේ. ඕනෑම client එකක සෘජුවම `auto/` උපසර්ගය භාවිත කරන්න.

### ඉක්මන් උදාහරණ

| Model ID       | ප්රභේදය | හැසිරීම                                                                            |
| -------------- | ------- | ---------------------------------------------------------------------------------- |
| `auto`         | පෙරනිමි | සම්බන්ධිත සියලු providers, LKGP උපායමාර්ගය, සමතුලිත weights                        |
| `auto/coding`  | coding  | ගුණාත්මකභාවයට ප්රමුඛත්වය දෙන weights, code ජනනය සඳහා සුදුසුය                       |
| `auto/fast`    | fast    | අඩු-ප්රමාද weighted තේරීම                                                          |
| `auto/cheap`   | cheap   | පිරිවැය-ප්රශස්ත කළ මාර්ගගත කිරීම (අඩුම පිරිවැය පළමුව)                              |
| `auto/offline` | offline | ඉහළම quota ලබාගත හැකි providers වෙත ප්රමුඛත්වය දෙයි                                |
| `auto/smart`   | smart   | වඩා හොඳ model සොයාගැනීම සඳහා ගුණාත්මකභාවයට ප්රමුඛත්වය + ඉහළ exploration rate (10%) |
| `auto/lkgp`    | lkgp    | පැහැදිලි LKGP (පෙරනිමි `auto` හා සමානයි)                                           |
| `auto/chaos`   | chaos   | සමාන්තර fan-out, එක් provider එකකට එක් model එකක් (fault injection නොවේ)           |

### ප්රවර්ගය × ස්තර සංයෝජනය (`auto/<category>:<tier>`)

OpenRouter-ශෛලියේ suffix මඟින් **කුමන ආකාරයේ මාර්ගයක්ද** (category) යන්න **එය ප්රශස්ත කරන්නේ කෙසේද** (tier) යන්නෙන් වෙන් කරයි, එබැවින් ඒවා නිදහසේ සංයෝජනය කළ හැකිය (#4235 Phase B, `open-sse/services/autoCombo/suffixComposition.ts`):

- **ප්රවර්ග** (හැකියාව අනුව candidate pool එක පෙරහන් කරන්න): `coding` · `reasoning` · `vision` · `chat` · `multimodal`. `vision`/`multimodal` මඟින් vision හැකියාව ඇති models තබා ගනී; `reasoning` මඟින් reasoning/thinking models තබා ගනී.
- **ස්තර** (scoring weights / pool filter එක තෝරන්න): `fast` (ඉක්මනින් නිකුත් කිරීම) · `cheap` (`floor` යන alias එක, පිරිවැය ඉතිරි කිරීම) · `reliable` (circuit-breaker සෞඛ්යය + latency ස්ථායීතාව) · `free` / `pro` (`classifyTier` හරහා model tier අනුව pool එක පෙරහන් කිරීම — free-tier එදිරිව premium).

| උදාහරණය                | විසඳෙන්නේ                                                         |
| ---------------------- | ----------------------------------------------------------------- |
| `auto/coding:fast`     | coding pool, අඩු-ප්රමාද weights                                   |
| `auto/coding:cheap`    | coding pool, පිරිවැය-ප්රශස්ත කළ (`auto/coding:floor` යන alias එක) |
| `auto/reasoning:pro`   | reasoning/thinking models පමණි, premium tier                      |
| `auto/vision`          | vision හැකියාව ඇති models (tier එකක් නැත → සමතුලිත weights)       |
| `auto/multimodal:free` | multimodal හැකියාව ඇති models, free tier පමණි                     |

වලංගු ඕනෑම `auto/<category>[:<tier>]` එකක් ඉල්ලුම අනුව resolve වේ; තෝරා සැකසූ subset එකක් `/v1/models` සහ dashboard එකෙහි ප්රචාරණය කෙරේ (`open-sse/services/autoCombo/builtinCatalog.ts` හි `AUTO_SUFFIX_VARIANTS`). Filtering **fail-open** වේ — constraint එකක් කිසිදු සම්බන්ධිත model එකකට නොගැළපෙන්නේ නම්, routing කිසි විටෙකත් බිඳ නොවැටෙන ලෙස සම්පූර්ණ pool එක භාවිත කෙරේ. මූලික scorer එක (`combo.ts`) වෙනස් කර නැත; category/tier filter එක `buildAutoCandidates` තුළ යොදනු ලැබේ.

> **සජීවී model බුද්ධිය:** `ARENA_ELO_SYNC_ENABLED` flag එක ක්රියාත්මක විට, auto-routing යෝග්යතාව සජීවී **Arena ELO** ශ්රේණිගත කිරීම් + **models.dev** tier දත්ත මඟින් දැනුවත් කෙරේ (එසේ නොමැති විට static fitness map එක වෙත ආපසු යයි).

## සැබෑ Model Id එකකට ගැළපෙන Combo නම්

හිස් model id එකකට සමාන `name` එකක් ඇති combo එකක් (උදා. `gpt-5.5` නමින් ඇති combo එකක්) යනු දෝෂයක් නොව, **හිතාමතාම සපයන සහය දක්වන රටාවකි**: එය [#6940](https://github.com/diegosouzapw/OmniRoute/issues/6940) හි ලේඛනගත කර ඇති එක් එක් model id සඳහා provider fallback යාන්ත්රණයයි. හිස්-model-id විසඳීමට පෙර combo විසඳීම පරීක්ෂා කරන බැවින් (`src/sse/services/model.ts` හි `getComboForModel()`), හිස් id එක වන `gpt-5.5` සඳහා ඉල්ලීමක් සෘජුවම තනි provider කෙනෙකු වෙත යැවීම වෙනුවට combo එකේ targets හරහා (උදා. `acme-responses/gpt-5.5`, `backup-responses/gpt-5.5`) යොමු කරයි — මෙය [#3227/#3233](https://github.com/diegosouzapw/OmniRoute/issues/3227) සඳහා ගොඩනැගූ combo-before-rewrite ප්රමුඛතාව නැවත භාවිත කරන අතර `tests/unit/responses-combo-resolution-3227.test.ts` සහ `tests/unit/combo-name-codex-responses-rewrite.test.ts` මඟින් regression පරීක්ෂාවට ලක් කර ඇත.

Boot වන අවස්ථාවේදී, `scanComboModelNameCollisionsAtBoot()` (`src/instrumentation-node.ts`) ද model id එකක් සඟවන සෑම පවතින combo එකක්ම ලැයිස්තුගත කරමින් එක් පේළියක `[STARTUP]` අනතුරු ඇඟවීමක් log කරයි. එමඟින් #6940 අනුව හිතාමතා කරනවාට වඩා අහම්බෙන් මෙයට මුහුණ දෙන operators හට සංඥාවක් ලැබේ. හඳුනාගැනීමේ helper එක `src/lib/combos/modelNameCollision.ts` හි ඇත.

## Client එකකින් Custom Combo එකක් ඇමතීම

Persist කර ඇති combos (Settings → Combos) භාවිත වන්නේ client එක `model` field එකෙහි combo එකේ **නිශ්චිත නම** යවන විට පමණි — combo නම සඳහා fuzzy හෝ partial matching නොමැති අතර `auto/` prefix එකක්ද සම්බන්ධ නොවේ. විසඳීමේ අනුපිළිවෙළ (`src/sse/services/model.ts` හි `getComboForModel()`):

1. නිශ්චිත combo-name ගැළපීම (`model: "my-combo"`),
2. `combo/<name>` prefix එක (`model: "combo/my-combo"`),
3. model→combo glob mappings (`/api/model-combo-mappings`).

```bash
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"my-combo","messages":[{"role":"user","content":"Hello"}]}'
```

පොදු වැරදි අවබෝධ දෙකක්:

- **`auto` ඔබගේ combos භාවිත නොකරයි.** `auto`/`auto/*` තමන්ගේම zero-config candidate pool එකක් ගොඩනඟන අතර, `auto` යන නමම ඇති combo එකක් තිබේ නම් පමණක් persist කර ඇති combos සලකා බලයි (නිර්දේශ නොකෙරේ). Combo එකක් හරහා යොමු කිරීමට, `auto` නොව එහි නිශ්චිත නම යවන්න.
- **`openrouter/auto` යනු සැබෑ ගෙවීම් සහිත OpenRouter නිෂ්පාදනයකි** ("Auto Best Available"), OmniRoute alias එකක් නොවේ. එය OpenRouter registry එකේ (`open-sse/config/providers/registry/openrouter/index.ts`) ඇති එකම static model entry එක වන අතර ඒ සඳහා වෙනම ගාස්තු අය කෙරේ. එය `auto` pools වෙතින් ඉවත් කිරීමට Settings → Routing → Hide paid models භාවිත කරන්න.

මෙහි ලේඛනගත කර ඇති මුල් ව්යාකූලතාව සඳහා [#7992](https://github.com/diegosouzapw/OmniRoute/issues/7992) සහ [#7111](https://github.com/diegosouzapw/OmniRoute/issues/7111) බලන්න.

## එය ක්‍රියාත්මක වන ආකාරය (Persisted Auto-Combos)

Auto-Combo Engine මඟින් එක් එක් ඉල්ලීම (request) සඳහා වඩාත්ම සුදුසු සැපයුම්කරු/ආකෘතිය (provider/model) තෝරා ගනු ලබන්නේ **සාධක 16 කින් යුත් ලකුණු කිරීමේ ශ්‍රිතයක් (16-factor scoring function)** භාවිතයෙනි (`open-sse/services/autoCombo/scoring.ts` → `DEFAULT_WEIGHTS` හි අර්ථ දක්වා ඇත). පෙරනිමි බර තැබීම්වල (default weights) එකතුව `1.0` කි; අභිරුචි බර තැබීම් `normalizeScoringWeights()` මඟින් යළි සාමාන්‍යකරණය (renormalized) කරනු ලැබේ. දහසයෙන් දෙකක් වන `cacheAffinity` සහ `resetWindowAffinity` සඳහා පෙරනිමි බර තැබීම `0` වේ; `DEFAULT_WEIGHTS` තුළ `reliability` සඳහා `0` ක් ලැබුණද, generic packs තුළ `0.03` ක් සහ `reliability-first` තුළ `0.04` ක් ලැබේ, තවද `quality` සඳහා packs තුළ `0.02` ක් ලැබේ (`quality-first` තුළ `0.03` ක්): ඒවා තවමත් සෑම candidate කෙනෙකු සඳහාම ගණනය කරනු ලබන අතර, `cacheAffinity` මඟින් ලකුණට පිටතින් prompt-cache deduplication පාලනය කරයි, එබැවින් පෙරනිමියෙන් ශුන්‍ය වන සාධක පෙරනිමියෙන් ඡන්දය ප්‍රකාශ නොකරන අතර packs මඟින් එසේ කරනු ලබයි.

### `weighted` අර්ථකථනය

`weighted` යනු **එක් ඉල්ලීමකට සමානුපාතික අහඹු තේරීමකි** (`open-sse/services/combo/targetSorters.ts` → `selectWeightedTarget`), එය සමානකාරකයක් (equalizer) නොවේ:

- එක් එක් ඉල්ලීම `weight / totalWeight` සම්භාවිතාව සමඟ **එක්** පියවරක් තෝරා ගනී; ඉතිරි පියවර එම ඉල්ලීම සඳහා fallback දාමය ලෙස බරෙහි අවරෝහණ අනුපිළිවෙලින් සකසා ඇත.
- බර `0` (හෝ නැති) පියවරක් වෙනත් ඕනෑම පියවරක බර > 0 වන විට **කිසිවිටෙක තෝරා නොගනී** — එය තෝරාගත් පියවර අසාර්ථක වූ පසු fallback එකක් ලෙස පමණක් සේවය කළ හැක. **සියලුම** බර 0 වන විට පමණක් තේරීම ඒකාකාර වේ.
- ඉලක්ක ලබා ගත නොහැකි පියවර — provider circuit breaker `OPEN`, connection cooldown, model lockout — සිදු වීමට පෙර තේරීමෙන් ඉවත් කරනු ලැබේ (`open-sse/services/combo/targetResolution.ts`), එබැවින් තනි සෞඛ්‍ය සම්පන්න පියවරකට තාවකාලිකව සෑම ඉල්ලීමක්ම දිනා ගත හැක.
- `stickyWeightedLimit` (combo config, default `1` = off) නැවත තේරීමට පෙර අනුක්‍රමික සාර්ථකත්වයන් ගණනක් සඳහා තෝරාගත් පියවර රඳවා ගනී.

දැඩි භ්‍රමණය (strict rotation) සඳහා `round-robin` භාවිතා කරන්න; `weighted` මත සමාන බර තැබීම මගින් සංඛ්‍යානමය - දැඩි නොවන - සමතුලිතතාවයක් ලබා දෙයි.

### ඒජන්ටික් පයිප්ලයින් මාදිලිය (Agentic pipeline mode)

අවම වශයෙන් මාදිලි දෙකක් සහිත `pipeline` එකතුවකට `config.agenticOrchestration.enabled` සමඟ සැලසුම්කරු/ක්‍රියාත්මක කරන්නා (planner/executor) රවුටින් තෝරා ගත හැක. පළමු ඉලක්කය සැලසුම් කිරීම සහ අවසාන පිළිතුරු සඳහා වගකිව යුතු වේ; දෙවන ඉලක්කය මගින් ක්ලයන්ට්-නේටිව් මෙවලම් ඇමතුම් (client-native tool calls) නිකුත් කරයි. OmniRoute මගින් ඉල්ලීම් ප්‍රොටෝකෝලය වෙතින් මෙවලම්-ප්‍රතිඵල අඛණ්ඩතාව හඳුනා ගනී, තවත් මෙවලම් වටයක් අවශ්‍ය දැයි සැලසුම්කරුගෙන් විමසයි, සහ ක්‍රියාත්මක කරන්නා හෝ සැලසුම්කරු යන දෙදෙනාගෙන් අයෙකු ගතිකව ක්ලයන්ට්-අභිමුඛ අවසාන පියවර බවට පත් කරයි.

විකල්ප `config.agenticOrchestration.contextCompaction` මගින් සෑම සැලසුම්කරු හෝ ක්‍රියාත්මක කරන්නා යැවීමකට පෙර වෙනම පේලෝඩ් අයවැයක් (payload budget) යොදයි. එය පැහැදිලිව සක්‍රීය කරන්න:

```json
{
  "enabled": true,
  "defaultMaxChars": 400000,
  "targetRatio": 0.72,
  "toolResultMaxChars": 24000,
  "modelMaxChars": { "provider/planner": 175000, "provider/executor": 300000 }
}
```

මේවා ක්‍රියාකරු විසින් තෝරාගත් අනුක්‍රමික JSON අක්ෂර අයවැය වේ, ටෝකන් සන්දර්භ කවුළු (token context windows) හෝ සහතික කළ අප්ස්ට්‍රීම් සීමාවන් නොවේ. නිශ්චිත මාදිලි හැඳුනුම්පත් (model IDs) පෙරනිමිය අභිබවා යයි. සීමාවට ඉහළින්, සම්පීඩනය මගින් සමාන මෙවලම් නිර්වචන ඉවත් කරයි, විශාල මෙවලම් සාක්ෂි සාරාංශයක් (digest) සමඟ කප්පාදු කරයි, සහ ඉලක්ක අනුපාතය කරා පැරණි සම්පූර්ණ ඉතිහාස කණ්ඩායම් ඉවත් කරයි. එය පද්ධති/සංවර්ධක උපදෙස්, නවතම පරිශීලක ඉල්ලීම, සමාන්තර ඇමතුම්/ප්‍රතිඵල ඇතුළත් අවසාන මෙවලම් වටය සහ Gemini හි ප්‍රමුඛ රවුටින් උපදෙස් රඳවා ගනී. ඉහළ මට්ටමේ උපදෙස් සහ මෙවලම් සැකසුම් සුරැකේ. මඟ හැරීමේ සලකුණක් මගින් ඉවත් කරන ලද ඉතිහාසය වාර්තා කරයි; මෙය අර්ථකථන සාරාංශයක් නොව නිර්ණායක කප්පාදුවකි (deterministic trimming). පින් කරන ලද සන්දර්භය තවමත් අයවැය ඉක්මවා යන්නේ නම්, මාදිලිය සම්බන්ධ කර ගැනීමට පෙර ඉල්ලීම 413 ආපසු ලබා දෙයි. සම්පීඩනය අක්‍රීය කර ඇති විට හෝ සීමාවට වඩා අඩු වූ විට ඉල්ලීම වෙනස් නොවී ගමන් කරයි.

දෙවන ඉලක්කයෙන් පසු අමතර මාදිලි අනුපිළිවෙලින් ක්‍රියාත්මක කරන්නාගේ උපස්ථ (executor backups) වේ. අසාර්ථක HTTP ප්‍රතිචාරයක් හෝ ප්‍රවාහන ව්‍යතිරේකයක් ඊළඟ ක්‍රියාත්මක කරන්නා වෙත ගමන් කරයි, එම සැලසුම්කරුගේ තීරණය සහ නේටිව් මෙවලම් රැගෙන යයි, නමුත් එම ක්‍රියාත්මක කරන්නාගේම පියවර විමසුම සහ විසඳන ලද සම්බන්ධතාවය භාවිතා කරයි. පළමු සාර්ථක ප්‍රතිචාරය SSE ස්ට්‍රීම් කිරීම ඇතුළුව වෙනස් නොවී ආපසු ලබා දෙනු ලැබේ; සාර්ථක ස්ට්‍රීම් එකක් ආරම්භ වීමෙන් පසු අසාර්ථකත්වයන් මෙහිදී නැවත උත්සාහ කළ නොහැක. සියලුම ක්‍රියාත්මක කරන්නන් අසාර්ථක වුවහොත්, අවසාන අසාර්ථකත්වය ආපසු ලබා දෙනු ලැබේ. ක්ලයන්ට් අත්හැරීම් (Client aborts) යැවීම නවත්වයි.

```json
{
  "strategy": "pipeline",
  "models": [{ "model": "provider/planner" }, { "model": "provider/executor" }],
  "config": {
    "agenticOrchestration": { "enabled": true, "maxToolRounds": 8 }
  }
}
```

ක්‍රියාත්මක කරන්නාට එක් ප්‍රතිචාරයකින් ස්වාධීන ඇමතුම් කිහිපයක් නිකුත් කළ හැක. යැපෙන ඇමතුම් (Dependent calls) පසුව එන ක්ලයන්ට් මෙවලම්-ප්‍රතිඵල වාර වලදී හසුරුවනු ලබන අතර, සැලසුම්කරු සෑම ප්‍රතිඵලයක්ම සමාලෝචනය කරයි. `maxToolRounds` පෙරනිමියෙන් `8` වන අතර `1`–`32` අතර අගයන් පිළිගනී; එය ළඟා වූ පසු, සැලසුම්කරු විසින් ලබා ගත හැකි හොඳම අවසාන පිළිතුර ඉදිරිපත් කළ යුතුය. අභ්‍යන්තර සැලසුම්කරු තීරණ බෆර් කරනු ලබන අතර, තෝරාගත් ක්ලයන්ට්-අභිමුඛ ප්‍රතිචාරය මුල් ස්ට්‍රීම් කිරීමේ මනාපය රඳවා ගනී.

### `round-robin` ස්ටිකි බැච් සහ ගිණුම් ප්‍රසාරණය (account expansion)

Round-robin යනු බැච් කරන ලද්දකි, පියවරකට-එක්-ඉල්ලීමක් නොවේ:

- `stickyRoundRobinLimit` (combo config, පසුව `comboStickyRoundRobinLimit`, පසුව `settings.stickyRoundRobinLimit`, පෙරනිමිය **3**) භ්‍රමණය වීමට පෙර අනුක්‍රමික සාර්ථකත්වයන් ගණන සඳහා එකම ඉලක්කය රඳවා ගනී. එක්-ඉල්ලීම් භ්‍රමණය සඳහා combo override එක `1` ලෙස සකසන්න. combo සංස්කාරකය මගින් ඵලදායී අගය සහ එය පැමිණි ස්ථරය පෙන්වයි.
- `connectionAwareExpansion` (combo config, පසුව settings, පෙරනිමිය **false**) භ්‍රමණය වීමට පෙර සෑම සැපයුම්කරු-මට්ටමේ පියවරක්ම ගිණුම-අනුව ඉලක්ක බවට ප්‍රසාරණය කරයි. Group-B උපාය මාර්ග (priority, weighted, round-robin, random, p2c, least-used, cost-optimized, lkgp, fill-first, strict-random, context-optimized, cache-optimized, context-relay, fusion, pipeline) මෙය සක්‍රීය වන තුරු සැපයුම්කරු-මට්ටමේ දසුනක් පවත්වා ගනී. combo සංස්කාරකය inherit / on / off නිරාවරණය කරයි; inherit මගින් ගෝලීය පෙරනිමිය (off) භාවිතා කරයි.
- Prompt-cache locality routing (`promptCacheAffinityEnabled`, පෙරනිමිය **true**) මගින් පින් කරන ලද සම්බන්ධතා නැවත සකස් කරන අතර එමඟින් ගැලපෙන cache keys එකම ගිණුමක පවතී. එය පින් කරන ලද ගිණුම-අනුව පියවර හරහා round-robin සහ weighted භ්‍රමණයට වඩා ප්‍රමුඛත්වය ගනී. ඔබට දැඩි භ්‍රමණය අවශ්‍ය නම් Settings → Combo defaults යටතේ එය අක්‍රීය කරන්න. per-combo override එකක් නොමැත.

එක් මාදිලියක බහු-ගිණුම් භ්‍රමණය සඳහා, පින් කරන ලද `connectionId` තුනක් නොව, sticky limit `1` සහිත **එක් ගතික-ගිණුම් පියවරක්** (හිස් `connectionId`, සම්පූර්ණ තටාකය) භාවිතා කරන්න. RR කවුන්ටරය ඉදිරියට යන විට පවා පින් කරන ලද පියවර සහ affinity එකම ගිණුමකට එකතු වේ.

## Fusion උපායමාර්ගය

`fusion` යනු එක් ඉලක්කයක් තෝරා **නොගන්නා** එකම උපායමාර්ගයයි. එය විමසුම
**සෑම පැනල් මොඩලයකටම සමාන්තරව** යවා, අනතුරුව වින්යාස කළ හැකි **විනිශ්චයකරු මොඩලයක්** මඟින්
සියලු පැනල් ප්රතිචාරවලින් එක් අවසාන පිළිතුරක් සංස්ලේෂණය කරයි. මෙය upstream `decolua/9router`
(OpenRouter හි Fusion සැලසුම) වෙතින් පෝට් කර ඇත; ක්රියාත්මක කිරීම `open-sse/services/fusion.ts` තුළ ඇත.

එය ක්රියා කරන ආකාරය:

0. **මෙවලම් සහිත ඉල්ලීම් මඟහැරීම** — හිස් නොවන `tools` අරාවක් සහ
   පැහැදිලිව `"none"` ලෙස සකසා නොමැති `tool_choice` එකක් සහිත ඉල්ලීමක් පැනලය සම්පූර්ණයෙන්ම මඟහරී: එය
   එක් මොඩලයකට (වින්යාස කළ විනිශ්චයකරු හෝ `panel[0]`) සෘජුවම යොමු කෙරෙන අතර `tools`/`tool_choice`
   කිසිදු වෙනසකින් තොරව ඉදිරියට යවනු ලැබේ. පැනල් සාමාජිකයන්ට මෙවලම් ප්රවේශය නොමැති අතර විනිශ්චයකරුගේ
   සංස්ලේෂණ විධානය මෙවලම්-ඇමතුම් නිකුත් කිරීම අධෛර්යමත් කරයි; එම නිසා agentic/මෙවලම්-ඇමතුම් සේවාදායකයන්ට
   සංස්ලේෂණය කළ ගද්යයක් වෙනුවට සැබෑ මෙවලම්-ඇමතුම් තීරණයක් ලැබේ (#6771).
1. **විහිදුවා යැවීම** (මෙවලම් රහිත ඉල්ලීම් සඳහා පමණි) — විමසුම සෑම පැනල්
   මොඩලයකටම එකවර යවනු ලබන අතර, මෙවලම් ඉවත් කර streaming නොවන ආකාරයට බල කෙරේ (සංස්ලේෂණය සඳහා විනිශ්චයකරුට
   සම්පූර්ණ ගද්යය අවශ්ය වේ).
2. **ගණපූරණ-සහන එකතුව** — `minPanel` පිළිතුරු ලැබුණු වහාම, ප්රමාදවන්නන් සඳහා කෙටි සහන
   කාලගණකයක් ආරම්භ වන අතර, ඉන්පසු එකතු කරගත් ඕනෑම දේ සමඟ fusion ඉදිරියට යයි.
   මෙය දැඩි කාල සීමාවකින් බැඳී, මන්දගාමීම මොඩලය නිසා සමස්ත ගතවන කාලයට සිදුවන බලපෑම සීමා කරයි.
3. **විනිශ්චයකරුගේ සංස්ලේෂණය** — පැනල් පිළිතුරු නිර්නාමික කර (`මූලාශ්රය 1`, `මූලාශ්රය 2`, … — එවිට
   විනිශ්චයකරු මොඩලයේ සන්නාමයට නොව අන්තර්ගතයට බර තබයි) විනිශ්චයකරු වෙත ලබා දෙයි; ඔහු
   එකඟතාව / පරස්පරතා / අර්ධ ආවරණය / අනන්ය අවබෝධයන් / නොපෙනුණු පැති විශ්ලේෂණය කර,
   **එක්** බලයලත් පිළිතුරක් ලියයි. විනිශ්චයකරුගේ ඇමතුම සේවාදායකයාගේ මුල්
   `stream` ධජය + මෙවලම් රඳවා ගනී; එම නිසා streaming සහ පහළ අදියරවල මෙවලම් භාවිතය තවදුරටත් ක්රියා කරයි.
4. **සුමට පිරිහීම** — පැනල් පිළිතුරු 0ක් → `503`; හරියටම එක් ප්රතිචාරයක් පමණක් ඉතිරි වුවහොත් → එම පිළිතුර
   සෘජුවම ආපසු ලබා දෙයි (ඒකාබද්ධ කිරීමට කිසිවක් නැත); එක් මොඩලයකින් පමණක් සමන්විත පැනලයක් සෘජුවම පිළිතුරු දෙයි.

පැනල් සාමාජිකයෙකු වෙනත් combo එකක් යොමු කරන `combo-ref` පියවරක් (`{kind: "combo-ref", comboName: "..."}`) ද විය හැක —
එය **එක් black-box පැනල් හඬක්** ලෙස විසඳනු ලැබේ (එම combo එකේම ඉලක්ක විහිදුවා යැවීමක් නොව,
යොමු කළ combo එක තුළට සිදුවන සම්පූර්ණ පුනරාවර්තී dispatch එකක් ලෙස), අනෙකුත් සෑම combo-ref-භාවිතා කරන
උපායමාර්ගයක්ම දැනටමත් භාවිත කරන එකම ගැඹුර/චක්ර ආරක්ෂාව සමඟින් (#6764).

### වින්යාසය

combo එකේ `config` blob එක මත වින්යාස කෙරේ (schema සංක්රමණයක් නොමැත — එය දැනට පවතින
`combos` වගුව නැවත භාවිත කරයි):

| ක්ෂේත්රය                                 | වර්ගය    | පෙරනිමිය         | අරමුණ                                                                                     |
| :--------------------------------------- | :------- | :--------------- | :---------------------------------------------------------------------------------------- |
| `config.judgeModel`                      | `string` | පළමු පැනල් මොඩලය | අවසාන පිළිතුර සංස්ලේෂණය කරන මොඩලය                                                         |
| `config.fusionTuning.minPanel`           | `number` | `2`              | සහන කාලගණකය ආරම්භ වීමට පෙර අවශ්ය සාර්ථක පිළිතුරු සංඛ්යාව (`[2, panelSize]` වෙත සීමා කෙරේ) |
| `config.fusionTuning.stragglerGraceMs`   | `number` | `8000`           | ගණපූරණය ළඟා වූ පසු ප්රමාදවන්නන් සඳහා රැඳී සිටින කාලය                                      |
| `config.fusionTuning.panelHardTimeoutMs` | `number` | `90000`          | එක් ප්රතිචාර නොදක්වන මොඩලයකට ඉල්ලීම ඇණහිටවිය නොහැකි වන පරිදි වන නිරපේක්ෂ උපරිම සීමාව      |

පෙරනිමි අගයන් `FUSION_DEFAULTS` (`open-sse/services/fusion.ts`) තුළ ඇත.

### උදාහරණය

```bash
curl -X POST http://localhost:20128/api/combos \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "fusion-panel",
    "strategy": "fusion",
    "targets": [
      { "model": "cc/claude-opus-4-7" },
      { "model": "cx/gpt-5.5" },
      { "model": "glm/glm-5.1" }
    ],
    "config": {
      "judgeModel": "cc/claude-opus-4-7",
      "fusionTuning": { "minPanel": 2, "stragglerGraceMs": 8000, "panelHardTimeoutMs": 90000 }
    }
  }'
```

ඉන්පසු වෙනත් ඕනෑම combo එකක් මෙන් එය අමතන්න: `{"model":"fusion-panel","messages":[...]}`.

## අතථ්ය Auto-Combo කර්මාන්තශාලාව

Auto Combo එන්ජිමට පෙර-නිර්වචිත combos අවශ්ය නොවේ. ඒ වෙනුවට, `open-sse/services/autoCombo/virtualFactory.ts` මඟින් අවශ්ය අවස්ථාවේදීම අපේක්ෂකයන් ගොඩනඟයි:

1. `getProviderConnections({ isActive: true })` (සක්රීය කර ඇති සියලු සම්බන්ධතා) ලබාගනී
2. වලංගු අක්තපත්ර ඇති ඒවාට පෙරහන් කරයි (API යතුරක් හෝ `hasUsableOAuthToken()` හරහා කල් ඉකුත් නොවූ OAuth ටෝකනයක්)
3. ආකෘති ලබාගත හැකි බව සහ මිලකරණය සඳහා `getProviderRegistry()` සමඟ හරස්-යොමු කරයි
4. සෑම `(provider, model, connection)` ටියුපලයක් සඳහාම `VirtualAutoComboCandidate` එකක් ගොඩනඟයි
5. යැවීමේ ඉලක්කය ලෙස `connection.defaultModel` (හෝ රෙජිස්ට්රියේ පළමු ආකෘතිය) තෝරයි
6. සාධක 16කින් යුත් `scorePool()` සහ ප්රභේදයේ බර පැකේජය භාවිතයෙන් සෑම අපේක්ෂකයෙකුටම ලකුණු ලබාදෙයි
7. `handleComboChat()` සඳහා ප්රතිඵලයක් ලෙස ලැබෙන මතකය තුළ පවතින `AutoComboConfig` ආපසු ලබාදෙයි — කිසිවිටෙක DB වෙත ස්ථිරව සුරකින්නේ නැත

මෙයින් අදහස් වන්නේ **`auto/*` සක්රීය කර ඇති නව සැපයුම්කරුවෙකු එක් කිරීමෙන් අපේක්ෂක සංචිතය ස්වයංක්රීයව පුළුල් වන බවයි** — combos අතින් සංස්කරණය කිරීමට අවශ්ය නොවේ. එක් එක් ඉල්ලීම සඳහා අතථ්ය combo එක නැවත ගොඩනඟන බැවින්, අලුතින් එක් කළ හෝ නැවත සෞඛ්ය සම්පන්න වූ සම්බන්ධතා වහාම භාවිතයට ගැනේ.

## ස්වයං-ප්රතිසාධනය

- **තාවකාලික බැහැර කිරීම**: ලකුණු < 0.2 → මිනිත්තු 5කට බැහැර කරයි (ක්රමයෙන් වැඩිවන පසුබැසීම, උපරිම මිනිත්තු 30)
- **Circuit breaker පිළිබඳ දැනුවත්භාවය**: OPEN → ස්වයංක්රීයව බැහැර කරයි; HALF_OPEN → පරීක්ෂණ ඉල්ලීම්
- **සිදුවීම් ප්රකාරය**: >50% OPEN → ගවේෂණය අක්රීය කර, ස්ථාවරත්වය උපරිම කරයි
- **සිසිලන කාලයෙන් පසු ප්රතිසාධනය**: බැහැර කිරීමෙන් පසු, පළමු ඉල්ලීම අඩු කළ කාලසීමාවක් සහිත "පරීක්ෂණයක්" වේ

## Bandit ගවේෂණය

ඉල්ලීම්වලින් 5%ක් (වින්යාස කළ හැක) ගවේෂණය සඳහා අහඹු සැපයුම්කරුවන් වෙත යොමු කෙරේ. සිදුවීම් ප්රකාරයේදී මෙය අක්රීය වේ.

## API

**`POST /api/combos/auto`** සඳහා කැපවූ endpoint එකක් නොමැත — Auto-Combo ක්‍රම දෙකකින් භාවිතා කළ හැක:

1. **Zero-config (නිර්දේශිතයි):** ඕනෑම chat completion ඉල්ලීමක් `model: "auto"` හෝ `model: "auto/<variant>"` සමඟ යවන්න. Virtual factory එක මගින් එක් එක් ඉල්ලීම සඳහා combo එක නිර්මාණය කරයි — persistence හෝ API ඇමතුම් අවශ්‍ය නොවේ.

2. **`strategy: "auto"` සමඟ Persisted combo:** `POST /api/combos` හරහා සාමාන්‍ය combo එකක් සාදා `strategy: "auto"` සහ `config.auto.weights` / `config.auto.candidatePool` සකසන්න. එම scoring engine එකම භාවිතා වේ; combo එක `combos` තුළ ගබඩා වන අතර ID මගින් නැවත භාවිතා කළ හැක.

සොයාගැනීම (discovery) සඳහා, `GET /api/combos/auto` මගින් සෑම variant එකක්ම එහි resolved candidate pool සහ `context_length` / `max_output_tokens` සමඟ ලැයිස්තුගත කරයි — මෙය candidate pool එකේ windows හරහා පවතින MAX අගයයි. Clients (උදා: opencode plugin) විසින් `0` වෙනුවට මෙම අගයන් ප්‍රචාරණය කළ යුතුය: zero context එකක් මගින් opencode හි auto-compaction සම්පූර්ණයෙන්ම අක්‍රිය කරයි, එමගින් gateway එකේ history purge මගින් context එක විනාශ වන තෙක් sessions වර්ධනය වීමට ඉඩ සලසයි. auto-combo context pre-filter මගින් විශාල ඉල්ලීම් (oversized requests) large-window candidates වෙත යොමු කරන බැවින්, MAX ප්‍රචාරණය කිරීම ආරක්ෂිත වේ.

```bash
# Zero-config usage (no combo creation)
curl -X POST http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto/coding","messages":[{"role":"user","content":"Hello"}]}'

# Persisted auto combo via the regular combos endpoint
curl -X POST http://localhost:20128/api/combos \
  -H "Content-Type: application/json" \
  -d '{"id":"my-auto","name":"Auto Coder","strategy":"auto","config":{"auto":{"candidatePool":["anthropic","google","openai"],"weights":{"quota":0.15,"health":0.3,"costInv":0.05,"latencyInv":0.35,"taskFit":0.1,"stability":0,"tierPriority":0.05}}}}'
```

### Auto router strategies

Persisted `strategy: "auto"` combos සඳහා `config.routerStrategy` (හෝ පැරණි `config.auto.routerStrategy`) පහත ඒවායින් එකකට සැකසිය හැක:

- `rules` — පෙරනිමි weighted scoring
- `score` — ඉහළම වින්‍යාසගත weighted score එක තෝරා ගනී. සමාන අගයන් (ties) පවතින විට වින්‍යාසගත candidate අනුපිළිවෙල ආරක්ෂා කරයි; පවතින `explorationRate` මගින් සම්පූර්ණ ranked pool එකෙන් සාම්පල ලබා ගනී.
- `cost` / `eco` — ලාභම healthy provider
- `latency` / `fast` — විශ්වසනීයත්ව දඩයක් (reliability penalty) සමඟ අඩුම p95 latency
- `sla-aware` / `sla` — p95 latency, error-rate, සහ විකල්ප cost SLOs සපුරාලන candidates වලට ප්‍රමුඛත්වය දෙයි
- `lkgp` — අවසන් වරට හොඳින් ක්‍රියාත්මක වූ provider හට ප්‍රමුඛත්වය දෙයි
- `nadir` — prompt එකට අවශ්‍ය pool එකේ ඇති model එක කුමක්දැයි [Nadir](https://getnadir.com)'s decision API එකෙන් විමසයි; opt-in, අසාර්ථක වූ විට `rules` වෙත යොමු වේ (fail-open)

### Router strategies in detail

Auto-combo engine එක මගින් pluggable **RouterStrategy** ක්‍රියාත්මක කිරීම් 7ක් නිරාවරණය කරයි, ඔබට ඒවා `config.routerStrategy` (හෝ පැරණි `config.auto.routerStrategy`) හරහා මාරු කළ හැක. සෑම strategy එකක්ම `RoutingContext` (task type, tool/vision hints, token estimate, විකල්ප SLA policy, විකල්ප last-known-good provider) ලබා දී ඇති විට, candidate pool එකෙන් එක් provider කෙනෙකු තෝරා ගනී.

#### 1. `rules` (පෙරනිමි) — 16-factor weighted scoring

පවතින scoring engine එක වටා ක්‍රියාත්මක වේ. `OPEN` circuit-breaker candidates පෙරහන් කර ඉවත් කරයි, පසුව වත්මන් task type සහ `getTaskFitness()` සමඟ `scorePool()` ධාවනය කර, ඉහළම ලකුණු ලබා ගන්නා provider තෝරා ගනී.

```ts
class RulesStrategyImpl implements RouterStrategy {
  readonly name = "rules";
  readonly description = "16-factor weighted scoring (see DEFAULT_WEIGHTS)";

  select(pool, context) {
    const eligible = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const ranked = scorePool(
      eligible.length > 0 ? eligible : pool,
      context.taskType,
      undefined,
      getTaskFitness
    );
    return { provider: ranked[0].provider /* ... */ };
  }
}
```

**භාවිතා කළ යුත්තේ කවදාද**: පෙරනිමි. සියලුම සංඥා හරහා සමබර trade-off එකක් අවශ්‍ය විට භාවිතා කරන්න.

**Alias**: `rules` (alias නොමැත)

---

#### 2. `cost` / `eco` — ලාභම healthy provider

candidate pool එක `costPer1MTokens` (ආරෝහණ අනුපිළිවෙලට) අනුව වර්ග කර ලාභම එක තෝරා ගනී. පළමුව `OPEN` candidates පෙරහන් කර ඉවත් කරයි.

```ts
class CostStrategyImpl implements RouterStrategy {
  readonly name = "cost";
  readonly description = "Always selects cheapest available provider";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort((a, b) => a.costPer1MTokens - b.costPer1MTokens);
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිතා කළ යුත්තේ කවදාද**: පිරිවැය-සංවේදී (cost-sensitive) වැඩ බර (workloads), batch processing, හෝ background jobs සඳහා.

**Aliases**: `cost`, `eco`

---

#### 3. `latency` / `fast` — විශ්වසනීයත්ව දඩයක් සමඟ අඩුම p95 latency

`p95LatencyMs + (errorRate * 1000)` අනුව වර්ග කරයි. error-rate දඩය මගින් විශ්වාස කළ නොහැකි providers වල nominal latency අඩු වුවද ඔවුන්ව පහළින් ශ්‍රේණිගත කිරීම සහතික කරයි.

```ts
class LatencyStrategyImpl implements RouterStrategy {
  readonly name = "latency";
  readonly description = "Prioritizes lowest p95 latency with reliability weighting";

  select(pool, context) {
    const healthy = pool.filter((c) => c.circuitBreakerState !== "OPEN");
    const sorted = [...healthy].sort(
      (a, b) => a.p95LatencyMs + a.errorRate * 1000 - (b.p95LatencyMs + b.errorRate * 1000)
    );
    return { provider: sorted[0].provider /* ... */ };
  }
}
```

**භාවිතා කළ යුත්තේ කවදාද**: real-time chat, autocomplete, හෝ interactive coding assistants වැනි latency-sensitive වැඩ බර සඳහා.

**Aliases**: `latency`, `fast`

---

#### 4. `sla-aware` / `sla` — latency/error/cost SLO අනුකූලතාව

වින්‍යාසගත SLO policy එක කොතරම් හොඳින් සපුරාලන්නේද යන්න මත පදනම්ව සෑම candidate කෙනෙකුම ලකුණු කරයි:

| සාධකය                            | බර  | සූත්‍රය                                               |
| -------------------------------- | --- | ----------------------------------------------------- |
| ප්‍රමාද ලකුණු (Latency score)    | 35% | `threshold / max(value, ε)`                           |
| දෝෂ ලකුණු (Error score)          | 35% | `threshold / max(value, ε)`                           |
| සෞඛ්‍ය ලකුණු (Health score)      | 15% | `1.0` (CLOSED) / `0.5` (HALF_OPEN) / `0.0` (OPEN)     |
| පිරිවැය ලකුණු (Cost score)       | 10% | `threshold / max(value, ε)` හෝ ප්‍රතිලෝම සාමාන්‍යකරණය |
| ස්ථායීතා ලකුණු (Stability score) | 5%  | ප්‍රතිලෝම සාමාන්‍යකරණය කළ ප්‍රමාද stddev              |

`hardConstraints: true` වන විට, අපේක්ෂකයින් ප්‍රධාන වශයෙන් වර්ග කරනු ලබන්නේ **උල්ලංඝන ලකුණු** (ඕනෑම SLO එකක් කොපමණ ඉක්මවා යයිද යන්න) අනුව වන අතර, පසුව සංයුක්ත ලකුණු අනුව වර්ග කෙරේ. එසේ නොමැති නම්, එය හුදෙක් සංයුක්ත ලකුණු පමණි.

```ts
class SLAStrategyImpl implements RouterStrategy {
  readonly name = "sla-aware";
  readonly description =
    "Selects the provider most likely to satisfy latency, error-rate, and cost SLOs";

  select(pool, context) {
    // ... scores each candidate against policy: { targetP95Ms, maxErrorRate, maxCostPer1MTokens, hardConstraints }
  }
}
```

**SLA ක්ෂේත්‍ර** (combo config හි සකසා ඇත):

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "sla-aware",
    "slaTargetP95Ms": 1500,
    "slaMaxErrorRate": 0.05,
    "slaMaxCostPer1MTokens": 5,
    "slaHardConstraints": true
  }
}
```

**භාවිතා කළ යුත්තේ කවදාද**: දැඩි ප්‍රමාද, දෝෂ අනුපාත හෝ පිරිවැය අයවැය සහිත නිෂ්පාදන කාර්යභාරයන් සඳහා.

**අන්වර්ථ නාම**: `sla-aware`, `sla`

#### 5. `lkgp` — අවසන් වරට හොඳින් ක්‍රියාත්මක වූ සැපයුම්කරු පළමුව

**අවසන් වරට හොඳින් ක්‍රියාත්මක වූ සැපයුම්කරු** (සකසා ඇත්නම්) පළමුව උත්සාහ කරයි, පසුව `rules` උපාය මාර්ගයට යොමු වේ. සැසි ස්ථාවරත්වය සඳහා ප්‍රයෝජනවත් වේ — එකම සැපයුම්කරු සංවාදයක පසු විපරම් ඉල්ලීම් හසුරුවයි.

```ts
class LKGPStrategyImpl implements RouterStrategy {
  readonly name = "lkgp";
  readonly description = "Tries last known good provider first, then falls back to rules";

  select(pool, context) {
    if (context.lkgpEnabled === false) {
      return getStrategy("rules").select(pool, context);
    }

    if (context.lastKnownGoodProvider) {
      const candidates = pool.filter(
        (c) => c.provider === context.lastKnownGoodProvider && c.circuitBreakerState !== "OPEN"
      );
      if (candidates.length > 0) {
        return { provider: candidates[0].provider /* ... */ };
      }
    }

    // Fallback to rules strategy
    return getStrategy("rules").select(pool, context);
  }
}
```

**භාවිතා කළ යුත්තේ කවදාද**: පසු විපරම් ඉල්ලීම් හැසිරවීමට එකම සැපයුම්කරු අවශ්‍ය වන බහු-වට සංවාද සඳහා (උදා: හැඹිලිගත කිරීම, සන්දර්භය අඛණ්ඩතාව හෝ මිලකරණ අනුකූලතාව සඳහා).

**අන්වර්ථ නාමය**: `lkgp` (අන්වර්ථ නාමයක් නොමැත)

#### 6. `nadir` — Nadir හරහා විමසුම්-දැනුවත් ආදර්ශ තේරීම

ඉහත සෑම උපාය මාර්ගයක්ම අපේක්ෂකයින් ඔවුන්ගේම ටෙලිමෙට්‍රි මගින් ශ්‍රේණිගත කරයි; ඒවායින් කිසිවක් ඉල්ලීම කියවන්නේ නැත. `nadir` අවසාන පරිශීලක වාරය සහ පූල් එකේ ආදර්ශ හැඳුනුම්පත් [Nadir](https://getnadir.com) හි තීරණ API (`POST /v1/bucket`) වෙත යවන අතර එම මෙනුවෙන් Nadir තෝරා ගන්නා ආදර්ශය වෙත යොමු කරයි (`simple` → ලාභම හැකියාව ඇති ආදර්ශය, `complex` → පෙරමුණේ ඇති ආදර්ශය). එම ආදර්ශයට සේවය කරන සම්බන්ධතාවය තවමත් තෝරා ගනු ලබන්නේ `rules` මගිනි, එබැවින් කෝටාව, සෞඛ්‍යය සහ පිරිවැය කුමන ගිණුමද යන්න තීරණය කරයි.

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "nadir",
    "nadir": {
      "apiKey": "ndr_...",
      "baseUrl": "https://api.getnadir.com",
      "timeoutMs": 2000
    }
  }
}
```

`OMNIROUTE_NADIR_API_KEY` සහ `OMNIROUTE_NADIR_BASE_URL` යනු එම තන්තු දෙක සඳහා පරිසර පසුබෑම් වේ. `baseUrl` අවශ්‍ය වන්නේ ස්වයං-සත්කාරක Nadir සඳහා පමණි (අග `/v1` තිබීම ගැටළුවක් නොවේ). යතුරක් නොමැති ඇමතුම් Nadir හි නිර්නාමික ස්ථරයට ගොඩබසින අතර, එය IP අනුව අනුපාත-සීමා කර ඇත.

පෙට්ටියෙන් පිටවන්නේ කුමක්ද: අවසාන පරිශීලක පණිවිඩයේ පෙළ (පළමු අක්ෂර 16k), අපේක්ෂක ආදර්ශ හැඳුනුම්පත් සහ `source: "omniroute"` නාලිකා ටැගය. පද්ධති විමසුමක්, ඉතිහාසයක්, මෙවලම් හෝ ශීර්ෂයන් නොමැත.

අසාර්ථක හැසිරීම fail-open වේ: කාලසීමාවක් (පෙරනිමි 2000 ms), non-2xx, ළඟා විය නොහැකි සත්කාරකයක්, වැරදි ලෙස හැඩගස්වා ඇති ප්‍රතිචාරයක් හෝ පූල් එකෙන් පිටත තේරීමක් `rules` තීරණයට විසඳෙන අතර හේතුව `NadirStrategy: fallback (…)` ලෙස උපසර්ග කර ඇත. අසාර්ථක ඇමතුමකින් පසු උපාය මාර්ගය තත්පර 30 ක් ජාලය මඟ හරියි, එබැවින් ඇනහිටීමක් එක් ඉල්ලීමකට එකක් වෙනුවට තත්පර 30 කට එක් කාලසීමාවක් වැය වේ. Nadir ඇත්ත වශයෙන්ම තේරීම සිදු කළ විට පමණක් මාර්ගගත සිදුවීම් `strategy: "nadir"` වාර්තා කරයි.

**භාවිතා කළ යුත්තේ කවදාද**: ආදර්ශ ස්ථර (කුඩා, මධ්‍යම සහ පෙරමුණේ ආදර්ශයක්) හරහා විහිදෙන පූල් එකක මිශ්‍ර-දුෂ්කරතා ගමනාගමනය, එහිදී සෑම විටම පෙරමුණේ ආදර්ශය භාවිතා කිරීම ඔබ කපා හැරීමට අවශ්‍ය පිරිවැය වේ.

**අන්වර්ථ නාමය**: `nadir` (අන්වර්ථ නාමයක් නොමැත)

### අභිරුචි රවුටර් උපාය මාර්ග

ඔබට ඔබේම `RouterStrategy` ක්‍රියාත්මක කිරීම පොදු API හරහා ලියාපදිංචි කළ හැකිය:

```ts
import {
  registerStrategy,
  type RouterStrategy,
} from "@omniroute/open-sse/services/autoCombo/routerStrategy";

class MyCustomStrategy implements RouterStrategy {
  readonly name = "my-custom";
  readonly description = "My custom routing strategy";

  select(pool, context) {
    // Your routing logic here
    return {
      provider: pool[0].provider,
      model: pool[0].model,
      strategy: this.name,
      reason: "MyCustomStrategy: ...",
      candidatesConsidered: pool.length,
      finalScore: 1.0,
    };
  }
}

registerStrategy("my-custom", new MyCustomStrategy());
```

ඉන්පසු එය භාවිතා කරන්න:

```json
{
  "strategy": "auto",
  "config": {
    "routerStrategy": "my-custom"
  }
}
```

## කාර්ය යෝග්යතාව

කාර්ය වර්ග 6ක් (`coding`, `review`, `planning`, `analysis`, `debugging`, `documentation`) හරහා ආකෘති 30කට වැඩි සංඛ්යාවක් ලකුණු කර ඇත. Wildcard රටා සඳහා සහාය දක්වයි (උදා., `*-coder` → ඉහළ coding ලකුණක්).

## Auto ප්රභේද සාරාංශය

හිස් `auto` (පෙරනිමි) සහ `autoPrefix.ts` තුළ ප්රකාශිත `AutoVariant` අගයන් 6 ඇතුළුව, **කැඳවිය හැකි model ID 7ක්** ඇත:

`auto`, `auto/coding`, `auto/fast`, `auto/cheap`, `auto/offline`, `auto/smart`, `auto/lkgp`

(`AutoVariant` විසින්ම අගයන් 6ක් ලැයිස්තුගත කරයි; 7 වන විකල්පය "ප්රභේදයක් නැත" යන්නයි — හිස් `auto` — එය `parseAutoPrefix()` මඟින් `variant: undefined` ලෙස හසුරුවයි.)

## Auto-Combo සමඟ ස්තර ගැළපෙන ආකාරය

සාධක 16ක ලකුණුකරණ ශ්රිතය (`open-sse/services/autoCombo/scoring.ts`) ස්තර
සාමාජිකත්වය සංඥා දෙකක් ලෙස සලකයි: `tierPriority` (0.0476) සහ `tierAffinity` (0.0476). සම්පූර්ණ
`DEFAULT_WEIGHTS` කට්ටලය සඳහා ඉහත ඇති සම්මත [ලකුණුකරණ සාධක වගුව](#how-it-works-persisted-auto-combos) බලන්න —
එක් එක් පැකේජයට අදාළ අතික්රමණ (ship-fast/cost-saver/quality-first/
offline-friendly) "එක් එක් පැකේජය සඳහා බර පැතිකඩ" වගුවේ දක්වා ඇත.

ස්තරය පමණක් **Tier 1** පළමුව තැබීමට බල නොකරයි — Tier 1 ප්රමාදය අයහපත් නම් හෝ
පිරිවැයට සාපේක්ෂ ගුණාත්මකභාවය ප්රශස්ත නොවේ නම්, Tier 2 ජය ගනී. ස්තර අනුපිළිවෙළ බලෙන් යෙදීමට,
`priority` සංයෝජන උපායමාර්ගය භාවිත කර සැපයුම්කරුවන් ස්තරය අනුව සකසන්න.

Tier 1 (දායකත්වය) දැඩි ලෙස ප්රිය කිරීමට, `tierPriority` බර වැඩි කරන්න:

```json
{
  "strategy": "auto",
  "config": { "auto": { "weights": { "tierPriority": 0.3, "costInv": 0.05 } } }
}
```

ස්තර නිර්වචන සහ සැපයුම්කරු වර්ගීකරණය සඳහා [`docs/guides/TIERS.md`](../guides/TIERS.md) බලන්න.

## පරීක්ෂණ සහ ආවරණය

### නිශ්චිත routing-තීරණ අනුකෘතිය (`npm run test:combo:matrix`)

`tests/integration/combo-matrix/*.test.ts` විසින් mock කළ upstream එකක් සමඟ සැබෑ combo pipeline එක හරහා පොදු උපායමාර්ග 19ම සඳහා routing **තීරණය** ආරම්භයේ සිට අවසානය දක්වා තහවුරු කරයි. ආවරණයට පහත දෑ ඇතුළත් වේ:

- `ROUTING_STRATEGY_VALUES` උපායමාර්ග 19ම (ordered, weighted, cost, context, fusion, …).
- `quota-share` (අභ්යන්තර) ආරම්භයේ සිට අවසානය දක්වා: සැබෑ `selectQuotaShareTarget` seam එක (`registerQuotaFetcher` / `setLKGP` / `__setHeadroomSaturationFetcherForTests`) හරහා DRR සාධාරණත්වය + සංතෘප්ති ප්රමුඛතාව අඩු කිරීම.
- සෑම target සංඛ්යාවක් පුරාම `context-relay` සාර්වත්රික-handoff ආවරණය.

මෙම suite එක CI තුළ (`test:integration` job) `--test-concurrency=1` සහ `--test-force-exit` සමඟ ධාවනය වන බැවින් එය නිශ්චිත වන අතර සජීවී අක්තපත්ර අවශ්ය නොවේ.

### Gated සජීවී smoke පරීක්ෂණ (CI තුළ නොවේ — සැබෑ සපයන්නන්)

| විධානය                                 | එයින් සිදු වන්නේ කුමක්ද                                                                  |
| :------------------------------------- | :--------------------------------------------------------------------------------------- |
